## 触发场景

### 显式触发（用户/主智能体主动要求）
- 用户说"验证集成""检查接口""集成检查""验证子任务""检查模块接口"
- 主智能体在「myworkflow:task-dispatch」派发完成后，检测到所有子智能体 completion.md 就绪

### 隐式触发（自动判断，满足任意一条时触发）
1. **整批触发**：`.task-manifest/task-contract.yaml` 中列出的**所有** task-id 的 `completion.md` 均已生成
2. **批次触发**：某一并行批次（如同一 `depends_on` 层级）的**全部** task-id 的 `completion.md` 均已生成 → 可先验证该批次，不等全部完成
3. **超时触发**：自「myworkflow:task-dispatch」派发后超过 **30 分钟**仍有子智能体未提交 completion.md → 触发本 skill 的缺失处理流程（见前置强制步骤中的崩溃恢复）

### 不触发（反例）
- 子智能体仍在运行中（completion.md 未全部生成且未超时）→ 等待，不要提前触发
- task-contract.yaml 不存在 → 说明「myworkflow:task-dispatch」未完成拆解，先完成拆解
- 用户只是想看某个子智能体的产出（不是验证）→ 直接读文件，不需要走完整验证流程
- 只有 1 个子任务 → 不需要本 skill，主智能体直接检查即可

### 触发边界 — 批次验证 vs 全体验证
- **批次验证模式**：同一并行层（如第 0 批的 3 个任务全部完成）→ 可触发，只验证该批次。验证通过后可立即开始下一批的派发（不等全体）
- **全体验证模式**：所有批次全部完成 → 触发完整验证（自动层 + 判断层 + 跨模块兼容性）
- **增量验证模式**：修正循环中某个任务重新提交 → 只对该任务重跑自动层，不走完整判断层

## 必需要素

- `.task-manifest/task-contract.yaml` 存在且完整（「myworkflow:task-dispatch」产出）
- 所有子智能体的 interface-declaration.md 和 self-check.md 已生成（「myworkflow:subagent-protocol」产出）
- 至少一个子智能体的 completion.md 已提交，或自派发起已超 30 分钟

## 推荐要素

- 子智能体的实际代码/文档产出已能在文件系统中查看
- 主智能体对项目的技术栈有基本了解

## 前置强制步骤

核心原则：验证可自动化——能自动检查的不依赖人工判断。重试有上限——修正最多 3 轮，之后升级为人工介入。

1. **读取合约**：读取 `.task-manifest/task-contract.yaml`，加载所有任务的接口定义。
   - **如果合约文件不存在**：区分两种场景——
     - `.task-manifest/` 目录也不存在 → "合约从未创建"，提示用户先运行「myworkflow:task-dispatch」拆解任务
     - `.task-manifest/` 目录存在但 task-contract.yaml 缺失 → "合约被删除"，尝试恢复：检查 git 历史（`git log -- .task-manifest/task-contract.yaml`）或询问用户是否重新拆解
2. **收集元文件**：对每个 task-id，检查 `.task-manifest/outputs/{task-id}/interface-declaration.md`、`self-check.md`、`completion.md` 是否存在且非空。缺失或为空→标记为"未完成"或"子智能体可能崩溃"（见下方处理）
3. **确认依赖已满足**：对每个子任务，检查其 depends_on 中列出的任务是否已完成，**同时验证引用的 task-id 在合约中确实存在**。依赖未满足→标记"依赖未就绪"；task-id 不存在→标记"合约引用错误"

**缺失/空 completion.md 的处理**：如果某个 task-id 的 completion.md 不存在（子智能体可能崩溃、超时、或仍在运行）：
- 检查该 task-id 的 self-check.md 是否存在且全部 [x] → 子智能体可能忘了写 completion.md，提示它补写
- completion.md 存在但为空 → 子智能体异常中断（崩溃或提前退出），视同缺失处理：检查 self-check.md 状态，决定补写还是重新派发
- self-check.md 也不存在或未完成 → 子智能体可能崩溃或超时。向用户报告该子任务状态，询问：重新派发 / 跳过该任务 / 人工完成
- 如果子智能体仍在运行（可通过 Agent 工具状态判断）→ 等待或设超时（建议 10 分钟），超时后视为崩溃处理

**状态路由**：对每个 completion.md 解析 `**状态**:` 字段：
- DONE → 正常进入自动验证层
- DONE_WITH_CONCERNS → 提取"已知担忧"条目，注入判断层作为高优先级检查项；正常进入自动验证层
- NEEDS_CONTEXT → 暂停该任务验证，向用户展示缺失信息列表，询问补充后重新派发
- BLOCKED → 暂停该任务验证，报告阻塞原因，询问是否解除阻塞或跳过该任务

## 目标

独立验证每个子智能体的产出是否与合约一致，检查跨模块接口兼容性，自动修正不合规项（最多 3 轮），生成集成验证报告。

### 自动验证层（检查 1-4）

**检查 1：文件存在性 + 跨任务路径唯一性**

对合约中每个 output.file，用 PowerShell 的 Test-Path 验证文件存在且非空。

**跨任务路径冲突检查**：收集所有任务的 `outputs[].file`，检查是否有两个不同任务声明了相同的输出文件路径。如有→❌ 标记"路径冲突"——两个子智能体将互相覆盖文件。必须在派发前修复合约。

所有文件存在且非空、无冲突→✅，缺失或为空→❌，路径冲突→❌（文件可能已被后运行者覆盖——从源头恢复被覆盖文件，同时修复合约中的路径冲突以防再次发生）。

#### 检查 1.5：副作用任务执行验证

对 verification 中包含 `test_passes` 条目的任务（通常 outputs 为空），在 shell 中执行对应命令：
- 退出码 0 → ✅
- 退出码非 0 → ❌，记录失败输出
- 如果命令依赖运行时环境（需先构建/启动），在修正循环中处理，首次标记为 ⚠️ "待环境就绪后验证"

**检查 2：导出签名匹配（best-effort）**

按文件类型执行对应检查：

| 文件类型 | 检查方式 | 命令示例 |
|----------|----------|----------|
| TypeScript (.ts) | grep 导出声明，比对名称 | `grep -E "export (function\|const\|interface\|type) {name}" {file}` |
| Python (.py) | grep 函数/类定义 | `grep -E "def {name}\|class {name}" {file}` |
| Markdown (.md) | grep 章节标题 | `grep -E "^##+ {name}" {file}` |
| JSON (.json) | 解析 JSON 检查 key | `(Get-Content {file} | ConvertFrom-Json).PSObject.Properties.Name`（执行时去掉 `\`——即使用 `|` 而非 `\|`） |
| 通用 | grep 导出名是否存在 | `grep -E "{name}" {file}` |

判定：所有 verification.export_matches 的名称在文件中可找到→✅；缺失→❌；参数数量不匹配→⚠️警告。

**风险标注审查**：如果 interface-declaration.md 的"风险和假设"中标注了合约签名问题（如"合约中 Session 类型缺少 refreshToken 字段"），读取这些标注并与合约对比。如果子智能体按风险标注修正了签名（与合约不一致但标注了原因），标记为 ℹ️ "合约建议修正"而非 ❌；如果签名与合约不一致且无风险标注→❌。

**检查 3：声明-合约一致性**

- 合约 outputs 是否全部在 interface-declaration.md 中被承诺
- 声明中的导出是否覆盖合约 verification.export_matches
- 声明中有但合约中没有的产出→ℹ️信息性警告

**检查 4：自检诚实度**

对比 self-check.md 与自动验证结果。self-check 声称通过但自动验证发现不匹配→标记 self-check-unreliable。

#### 检查 4.5：Per-task 规范符合性 + 代码质量审查（深度审查模式）

**触发条件**：任务对代码质量有较高要求时启用。

**执行方式**：dispatch 审查子智能体，输入为 task-contract.yaml、子任务产出 diff、子任务自检报告。

**两个独立判决**：

| 维度 | 检查内容 | 严重度 |
|------|---------|--------|
| 规范符合性 | 是否漏了规范要求？多做了规范外的事？误解了规范？ | 🔴 缺失/错误=阻断；🟠 多余=判定 |
| 代码质量 | 关注点分离、错误处理、DRY、边界处理、命名 | 🔴 安全/崩溃=阻断；🟠 可维护性降级=记录 |

**审查纪律**：
- 审查者直接读 diff 文件（不通过实现者报告间接判断）
- "不信任自检报告"——每个声明在 diff 中找到对应代码变更
- 只报告有代码证据的问题

**审查后处理**：🔴 → 派发修复（可能是新子智能体）；🟠 → 记录，用户判定

### 判断验证层（检查 5-7）

**检查 5：跨模块接口兼容性**

对每对有依赖关系的任务（A 依赖 B），检查：
- A 引用的类型名是否与 B 导出的一致
- A 调用 B 的函数时参数数量是否与 B 声明的签名一致
- A 的 import 路径是否与 B 的实际产出文件路径一致

判定：所有引用一致→✅；不匹配→⚠️记录兼容性问题

> **语言适配**：以上检查项以 TypeScript/JavaScript 为默认语法。其他语言的对应检查方式见检查 2 的多语言命令表——例如 Python 检查 `import` 路径和函数签名、Rust 检查 `use` 声明和 trait 实现、Go 检查 `import` 和函数签名。

**检查 6：质量抽查**

抽查关键模块（被多任务依赖的、自检最完美的）：
- 接口契约是否被诚实履行
- 错误处理是否覆盖
- 有没有空函数体、硬编码返回值、未实现的 TODO

抽查 20-30% 模块即可（至少抽查 1 个；如果 ≤3 个任务则全查）。

**检查 7：集成风险标注**

标注自动层无法检测的风险：语义不匹配、隐含假设冲突、缺失的接口。

#### 检查 7.5：全分支最终代码审查

**触发条件**：所有子任务完成且自动验证层通过后自动触发。

**执行方式**：
1. 获取整个分支完整 diff（git diff merge-base...HEAD）
2. Dispatch 审查子智能体，审查维度：
   - 跨模块一致性：命名不一致、数据格式冲突、隐式约定被破坏
   - 全局模式：重复逻辑、错误处理不统一
   - 盲点：所有 per-task 审查都遗漏的问题

**输出**：🔴 阻断/🟠 重要/🟡 建议

**优化**：如果只有 1 个子任务 → 合并到 per-task 审查。

**处理**：🔴 → 回到修复阶段；🟠+🟡 → 记录，用户判定

### 审查独立性原则

**禁止预判**：控制器发起审查时，不得在审查 prompt 中包含：
- ❌ "这个模块应该没问题"——诱导审查者降低标准
- ❌ "忽略 X 方面的检查"——除非注明理由
- ❌ 预先降级预期发现

**计划规定的缺陷**：如果合约规定审查 rubric 视为缺陷的做法 → 标注 🟠 "plan-mandated"→ 用户决定。

**控制器角色**：
- ✅ 选审查 prompt、确保审查者访问所有文件、汇总结果
- ❌ 在审查完成前评估/过滤发现
- ❌ 在审查后 downgrade 发现

### 修正循环

自动层发现不合规时：

**第 0 步（仅首轮）：合约审视**
在生成修正 prompt 之前，先判断不合规的根因：
- 如果多个子任务都因同一合约条目不合规 → 可能是合约定义有问题，向用户提议审视合约
- 如果风险标注审查（检查 2）发现了子智能体的"合约建议修正"标注 → 优先审视这些标注，判断是否应修复合约而非修正代码
- 如果只有单个子任务不合规且无风险标注 → 进入正常修正流程

**第 1 步：生成修正 prompt**

```
你的子任务 {task-id} 在集成验证中发现以下不合规项：
- [{检查X}] 期望: {expected}，实际: {actual}，位置: {file:line}
请修正实现使接口与合约一致。
如果你认为合约定义本身有误（而非你的实现问题），请在修正报告中标注 [合约异议] 并说明原因——不要默默按错误合约实现。
修正后重新执行「myworkflow:subagent-protocol」的阶段 1-5（阶段 1 读取合约了解完整上下文；如果未修改接口声明可跳过阶段 2），
如果未修改接口声明，可跳过阶段 2。
```

**第 2 步：派发修正子智能体** — 新建 Agent，传入修正 prompt + 合约条目

**第 3 步：重试验证 + 跨模块影响检查** — 修正完成后：
- 重新走自动层（检查 1-4），同时检查是否引入了新的不合规项（对比修正前后的检查结果差异）
- **跨模块影响检查**：如果该任务被其他任务依赖（检查合约中的 depends_on），验证修正后的接口签名是否仍与依赖方兼容。如果该任务修改了导出的函数签名或类型定义 → 对所有依赖此任务的下游任务标记 ⚠️ "上游接口变更，需验证兼容性"。同时标记所有传递依赖方（B 依赖 A，C 依赖 B，A 修改后 C 同样受影响）为 '⚠️ 需验证传递兼容性'。

**第 4 步：判定**
- ✅ 全部通过→进入判断层
- ⚠️ 子智能体标注了 [合约异议] → 暂停修正循环，审视合约。如果合约确实有误 → 修复合约 → 重新派发所有受影响任务。如果合约无误 → 继续修正
- ❌ 仍有不合规→轮次+1
- ❌ 第 3 轮后仍不通过→标记 REQUIRES_MANUAL_INTERVENTION，建议审视合约
- ❌ 如果 >50% 任务标记 REQUIRES_MANUAL_INTERVENTION → 建议重新审视整个合约——可能是拆解粒度或接口定义存在系统性问题，考虑重新运行「myworkflow:task-dispatch」

### 生成验证报告

> 以下为完整模板。实际使用时可根据验证规模精简——小规模验证（≤3 个子任务）只保留必填字段。

写入 `.task-manifest/verification-report.md`。报告必须包含以下表格和内容：

```markdown
# 集成验证报告 — {项目名}

> 验证时间: {ISO 8601 时间戳}

## 总览

| 任务 ID | 自动层 (1-4) | 修正轮次 | 判断层 (5-7) | 最终状态 |
|---------|-------------|---------|-------------|---------|
| build-shared-types | ✅ 全部通过 | 0 | ✅ 全部通过 | ✅ 通过 |
| build-auth-logic | ⚠️ 检查2失败 | 1 | ✅ 全部通过 | ✅ 通过 |
| build-auth-middleware | ❌ 检查1+2+3失败 | 3 | — | ❌ 需人工介入 |

**汇总**: 2/3 通过，1 需人工介入

## 自动验证详情

### build-shared-types

| 检查项 | 结果 | 备注 |
|--------|------|------|
| 1. 文件存在性 | ✅ | src/auth/types.ts (2.3KB, 非空), src/auth/index.ts (0.8KB, 非空) |
| 2. 导出签名匹配 | ✅ | User, LoginRequest, LoginResponse, ApiError 均以 export interface 导出 |
| 3. 声明-合约一致性 | ✅ | interface-declaration.md 列出的 4 个导出全部匹配合约; 无额外导出 |
| 4. 自检诚实度 | ✅ | self-check.md 声称通过，与自动验证结果一致 |
```

## 常见错误

| 错误 | 为什么错 | 正确做法 |
|------|---------|---------|
| 跳过判断层，自动层通过就宣布完成 | 自动层只检查"有没有"，不检查"对不对" | 自动层通过后必须走判断层 |
| 修正 prompt 不指定具体不合规项 | 子智能体不知道改什么 | 修正 prompt 必须包含：期望、实际、位置 |
| 重试超过 3 轮仍继续 | 同一个问题 3 次修正不动→大概率是合约问题 | 第 3 轮后升级人工介入 |
| 对标记 self-check-unreliable 的子任务不加重检查 | 自检造假的子任务所有产出都应被怀疑 | 对该任务所有检查项加深验证 |
| 验证报告缺少跨模块兼容性检查 | 最重要的 bug 在模块边界 | 检查 5 不可跳过 |

## 危险信号 — 停下重新检查

- 所有子任务自动层一次通过且自检诚实度全满分 → 要么任务太简单，要么自检集体造假
- 同一个不合规项在 3 轮修正中完全相同 → 子智能体不理解修正 prompt，或合约不可实现
- 两个任务接口在自动层通过但在判断层发现语义完全相反 → 合约 signature 不足以描述接口语义
- 某个被所有其他任务依赖的任务未通过 → 整个集成阻塞
