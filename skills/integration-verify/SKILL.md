## 核心流程：读合约 → 自动层核对 → 判断层兼容 → 报告与修复

**何时加载**：某交付物已结算要验该份，或依赖就绪、合并/发布前整体验一次。**不加载**：未结算、合约缺失（先补拆解）、只想看某份产出（直接 read）。

**硬步骤**
1. **读基准**：取合约 outputs/verification/version/requires 与接口声明、自检、完成记录；DONE/DONE_WITH_CONCERNS 进自动层，NEEDS_CONTEXT/BLOCKED 暂停；缺合约先补拆解，缺记录先查进展。
2. **自动层（1–4.5）**：输出存在非空、路径不冲突、test_passes 可执行、导出名与合约一致、声明覆盖 outputs、自检对照实测；自称通过而实测不符标 self-check-unreliable，该 owner 其余结论降权。
3. **判断层（5–7.5）**：核对依赖的类型名、参数数量、import 路径；按 20–30% 抽查空函数体、硬编码、TODO；标集成风险，门槛处再审，按 🔴/🟠/🟡 分级。
4. **修复与复验**：不合规先查合约（多份同因优先修合约），再生成含期望/实际/位置的指令交回原 owner，重跑自动层并查下游；以进展与可恢复判失败。
5. **报告分层**：落盘 verification-report.md，上层只放结论 + evidence refs，下层放明细与修复历史；通过项 requires 可升 verified-result，needs_user 附已尝试与最小下一步，不自己重排队列。

**完成判据**：每份交付物有逐项结论与可核查证据（命令 + 退出码、file:line、commit），已核实与推测分开写，未覆盖范围与取样遗漏如实标注。
**口径修正**：interface-declaration / self-check / completion 为可选模板，存在则核对、不存在不判未完成；旧「由 subagent-protocol 产出」链路已废弃。
**诚实汇报门禁**：完成附 team_exec_check runId + 产物 sha256；produced ≠ verified ≠ accepted，缺证只报前一档；未重启不得称「已生效」；「文件写完」「我跑过」不算完成。

## 触发

- **显式触发**：用户/leader 说"验证集成/检查接口/集成检查/验证子任务/检查模块接口"；`skill(name="myworkflow-task-dispatch")` 拆解后的交付物开始结算。
- **隐式触发**：
  - **单份结算即验证**：任意一份交付物（module / object / evidence-package）提交 completion.md 后，立即验证该份，不等同批其它交付物，也不等任何一层全部完成。
  - **验证门槛触发整体验证**：跨交付物的 published-interface 或 verified-result 依赖全部就绪、或进入合并/发布/交付用户前，按门槛集中做一次整体验证（跨模块兼容性 + 整体代码审查），不做逐层门禁。
  - **进展异常触发**：某份交付物迟迟未结算。先判断进展与可恢复性（是否有新写入、是否有活跃证据），**「状态未知/暂停」与「真正失败」严格分开**，不把"没消息""超时"直接判成失败。
- **不触发**：交付物仍在进行且未结算；合约不存在（先补拆解）；用户只是想看某一份产出（直接 read）。
- **输入契约**：交付合约（每份交付物的 `outputs[].file`、`verification.export_matches`、`version`、`requires`）、`interface-declaration.md`、`self-check.md`、`completion.md`。
- **关联 Skill**：输入 ← `skill(name="myworkflow-task-dispatch")` 产出的合约作为验证基准；输入 ← `skill(name="myworkflow-subagent-protocol")` 产出的 interface-declaration.md 与 self-check.md 作为验证对象。

## 横向交付合约（验证基准）

- **按可独立交付的产物切分**：module 模块 / object 对象 / evidence-package 证据包。**每份交付物由一个 owner 端到端负责**：调查 → 实现 → 自检 → 修复 → 验收。
- **拒绝同一交付物的阶段接力**：「背景调查→设计→检查」「计划→编码→审查」这类切法会把一个交付物拆给多个角色，上下文在交接处丢失。横向重排建议：把同一交付物的全部阶段收回同一个 owner 的垂直切片，只在**不同交付物之间**保留依赖与交接。
- **依赖只允许存在于不同交付物之间**，并显式声明 `version` + `requires`（`published-interface` 或 `verified-result`）；缺任一字段视为依赖未就绪，不得当作已就绪验证。
- **未 ready 不派发**；容量满时**拒绝并保持 ready 状态（CAPACITY_FULL）**，不排队空等，也不用一次性旁路绕过上限。
- **事件驱动滚动补位**：任一份交付物结算（提交或修复完成）就立即补位验证/推进，**不等同批其它任务、无全批屏障、无整层等待**；慢交付物不阻塞其他 ready 项。
- **同一 owner 收尾修复**：发现问题后由该交付物的 owner 带上下文修复。**全局集成由 leader 与相关 owner 共同负责**，不撤走前面的人、换一个无上下文的审查者接管后半程。

## 前置强制步骤

核心原则：验证可自动化——能自动检查的不依赖人工判断；修复以"进展"为判据，不以固定轮次或固定时长判失败。

1. **读取合约**：加载所有交付物的接口定义与 `version` / `requires`。
   - 合约缺失 → 区分两种场景：交付目录从未创建 = "合约从未创建"，提示先运行 `skill(name="myworkflow-task-dispatch")` 拆解；目录存在但合约缺失 = "合约被删除"，从版本历史恢复（如 `git log -- <合约路径>`）或询问用户是否重新拆解。
2. **收集元文件**：对每份交付物，检查 `interface-declaration.md`、`self-check.md`、`completion.md` 是否存在且非空。缺失或为空 → 标记"未完成"或"执行中断"。
3. **确认依赖已满足**：检查 `requires` 中列出的交付物是否已 `verified-result` 或 `published-interface` 就绪，并**验证引用的交付物 id 确实存在**。未满足 → 标记"依赖未就绪"；id 不存在 → 标记"合约引用错误"。未就绪项不派发、不空等，先处理其它 ready 项。

**缺失/空 completion.md 的处理**（执行中断、仍在进行、或已崩溃）：
- self-check.md 存在且全部 [x] → 可能只是忘了写 completion.md，提示补写。
- completion.md 存在但为空 → 视为异常中断：看 self-check.md 状态，决定补写还是请原 owner 重新执行。
- self-check.md 也不存在或未完成 → 先查进展证据（有无新文件写入、有无最近修改、`team_work_report` 类状态回报）；**有进展 → 继续等待并记录当前状态；确无任何进展且本地可做路径已穷尽 → 才按"真正失败"处理**，向用户报告并给出已尝试路径与最小下一步。
- 状态记不清时用 `team_recover` / `job_list` / `job_output` 确认实际状态，不凭猜测判失败。

**状态路由**（解析 completion.md 的 `**状态**:` 字段）：
- DONE → 正常进入自动验证层
- DONE_WITH_CONCERNS → 提取"已知担忧"条目，注入判断层作为高优先级检查项；正常进入自动验证层
- NEEDS_CONTEXT → 暂停该份验证，向用户展示缺失信息列表，补充后请原 owner 重新执行
- BLOCKED → 暂停该份验证，按下方"阻塞处理顺序"逐级推进，不直接结束

## 阻塞处理顺序

1. **记录**：确切失败现象、已尝试的动作、影响范围、当前仍可做的事。
2. **就地取材**：查已装服务、源码、现成工具、当前权限，先确认不是"本来就能做"。
3. **补齐能力**：能写适配器 / 接口 / 本地桥接就补齐，先把路径打通。
4. **局部绕行**：局部阻塞就先做其它 ready 项，并把 blocker 精确挂到受影响的交付物上。
5. **needs_user**：确实需要外部账号、人工决策或无法获得的资源时，标记 needs_user，并附**已尝试路径与最小下一步**。

纪律：不得固定"试三次就结束"；也不得无预算地重复同一失败——同一失败路径不重复，每轮必须换假设或换手段。权限拒绝不可绕过，遇到即上报用户。

## 用户交互

- 用户已授权任务范围内的可逆开发，**不重复询问**。
- 审批与扩权**只有用户入口**，模型没有等价工具；不要自我授权。
- 只在**真正改变决策且项目里查不到**时才用 `ask_user_question` 提问；能自己查证、自己判断的不问。

## 执行流程

**主线**：自动验证层（检查 1–4.5）→ 通过 → 判断验证层（检查 5–7.5）→ 通过 → 生成验证报告；自动层不合规 → 收尾修复 → 重跑该份的自动层 + 跨模块影响检查。以上针对**单份交付物**逐份滚动执行，互不阻塞。

> **编号说明**：带 `.5` 的检查为补充性检查，条件满足才启用——1.5 只对有 `test_passes` 条目的交付物执行，4.5 只在要求较高、启用深度核对时执行，7.5 是**整体级**检查（不归属任何单份交付物），其余检查对所有交付物执行。报告中未启用的项填 `—`。

### 自动验证层（检查 1–4.5）

**检查 1：文件存在性 + 跨交付物路径唯一性** — 对合约中每个 output.file，用 `pwsh` 的 Test-Path 验证存在且非空。**路径冲突检查**：收集所有交付物的 `outputs[].file`，若两份不同交付物声明相同输出路径 → ❌ 标记"路径冲突"（会互相覆盖）——从源头恢复被覆盖文件，同时修复合约中的冲突以防再次发生。

**检查 1.5：副作用交付物执行验证** — 对 verification 中包含 `test_passes` 条目的交付物（通常 outputs 为空），在 `pwsh` 中执行对应命令：退出码 0 → ✅；非 0 → ❌ 记录失败输出；依赖运行时环境（需先构建/启动）→ 首次记 ⚠️"待环境就绪后验证"，在收尾修复中补做。

**检查 2：导出签名匹配（best-effort）** — 按文件类型执行对应检查：

| 文件类型 | 检查方式 | 命令示例 |
|----------|----------|----------|
| TypeScript (.ts) | grep 导出声明，比对名称 | `grep -E "export (function\|const\|interface\|type) {name}" {file}` |
| Python (.py) | grep 函数/类定义 | `grep -E "def {name}\|class {name}" {file}` |
| Markdown (.md) | grep 章节标题 | `grep -E "^##+ {name}" {file}` |
| JSON (.json) | 解析 JSON 检查 key | `(Get-Content {file} \| ConvertFrom-Json).PSObject.Properties.Name` |
| 通用 | grep 导出名是否存在 | `grep -E "{name}" {file}` |

判定：所有 `verification.export_matches` 的名称在文件中可找到 → ✅；缺失 → ❌；参数数量不匹配 → ⚠️ 警告。

**风险标注审查**：若 interface-declaration.md 的"风险和假设"标注了合约签名问题（如"合约中 Session 类型缺少 refreshToken 字段"），读这些标注并与合约对比。按标注修正了签名（与合约不一致但写明原因）→ ℹ️"合约建议修正"而非 ❌；与合约不一致且无标注 → ❌。

**检查 3：声明-合约一致性** — 合约 outputs 是否全部在 interface-declaration.md 中被承诺；声明中的导出是否覆盖合约 `verification.export_matches`；声明中有但合约中没有的产出 → ℹ️ 信息性警告。

**检查 4：自检诚实度** — 对比 self-check.md 与自动验证结果。self-check 声称通过但自动验证发现不匹配 → 标记 `self-check-unreliable`，并把该 owner 的其它自检结论一并降权。

**检查 4.5：规范符合性与代码质量核对（深度核对，可选）** — 交付物对代码质量有较高要求时启用。核对材料：合约、该份产出的 diff、该份自检报告。两个独立判决：

| 维度 | 检查内容 | 严重度 |
|------|---------|--------|
| 规范符合性 | 是否漏了规范要求？多做了规范外的事？误解了规范？ | 🔴 缺失/错误=阻断；🟠 多余=判定 |
| 代码质量 | 关注点分离、错误处理、DRY、边界处理、命名 | 🔴 安全/崩溃=阻断；🟠 可维护性降级=记录 |

**核对纪律**：
- 直接读 diff 文件，**不通过实现者报告间接判断**；**不信任自检报告**——每个声明都要在 diff 中找到对应代码变更；只报告有代码证据的问题。
- 不预判、不预设结论，不预先降级预期发现，也不在核对后 downgrade 发现；计划规定导致的缺陷标注 🟠 `plan-mandated`，交用户决定。
- 角色边界：leader 负责取材、保证核对者能访问全部文件、汇总结果，不在核对完成前过滤发现。
- 需要独立判断时，这是一次**有界交叉核对**：交付物的 owner 始终对该份产物负责，核对结论回来后由**同一 owner 收尾修复**，不做"换审查者接管后半程"的接力。

### 判断验证层（检查 5–7.5）

**检查 5：跨模块接口兼容性** — 对每对有依赖关系的交付物（A requires B），检查：A 引用的类型名是否与 B 导出一致；A 调用 B 的函数时参数数量是否与 B 声明签名一致；A 的 import 路径是否与 B 的实际产出文件路径一致。判定：一致 → ✅；不匹配 → ⚠️ 记录兼容性问题并挂到 A（必要时同时挂 B）。
> **语言适配**：以上以 TypeScript/JavaScript 为默认语法。其他语言对应检查：Python 检查 import 路径与函数签名、Rust 检查 use 声明与 trait 实现、Go 检查 import 与函数签名。

**检查 6：质量抽查** — 抽查关键产出（被多份依赖的、自检最"完美"的）：接口契约是否诚实履行、错误处理是否覆盖、有没有空函数体/硬编码返回值/未实现 TODO。按比例抽查（约 20–30%，至少 1 份；交付物规模很小时全查）。

**检查 7：集成风险标注** — 标注自动层检测不到的风险：语义不匹配、隐含假设冲突、缺失的接口、未核实的推测。

**检查 7.5：整体代码审查（验证门槛触发）** — 在依赖全部就绪、进入合并/发布/交付用户等门槛处执行，是整体级检查，不属于任何单份交付物；先取整体 diff（**可直接复制执行**；`<base-branch>` 通常是 `main` 或 `master`）：

```bash
# 写法一：显式算出合并基点，再取三点 diff（推荐）
git diff $(git merge-base <base-branch> HEAD)...HEAD

# 写法二：三点语法简写（前提：本地已存在名为 main 的分支，且它就是当前分支的分叉基点）
git diff main...HEAD

# 先确认 base 分支名（本地不一定有 main，可能是 master）
git branch --list main master
```

> 边界情况：若本次工作直接发生在 base 分支上（没有独立特性分支），`git merge-base main HEAD` 就等于 `HEAD`，三点 diff 为空。此时改用「本次工作起点」到 HEAD 的两点 diff，例如 `git diff {起始commit}..HEAD`（起点可用 `git log --oneline` 定位）。

审查维度：跨模块一致性（命名不一致、数据格式冲突、隐式约定被破坏）、全局模式（重复逻辑、错误处理不统一）、盲点（各份核对遗漏的问题）。输出 🔴 阻断 / 🟠 重要 / 🟡 建议。处理：**🔴 → 由相关 owner 收尾修复**；🟠+🟡 → 记录并交互判定；跨交付物的收口由 leader 与相关 owner 共同完成。

### 收尾修复（同一 owner）

自动层发现不合规时：

**第 0 步（首轮）：合约审视** — 生成修复指令前先判断根因：多份交付物因同一合约条目不合规 → 可能是合约本身有问题，向用户提议审视合约；检查 2 的"合约建议修正"标注 → 优先审视这些标注，判断该修合约而不是改代码；只有单份不合规且无风险标注 → 进入正常修复。

**第 1 步：生成修复指令**：

```
你的交付物 {deliverable-id} 在集成验证中发现以下不合规项：
- [{检查X}] 期望: {expected}，实际: {actual}，位置: {file:line}
请修正实现使接口与合约一致。
如果你认为合约定义本身有误（而非你的实现问题），请在修复报告中标注 [合约异议] 并说明原因——不要默默按错误合约实现。
修正后重新执行 skill(name="myworkflow-subagent-protocol") 的对应阶段（先读合约了解完整上下文；未改接口声明可跳过接口声明重写）。
```

**第 2 步：交回同一 owner 修复** — 把指令发回该交付物的 owner（用 `team_message`；确实需要重建责任范围时由 leader 用 `team_member_create` 并说明上下文来源），保留其已有上下文与责任；不让无上下文的第三方接管该份交付物。

**第 3 步：重跑验证 + 跨模块影响检查** — 修复完成后重跑自动层（检查 1–4.5），对比修复前后的检查结果差异，确认没有引入新的不合规项。**跨模块影响检查**：该份被其他交付物 requires 时，验证修复后的接口签名是否仍与依赖方兼容；若改了导出函数签名或类型定义 → 对所有下游交付物标 ⚠️"上游接口变更，需验证兼容性"，并标记传递依赖方（C requires B、B requires A，A 变更后 C 同样受影响）为 ⚠️"需验证传递兼容性"。

**第 4 步：判定**：
- ✅ 全部通过 → 进判断层
- ⚠️ 标注 [合约异议] → 暂停修复，审视合约：合约确实有误 → 修复合约 → 重新验证受影响交付物；合约无误 → 继续修复
- ⚠️ 有实质进展但未通过 → 换假设或换手段继续修复（记录每轮改了什么、是否收敛）
- ❌ 无进展且本地可做路径已穷尽 → 标记 `needs_user`，附已尝试路径与最小下一步；若多份同时卡在同一根因 → 建议审视合约粒度与接口定义，考虑重新拆解
- 判定依据是"是否有进展、是否可恢复"，不是"跑了几轮"或"过了几分钟"；超时不等于失败。

## 结果分层与证据诚实

- **分层**：parent/leader 只收简短结论 + 可核查的 evidence/artifact refs；原始 diff、命令输出、长表格留在报告文件或子会话。
- **摘要必含**：来源、版本、遗漏、不确定性、未完成项。
- **证据诚实**：每条结论区分"已核实/有来源"与"推测/未核实"；不夸大，不在无证据时声称"验证通过"；证据不足时如实写"未验证/待确认"。
