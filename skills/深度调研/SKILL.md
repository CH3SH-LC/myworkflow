# 深度调研

## 定位

本 skill 是 myworkflow 技能包的**调研专用通道**。与「myworkflow:需求澄清」互补——需求澄清是"帮用户想清楚要什么"，深度调研是"帮用户查清楚事实是什么"。

**与其他 skill 的关系**：

| Skill | 关系 | 说明 |
|-------|------|------|
| **需求澄清** | 前置或并行 | 需求不清晰时先调需求澄清，明确调研范围后再进入本 skill |
| **任务分类入口** | 上游 | 三步工作流中，深度调研类任务路由到本 skill |
| **轻量级派发** | 内部工具 | 多源搜索阶段使用轻量级派发并行搜索 |

## 触发场景

### 必须触发

1. 用户要求"调研""研究""全面了解""写一份报告"某个主题
2. 技术选型/方案对比（"A vs B 哪个好""有哪些选择"）
3. 用户需要经多来源验证的事实信息
4. 用户说"帮我查一下 XX 的最新状况"
5. 涉及需要搜索 web + 验证的复杂问题

### 不触发

- 简单事实查询（"Python 3.12 什么时候发布的"）→ 直接搜索回答
- 纯代码相关问题 → 走代码编写通道
- 用户已有明确答案只需要确认 → 直接回答

## 执行流程

**闭环总览：**

```
┌──────────────────────────────────────────────────────────────────────┐
│                           深度调研闭环                                │
│                                                                       │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐          │
│  │ 阶段 1   │   │ 阶段 2   │   │ 阶段 3   │   │ 阶段 4   │          │
│  │ 明确范围 ├──►│ 多源搜索 ├──►│ 交叉验证 ├──►│ 综合报告 │          │
│  │          │   │ (并行)   │   │          │   │          │          │
│  └──────────┘   └──────────┘   └────┬─────┘   └────┬─────┘          │
│       ▲                             │               │                │
│       │                             │ 发现矛盾       │               │
│       │                             ▼               │               │
│       │                        ┌──────────┐         │               │
│       │                        │ 补充搜索 │         │               │
│       └────────────────────────┤ (聚焦)   │◄────────┘               │
│              范围需要调整       └──────────┘  可信度不足              │
└──────────────────────────────────────────────────────────────────────┘
```

### 阶段 1：明确调研范围

> **目标**：锁定调研问题，避免搜索范围过大或过小。

#### 第一步：解析用户意图

从用户请求中提取以下要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| **主题** | 调研的核心问题是什么？ | "Python Web 框架性能对比" |
| **深度** | 概览 / 详细分析 / 学术级？ | 概览→快速通道，学术级→完整流程 |
| **时效性** | 需要最新信息还是历史全貌？ | "最新"→优先近期来源 |
| **输出形式** | 口头回答 / 结构化报告 / 对比表？ | 对比表→需表格化数据 |
| **约束** | 语言/地域/排除项？ | "只看开源方案""排除 AWS 相关" |

#### 第二步：锁定调研问题（AskUserQuestion）

如果用户请求模糊（如"帮我调研一下 AI"），用 AskUserQuestion 逐项缩小：

1. **第一轮：缩小主题** — "你想了解 AI 的哪个方面？（模型对比 / 应用场景 / 成本分析 / 技术趋势）"
2. **第二轮：确认深度** — "需要多深的分析？（快速概览 5 分钟 / 详细报告 30 分钟 / 完整调研 2 小时）"
3. **第三轮：确认输出** — "输出形式？（口头总结 / 结构化 Markdown 报告 / 对比表格）"

**超过 3 轮仍模糊** → 在报告中标注"范围基于以下假设：..."，列出假设。

#### 第三步：生成调研提纲

将锁定的问题展开为结构化提纲：

```
## 调研提纲：<主题>

### 核心问题
[一句话——这次调研要回答什么？]

### 子问题
1. [子问题 1]
2. [子问题 2]
3. ...

### 搜索关键词
- 英文: [keyword 1], [keyword 2], ...
- 中文: [关键词 1], [关键词 2], ...

### 排除项
- [明确不搜索的内容]
```

**阶段 1 出口条件**：
- [ ] 核心问题已明确（一句话能说清）
- [ ] 调研提纲已生成
- [ ] 用户已确认提纲（或用户说"直接开始"）

---

### 阶段 2：多源搜索（并行）

> **目标**：从多个独立来源获取信息，避免单一来源偏见。本阶段使用轻量级派发并行执行。

#### 第一步：设计搜索维度

根据调研主题，从以下维度中选择 ≥3 个：

| 搜索维度 | 适用场景 | 方法 |
|---------|---------|------|
| **官方文档** | 技术选型、API 调研 | 搜索 "<topic> official documentation" |
| **社区讨论** | 实践体验、坑点 | 搜索 "<topic> reddit/hackernews" |
| **对比评测** | 方案对比 | 搜索 "<A> vs <B> comparison 2026" |
| **学术/技术博客** | 原理、深度分析 | 搜索 "<topic> deep dive" |
| **中文社区** | 国内视角 | 搜索 "<主题> 实践 经验" |
| **GitHub/开源** | 活跃度、维护状况 | 搜索 "<topic> github stars" |
| **定价/成本** | 成本分析 | 搜索 "<service> pricing 2026" |
| **负面/批评** | 平衡视角 | 搜索 "<topic> problems/issues/criticism" |

#### 第二步：并行搜索

为每个搜索维度生成一个搜索子任务，使用「myworkflow:轻量级派发」或直接 Agent 并行派发：

```
任务模板（每个搜索维度一个）：
---
## 任务：<维度名>搜索

搜索关键词：<keywords>

要求：
1. 用 WebSearch 搜索（至少 3 次不同关键词组合）
2. 从搜索结果中选出 3-5 个最相关的来源
3. 对每个来源用 WebFetch 获取完整内容
4. 提取与调研提纲相关的关键信息

输出格式：
### <维度名>搜索结果
| # | 来源 | URL | 关键发现 | 可信度 |
|---|------|-----|---------|--------|
| 1 | ... | ... | ... | 🟢高/🟡中/🔴低 |

### 详细摘录
#### 来源 1: <标题>
- **URL**: ...
- **关键摘录**: ...
- **与调研问题的关联**: ...
```

可信度判定标准：

| 等级 | 标准 |
|:----:|------|
| 🟢 高 | 官方文档、权威机构、经同行评议、数据可复现 |
| 🟡 中 | 知名技术博客、社区高赞、公司技术博客 |
| 🔴 低 | 个人博客、匿名来源、未注明日期、明显偏见 |

**阶段 2 出口条件**：
- [ ] ≥3 个搜索维度已并行执行
- [ ] 每个维度返回 ≥2 个有效来源
- [ ] 总来源数 ≥8 个（确保多角度覆盖）
- [ ] 每个来源已标注可信度

---

### 阶段 3：交叉验证

> **目标**：不信任单一来源。至少 2 个独立来源确认的事实才算"已验证"。

#### 第一步：提取核心声明

从所有来源中提取调研提纲的核心问题所涉及的关键声明（claims）：

```
## 声明清单

| # | 声明 | 来源 A | 来源 B | 来源 C | 验证状态 |
|---|------|--------|--------|--------|:--------:|
| 1 | FastAPI 比 Flask 快 2-3 倍 | 官方 benchmark | TechEmpower 排名 | 社区测试 | ✅ 已验证 |
| 2 | Rust 的 Web 框架中 Actix-web 最快 | TechEmpower | 个人博客 | — | ⚠️ 单一验证源 |
| 3 | ... | ... | ... | ... | ❌ 来源矛盾 |
```

#### 第二步：分类处理

| 验证状态 | 处理 |
|:--------:|------|
| ✅ **已验证**（≥2 独立来源） | 直接纳入报告，标注来源 |
| ⚠️ **单一验证源**（仅 1 个来源） | 纳入报告但标注"单一来源，未交叉验证" |
| ❌ **来源矛盾**（不同来源说法冲突） | **触发补充搜索**——聚焦矛盾点，找第 3-4 个来源裁决 |
| 🔴 **无来源**（关键问题查不到） | 标注为"信息缺口"，建议用户通过其他渠道获取 |

#### 第三步：处理矛盾

来源矛盾时，不选边站——而是：

1. 补充搜索聚焦矛盾点
2. 报告中将矛盾的各方观点都呈现，标注各方依据
3. 给出你自己的判断（基于方法论：哪方证据更充分、来源更权威），但标注"仅供参考"

**阶段 3 出口条件**：
- [ ] 所有核心声明已列入清单
- [ ] 每个声明有 ≥2 个来源交叉验证（或标注为单一/矛盾/缺口）
- [ ] 矛盾声明已补充搜索
- [ ] 信息缺口已标注

---

### 阶段 4：综合报告

#### 报告结构

```markdown
# 调研报告：<主题>

> **调研日期**：YYYY-MM-DD
> **调研范围**：[阶段 1 的核心问题]
> **来源数量**：N 个独立来源
> **可信度**：🟢 高（多源一致）/ 🟡 中（部分验证）/ 🔴 低（信息不足）

---

## 1. 执行摘要
[3-5 句话总结——让没时间读全文的人也能抓住要点]

### 核心结论
- **结论 1**：[一句话]（可信度：🟢/🟡/🔴）
- **结论 2**：[一句话]（可信度：🟢/🟡/🔴）

> ⚠️ 以下结论基于 [N] 项假设，如假设不成立结论可能不适用

---

## 2. 调研方法
- **搜索维度**：[使用的维度列表]
- **来源总数**：N
- **来源类型分布**：官方文档 X / 技术博客 X / 社区讨论 X / 学术论文 X
- **验证方法**：交叉验证（≥2 独立来源确认）

### 基于的假设
- [列出报告依赖但未经充分验证的假设]

---

## 3. 调研发现

### 3.1 <子问题 1>
[详细分析，引用来源]

### 3.2 <子问题 2>
[详细分析，引用来源]

---

## 4. 方案对比（如适用）

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 性能 | ... | ... | ... |
| 生态 | ... | ... | ... |
| 学习曲线 | ... | ... | ... |
| 维护状况 | ... | ... | ... |
| 适用场景 | ... | ... | ... |
| **推荐** | ⭐ 首选 | 备选 | 特殊场景 |

---

## 5. 对立观点与争议
[阶段 3 发现的矛盾——呈现各方说法，不掩盖分歧]

---

## 6. 信息缺口
[查不到的内容、单一来源的声明、需要进一步调研的方向]

---

## 7. 来源清单

| # | 标题 | URL | 类型 | 可信度 | 关键引用点 |
|---|------|-----|------|:------:|-----------|
| 1 | ... | ... | 官方文档 | 🟢 | 第 3.1, 3.2 节 |
| 2 | ... | ... | 技术博客 | 🟡 | 第 3.1 节 |

---

## 8. 建议与下一步
- [基于调研结果的具体建议]
- [建议用户进一步验证的方向]
- [信息缺口何时重新调研]
```

## 快速参考

| 你在做什么 | 看哪个阶段 |
|-----------|-----------|
| 用户说"帮我调研 XX"，但范围不清楚 | 阶段 1：明确范围——用 AskUserQuestion 锁定 |
| 范围已明确，需要搜资料 | 阶段 2：多源并行搜索 |
| 资料搜完了，需要判断可信度 | 阶段 3：交叉验证 |
| 信息收集完毕，需要输出 | 阶段 4：综合报告 |
| 不同来源说法矛盾 | 阶段 3 第三步：补充搜索 + 呈现各方观点 |
| 关键问题查不到 | 阶段 3：标记为信息缺口 |

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 只搜一个关键词就说"查完了" | 至少 3 个搜索维度 × 多个关键词变体 |
| 看到第一个来源的结论就当作真理 | 每个核心声明必须 ≥2 个来源交叉验证 |
| 来源矛盾时装作没看见 | 呈现各方观点——调研不是选边站 |
| 报告写"根据研究显示"但不标注具体来源 | 每个声明后标注 `[来源 N]`，报告末尾有完整来源清单 |
| 用 AI 模型自身的知识代替搜索 | 训练数据可能有偏见、过时——必须实际搜索 |
| 调研范围过大（"调研 AI 行业"）| 阶段 1 缩小到可操作范围（"2026 年开源 LLM 部署方案对比"）|
| 跳过阶段 1 直接搜 | 范围不清 = 搜索结果泛而浅 |

## 危险信号

- 你准备只搜一个维度就说"调研完成" → **覆盖面不足**
- 所有来源说法一致 → **可能都是互相引用的同一来源。检查是否独立来源**
- 你准备用自己的知识代替搜索 → **你的知识截止到训练日期。必须搜**
- 来源全是同一类型（如全是博客）→ **缺少官方文档/社区/学术视角**
- 矛盾声明被你简化成"大家普遍认为" → **你在掩盖分歧。呈现争论**

- [ ] 调研提纲已生成并经用户确认（或用户说"直接开始"）

- [ ] 总来源数 ≥8 个独立来源
- [ ] 核心声明已交叉验证（≥2 来源或已标注单一/矛盾/缺口）
- [ ] 矛盾声明已补充搜索
- [ ] 报告已生成（8 章节完整）
- [ ] 所有声明有来源标注

- [ ] 报告已落盘到 `docs/information/`
