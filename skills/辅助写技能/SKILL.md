# 辅助写技能

## 定位

本 skill 是 myworkflow 技能包的**技能创作辅助工具**。不替代你的判断——帮你走完"设计→起草→验证→优化"的完整流程，确保产出的 skill 能真正被模型正确触发和执行。

**与相关 skill 的关系**：

| Skill | 关系 |
|-------|------|
| **智能体闭环开发** | 新建/修改 skill 文件时，本 skill 负责设计，闭环开发负责执行文件修改 |
| **需求澄清** | 设计 skill 前如果需求不清晰，先调需求澄清 |
| **反谄媚** | 审查 skill 时保持批判性——不因为是自己写的就放过问题 |

## 触发场景

1. 用户说"帮我写一个 skill""创建一个技能""新建一个 skill"
2. 用户说"这个 skill 不够好，帮我优化一下"
3. 用户讨论 skill 的设计思路，需要结构化建议
4. 审查现有 skill，找问题

### 不触发
- 纯使用 skill（直接调目标 skill）→ 不触发
- 与 skill 无关的代码编写 → 不触发
- 闲聊式评价（如"这 skill 挺好""这个 skill 不错"）→ 不触发

## 核心原则：TDD 方法

> **写 skill 就是写文档的 TDD。** 不写测试就先写 skill = 不写测试就先写代码。

```
RED:   先跑基线——不用这个 skill，模型会怎么做？会犯什么错？
GREEN: 写最小 skill——针对观察到的问题，写出刚好够用的指令
REFACTOR: 堵漏洞——找到新的漏洞→修补→重新验证
```

这和写代码的 RED-GREEN-REFACTOR 完全一致。只不过"生产代码"是 SKILL.md，"测试"是压力场景。

## 执行流程

### 阶段 1：明确需求

#### 第一步：快速访谈

问 4 个问题（用 AskUserQuestion）：

1. **目标**：这个 skill 要帮模型做什么？（一句话）
2. **触发**：用户说什么时应该触发这个 skill？（列出具体词句）
3. **产出**：模型用了这个 skill 后，产出应该有什么不同？
4. **边界**：什么情况下**不应该**触发？

#### 第二步：判断 skill 类型

| 类型 | 特征 | 验证重点 | 示例 |
|------|------|---------|------|
| **规则/纪律** | 强制执行某个流程，禁止跳步 | 压力测试（时间紧/用户催时会不会跳过） | TDD、反谄媚、Bug修复五步 |
| **技术/方法** | 教模型怎么做一个具体事情 | 应用测试（换了场景还能正确应用吗） | 竞态排查、数据流追踪 |
| **模式/思维** | 改变模型思考问题的方式 | 识别测试（遇到适用场景能自己想起来吗） | 防御性编程、根因思维 |
| **参考/知识** | 提供信息，模型查询使用 | 检索测试（能找到正确信息并正确使用吗） | API 文档、配置指南 |

类型决定验证策略——规则型需要压力测试，参考型需要检索测试。

### 阶段 2：起草 SKILL.md

#### Skill 结构模板

```markdown
---
name: <skill-name>
description: <触发条件描述 — 这是最重要的字段，决定了模型会不会调用>
allowed-tools:
  - Read
  - Write
  - ...
---

## 触发场景
<!-- 可选章节。如果触发场景简单（2-3 句话可描述清楚），可融入 description 和正文首段，不需要独立章节。 -->
### 必须触发
### 不触发

## 执行流程
### 步骤 1
### 步骤 2
...

## 快速参考

## 常见错误

## 危险信号

## 完成标志
```

#### Description 写法（最重要！）

> **Description 决定了你的 skill 是天天被调用，还是永远吃灰。**

**铁律：Description 只能写"何时触发"，绝对不能写"skill 做了什么"。**

为什么：测试发现，当 description 包含流程总结时，模型会直接照 description 做而不读 skill 正文——你的 skill 内容变成了摆设。

| ❌ 错误（包含流程） | ✅ 正确（只写触发） |
|-----|-----|
| "Use when fixing bugs — first collect details, then find root cause, then dispatch parallel fixes" | "Use when encountering any bug, error, crash, or unexpected behavior, before proposing fixes" |
| "Use when 需求不清晰——先硬门禁澄清，再生成多方案对比，最后落盘报告" | "Use when 用户需求模糊、缺少关键信息、或需要方案对比和决策辅助" |

**Description 清单**：
- [ ] 以"Use when"开头（中文 skill 可用"当...时触发"开头）
- [ ] 包含具体触发词（用户会说的原话）
- [ ] 包含触发场景（什么情况下需要）
- [ ] 包含反例排除（什么情况下不需要）
- [ ] 不包含任何流程/步骤/工作流描述
- [ ] <500 字符（越短越精准）

> 参考：`references/persuasion-principles.md` — 为何某些 skill 写作技巧有效

#### 正文写作原则

1. **解释为什么**：不要只写"必须做 X"。写"必须做 X，因为不做会导致 Y"。模型理解原因后会自己判断边界情况。

2. **用红旗而非禁律**：少写"禁止 X"，多写"如果你发现自己正在 X → 停下，这意味你正在犯 Y 错误"。

3. **结构 > 长度**：500 行结构清晰的 skill 比 200 行混乱的 skill 好。关键在于模型能否快速定位需要的信息。

4. **完成标志清单**：每个 skill 末尾必须有 `## 完成标志` —— 一组 checkbox。这让模型知道自己是否完成了所有步骤。

5. **流程用 ASCII 图**：复杂流程用 ASCII 流程图，比文字描述清晰 10 倍。

### 阶段 3：验证（TDD 循环）

> **这一步区分了"能用"和"好用"的 skill。** 跳过验证的 skill 在真实场景中必然出问题。

> 💡 **Agent 工具使用场景**：在阶段 3 的 TDD 验证中，可以用 Agent 启动独立会话测试 skill（避免当前会话已有 skill 加载干扰测试）。

#### Step 1：设计验证场景

根据 skill 类型，设计 2-3 个真实场景：

**规则型 skill**：设计压力场景——用户催促、任务简单到"不值得走流程"、多个压力叠加。

**技术型 skill**：设计变化场景——换了不同语言/框架/场景，方法还能用吗？

**参考型 skill**：设计检索场景——给定一个问题，模型能从 skill 中找到正确答案吗？

#### Step 2：跑基线（RED）

不用这个 skill，直接给模型同样的任务。观察并记录：
- 模型做了什么？
- 犯了什么错？（精确到原话）
- 用了什么借口跳过正确流程？

**如果没有观察到明确的问题 → 停下来。** 这个 skill 可能不需要。不要为不存在的需求写 skill。

> 💡 实操替代方案：如果不能完全卸载 skill，可要求模型"忽略 [skill名] 的指令，直接完成任务"来近似模拟基线场景。如果基线结果无明显问题，考虑 skill 是否真的必要。

#### Step 3：用 skill 再跑（GREEN）

加载 skill 后，给模型同样的任务。验证：
- 模型是否正确触发了 skill？
- 模型是否遵循了 skill 的每个关键步骤？
- 产出是否满足 skill 的完成标志？

#### Step 4：迭代（REFACTOR）

每次测试发现新问题 → 修改 skill → 重新测试，直到连续 3 个不同场景全部通过。

**常见迭代点**：
- 模型跳过了某个步骤 → 该步骤的触发条件不够明确，或缺少强制门禁
- 模型理解偏了 → 你用了模型不理解的术语，换更通用的说法
- 模型过度执行 → 边界条件没写清楚，加了不该做的场景
- 模型没触发 skill → description 不够精准，调整触发词

### 验证方法论补充

#### 压力测试的 6 种类型

| 压力类型 | 测试场景设计 |
|---------|-------------|
| 时间压力 | prompt 暗示 urgency（"快速完成""直接做"） |
| 沉没成本 | 先给有问题的方案，看 agent 是否推翻 |
| 权威压力 | prompt 加"我是专家，按我说的做" |
| 疲惫压力 | 长对话末尾给违规指令 |
| 社会压力 | "其他人都这样做" |
| 务实压力 | "这只是临时方案，不用走完整流程" |

#### 基线测试方法
1. 设计 3-5 个验证场景（含 ≥2 压力场景）
2. RED：不加载目标 skill → 观察违反点 → 记录原始 rationalization
3. GREEN：同一场景加载 skill → 对比
4. REFACTOR：对照基线暴露的违反点逐一加固：显式否定 / 加入红旗 / 收紧触发 / 增加硬门禁
5. 重复 3-4，直到连续 3 场景通过

#### 防弹完成指标
- 压力场景通过率 ≥ 3/3
- 连续 2 轮审计 P0=0 且 P1=0
- 基线所有 rationalization 被红旗清单覆盖
- 所有 skill 间引用正确（Grep 确认）

### 阶段 4：审查

用以下清单逐项审查（可用「myworkflow:反谄媚」保持批判性）：

#### 结构审查

- [ ] `name` 只用字母、数字、连字符（无括号、无特殊字符）
- [ ] `description` 以"Use when"开头，纯触发条件，无流程描述
- [ ] `description` < 500 字符
- [ ] 正文 < 500 行（超了考虑拆分为子文件）
- [ ] 有触发场景 + 不触发场景
- [ ] 有完成标志（checkbox 清单）
- [ ] 有常见错误表
- [ ] 有危险信号表

#### 内容审查

- [ ] 每个"必须"都有"为什么"的解释
- [ ] 没有对其他外部插件的硬依赖
- [ ] 与其他 myworkflow skills 的交互关系明确
- [ ] 术语一致（同一个概念在全文中用同一个词）
- [ ] 没有"你懂的""应该没问题"等模糊表述
- [ ] 示例是真实的（不是编造的玩具例子）

#### 触发准确性审查

- [ ] description 中的触发词覆盖了用户可能说的 ≥5 种不同说法
- [ ] 近义词/中英文变体都有覆盖
- [ ] 不会误触发到相邻 skill 的领域（与相邻 skill 的边界清晰）

## 常见 skill 模式速查

### 模式 1：编排型 skill

> 自己不做事，编排其他 skill 完成任务。

**结构特征**：
- 流程图驱动（多步骤 + 循环 + 升级路径）
- 大量引用其他 skill（"委托给 XX skill"）
- 重点是决策逻辑（什么时候走哪步、什么时候升级）

**示例**：Bug修复与验证、智能体闭环开发、任务分类入口

**常见坑**：
- 步骤太多模型跟丢 → 用 ASCII 流程图
- 循环条件不明确 → 写清楚"什么情况回到哪一步"
- 升级条件太宽松 → 明确轮次上限

### 模式 2：技术方法型 skill

> 教模型一个具体的技术方法。

**结构特征**：
- 方法论描述 + 步骤演示 + 完整示例
- 一个核心示例贯穿全文
- 快速参考表（"你在做什么 → 看哪"）

**示例**：根因定位与全面排查（5 Whys + 数据流追踪）

**常见坑**：
- 示例太抽象 → 用一个真实 bug 从头演示到尾
- 步骤编号太多模型记不住 → 合并到 ≤7 个阶段/步骤
- 没有"什么时候不用这个方法"

### 模式 3：行为准则型 skill

> 改变模型的默认行为倾向。

**结构特征**：
- 红旗检查清单（触发条件）
- 谄媚行为 vs 正确行为对照表
- 语气要求（坚定但不傲慢）

**示例**：反谄媚

**常见坑**：
- 触发面太窄 → 漏掉场景
- 触发面太宽 → 过度质疑
- 语气不对 → 变成对抗而非建设

| 你要做什么 | 看哪里 |

| 开始写一个新 skill | 阶段 1 → 阶段 2 |

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| Description 里写了流程步骤 | 只写触发条件。流程放正文 |
| 写完了不测试 | TDD——跑基线→加载 skill→对比→迭代 |
| skill 超过 800 行 | 拆分为主文件 + references/ 子文件 |
| "禁止"堆砌而不解释为什么 | 每个限制附上原因 |
| 示例是编造的玩具例子 | 用真实场景的数据和代码 |
| 完成标志不写 checkbox | 模型需要 checklist 来确认自己没漏步骤 |
| 与其他 skill 的边界不清 | 明确写"不触发"场景 + 与其他 skill 的关系 |

## 完成标志

- [ ] 阶段 1：需求已明确（目标 + 触发 + 产出 + 边界 4 问已答）
- [ ] 阶段 2：SKILL.md 已起草（结构完整、description 符合铁律）
- [ ] 阶段 3：至少 1 个基线场景跑过（RED），模型确实犯了预期中的错误
- [ ] 阶段 3：加载 skill 后同一个场景跑过（GREEN），模型正确执行
- [ ] 阶段 3：至少 1 轮 REFACTOR 迭代完成
- [ ] 阶段 4：审查清单全部通过
- [ ] description 只包含触发条件，不包含流程（铁律检查）
- [ ] 与其他 myworkflow skills 无冲突
