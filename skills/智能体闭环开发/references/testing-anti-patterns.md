# 测试反模式手册

## 反模式 1：测试 Mock 行为而非真实行为
**症状**：断言 mock 对象被调用过，但没有验证实际输出
**为什么错**：mock 调用通过 ≠ 功能正确
**门函数**：
- [ ] 每个测试至少有一个断言验证了具体的返回值/输出（不是 mock.verify()）
- [ ] 如果有 mock.verify() 断言，是否同时也有业务逻辑断言？

## 反模式 2：为测试添加专用方法
**症状**：在生产代码中添加只在测试中使用的 resetForTests()、destroyForTests()
**为什么错**：测试专用方法在生产中不可用、不被维护，制造虚假安全感
**门函数**：
- [ ] 所有 public/exported 方法是否在生产代码中至少被调用一次？
- [ ] 如果有方法只被测试调用 → 删除它，重构测试用真实 API

## 反模式 3：不理解就 Mock
**症状**：Mock 了一个方法但不知道它的真实行为（返回值、异常、副作用）
**为什么错**：mock 行为是编造的，测试通过但集成时崩溃
**门函数**：
- [ ] 每个 mock 的返回值/异常是否与真实依赖的文档/源码一致？

## 反模式 4：不完整的 Mock
**症状**：只 mock 了测试直接使用的字段，但下游代码消费了未 mock 的字段
**为什么错**：测试环境下的对象结构与生产环境不一致
**门函数**：
- [ ] mock 对象是否包含真实对象的所有字段？

## 反模式 5：集成测试当马后炮
**症状**：先实现所有功能，然后声称"可以写测试了"
**为什么错**：实现时没有考虑可测试性，写出的测试只能测 happy path
**TDD 如何防止**：先写测试 → 必须考虑可测试性 → 边界和错误路径在设计阶段就被覆盖

## Mock 铁律
1. 永远不 mock 被测试的代码本身
2. 每个 mock 的行为必须与真实依赖的文档一致
3. 当 mock 超过 3 层时 → 停，考虑重构为集成测试

## 快速参考表
| 反模式 | 一句话识别 | 最关键的检查 |
|--------|----------|------------|
| Mock 行为 | 断言 mock.verify() | 有没有业务断言？ |
| 测试专用方法 | 方法只在 test 文件中出现 | 生产代码谁在用？ |
| 不理解就 Mock | 没看过文档就 mock | 返回值跟真实依赖一致吗？ |
| 不完整 Mock | mock 对象少字段 | 缺失的字段下游用不用？ |
| 集成测试马后炮 | "先做出来再补测试" | 边界和错误路径覆盖了吗？ |
