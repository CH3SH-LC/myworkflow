## 触发场景

### 显式触发
- 用户说"初始化大项目""建立项目文档体系"
- 用户说"帮我创建 CLAUDE.md / PROGRESS.md / STRUCTURE.md"
- 用户说"这个项目变大了，需要规范管理"
- 用户说"帮我搭建项目骨架"

### 隐式触发（自动判断）
- 项目已有 ≥5 个源文件分布在 ≥2 个目录中，但根目录缺少 CLAUDE.md 或 STRUCTURE.md。当 CLAUDE.md 不存在、且通过 Glob 扫描发现项目有 ≥5 个源文件分布在 ≥2 个目录中时，**主动向用户建议初始化**（不要默默等待用户发现）。
- 用户在新项目中开始第一项开发工作，项目没有任何文档管理文件

### 不触发
- 项目已有 4 文件体系 → 应使用「myworkflow:大项目工作维护」
- 单文件脚本、一次性工具、临时实验
- 用户在已有框架（create-react-app 等）的标准结构下工作且无额外管理需求

## 必需要素

- 项目根目录路径（如未指定，默认为当前工作目录）
- 项目的基本信息：项目名称、一句话定位、主要技术栈

## 推荐要素

- 项目已有的目录结构（通过 Glob/Bash 扫描）
- 项目的 README.md 或 package.json（如果存在）
- 用户对文档语言的偏好

## 前置强制步骤

1. **确认项目根目录**：如果用户未明确指定，用 AskUserQuestion 确认。根目录应包含 `.git` 或 `package.json` 等项目标识
2. **扫描现有结构**：用 Glob/Bash 获取完整目录树
3. **检查 4 文件状态**：逐一检查 CLAUDE.md、PROGRESS.md、PROGRESS-LITE.md、STRUCTURE.md 是否存在
4. **决定初始化范围**：
   - **全部缺失** → 走完整六步流程
   - **部分缺失** → 按以下决策表操作：

| 缺失的文件 | 执行步骤 | 特殊处理 |
|-----------|---------|---------|
| 仅缺 CLAUDE.md | 第一步 + 第二步 | 读取已有的 STRUCTURE.md，反向填充 CLAUDE.md 的目录树和项目信息 |
| 仅缺 PROGRESS.md / PROGRESS-LITE.md | 第三步 / 第四步 | 无需额外处理 |
| 仅缺 STRUCTURE.md | 第一步 + 第五步 | 读取已有的 CLAUDE.md 获取项目信息。重新扫描目录树 |
| 缺多个文件 | 组合执行对应步骤 | 按依赖顺序执行：CLAUDE.md → STRUCTURE.md → PROGRESS.md → PROGRESS-LITE.md，确保新文件引用已有文件中的信息。 |

在任何部分缺失场景中，**已有文件必须先被读取**，其内容必须被新创建的文件引用以保证一致性。

   - **全部存在但内容为空/模板错误** → 询问用户是否需要重新生成

## 目标

为项目从零建立 CLAUDE.md / PROGRESS.md / PROGRESS-LITE.md / STRUCTURE.md 四文件文档体系。这是一次性操作，完成后后续维护由「myworkflow:大项目工作维护」skill 接管。

## 核心理念

这 4 个文件的关系是：**CLAUDE.md 定规则 → PROGRESS.md 记事实 → PROGRESS-LITE.md 建索引 → STRUCTURE.md 画地图。**

初始化只需做一次，但必须做对——因为后续所有智能体都依赖这些文件理解项目。

---

## 执行流程：六步初始化

### 第一步：收集项目信息

1. 扫描项目目录结构，生成完整目录树
2. 读取已有文件提取信息：
   - `package.json` → 项目名称、技术栈
   - `README.md` → 项目定位
   - `.git/config` → 仓库信息
3. 如果信息不足，用 AskUserQuestion 确认：
   - 项目的一句话定位是什么？
   - 主要给谁用？
   - 核心子项目或模块有哪些？

### 第二步：创建 CLAUDE.md

这是**最关键**的文件——它是所有智能体进入项目的入口。

> 以下是 CLAUDE.md 的实际内容模板（不含最外层的 ` ```markdown ` 围栏标记）。

```markdown
# [项目名称] 工作区指令

## 每次启动会话的强制步骤

**每次新会话开始工作时，必须先调用「myworkflow:大项目工作维护」skill。** 该 skill 会引导你完成：

1. 读取本文件（CLAUDE.md）了解项目规则
2. 读取 PROGRESS-LITE.md 了解项目最近进展
3. 读取 STRUCTURE.md 了解项目布局
4. 在工作完成后强制更新 PROGRESS.md + PROGRESS-LITE.md + STRUCTURE.md

> 不要跳过这个步骤。文档体系的价值取决于每一次工作都留下记录。

## 当前项目

正在开发 **[项目名称]**（一句话定位）。

## 工作区目录结构

```
[项目根目录]/
├── CLAUDE.md              # 本文件 — 工作区入口指令
├── README.md              # 项目说明
├── STRUCTURE.md           # 项目结构文档
├── PROGRESS.md            # 详细开发进度
├── PROGRESS-LITE.md       # 精简进度（标签化）
├── src/                   # 源代码
│   └── ...
└── docs/                  # 文档
```

## 目录结构更新规则

**仅当以下情况发生时，才需要更新本文件中的目录结构树：**
- 根目录（顶层）新增/删除/重命名了目录或文件
- 新增了子项目
- 项目的核心规则或约定发生了变化

日常在 `src/`、`tests/` 等子目录内的文件增删**不需要**更新本文件——这些细节由 STRUCTURE.md 管理。

## 每次变更的文档同步规则

**每次对项目代码进行修复、重构或功能变更后，必须同步更新以下文档：**

1. **`PROGRESS.md`** — 在 `---` 分隔线之后追加详细条目（日期 + 问题描述 + 根因 + 文件列表 + 验证）
2. **`PROGRESS-LITE.md`** — 同步追加精简条目（`[标签]` + 一句话描述）
3. **`STRUCTURE.md`** — 如果文件/目录有增删改，必须同步更新目录结构树
4. **`docs/` 中相关文档** — 必须与代码实际状态一致

此规则无例外。文档即代码的一部分。
```

**适配要点**：
- 上面目录树中的 `[项目根目录]/` 和 `src/`、`docs/` 等内容是**占位符**——必须替换为第一步扫描到的实际目录结构。不要照搬模板中的目录名到真实项目
- 小型项目（<20 文件）保持简洁，大型 monorepo 可列出各子项目路径
- 如果项目有特殊规则（如"修改 `.ts` 文件后必须 build"），追加在"每次变更的文档同步规则"之后
- "每次启动会话的强制步骤"一节**不可删除**——这是连接初始化与后续维护的桥梁
- 确保「myworkflow:大项目工作维护」skill 也已安装，否则 CLAUDE.md 中的引用将无法触发

### 第三步：创建 PROGRESS.md

```markdown
# [项目名称] 开发进度记录

> 本文件记录每次代码变更的完整过程。精简版见 PROGRESS-LITE.md。
> 新条目追加位置：在 `---` 分隔线之后、已有最新条目之前。

---
```

> **追加位置说明**：`---` 是分隔线——线上是文件头（标题和说明），线下是内容区。每次追加新条目时，在 `---` 的下一行插入。第一个 `## YYYY-MM-DD` 永远是最新的日期。

> 条目格式（含标签体系、根因分析写法、好坏对比示例）详见「myworkflow:大项目工作维护」skill 的阶段 3.1 和 3.2。此处仅定义空模板结构。

### 第四步：创建 PROGRESS-LITE.md

```markdown
# [项目名称] 开发进度（精简版）

> 标签：[New Feature] 新功能 / [Debug] 修复 / [Change] 变更 / [Build] 构建
> 详细记录见 PROGRESS.md

---
```

条目格式（供后续维护时参考）：
```markdown
## YYYY-MM-DD

- [标签] 一句话描述做了什么
```

每条严格一行，不写"为什么"。

### 第五步：创建 STRUCTURE.md

基于第一步扫描的目录树生成。核心要求：**每个文件和目录都要有注释说明用途**。

```markdown
# [项目名称] 项目结构

> 最后更新：YYYY-MM-DD
> 新增、删除、重命名文件或目录时必须同步更新本文件。

## 当前核心事实

- 运行时：Node.js 22
- 包管理器：pnpm
- 测试框架：Vitest（X files, Y tests）
- 默认端口：3000
- ...

**关键原则**：
- 按重要性分层：顶层 → 主要子目录 → 更深层
- 注释写**用途**，不要照搬文件名
- 结构与实际文件系统必须 100% 一致

**"当前核心事实"如何提取**：从项目配置文件中自动提取，不能编造。通用方法：

| 信息 | 提取方法 |
|------|---------|
| 运行时/语言版本 | 检查 `.nvmrc`、`.python-version`、`go.mod` 的 `go` 行、`package.json` 的 `engines`、`pyproject.toml` 的 `requires-python`、`Cargo.toml` 的 `edition` |
| 包管理器 | 检查 `package-lock.json`(npm) / `pnpm-lock.yaml`(pnpm) / `yarn.lock`(yarn) / `poetry.lock`(poetry) / `Cargo.lock`(cargo) |
| 测试框架 | 检查依赖文件中的 `vitest`/`jest`/`mocha`/`pytest`/`go test`/`cargo test` |
| 默认端口 | 搜索 `.env`、`.env.example`、`config/` 目录中的 `PORT` 变量 |
| 数据库 | 检查 `prisma/`、`migrations/`、`database.*` 等 |
| 其他约定 | README.md、CONTRIBUTING.md 中的说明 |

> 以上是建议的检查项，不是完整清单。根据项目的实际技术栈灵活调整。

创建完 4 文件后，执行以下验证，然后向用户报告：

**验证清单**：

□ 3. STRUCTURE.md 的目录树与实际文件系统一致（抽查关键目录）
□ 4. 「myworkflow:大项目工作维护」skill 已安装（尝试读取其 SKILL.md；若不存在，警告用户）

## 设计原则（来自实战验证）

本 skill 的设计模式来自对多个大型项目的实际组织方式的调研，核心经验：

- **CLAUDE.md 是入口而非百科全书**：只写规则和引用，不写详细文档。让 STRUCTURE.md 承载空间信息，PROGRESS.md 承载时间信息
- **PROGRESS.md 的价值在根因不在记录**：记录"做了什么"只需一行。记录"为什么发生、为什么这样修"才是未来智能体真正需要的上下文
- **PROGRESS-LITE.md 只做一件事：快速扫描**：每条严格一行，不用 Markdown 子标题嵌套。这个文件存在的唯一理由是让智能体一次读取几百条记录
- **STRUCTURE.md 的核心是注释而非树结构**：`ls -R` 能生成树结构，但只有人能写出"这个文件是干什么的"。每一行注释都是对后续智能体的路标
- **文档体系的价值靠纪律维持**：4 文件体系初始化只需要 5 分钟，但它是否有效取决于每一次工作是否更新。CLAUDE.md 中对「myworkflow:大项目工作维护」的强制引用是这套纪律的技术保障
