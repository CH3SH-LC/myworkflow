## 触发

- **必须触发**（满足任意一条）：用户说"有个 bug/修一下/报错了/不工作/出问题了/帮我看看这个错误"；用户描述异常行为（预期 X 但实际 Y）；用户贴了错误日志/堆栈跟踪/测试失败输出；用户说"怎么崩溃了/为什么不对/帮我排查一下"；任何修复现有代码缺陷的请求——无论 bug 大小；测试失败、构建失败、运行时异常；用户说"fix/error/crash/broken/doesn't work/bug"。
- **不触发**：纯新增功能（走「myworkflow:agent-dev-loop」）；重构/改进无 bug（走「myworkflow:agent-dev-loop」）；代码解释、问答、搜索；用户明确"不是 bug，是功能需求"。
- 既有 bug 又有功能需求 → 先走本 skill 修 bug，再走闭环开发做功能；仅"帮我看看这个"且上下文不足 → 默认触发本 skill（先排查是否为 bug）。
- 本 skill 与「myworkflow:agent-dev-loop」是**平行通道，互斥触发**，不会同时激活。步骤 ③ 派发的子智能体**不应递归调用本 skill**——它们接收的已经是明确的修复任务。

## 目标

确保每次 bug 修复走完整五步闭环：**① 引导用户明确细节（硬门禁）→ ② 调用排查 skill 定位根因 → ③ 并行派发修复 → ④ 审查每个修复 → ⑤ 不通过则循环**。

## 前置强制步骤（核心原则）

> **不填完细节不排查，不找到根因不动手。** 本 skill 是编排者——不自己排查根因（委托给排查 skill），不自己修代码（派发子智能体）。职责：收细节 → 委托排查 → 派发修复 → 审查 → 循环。

1. **硬门禁——用户必须填完 5 项细节**：复现步骤、预期 vs 实际行为、环境信息、日志/错误信息、出现频率。不填完不进入步骤 ②。
2. **禁止跳过排查**：必须先委托「myworkflow:root-cause-analysis」找到根因，才能进入修复。不允许"这个简单，我直接修"。
   - **轻量分析例外**：根因一目了然的 bug（语法错误、类型不匹配、缺 import、拼写错误）→ 允许跳过委托，由本 skill 在步骤 ② 直接完成轻量根因确认（Grep 定位、Read 确认上下文），标注"根因自明，已跳过深度排查"并附理由。逻辑错误、行为异常、性能问题、竞态问题**不可跳过**。
3. **禁止自己动手修代码**：修复由隔离 worktree 中的子智能体执行。本 skill 只编排、审查和循环控制。

## 执行流程

**主线**：① 引导用户填细节（硬门禁）→ ② 委托 root-cause-analysis 定位根因 → ③ 并行派发修复 → ④ 审查（先真实验证再审）→ ⑤ 不通过循环（≤3 轮后升级给用户）。

### 步骤 ①：引导用户明确细节（硬门禁）

> **第一道关卡。** 不接收"页面坏了""登录不上去"这类模糊描述。用户必须提供足够细节，排查才能有的放矢。**不填完不进入步骤 ②。**

#### 第一步：展示信息清单

立即展示以下 5 项必填信息清单，逐项标注当前状态：

| # | 信息项 | 说明 | 状态 |
|---|--------|------|------|
| 1 | 复现步骤 | 精确到每一步操作，从"打开应用"开始到"bug 出现"结束 | ❓待填写 |
| 2 | 预期行为 vs 实际行为 | 你期望发生什么？实际发生了什么？ | ❓待填写 |
| 3 | 环境信息 | 操作系统、应用版本、浏览器/运行时版本、相关配置 | ❓待填写 |
| 4 | 日志/截图/错误信息 | 完整错误消息（原文非转述）、堆栈跟踪、截图 | ❓待填写 |
| 5 | 出现频率 | 每次必现 / 偶发（大概频率）/ 只在特定条件下出现 | ❓待填写 |

#### 第二步：逐项收集（使用 AskUserQuestion）

**每次只问一项**（避免选项框过多导致用户跳过）；**能用选项的尽量用选项**；**必须追问到足够具体**——"登录页面"不够，要精确到"哪个 URL、点击哪个按钮、输入什么数据"。参考话术（根据已提供信息灵活调整，不机械套用）：

- **第 1 项（复现步骤）优先收集**：请描述复现步骤，从打开应用开始，每步写清楚做了什么操作（例："1. 打开 https://example.com/login 2. 输入邮箱 test@example.com 3. 点击登录 4. 页面显示网络错误"）。用户无法精确复现 → 描述最近一次遇到 bug 时在做什么。
- **第 2 项（预期 vs 实际）**：选项"我期望 [A]，但实际 [B]" / "我不确定预期行为应该是什么"。
- **第 3 项（环境信息）**：操作系统 Windows/macOS/Linux、浏览器 Chrome/Firefox/Safari/Edge、环境类型 本地/测试/生产，版本号和具体配置在回复中补充。
- **第 4 项（日志/错误信息）**：选项"贴完整错误消息和堆栈" / "有截图但无法粘贴文字" / "没保存但记得大概内容" / "没有任何错误信息——bug 表现是 [静默错误/行为异常/卡住不动]"。
- **第 5 项（出现频率）**：选项"每次必现" / "偶发——大概 N 次中 M 次" / "只在特定条件下——条件" / "只出现过一次"。

**已提供信息的补充追问**：用户贴了日志但不完整（堆栈被截断、只贴一行）→ 追问"完整的堆栈跟踪通常包含更多行，特别是 'Caused by' 或更上层调用链。能否提供完整版本？如果没有，请确认。"

#### 第三步：质量检查（硬门禁判定）

| 质量等级 | 判定标准 | 处理 |
|---------|---------|------|
| ✅ 通过 | 5 项都足够具体（复现可操作、错误信息原文可用、环境明确） | 进步骤 ② |
| ⚠️ 勉强通过 | 1-2 项不具体（如"环境不确定"），但核心信息（错误信息 + 预期vs实际）可用 | 标注缺失项"待排查补充"，进步骤 ② |
| ❌ 不通过 | 核心信息缺失（无错误信息且无法描述实际行为、复现步骤完全不知道） | 继续追问，直到至少达到 ⚠️ |

**硬门禁规则**：不通过 → **绝不进入步骤 ②**，追问直到通过或用户明确无法提供更多信息（此时降级 ⚠️）。用户急躁（"直接帮我查吧，我不知道这些"）→ 回复"没有复现步骤和错误信息，排查就像大海捞针。请至少告诉我：你当时在做什么操作？看到了什么现象？"。用户跳过提问不回复具体内容 → 追问，不放过。

**步骤 ① 出口条件**：5 项信息清单全部填写（状态 ✅ 或 ⚠️）；质量等级至少 ⚠️；缺失项已标注"待排查补充"（供步骤 ② 传递给排查 skill）。

### 步骤 ②：调用排查 skill

> 将步骤 ① 收集的细节打包，委托给「myworkflow:root-cause-analysis」深度根因定位和全面扫描。本 skill 不自己做排查——排查是排查 skill 的专业领域。

#### 第一步：打包排查输入

将步骤 ① 的 5 项信息 + 上下文整理为结构化输入：

```
## 排查委托（由 Bug修复与验证 步骤 ① 产出）
### Bug 症状
- 复现步骤：[第1项] / 预期行为：[第2项-预期] / 实际行为：[第2项-实际]
- 环境信息：[第3项] / 错误信息日志：[第4项-原文] / 出现频率：[第5项]
### 已知缺失
- [步骤 ① 标注为 ⚠️ 的缺失项列表]
### 项目上下文
- 项目根目录：[当前工作目录] / 相关线索：[用户提到的具体文件/模块/功能名]
请执行完整的 6 阶段排查流程（症状收集→5 Whys→数据流追踪→假设验证→全面扫描→输出交接），返回排查报告。特别关注：根因因果链（至少 Why 3）、受影响位置分类清单（🔴🟠🟡🔵）、交接清单。
```

#### 第二步：调用排查 skill

`Skill(skill="myworkflow:root-cause-analysis", args="[上面格式化的排查委托]")`

#### 第三步：接收并解读排查报告

| 提取内容 | 来源（报告章节） | 用途 |
|---------|----------------|------|
| 确认的根因（一句话） | 第 4 节：根因确认 | 步骤 ③ 每个子智能体的修复目标 |
| 🔴 同类 bug（确认）位置清单 | 第 5 节：全面扫描 | 步骤 ③ 必须修复的 bug 列表 |
| 🟠 同类 bug（高概率）位置清单 | 第 5 节：全面扫描 | 步骤 ③ 必须修复的 bug 列表 |
| 🟡 相似 bug（中概率）位置清单 | 第 5 节：全面扫描 | 步骤 ③ 必须修复的 bug 列表 |
| 建议修复方式 | 第 5 节：详细位置清单 | 步骤 ③ 每个子智能体的修复方向指引 |
| 回归检查清单 | 第 6 节：交接清单 | 步骤 ④ 审查时的回归验证依据 |
| 已知局限 | 第 7 节：已知局限 | 步骤 ④ 审查时注意无法验证的部分 |

**如果排查 skill 无法确认根因**（可信度 🟡 中或 🔴 低）→ 将"被推翻的假设"和"已知局限"展示给用户，询问：接受当前最佳假设带不确定性继续修复 / 补充更多信息重新排查 / 标记"需人工深入调查"。

**步骤 ② 出口条件**：排查委托已格式化并传入 root-cause-analysis；排查报告已返回（完整 7 章节）；根因已确认（可信度 ≥🟡）或用户已接受不确定性；修复目标清单已提取（🔴🟠🟡 位置，每个有文件路径和修复方向）；已知局限已记录（供步骤 ④ 参考）。

### 步骤 ③：并行派发修复

> 将排查报告中的 bug 派发给子智能体并行修复。每个子智能体在隔离 worktree 中独立工作，互不干扰。本 skill 不自己修代码。

#### 第一步：整理修复任务清单

| 优先级 | 分类 | 处理策略 |
|--------|------|---------|
| 必须修 | 🔴 同类 bug（确认） | 全部纳入本次修复 |
| 必须修 | 🟠 同类 bug（高概率） | 全部纳入本次修复 |
| 必须修 | 🟡 相似 bug（中概率） | 全部纳入本次修复（P2 不留漏洞） |
| 记录跟踪 | 🔵 潜在风险（低概率） | 不修——记录在最终报告，建议建独立 issue |

向用户展示修复任务清单，确认范围后进入下一步。

#### 第二步：分组（将相关 bug 归入同一子智能体）

| 分组规则 | 说明 |
|---------|------|
| 同文件/同模块 | 同一文件或同一模块内多个 bug → 归入同一子智能体（避免两个子智能体改同一文件冲突） |
| 同调用链 | 同一调用链上的多个 bug → 归入同一子智能体（修复可能相互影响） |
| 独立文件/独立模块 | 不同文件、不同模块、无依赖 → 分别派发不同子智能体（可并行） |

#### 第三步：为每个子智能体准备修复 prompt

```
## Bug 修复任务
### 要修复的 bug
根因：[排查报告第 4 节——一句话根因]
修复清单：
| # | 文件:行号 | 问题 | 建议修复方式 |
### 修复约束
- 只修复上述清单中的 bug，不夹带重构、优化或范围外改动
- 修复根因而非症状——对照根因描述，确保修复从根因层面解决问题
- 修改完每个文件后自检：改动是否最小化？是否引入了新问题？
- 验证你的修复：可运行项目实际运行相关测试或用例确认 bug 消失；检查所有受影响调用方行为未退化；确保不引入新类型/lint/编译错误
### 排查报告参考
[附上排查报告关键章节摘要：根因因果链 + 数据流分析 + 该组 bug 详细位置]
### 产出要求
1. 修改了哪些文件、做了什么改动（每个文件的具体变更说明）
2. 验证方式和验证结果（实际运行输出/测试结果，不可用"应该没问题"代替）
3. 任何未解决的疑虑或已知局限
```

#### 第四步：并行派发

| 情况 | 派发方式 |
|------|---------|
| 只有 1 组 | 当前会话直接用 Agent 派发单个子智能体（`isolation: "worktree"`） |
| 2-3 组，均为简单修复 | 并行 Agent 派发多个子智能体（每个 `isolation: "worktree"`）；「myworkflow:lightweight-dispatch」可用则优先使用 |
| 2+ 组，含复杂修复（跨模块协调、需接口合约） | 优先「myworkflow:task-dispatch」；不可用时降级为并行 Agent 调用 |

多个 Agent 调用放在同一条消息中并行执行。每个子智能体尽量用 worktree 隔离。

**worktree 降级**：项目不是 git 仓库或无 git 历史 → worktree 隔离不可用。降级为：同会话顺序派发子智能体（无需隔离），步骤 ④ 特别关注文件冲突，最终报告标注"无 worktree 隔离，已通过审查确认无文件冲突"。

#### 第五步：收集各子智能体的修复结果

收集每个子智能体的产出：修改的文件和变更内容、验证结果和证据、已知疑虑。

**步骤 ③ 出口条件**：修复任务清单已展示并获用户确认；bug 已按模块/文件分组（避免冲突）；每个 prompt 包含根因+修复清单+约束+验证要求；所有子智能体已并行派发（worktree 隔离）并返回修复结果。

### 步骤 ④：审查（先跑再审）

> 逐个审查每个子智能体的修复结果。不因"看起来差不多"就放过——每个修复必须经得起以下审查。

#### 第一步：真实验证（硬门禁——先跑再审）

> **审查代码之前，先把修复后的程序跑起来。代码看着对 ≠ 真的能用。**

对每个子智能体的修复，调用 `Skill("myworkflow:real-world-verify", args="[项目上下文 + 该子智能体的修复概要]")`。返回 ❌ → 审查直接不通过（无需进三问），标记"需返工"，进步骤 ⑤ 循环。返回 ✅ → 进第二步（审查三问）。

#### 第二步：审查三问

**问题 1：是否真正解决了根因（而非掩盖症状）？**

| 检查项 | 通过标准 |
|--------|---------|
| 修复位置是否与排查报告中的根因一致？ | 修复在根因层面（因果链最深标注层），而非症状层面 |
| 修复不在根因层 → 是否会在其他条件下复发？ | 不会——修复消除了根因条件，而非仅处理触发条件 |
| 修复后因果链中的上层症状是否全部消失？ | 是——可从 Why 1 到 Why N-1 逐层验证 |

**问题 2：是否引入了新问题？**

| 检查项 | 通过标准 |
|--------|---------|
| 改动是否最小化（没有夹带重构/优化/格式化）？ | 改动仅涉及修复根因的必要代码，无 scope creep |
| 改动是否破坏已有类型/接口约定？ | 类型检查通过，接口签名未变（或变更了所有调用方） |
| 改动是否引入新 edge case（空值/边界/并发）？ | 新代码路径对所有输入都有合理处理 |
| 是否有遗漏的受影响调用方？ | Grep 搜索被修改函数/类型的所有引用，逐一确认 |

**问题 3：是否覆盖了排查报告标记的所有影响范围？**

| 检查项 | 通过标准 |
|--------|---------|
| 🔴🟠🟡 类 bug 是否全部修复？ | 排查报告中的每一个 🔴🟠🟡 位置都有对应修复 |
| 排查报告的回归检查清单是否逐项验证？ | 每一项都有验证结果（✅ 或明确的不适用说明） |

#### 审查判定

| 判定 | 标准 | 处理 |
|------|------|------|
| ✅ 通过 | 三问全部通过，验证证据充分 | 该修复合格，进入步骤 ⑤ |
| ❌ 需返工 | 三问中任一不通过，但问题明确可在子智能体层面修复 | 回步骤 ③ 对该组重新修复 |
| ❌ 需重新排查 | 修复过程中发现根因假设有误，或排查报告遗漏关键信息 | 回步骤 ② 重新排查 |

**审查记录模板**：

```
## 审查记录 — [子智能体/分组]
### 修复概要
- 修复文件：[列表] / 修复内容摘要：[一段话]
### 问题1 是否真正解决根因：[回答+证据]  判定 ✅/❌
### 问题2 是否引入新问题：[改动最小化/类型接口/edge case/调用方覆盖]  判定 ✅/❌
### 问题3 是否覆盖所有影响范围：[🔴🟠🟡覆盖 N/N / 回归检查逐项]  判定 ✅/❌
### 总体判定：✅ 通过 / ❌ 不通过（需返工 / 需重新排查）
```

**步骤 ④ 出口条件**：每个子智能体的修复都已通过三问审查；审查记录已生成（每个子智能体一份）；不通过的修复已明确标注不通过原因和修正方向。

### 步骤 ⑤：不通过则循环

> 任何修复在步骤 ④ 审查中不通过 → 回到对应步骤重新来。3 轮后仍未全部通过 → 升级给用户，请求人工介入。

#### 循环逻辑

```
全部 ✅ 通过 → 完成。向用户报告最终结果
存在 ❌ → 按不通过原因回退：
  需返工（问题明确，修复方向正确但实现有问题）→ 回步骤 ③：更新该组修复 prompt（加入审查发现的具体问题+修正要求），重新派发
  需重新排查（根因假设有误/报告遗漏/发现新影响因素）→ 回步骤 ②：将新发现传给排查 skill，请求补充排查或修正根因假设
  需补充信息（用户最初提供的信息有误或不完整）→ 回步骤 ①：对具体缺失项追加提问
```

#### 严重程度校准

| 典型场景 | 回退到 |
|---------|--------|
| 修复代码有 bug（逻辑错误/typo/漏边界条件）、类型检查失败、import 路径错误 | 步骤 ③ |
| 只修了症状没修根因、夹带范围外重构 | 步骤 ③ |
| 修复后发现新受影响位置（报告遗漏）、根因假设被修复过程推翻（"修了 A 但 bug 还在"） | 步骤 ② |
| 用户最初提供的复现步骤有误、两个子智能体的修复产生冲突 | 步骤 ③（重新分组） |
| 排查报告根因判断被证伪、用户说"不对，我说的 bug 不是这个意思" | 步骤 ② / 步骤 ① |

#### 循环规则

- **不允许"差不多就行"**：每一个 ❌ 都必须被处理。
- **不允许降级**：不能把 ❌ 改成 ⚠️ 然后跳过。
- **最多 3 轮完整循环**：从步骤 ⑤ 回到步骤 ①/②/③ 并再次走完步骤 ④ 算 1 轮。步骤 ③ 内部同一修复 prompt 重试不计入轮次。
- **3 轮后仍未全部通过 → 升级**：向用户展示当前状态（哪些通过/未通过、每轮尝试了什么、为什么失败）；明确请求人工介入（可能是架构问题、排查 skill 的局限、或需更深入领域知识）；给出建议的下一步方向（而非只说"我修不好"）。
- **每次循环追加记录**：在审查记录末尾追加「第 N 轮修复」章节。

**循环记录模板**：

```
## 第 N 轮修复（追加在审查记录末尾）
### 上一轮不通过的问题
- [子智能体/分组]：[具体不通过原因]（审查问题 [1/2/3] 不通过）
### 本轮调整
- 回退到步骤 [①/②/③] / 调整内容：[更新的修复 prompt / 补充的排查信息 / 追加的用户提问]
### 本轮审查结果
- [子智能体/分组]：审查三问重新判定 → ✅/❌
```

**升级报告模板**（3 轮后仍未通过时使用）：

```
## 升级报告 —— 3 轮修复仍未全部通过
### 当前状态
- 总修复数：[N] / 已通过：[M]（列表） / 仍未通过：[K]（列表 + 每轮尝试内容和失败原因）
### 失败分析
- [仍未通过的 bug]：第 1 轮 [尝试→失败] / 第 2 轮 [...] / 第 3 轮 [...]
- 推测原因：[根因假设问题 / 架构限制 / 信息不足 / 其他]
### 建议
- [具体建议——确认某假设 / 重新设计某模块 / 引入更专业排查手段]
请审核以上信息，指示下一步方向。
```

**步骤 ⑤ 出口条件**：所有修复判定为 ✅ 通过；或 3 轮循环后仍未通过已生成升级报告并提交给用户；每轮循环都有记录。
