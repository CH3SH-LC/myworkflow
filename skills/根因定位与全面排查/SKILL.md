## 触发场景

### 必须触发（满足任意一条）

1. Bug修复与验证 的步骤 ② 调用本 skill 进行深层根因追踪 + 全面性扫描
2. 用户直接说"帮我找到根因""深度排查""为什么会出现这个 bug""全面扫描同类问题"
3. 用户说"还有没有别的地方有这个问题""帮我找全""扫描一下类似 bug"
4. 用户提供了 bug 症状但你发现表面修复无法解决问题——需要追到根因
5. 同一个 bug 被修了 2 次以上仍然复发 → 说明没找到根因
6. 用户说"这个 bug 的根本原因是什么""数据是在哪里变坏的"

### 不触发（反例）

- 用户只想知道一个简单事实（"这个变量在哪定义的"）→ 直接 grep
- Bug 根因已经一目了然（如明显的语法错误、拼写错误）→ 不需要深度排查。Bug修复与验证 skill 会在步骤 ② 的「轻量分析例外」中自行处理此类情况
- 纯功能开发、重构、代码审查 → 用智能体闭环开发
- 用户已经确认了根因，只需要修 → 直接走 Bug修复与验证 的阶段 3

### 触发边界

- 本 skill **被** Bug修复与验证 的步骤 ② 调用——当用户细节收集完毕后，委托本 skill 进行深度根因定位和全面扫描
- 用户也可以**直接**调用本 skill——当需求明确是"排查根因"而非"修 bug"时
- 如果 Bug修复与验证 正在运行且已调用本 skill → 排查完成后将结果交回 Bug修复与验证
- 如果用户直接调用本 skill → 排查完成后建议用户走 Bug修复与验证 进行修复

## 必需要素

- bug 的症状描述（错误信息、异常行为、复现步骤，至少其一）
- 项目上下文（相关代码文件可访问）

## 推荐要素

- 完整的错误堆栈/日志
- 稳定复现步骤
- 最近变更记录（git log / git diff）
- 相关测试文件

## 前置强制步骤

> **核心原则：不找到根因不停止追问。不扫完全局不下结论。** 表面修复 = 掩盖症状。深层根因 = 彻底解决。单一修复 = 按下葫芦浮起瓢。全面扫描 = 一网打尽。

1. **接收 bug 上下文**：如果由 Bug修复与验证 调用 → 接收其步骤 ① 已产出的信息（5 项细节：复现步骤、预期vs实际、环境、日志、频率）。如果用户直接调用 → 先用 1 轮快速提问了解症状
2. **确认不跳过深度追问**：如果你脑子里出现了"这很明显就是 X 的问题"——这正是需要本 skill 的时刻。直觉可能是对的，但必须经过验证
3. **禁止急于修复**：在完成全部 6 个阶段之前，不提出修复建议。排查和修复分离——修代码是 Bug修复与验证 → 智能体闭环开发 的事

## 目标

确保每次 bug 排查都抵达真正的根因——而非停留在表面症状。确保每次修复前都已找全所有受影响的代码位置——而非只修一处、遗漏一片。**本 skill 只排查不修复**——修复是 Bug修复与验证 → 智能体闭环开发 的职责。

### 阶段 1：症状收集与分类

> **目标**：把用户提供（或 Bug修复与验证 传入）的 bug 信息整理为结构化的症状档案。不满足于表面描述——收集所有可用的客观证据。

#### 第一步：信息收集清单

在进入深度分析之前，逐项确认以下信息是否可用：

| 信息项 | 状态 | 来源 |
|--------|------|------|
| 错误信息原文（非转述） | ✅/❌/⚠️部分 | [谁提供的 / 从哪读取的] |
| 完整堆栈跟踪（含行号） | ✅/❌/⚠️部分 | [...] |
| 稳定复现步骤 | ✅/❌/⚠️偶发 | [...] |
| 预期行为 vs 实际行为 | ✅/❌ | [...] |
| 最近相关变更（git log） | ✅/❌ | [...] |
| 环境信息（OS/版本/配置） | ✅/❌ | [...] |
| 相关日志 | ✅/❌ | [...] |

缺失项 ≤2 → 可继续。缺失项 ≥3 → 先用 AskUserQuestion 补充关键信息（最多 2 轮）。

> **关于"最近相关变更"**：如果 bug 是回归型（"之前好的，现在坏了"），此项为关键信息。当需要精确定位引入 bug 的提交时，使用「专项排查技术库 → 技术 C：Bisect 二分定位」。

#### 第二步：症状分类

根据症状特征将 bug 归入一个主类别：

| 类别 | 特征 | 排查重点 |
|------|------|---------|
| 🔴 **崩溃/异常** | 抛出错误、进程退出、panic、segfault | 阶段 3——追踪异常的触发条件 |
| 🟠 **错误输出** | 不崩溃但返回值/显示内容错误 | 阶段 3——追踪数据从哪一步开始变错 |
| 🟡 **性能/超时** | 慢、卡顿、超时、内存泄漏 | 阶段 3——追踪瓶颈点和资源消耗链 |
| 🟢 **数据损坏** | 数据静默变成错误值、持久化后无法读取 | 阶段 3——追踪数据写入和变换链路 |
| 🔵 **竞态/不稳定** | 偶发 bug、时序相关、并发问题、不可稳定复现 | 阶段 2——多问几层"为什么偶发"；如属并发/竞态 → 使用「专项排查技术库 → 技术 A：竞态条件排查」 |

#### 第三步：精确定位出错点

- 从堆栈/错误信息中提取确切的 **文件:行号**
- 读取出错代码及其上下文（上下各 30 行）
- **如果用户没有提供错误信息** → 根据症状描述搜索可能的出错位置（Grep 关键词），定位到 1-3 个候选文件

**阶段 1 出口条件**：

- [ ] 信息收集清单已填写（缺失项 ≤2）
- [ ] 症状已归入主类别
- [ ] 出错点已定位到文件:行号级别（或 ≤3 个候选）
- [ ] 出错代码上下文已读取
- [ ] 如果分类为 🔵 竞态/不稳定 → 已确认是否需要启动技术 A（竞态条件排查）
- [ ] 如果是回归型 bug 且需要定位引入提交 → 已确认是否需要启动技术 C（Bisect 二分定位）

### 阶段 2：5 Whys 深度追问

> **这是本 skill 区别于其他排查方法的标志性阶段。** 5 Whys 不是"问 5 次为什么就停"——而是问到不能再问为止。每一层"因为"必须基于代码证据，不能基于猜测。

#### 方法论：逐层追问

从症状出发，层层深入：

```
症状（What）:  页面点击登录后显示"网络错误"
     │
     ▼
Why 1: 为什么显示"网络错误"？
     → 因为 API 返回了 500 状态码
     │ [证据：Network 面板截图 / 日志]
     ▼
Why 2: 为什么 API 返回 500？
     → 因为后端 `AuthController.login()` 抛出 NullPointerException
     │ [证据：堆栈跟踪指向 AuthController.java:47]
     ▼
Why 3: 为什么 `login()` 抛出 NullPointerException？
     → 因为 `userService.findByEmail(email)` 返回了 null
     │ [证据：代码审查——findByEmail 在用户不存在时返回 null 而非 Optional.empty()]
     ▼
Why 4: 为什么 findByEmail 会返回 null？
     → 因为数据库查询未找到匹配的用户记录
     │ [证据：检查数据库——email 字段存储的是旧格式，登录传入的是新格式]
     ▼
Why 5: 为什么 email 格式不一致？
     → 因为最近的数据迁移脚本（commit abc123）将 email 字段统一转成了小写，
     │   但登录页面没有对用户输入做 `.toLowerCase()` 处理
     │ [证据：git log + 代码对比]
     ▼
Why 6: 为什么迁移脚本和前端修改没有同步上线？
     → 这是系统性原因——部署流程允许前后端独立发布，没有合约测试保证兼容性
     [根因层面：不是一个人写错代码，而是流程缺陷使得此类错误必然发生]
```

#### 追问规则

| 规则 | 说明 |
|------|------|
| **每层"因为"必须有证据** | 不能写"因为可能是 X"——必须基于代码/日志/测试结果 |
| **问到不能再问为止** | 通常 3-7 层。停止条件：答案涉及外部系统（第三方 API、硬件）或已达物理/数学限制 |
| **不跳过任何一层** | 从"为什么返回 500"不能直接跳到"因为架构不好"——中间必须经过代码层、数据层 |
| **区分技术根因和流程根因** | Why 1-4 通常是技术层；Why 5+ 可能进入流程/架构层。两者都要记录 |
| **标记最深层** | 在因果链中标注"← 这是根因。修复这一层即可消除所有上层症状" |

#### 因果链记录模板

每完成一轮 5 Whys，记录为结构化因果链：

```
## 因果链 — [bug 简述]

症状（What）: [一句话——用户看到了什么]

Why 1: [直接原因]
  ├── 证据: [代码位置 / 日志行 / 测试结果]
  └── 如果是这层的问题: [只修这里的话，bug 还会不会复发？]

Why 2: [底层原因]
  ├── 证据: [...]
  └── 如果是这层的问题: [...]

Why N: [根因] ← 根因
  ├── 证据: [...]
  └── 修复这一层即可从根本上消除症状

Why N+1: [系统性原因——如适用]
  ├── 证据: [...]
  └── 说明: [为什么系统设计/流程使得此类 bug 必然发生]
```

**阶段 2 出口条件**：

- [ ] 因果链至少追问到 Why 3（即至少 3 层）
- [ ] 每层"因为"都有代码/日志证据支撑（不是猜测）
- [ ] 已标注最深根因层
- [ ] 如果根因指向外部系统（第三方 API、硬件），已记录并准备跳过阶段 3-4（无法追踪外部系统的数据流）

### 阶段 3：数据流逆向追踪

> **目标**：从出错点出发，向上游追溯数据的完整流动路径，精确定位**数据是在哪一步变坏/丢失/变错的**。

#### 第一步：绘制数据流图

从出错点开始，向上游追溯每一步数据变换：

```
用户输入
  │
  ▼
[变换点 1] 前端表单 → JSON payload
  │ 数据: { email: "User@Example.com", password: "***" }
  │ 检查: email 是否被规范化？❌ 没有 .toLowerCase()
  │
  ▼
[变换点 2] HTTP 请求 → 后端路由
  │ 数据: req.body.email = "User@Example.com"
  │ 检查: 中间件是否修改了 email？无
  │
  ▼
[变换点 3] Controller → Service → Repository
  │ 数据: email 传入 `userService.findByEmail("User@Example.com")`
  │ 检查: 是否有大小写转换？❌
  │
  ▼
[变换点 4] Repository → SQL 查询
  │ SQL: SELECT * FROM users WHERE email = 'User@Example.com'
  │ 数据库存储: email = 'user@example.com'（小写）
  │ 检查: SQL 是否做大小写不敏感匹配？❌ 默认区分大小写
  │
  ▼
[出错点] 查询返回空 → null → NullPointerException
  ★ 坏数据源头: [变换点 1]——前端未做 .toLowerCase()
  ★ 或者: [变换点 4]——SQL 查询应使用 LOWER() 或 CI 排序规则
```

#### 第二步：标注每个变换点的检查结果

对数据流图中的每个变换点，回答：

1. **这个变换点做什么？**（转换/过滤/校验/存储/传递——不做任何事也是"传递"）
2. **进入和离开时的数据分别是什么？**（如果能获取真实数据则用真实数据，否则推理）
3. **数据在这里是否已经不正确了？**（是/否/不确定）
4. **如果数据在此处正确，下一步在哪变坏的？**

#### 第三步：标记坏数据源头

在数据流图中用 `★★★` 标记**最先**出现坏数据的变换点——这就是数据层面的根因位置。

如果数据在所有变换点都正确，唯独在出错点出错 → 根因在出错点本身的逻辑，不需要再向上追溯。

#### 数据流追踪策略

| 策略 | 适用场景 | 做法 |
|------|---------|------|
| **正向追踪** | 知道输入、不知道输出为什么错 | 从输入开始，一步步执行，观察每步的数据变化 |
| **逆向追踪**（默认） | 知道出错点、不知道坏数据从哪来 | 从出错点向上游追溯，检查每个变换点的输入和输出 |
| **二分法** | 数据变换链很长（10+ 步） | 在链路中间插入检查点，先确定坏数据在前半段还是后半段 |
| **并行追踪** | 多条数据流汇聚到出错点 | 用 Agent 工具派多个只读子智能体，每个追踪一条数据流分支 |
| **插桩调试** | 多个变换点状态为"不确定"，或需要精确定位多组件系统中的断裂点 | 在组件边界插入诊断日志/断点。详见「专项排查技术库 → 技术 B：插桩调试」 |

**阶段 3 出口条件**：

- [ ] 数据流图已绘制（至少覆盖出错点上游 3 层）
- [ ] 每个变换点的检查结果已记录
- [ ] 坏数据源头已用 ★★★ 标记
- [ ] 如果坏数据源头在外部系统（API 返回、数据库已有数据）→ 已标注，进入阶段 4 时调整为"已知局限"
- [ ] 如果有 ≥2 个变换点状态为"不确定" → 已考虑启动技术 B（插桩调试）

### 阶段 4：假设-验证循环

> **这是本 skill 的"科学方法"阶段。** 不要相信你的第一个假设——设计实验来证伪它。只有经得起证伪尝试的假设才是可信的根因。

#### 第一步：形成假设

基于阶段 2（5 Whys）和阶段 3（数据流）的发现，用一句话精确表述根因假设：

```
我认为根因是 [X 位置的 Y 逻辑]，
因为 [证据 A + 证据 B]。
如果这个假设正确，那么 [可观察的预测 C] 应该成立。
```

**好的假设 vs 坏的假设：**

| 坏的假设（不可证伪） | 好的假设（可证伪） |
|---------------------|-------------------|
| "可能是环境问题" | "如果根因是环境问题，那么在 staging 环境（配置相同）也应能复现" |
| "代码写得不好" | "如果根因是 `getUser()` 没有 null 检查，那么传入 null 时应抛出 TypeError" |
| "数据库有问题" | "如果根因是 email 字段大小写不匹配，那么用 LOWER() 包装查询后 bug 应消失" |

> **关于 Flaky / 偶发 bug**：如果症状表现为测试偶发失败或不可稳定复现，仅设计一次验证实验不足以确认根因。需要结合统计显著性判定——不是"跑了 3 次没挂"就算确认。详见「专项排查技术库 → 技术 E：Flaky test 分析」。

#### 第二步：设计验证实验

对每个假设设计一个**证伪实验**——不是证明它正确，而是试图证明它错误：

| 假设 | 证伪实验 | 如果假设正确，预测是... | 如果假设错误，预测是... |
|------|---------|----------------------|----------------------|
| 根因是前端未做 toLowerCase | 在前端加 toLowerCase → 重新测试 | bug 消失 | bug 仍然存在 |
| 根因是 SQL 大小写敏感 | 手动执行 LOWER() 查询 → 检查是否返回用户 | 返回用户 | 仍然不返回（说明不只是大小写问题） |

在形成每个假设后，先写出"如果这个假设是错的，我应该看到什么现象"，再设计实验验证。这样可以抵抗 LLM 天然倾向于寻找确认性证据的偏差。

#### 第三步：执行验证并判定

对每个实验：

1. **执行**：实际运行代码、查询数据库、查看日志——不要推理，要亲眼看到结果
2. **记录结果**：
   - ✅ **假设通过证伪尝试** → 实验按"假设正确"的预测发生 → 假设可信度 ↑
   - ❌ **假设被推翻** → 实验按"假设错误"的预测发生 → 回到阶段 2 或 3 重新形成假设
   - ⚠️ **不确定** → 实验结果不清晰 → 设计更精确的实验

#### 第四步：多假设竞争（如有）

如果阶段 2 产出了多个可能的根因假设，并发设计实验、并行验证：

```
假设 A: 根因在前端 toLowerCase
假设 B: 根因在后端 SQL 大小写
假设 C: 根因在数据库迁移脚本未完成

对每个假设设计证伪实验，按"最容易验证"的顺序执行。
容易程度排序：不需要修改代码就能验证 > 需要修改测试代码 > 需要修改源码 > 需要部署到其他环境
1. 先验证 C（最快：检查迁移脚本的完成状态）
2. 再验证 B（中等：手动执行 SQL）
3. 最后验证 A（最慢：需要改前端代码并重新构建）
```

#### 假设-验证循环规则

```
形成假设 → 设计证伪实验 → 执行验证
              │                │
              │                ├── ✅ 确认 → 记录为"确认的根因" → 进入阶段 5
              │                │
              │                ├── ❌ 推翻 → 回到阶段 2（重新追问）
              │                │             或阶段 3（重新追踪数据流）
              │                │
              │                └── ⚠️ 不确定 → 设计更精确的实验
              │
              └── 无法设计实验 → 标注"无法验证" + 降为中等可信度
```

**推翻次数警告**：

- 1 个假设被推翻 → 正常，形成第 2 个假设
- 2 个假设被推翻 → 停下来，检查是否遗漏了关键信息（回到阶段 1 补充）
- 3+ 个假设被推翻 → **升级**：可能是架构性问题、第三方依赖 bug、或用户提供的信息有误。生成"假设推翻报告"交回 Bug修复与验证，建议用户重新审视 bug 描述或考虑外部因素

**阶段 4 出口条件**：

- [ ] 至少 1 个根因假设已经过证伪实验验证
- [ ] 确认的根因假设有 ≥2 个独立证据支撑（证据来源不能是同一个文件或同一条日志）
- [ ] 所有被推翻的假设已记录推翻原因和证据
- [ ] 如果 3+ 假设被推翻 → 已生成"假设推翻报告"并建议升级
- [ ] 如果根因指向外部系统 → 已标注"已知局限"
- [ ] 如果 bug 表现为偶发/不可稳定复现 → 已按技术 E（Flaky test 分析）的标准评估置信度

### 阶段 5：全面性扫描

> **找到根因只是完成了一半。另一半是：确保代码库中没有其他地方存在同样或类似的 bug。** 一个 bug 的出现通常意味着一个模式被错误地使用了多次。

#### 第一步：提取 bug 模式

从阶段 4 确认的根因中，提取可搜索的 **bug 模式**：

| 模式维度 | 提取方法 | 示例 |
|---------|---------|------|
| **函数/API 误用** | 出错的函数调用签名 | `findByEmail(email)` 未处理 null 返回 → 搜索所有 `findByEmail` 调用点是否都做了 null 检查 |
| **数据变换缺失** | 应该做但没做的数据操作 | `email.toLowerCase()` 缺失 → 搜索所有 email 比较/查询处是否做了大小写规范化 |
| **条件/边界遗漏** | 缺失的 if 判断或边界条件 | 缺少 `if (result == null)` 检查 → 搜索所有数据库查询返回值的使用点 |
| **配置/环境差异** | 不一致的配置或环境假设 | 开发环境不区分大小写但生产区分 → 搜索所有大小写敏感的字符串比较 |
| **时序/顺序依赖** | 错误的调用顺序或竞态条件 | 先渲染后取数据 → 搜索所有在 async 函数外使用 await 结果的代码 |
| **校验/防护缺失** | 缺少输入校验或边界防护 | 未对用户输入做规范化 → 搜索所有外部输入入口是否有前置校验 |

#### 第二步：多维度搜索

对每个提取的 bug 模式，用以下维度覆盖式搜索。**不允许只用一个 grep 就说"找全了"——每个维度可能发现不同的结果。**

**维度 1：相同函数/API 调用**

搜索出错的函数名、方法名、API 路径的所有调用点。检查每个调用点是否有同样的错误模式。

```
grep 策略: 搜索函数名/方法名 → 对每个调用点检查关键上下文（返回值处理、参数传入、错误处理）
```

**维度 2：相同数据结构/字段**

搜索同一数据字段/变量的所有使用点。检查是否有同样的数据假设错误。

```
grep 策略: 搜索字段名/变量名 → 检查每个使用点是否做了同样的数据假设
```

**维度 3：相同逻辑结构/代码模式**

搜索结构上相似的代码——即使函数名不同。适用于：同一设计模式的多个实现、复制粘贴的代码、同一模板生成的文件。

```
grep 策略: 搜索关键语法结构（如 `if.*== null`、`.then(`、`await.*catch`）→ 在上下文窗口中分析逻辑相似性
```

**维度 4：相同调用链**

搜索出错的整个调用链（A→B→C）是否在其他上下文中以同样的方式被组装。用 Agent 派出只读子智能体探索不同的调用路径。

**维度 5：相同开发者/提交**

用 git blame 找出出错代码的作者和提交。搜索同一作者在同一时期的其他修改是否有类似模式。

```
git 策略: git log --author="name" --since="date" --oneline → 检查相关提交是否引入了同类问题
```

**维度 6：相反/对称逻辑**

如果 bug 是"X 情况下应该做 Y 但没做"，搜索所有 X 的相反情况（非 X、反 X）或对称情况。很多 bug 成对出现。

**维度 7：防御性缺口分析**

> 基于防御性排查方法论（详见「专项排查技术库 → 技术 D：防御性排查」）。

检查 bug 模式所涉及的校验逻辑是否**只在单层存在**——攻击面分析：

- **输入层**：对外部输入（用户输入、API 请求、文件读取）是否有前置校验？
- **中间层**：对内部数据传递是否做了冗余校验（即使上游"应该"校验了）？
- **输出层**：对持久化/发送前是否做了最终校验？

```
分析策略: 假设每个输入都是异常的 → 校验逻辑是否在所有层都存在？
→ 如果只在某一层校验 → 记录为防御缺口，连同 🔴🟠 类 bug 一同报告
```

> 注意：防御性缺口的修复建议属于「Bug修复与验证」的职责范围。本 skill 只负责**识别和报告**缺口。

#### 第三步：分类和优先级

对搜索到的每个潜在 bug 位置进行分类：

| 分类 | 定义 | 处理建议 |
|------|------|---------|
| 🔴 **同类 bug**（确认） | 完全相同的根因导致的可复现异常 | 必须与主 bug 一同修复 |
| 🟠 **同类 bug**（高概率） | 代码模式完全一致，仅在特定输入下触发 | 强烈建议与主 bug 一同修复 |
| 🟡 **相似 bug**（中概率） | 根因不完全相同，但属于同一缺陷类型 | 建议在本次修复中一并处理，或建独立 issue |
| 🔵 **潜在风险**（低概率） | 代码模式相似但当前未触发——防御性修复可选 | 建议记录但不阻塞本次修复 |
| ⚫ **防御缺口** | 校验/防护在某一层缺失，当前未被利用但构成攻击面 | 建议在本次修复中补上防护 |

#### 第四步：生成全面扫描报告

```

- 搜索维度: [实际使用的维度列表]

| 🔵 潜在风险（低概率） | N | 记录跟踪 |
| ⚫ 防御缺口 | N | 建议补防护 |

### 详细位置清单

| 5 | 🔵 | search/index.ts:56 | 数据库查询后使用了 `result[0]` 未检查长度 | 搜索无结果时 | 加空数组检查 |
| 6 | ⚫ | api/middleware/auth.ts:12 | 认证中间件未校验 token 格式，依赖下游 Service 校验 | 畸形 token 进入系统 | 在入口层加 token 格式校验 |

### 搜索覆盖度声明

| 搜索维度 | 状态 | 搜索范围 |
|---------|------|---------|
| 相同函数调用 | ✅ 已完成 | 全局搜索 `findByEmail` — 找到 N 个调用点 |
| 相同数据结构 | ✅ 已完成 | 全局搜索 `email` 字段使用 — 检查了 M 个位置 |
| 相同逻辑结构 | ✅ 已完成 | 搜索 `\.findBy\w+\(` 模式的返回值处理 |
| 防御性缺口分析 | ✅ 已完成 | 检查了输入层-中间层-输出层的校验覆盖 |
| ... | ... | ... |

### 扫描局限性
- 动态生成的代码（如运行时反射调用的方法）未被 grep 覆盖
- 第三方库内部使用不受本次扫描影响
- 如代码库包含非当前项目语言的文件，已标注在搜索覆盖度中
```

**阶段 5 出口条件**：

- [ ] Bug 模式已从根因中提取（至少 2 个维度的模式）
- [ ] 多维度搜索已完成（至少使用 3 个不同维度）
- [ ] 每个搜索结果已分类（🔴🟠🟡🔵⚫）
- [ ] 全面扫描报告已生成，包含搜索覆盖度声明
- [ ] 扫描局限性已标注（让调用方知道哪些区域未被覆盖）
- [ ] 防御性缺口分析（维度 7）已在 bug 涉及外部输入/多组件系统时执行

## 专项排查技术库

> 以下五项技术是本 skill 的**深度工具**。它们不是独立阶段——而是从对应阶段分叉进入的可选方法。每项技术描述：何时触发、如何执行、产出什么。在对应阶段的出口条件中，已注明何时应启动这些技术。

### 技术 A：竞态条件排查

**触发条件**（满足任意一条即启动）：

- 症状分类为 🔵 竞态/不稳定
- bug 偶发、不可稳定复现（复现率 < 50%）
- bug 与并发操作相关（多线程/多进程/异步事件/定时器）
- 同样的输入有时正常工作、有时异常
- 加 sleep/延迟后 bug 行为改变

**执行方法**：

#### A1. 事件顺序重建

列出 bug 场景中所有并发的操作/事件，确定它们之间可能的执行顺序：

```
并发单元: [线程 A] [线程 B] [异步回调 C] [定时器 D]
共享资源: [变量 X] [文件 Y] [数据库连接 Z]

时间线（正常情况）:
  T1: A 写入 X=1
  T2: B 读取 X=1  ← 预期行为
  T3: C 基于 X=1 执行逻辑

时间线（bug 触发）:
  T1: A 开始写入 X（未完成）
  T2: B 读取 X=旧值  ← 脏读
  T3: A 完成写入 X=1  ← 太晚了，B 已经用了旧值
```

#### A2. 时序图分析

绘制并发组件交互的时序图，标注关键的事件顺序依赖：

```
线程A         线程B         共享状态
  │             │             │
  ├─lock()──────┤             │
  │             ├─read()──────┤ ← B 未获取锁，直接读
  │             │ 返回旧值    │
  ├─write(1)───┤             │
  │             │             │
  ├─unlock()───┤             │
  │             ├─write(2)───►│ ← B 基于旧值算出 2，覆盖了 A 的 1
  ▼             ▼             ▼
```

#### A3. Interleaving 分析

枚举关键的指令交错可能性。对于涉及 N 个并发单元、每个单元有 M 个关键操作的场景，列出所有导致异常的交错序列：

```
关键操作:
  A1: user = cache.get(key)    // 检查缓存
  A2: if (!user) user = db.query(key)  // 缓存未命中，查数据库
  A3: cache.set(key, user)     // 回填缓存

  B1: cache.delete(key)        // 更新用户后删除缓存

异常交错:
  A1 → B1 → A2 → A3  ← A 在 B 删除缓存后查到了旧数据并回填，缓存变成脏数据
```

#### A4. 条件轮询替代盲等

如果 bug 涉及任意 timeout（如 `sleep(1000)`、`setTimeout(..., 5000)`），分析是否可以用**事件驱动等待**替代：

```
盲等（脆弱）:
  await sleep(5000)  ← 在慢机器上不够，在快机器上浪费
  checkResult()

条件轮询（可靠）:
  await waitFor(() => result !== undefined, {timeout: 30000, interval: 200})
  // 一旦条件满足立即返回，绝不盲等
```

> 详细的条件轮询实现（通用 helper、模式速查、常见错误）见参考文件：[references/condition-based-waiting.md](references/condition-based-waiting.md)

**产出**：

- 事件顺序对比（正常 vs 异常）
- 时序图（标注竞态窗口）
- Interleaving 异常序列列表
- 竞态条件假设（哪个操作序列导致了不一致）
- 条件轮询替代建议（如适用）

### 技术 B：插桩调试

**触发条件**（满足任意一条即启动）：

- 数据流图中有 ≥2 个变换点状态为"不确定"
- 需要精确定位多组件系统中的断裂点（前端 → API → Service → DB 等）
- 错误信息不包含足够的位置信息（如"内部错误"、"未知异常"）
- 怀疑环境/配置传播在某层丢失

**执行方法**：

#### B1. 组件边界插桩

在多组件系统的每个边界处插入诊断日志/断点，记录进入和离开的数据：

```
原则：对每个组件边界，记录「进」和「出」

示例（前端 → API → Service → DB 四层系统）:

[边界 1: 前端 → API]
  进: HTTP Request { method, path, headers, body }
  出: HTTP Response { status, body }

[边界 2: API → Service]
  进: Service 方法调用参数
  出: Service 方法返回值 / 异常

[边界 3: Service → DB]
  进: SQL 查询语句 + 参数
  出: 查询结果 rows / 异常

运行一次，收集所有边界的日志 → 对比分析哪一层的「出」与预期不符
```

插桩代码示例：

```javascript
// 在边界处插入诊断日志（排查完成后移除）
console.log('[DIAG] Layer: API→Service | In:', JSON.stringify(params));
const result = service.doSomething(params);
console.log('[DIAG] Layer: API→Service | Out:', JSON.stringify(result));
```

#### B2. 二分法缩小范围

当数据变换链较长（5+ 步）且不确定坏数据出现在哪一段时，使用二分法：

```
步骤链: A → B → C → D → E → F → G → H → 出错

第 1 轮: 在 D 和 E 之间插入检查点 → D 的输出正确吗？
  正确 → 坏数据在 E→H 之间 → 缩小到后半段
  错误 → 坏数据在 A→D 之间 → 缩小到前半段

第 2 轮: 在缩小的范围内继续二分 → 直到定位到确切步骤

对数复杂度: 8 步链 → 最多 3 轮定位；16 步链 → 最多 4 轮
```

#### B3. 环境/配置传播验证

如果怀疑环境变量、配置或上下文在组件间传递时丢失：

```
对每一层检查:
  - 该层接收到了哪些环境变量/配置？
  - 该层使用了哪些？值与预期是否一致？
  - 该层传递给下一层时是否有遗漏或覆盖？
```

**产出**：

- 组件边界数据对比表（每个边界的"进"与"出"）
- 精确定位的断裂组件 + 断裂点前后的数据差异
- 二分法缩小后的最小可疑区间
- 环境/配置传播异常的层（如适用）

### 技术 C：Bisect 二分定位

**触发条件**（满足任意一条即启动）：

- bug 是回归型（"之前好的，现在坏了"）
- 有可用的 git 历史
- 不确定是由哪次提交引入的
- 有 ≥2 个候选提交范围需要缩小

**执行方法**：

#### C1. git bisect 自动化

当存在可自动执行的验证方式（测试命令、脚本等）时：

```bash
# 启动 bisect
git bisect start

# 标记当前版本为坏
git bisect bad HEAD

# 标记已知好的版本（如上次发布的 tag）
git bisect good v2.1.0

# 如果有自动化验证脚本
git bisect run ./scripts/verify-fix.sh
# 或
git bisect run npm test -- --testPathPattern="failingTest"

# 完成后查看结果
git bisect log
# → 自动定位到引入 bug 的 commit

# 结束 bisect
git bisect reset
```

#### C2. 脚本化验证

编写可自动执行的验证脚本——测试失败即 exit 1，通过即 exit 0：

```bash
#!/bin/bash
# verify-fix.sh — 验证 bug 是否存在的脚本
# 返回 0 表示 bug 不存在（good），返回 1 表示 bug 存在（bad）

# 编译/构建
npm run build || exit 1

# 运行相关测试
npm test -- --testPathPattern="login" || exit 1

# 执行手动验证步骤
node -e "
const result = require('./dist/login').validateEmail('User@Example.com');
if (result === false) process.exit(1);  // bug 存在
"
```

#### C3. 手动 bisect（无自动化验证时）

当无法自动验证（如需要 UI 操作、需要特定环境等）时：

```
1. git log --oneline <good>..<bad>  ← 获取所有候选提交
2. 二分检出中间的 commit → git checkout <mid_commit>
3. 手动测试 bug 是否存在
4. 如果 bug 存在 → bad = mid_commit
   如果 bug 不存在 → good = mid_commit
5. 重复 2-4 直到范围缩小到 1-2 个提交
6. 查看可疑提交的 diff: git show <bad_commit>
```

**产出**：

- 引入 bug 的提交 SHA
- 提交的完整 diff（变更内容、文件列表）
- 提交信息（作者、时间、关联 issue）
- 引入 bug 的具体变更行

### 技术 D：防御性排查

**触发条件**（满足任意一条即启动）：

- bug 涉及外部输入（用户输入、API 请求、文件上传、消息队列）
- 根因与输入校验缺失或边界条件遗漏相关
- 系统有多个层级（前端→后端→数据库 / 多层微服务）
- 修复可能只在单层进行——需要评估上下游是否同样脆弱

**执行方法**：

#### D1. 假设输入异常（穷举异常值）

对 bug 相关的每个关键输入接口，穷举可能的异常输入值：

```
关键输入: email 字段
正常值: "user@example.com"

异常值穷举:
  null / undefined         → 代码如何处理？
  ""（空字符串）            → 是否有空值检查？
  "not-an-email"           → 是否有格式校验？
  "a" * 10000（超长）       → 是否有长度限制？
  "<script>alert(1)</script>" → 是否有 XSS 防护？
  "../../etc/passwd"（路径遍历）→ 是否有路径校验？
  "user@example.com" + "\x00" + "extra" → 是否有 null byte 注入保护？
```

对每个异常值，追踪它从入口到出错点的完整路径，记录每层如何处理（校验/转换/忽略/崩溃）。

#### D2. 边界条件穷举

对每个关键数值、状态转移、集合操作，检查边界条件：

```
数值边界:
  0, -1, 1, MAX_INT, MIN_INT, MAX_INT+1（溢出）

集合边界:
  空数组 [], 单元素 [x], 大量元素（性能/内存）

状态转移边界:
  初始状态 → 重复初始化
  终态 → 再次触发转移
  非法状态 → 能否进入

时间边界:
  时间戳 = 0（epoch）
  过期时间 = 当前时间（边界刚好过期）
  时间回拨（NTP 调整）
```

#### D3. 多层校验缺口分析

检查校验逻辑是否在所有层都存在——而非仅依赖某一层：

```
示例: 用户登录的 email 校验

│ 层          │ 当前校验                        │ 应有哪些校验              │ 缺口 │
│─────────────│─────────────────────────────────│──────────────────────────│──────│
│ 前端 (UI)   │ HTML5 type="email"             │ 格式 + 非空 + 长度限制    │ ⚠️ 长度 │
│ 网关 (API)  │ 无——直接透传                    │ 格式 + 非空              │ 🔴 全缺 │
│ Service     │ 不为 null（代码中的 if 判断）   │ 格式 + 非空 + 合法域名    │ 🟠 格式 │
│ DB          │ 无——直接 SELECT                │ SQL 注入防护             │ ✅ 有参数化 │
│─────────────│─────────────────────────────────│──────────────────────────│──────│
│ 结论: 如果前端被绕过（curl/脚本），畸形 email 直通 Service。需要至少在 API 或 Service 层加校验。 │
```

**产出**：

- 异常输入穷举表（每个关键输入 → 异常值列表 → 每层的行为）
- 边界条件覆盖检查表
- 多层校验缺口清单（⚫ 类）
- 易受攻击的输入点优先排序（按风险：🔴 无任何校验 > 🟠 单层校验 > 🟡 校验不完整）

#### D3.1：防御纵深四层模型

| 层级 | 名称 | 做什么 | 设计问题 |
|------|------|--------|---------|
| **L1** | 入口点验证 | API 边界拒绝非法输入（类型/格式/范围） | "如果调用方传了 null？" |
| **L2** | 业务逻辑验证 | 确保数据对当前操作有意义（状态前置条件/业务规则） | "如果状态不是 ACTIVE？" |
| **L3** | 环境守卫 | 防止在错误上下文中执行危险操作（测试环境不连生产DB） | "如果在错误上下文被调用？" |
| **L4** | 调试插桩 | 捕获足够上下文用于取证（关键变量/调用栈/时间戳） | "如果 bug 在生产中发生，有什么诊断信息？" |

**使用方式**：排查到 bug 时，不只修复——问：从哪一层能阻止它？
- L1 被绕过 → 加强入口验证
- L2 缺失 → 增加前置条件检查
- L3 没考虑 → 增加环境检查
- L4 缺失 → 增加诊断日志

**案例**：
```
Bug：生产环境误发测试邮件

L1：地址合法 → 无法拦截
L2：用户状态 ACTIVE → 无法拦截 —— 到此防不住
L3：[缺失] 没有检查运行环境——测试环境应拒绝发送
L4：[缺失] 不知道哪封邮件从何触发

根因：L3 缺失。修复 = 发送前检查环境 + L4 加环境标识日志
```

### 技术 E：Flaky test 分析

**触发条件**（满足任意一条即启动）：

- bug 表现为测试偶发失败，不可稳定复现
- 修复后的验证——需要判断"到底是真的修好了，还是恰好这次没触发"
- 同一个测试多次运行结果不一致

**执行方法**：

#### E1. 统计显著性判定

**核心原则**：不是"跑了 3 次没挂就算过"。修复的可信度需要用统计方法评估。

```
原始失败率估算:
  收集足够多的历史运行数据（≥20 次），计算失败率 P_fail
  例如: 20 次中失败 6 次 → P_fail ≈ 30%

修复后验证所需连续通过次数 N:
  N = log(α) / log(1 - P_fail)
  其中 α = 可接受的误判概率（建议 0.01，即 1%）

  对于 P_fail = 30%:
    N = log(0.01) / log(0.70) ≈ 13 次连续通过

  含义: 如果你连续跑 13 次全部通过，那么"修复无效"（bug 仍然以 30% 概率存在）的可能性 < 1%

  对于 P_fail = 10%:
    N = log(0.01) / log(0.90) ≈ 44 次连续通过
  → flaky 越稀有，需要的验证次数越多
```

**快速判定表**（默认 α = 0.01）：

| 原始失败率 | 需要连续通过次数 | 判定 |
|-----------|:-------------:|------|
| 50%（每次都有机会挂） | 7 | 跑 7 次全过 → 可信 |
| 30%（3 次里挂 1 次） | 13 | 跑 13 次全过 → 可信 |
| 10%（10 次里挂 1 次） | 44 | 跑 44 次全过 → 可信 |
| 5% | 90 | 跑 90 次全过 → 可信 |
| < 5%（极稀有） | 100+ | 增加日志 + 标记"低置信度" |

#### E2. 失败模式聚类

收集多次失败日志，按错误类型聚类：

```
失败日志 #1: "TimeoutError: connection timeout after 5000ms"
失败日志 #2: "TimeoutError: connection timeout after 5000ms"
失败日志 #3: "AssertionError: expected 200, got 500"
失败日志 #4: "TimeoutError: connection timeout after 5000ms"
失败日志 #5: "NullPointerException at UserService:47"

聚类结果:
  模式 A（超时）: 3/5 = 60%  ← 主要模式
  模式 B（500 错误）: 1/5 = 20%
  模式 C（空指针）: 1/5 = 20%  ← 可能是独立 bug
```

> 如果有 ≥2 种不同的失败模式 → 可能存在多个独立根因。每种模式都需要独立的假设-验证。

#### E3. 环境因素隔离

逐一排除常见的 flaky 根因。对每个因素，设计一个排除实验：

| 可能因素 | 排除实验 | 如果排除后变稳定... |
|---------|---------|-------------------|
| **时间依赖** | 固定时钟（mock Date.now / sinon fakeTimers） | 根因是时间相关逻辑（过期、超时、定时任务） |
| **执行顺序依赖** | 随机化测试执行顺序（--shuffle） | 根因是测试间共享状态未清理 |
| **外部服务** | Mock 外部 API 返回固定数据 | 根因是外部服务不稳定 |
| **随机数** | 固定随机种子 | 根因是对随机值的隐式依赖 |
| **异步时序** | 所有 async 操作改为同步 flush | 根因是竞态条件（→ 同时使用技术 A） |
| **资源竞争** | 单线程运行（--runInBand / -j 1） | 根因是测试并行执行时的资源冲突 |
| **数据污染** | 每个测试前重建数据库/清理状态 | 根因是前一个测试的副作用 |

**产出**：

- 原始失败率估算 + 所需连续通过次数 N
- 失败模式分类（可能揭示多个独立根因）
- 环境因素隔离实验矩阵（哪些因素已排除，哪些存疑）
- flaky 修复置信度评估（🟢 高 / 🟡 中 / 🔴 低——基于统计判定）

4. 确认交接清单与报告内容一致

## 快速参考

| 你在做什么 | 看哪个阶段 |
|-----------|-----------|
| 刚收到一个 bug 需要排查根因 | 阶段 1：先收集信息，别急着推论 |
| 大概知道原因但想确认是否深层 | 阶段 2：5 Whys——追问到不能再问 |
| 知道出错点但不知道数据什么时候变坏的 | 阶段 3：数据流逆向追踪 |
| 有一个根因猜测但不确定 | 阶段 4：假设-验证循环——设计实验证伪 |
| 根因已确认，想知道还有没有别处有同样问题 | 阶段 5：全面性扫描 |
| 排查完了，需要交给修复流程 | 阶段 6：输出与交接 |
| 同一个 bug 修了又复发 | 回到阶段 2：上次没追到真根因 |
| 用户说"还有没有别的" | 阶段 5：全面性扫描 |
| 3 个假设都被推翻 | 阶段 4 第四步：升级处理 |
| bug 偶发、时好时坏、并发相关 | 专项技术 A：竞态条件排查 |
| 多组件系统中不确定哪一层坏了 | 专项技术 B：插桩调试 |
| 不知道 bug 是哪次提交引入的 | 专项技术 C：Bisect 二分定位 |
| 想检查系统各层的防护是否足够 | 专项技术 D：防御性排查 |
| 测试偶发失败、修复后不确定是否真修好 | 专项技术 E：Flaky test 分析 |

## 常见错误

| 错误 | 为什么错 | 正确做法 |
|------|---------|---------|
| 问了一两层"为什么"就停下 | 停在表面原因 → 修的只是症状 | 5 Whys 追到技术根因层（通常 ≥4 层） |
| 每层"因为"不写证据 | 因果链变成猜测链——不可信 | 每层必须引用代码行号或日志行 |
| 数据流追踪只看到出错点，不向上游追溯 | 修复出错点可能只是掩盖症状——坏数据源头还在 | 逆向追踪至少 3 层变换点 |
| 只设计验证假设的实验，不设计证伪实验 | 确认偏误——只找支持自己的证据 | 每个实验必须能推翻假设 |
| 第一个假设通过验证就停止 | 可能有更深的根因——浅层假设也能通过某些实验 | 至少验证到 ≥3 层因果深度 |
| 全面扫描只搜一个 grep 就说"找全了" | 同一个 bug 模式可能以不同形式出现在不同维度 | 至少 3 个维度搜索（见阶段 5 第二步） |
| 扫描结果全标 🔴 或全标 🔵 | 没有认真评估每个位置的实际触发概率 | 按阶段 5 第三步的定义逐项分类 |
| 排查报告不给交接清单 | Bug修复与验证 不知道你的产出对应它的哪个输入 | 阶段 6 的交接清单表格必须填写 |
| 排查发现根因后直接动手修 | 越权——修代码是 Bug修复与验证→智能体闭环开发 的事 | 止步于报告——交回给调用方 |
| 3 个假设被推翻后继续形成第 4 个假设而不升级 | 可能根因不在代码层面——死循环 | 升级：生成"假设推翻报告"，建议重新审视 |
| 对无法验证的假设标"高可信度" | 不可验证 ≠ 正确 | 标注"无法验证" + 降为 🟡 中等或 🔴 低可信度 |
| 全面扫描跳过维度 5（git blame） | 同一作者可能在其他地方犯了同样的错误 | 至少检查同期的相关提交 |
| 数据流图用"可能""大概"代替确定性的数据状态 | 不确定就没有分析价值 | 不确定的地方标注"⚠️ 待确认"并建议如何确认 |
| 竞态 bug 用加 sleep 来"修复" | timeout 只降低概率不消除根因——在慢机器上仍会触发 | 用条件轮询/事件驱动等待替代盲等（见技术 A4） |
| 多组件 bug 只看最终出错点，不逐层定位 | 修复出错层可能掩盖上游的数据错误 | 使用插桩调试逐层定位断裂点（见技术 B） |
| flaky bug 修完跑 3 次通过就声称"修好了" | 3 次连续通过对于失败率 30% 的 bug 仅有 34% 置信度 | 按统计显著性计算所需连续通过次数（见技术 E1） |
| git bisect 用完后不 reset | 留在 detached HEAD 或 bisect 状态中 | `git bisect reset` 回到正常分支（见技术 C1） |

## 危险信号 — 停下重新检查

- 因果链中某层的"因为"写的是"代码写得不好" → **太模糊。追问：具体哪一行、什么逻辑写得不好？**
- 你脑子里出现"这很明显就是 X 的问题，不用追了" → **你在猜，不是在排查。回到阶段 2**
- 数据流图中所有变换点都标"不确定" → **你没有实际读代码。回到阶段 3，打开文件——或启动技术 B（插桩调试）**
- 假设验证实验中你只找了支持假设的证据 → **确认偏误。设计一个证伪实验**
- 全面扫描只用了 1 个 grep 命令 → **覆盖度不足。至少 3 个维度**
- 排查报告没有标注任何局限性 → **你假装什么都找到了。找出至少 1 个局限**
- 你准备在排查报告后面直接写修复代码 → **越权。修复是 Bug修复与验证 的事**
- 因果链只有 Why 1 和 Why 2 → **深度不够。至少 Why 3**
- 同一个假设验证了 3 次（每次实验稍有不同）→ **你在试图挽救一个该被推翻的假设。承认它错了，形成新假设**
- 对偶发 bug 用"加个 sleep(2000)"来"修复" → **这不是排查——这是在掩盖竞态窗口。见技术 A**
- 发现多组件 bug 后直接在出错层加 try-catch → **这会让上游的坏数据静默传播到更多地方。用插桩逐层定位（技术 B）**
- flaky test 修完跑了 3 次没挂就说"修好了" → **统计上不可信。必须计算实际所需次数（技术 E1）**
- 发现校验缺失后只在一个层补了校验 → **其他层仍然裸奔。用防御性排查（技术 D）评估全链路**
