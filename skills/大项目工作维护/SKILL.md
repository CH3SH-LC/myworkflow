## 触发场景

本 skill 在**两个时机**被调用，分工不同：

| 调用时机 | 做什么 | 触发方式 |
|----------|--------|---------|
| **进入时**（动手写代码之前） | 阶段 1（读文档知上下文）+ 阶段 2 准备 | CLAUDE.md 引导、或用户说"开始工作" |
| **完成时**（代码变更验证通过后） | 阶段 3（强制文档同步）+ 阶段 4（验证无遗漏） | 每次代码变更完成后自动触发 |

### 显式触发
- CLAUDE.md 中写明了"每次启动会话必须先调用本 skill" → 进入时无条件触发
- 用户说"更新 PROGRESS""同步项目文档""记录一下工作"→ 完成时触发

### 隐式触发
- 项目根目录存在 CLAUDE.md，且其中定义了文档同步规则 → 进入时 + 完成时自动触发
- 完成了任何代码变更（bug 修复、功能开发、重构）→ 完成时触发

### 不触发
- 项目没有 4 文件体系 → 应先调用「myworkflow:大项目初始化」
- 纯问答、代码解释、文件阅读（没有产生代码变更）
- 单文件脚本、临时小工具

## 必需要素

- 项目根目录存在 CLAUDE.md（且其中包含文档同步规则）
- 本次工作产生了代码变更（或即将产生变更）

## 前置强制步骤

> **核心原则：文档是工作的副产品，不是额外负担。** 边做边在脑子里组织 PROGRESS 条目，到写的时候就是填空——几分钟就能完成同步。

1. **找到项目根目录**：向上查找 CLAUDE.md
2. **读取 CLAUDE.md**：了解项目规则和文档同步约定
3. **读取 PROGRESS-LITE.md**：了解最近做了什么，避免重复劳动（文件 ≤200 行全读，否则读最近 3 天）

## 目标

让"维护项目文档"变成肌肉记忆——每次工作自动走完 工作前→工作中→工作后→验证 四阶段，不留遗漏。

## 执行流程：四阶段维护

本 skill 的四个阶段横跨两个调用时机：

```
【进入时】调用本 skill → 阶段 1（工作前）→ 阶段 2（工作中，准备就绪）
                          ↓
                    执行实际开发工作（由「myworkflow:智能体闭环开发」或其他 skill 驱动）
                          ↓
【完成时】再次调用本 skill → 阶段 3（工作后）→ 阶段 4（验证）
```

### 阶段 1：工作前 — 读文档，知上下文

在动手写代码之前：

```
必须读：
□ CLAUDE.md — 了解项目规则
□ PROGRESS-LITE.md — 了解最近动态（≤200 行全读，否则读最近 3 天）

按需读：
□ STRUCTURE.md — 不知道文件在哪时
□ PROGRESS.md 中的相关条目 — 了解之前类似工作的细节
```

**为什么重要**：避免"这个 bug 昨天刚修过又复现了""这个功能上周已经有人做了一半"。

### 阶段 2：工作中 — 边做边记

执行代码变更时，在对话中以简短 Markdown 列表形式维护一个**变更草稿**（确保多轮对话中可追溯）：

1. **开始前**：列出预期要修改的文件清单
2. **每完成一个文件的修改**：在清单中标注实际操作（Add / Modify / Delete）和一句话原因
3. **全部完成后**：对照清单确认所有变更的验证结果

**草稿以对话中的 Markdown 列表形式维护**——它在阶段 3 写正式条目时提供原材料。核心是确保阶段 3 开始时你不是"空白的"，而是有一份完整的变更摘要可以展开。

### 阶段 3：工作后 — 强制文档同步

代码变更完成且验证通过后，**立即**按以下顺序更新。不可跳过，不可推迟。

#### 3.1 更新 PROGRESS.md（详细条目）

在 `---` 分隔线之后、已有最新条目之前插入新内容。如果今天的日期标题已存在，在该日期标题下追加子标题；否则新建日期标题。

> **插入位置**：PROGRESS.md 的结构是 `文件头（标题+说明）→ --- → 内容区`。新条目永远插入在 `---` 的下一行（即内容区的最顶部），确保最新记录在最前面。如果文件只有 `---` 而尚无任何日期条目，直接在 `---` 下一行开始写。

```markdown
## YYYY-MM-DD

### [标签] 简短标题

问题描述 / 变更原因：
（背景和动机）

根因分析：（仅 bug 修复需要）
（技术深挖：为什么会发生、为什么之前没发现、为什么这样修复）

修改文件：
- [操作]: `路径/到/文件` — 改了什么

验证：
（构建/测试/手动验证结果）
```

**标签**：`[New Feature]` 新增功能 / `[Debug]` 修复 bug / `[Change]` 重构优化 / `[Build]` 构建部署

**好坏对比**：

```markdown
# ✗ 差 — 3 个月后看不懂
### [Debug] 修复了一个 bug
问题描述：登录有问题。
修改文件：
- Modify: auth.ts — 修好了

# ✓ 好 — 3 个月后一目了然
### [Debug] 修复登录超时后未重定向到登录页

问题描述：
用户会话过期后 API 返回 401，前端未拦截该状态码重定向到登录页，
而是将 401 响应当作正常数据显示（显示 "undefined"）。

根因分析：
axios 拦截器中只处理了 200/201/404/500，401 落入了 default 分支。
该拦截器在 2026-03 重构时从全局移至 AuthContext 内，重构时遗漏了 401 case。
之前未暴露因为 token 有效期 7 天，测试期间从未触发过期。

修改文件：
- Modify: `src/api/interceptors.ts` — 新增 401 case，清除 token 并 redirect 到 /login
- Modify: `src/api/interceptors.test.ts` — 新增 401 拦截测试（2 tests）

验证：
pnpm test（48 files, 312 tests）全部通过；手动验证：清除 cookie 后刷新确认自动跳转登录页。
```

**根因分析怎么写**：不只说"XX 文件少了一行代码"（这是现象），追问"为什么少？什么时候少的？为什么之前没暴露？"。好的根因指向流程问题（重构遗漏）、假设错误、测试覆盖不足。

#### 3.2 更新 PROGRESS-LITE.md（精简条目）

在 `---` 分隔线之后插入（与 PROGRESS.md 相同的规则：最新条目在最前面）。如果今天的日期标题已存在，在该标题下追加条目；否则新建日期标题。

```markdown
## YYYY-MM-DD

- [Debug] 修复登录超时后未重定向到登录页
- [New Feature] 新增用户头像上传功能
```

**约束**：
- 每条**严格一行**——LITE 版的唯一价值是"能一次读几百条"
- 只写"做了什么"，不写"为什么"（为什么在 PROGRESS.md）
- 同日多条按重要性排序：[New Feature] > [Debug] > [Change] > [Build]
- 同日 >10 条时用子标题分组

#### 3.3 检查并更新 STRUCTURE.md

**需要更新**：新增/删除/重命名了文件或目录。
**不需要更新**：仅修改了文件内容。

更新方法：在对应目录树中添加/删除/重命名条目，为新文件加用途注释，更新顶部日期。

#### 3.4 检查并更新 CLAUDE.md

**仅在以下情况更新**：根目录结构变化、核心规则变化、新增了子项目。
大多数日常变更不需要更新 CLAUDE.md。

### 阶段 4：验证 — 确保无遗漏

#### 4.1 变更覆盖检查

```bash
# Bash/Git Bash: 覆盖三种情况——有历史commit / 仅一个commit / 无commit
(git rev-parse --verify HEAD >/dev/null 2>&1 && git diff --name-only HEAD~1 2>/dev/null) || git status --short
```
```powershell
# PowerShell 等效命令:
if (git rev-parse --verify HEAD 2>$null) { git diff --name-only HEAD~1 2>$null } else { git status --short }
```

```bash
# 备选：检查当前分支所有未合并提交的文件
git diff --name-only $(git merge-base HEAD main 2>/dev/null || git rev-parse --verify HEAD~10)..HEAD 2>/dev/null || git status --short
```

> **局限**：此命令只检查最近一次提交的变更。如果自上次文档同步以来有多次提交（如一次会话中做了 3 个独立变更），可能漏掉第 2、3 次提交的文件。解决方法是每次同步完立即提交（推荐），或手动比对 `git log --oneline` 确认本次会话的所有提交都被覆盖。
> **单 commit 仓库**：如果 fallback 到 `git status --short`，仅关注 M（modified）、A（added, staged）、D（deleted），忽略 ??（untracked）。若仍无法精确区分范围，手动列出已知变更文件并对照 PROGRESS.md 逐项检查。

确保每个变更文件都在 PROGRESS.md 中有记录。如果 git 不可用，手动回忆本次修改了哪些文件，逐一核对。

#### 4.2 结构一致性检查

用 Glob 扫描项目关键目录（src/、tests/、docs/、config/ 等），对照 STRUCTURE.md 记录的目录树：

- 文件系统中存在但 STRUCTURE.md 中没有 → 新增了文件/目录但忘了更新 STRUCTURE.md → 补上
- STRUCTURE.md 中有但文件系统中不存在 → 删除或重命名了文件但忘了同步 STRUCTURE.md → 删除过时条目
- 文件名或路径不匹配 → 重命名了但忘了更新 → 修正 STRUCTURE.md

如果项目文件很多（>100），优先检查本次变更涉及的目录，不必全量扫描。

#### 4.3 日期检查

- PROGRESS.md 顶部有没有今天的日期标题？
- PROGRESS-LITE.md 顶部有没有今天的日期标题？
- 没有 → 现在补。

#### 4.4 输出验证摘要

```
📋 文档同步完成：
✓ PROGRESS.md — 已追加 1 条详细记录
✓ PROGRESS-LITE.md — 已追加 1 条精简记录
✓ STRUCTURE.md — 无需更新（本次无文件增删）
✓ CLAUDE.md — 无需更新
```

如有遗漏已补正，用 `⚠️ 已补正` 标记。

## 项目规模适配

| 规模 | 文件数 | PROGRESS.md | PROGRESS-LITE.md | STRUCTURE.md |
|------|--------|-------------|-----------------|-------------|
| 小型 | <20 | 简短条目（简短根因：一句话，如'修复了 X 参数未校验导致的 Y 错误'） | 正常 | 顶层+1层 |
| 中型 | 20-100 | 标准条目（bug 必写根因） | 正常 | 顶层+2层 |
| 大型 | 100-500 | 完整条目（全写根因） | 可按阶段分组 | 顶层+3层+核心事实 |
| 超大型 | >500 | 根+子项目各自维护 | 根+子项目各自维护 | 分级维护 |

## 常见问题

### Q: 每次改一行代码也要更新 PROGRESS.md 吗？
A: 独立的、有意义的变更——是的。连续多个小改动（3 个拼写错误）可合并为一条。

### Q: PROGRESS.md 太大了怎么办？
A: 这正是 PROGRESS-LITE.md 存在的意义。智能体先读 LITE（≤200 行），需要细节时用 Grep 搜索 PROGRESS.md：
```bash
# 搜索某个日期的工作（需在 Bash/Git Bash 中运行）
grep -A 50 "## 2026-07-09" PROGRESS.md
# 搜索某个关键字的变更
grep -B 2 -A 30 "登录超时" PROGRESS.md
```
不要尝试用 Read 工具读取整个 300K 的文件——用 offset/limit 或者 Grep 定位到具体条目再读。

### Q: 忘了实时记录怎么办？
A: 看 git log 回顾今天的变更，然后补写。不如实时好，但比不写强。阶段 4 的日期检查会发现"今天没有记录"。

### Q: 一次会话做了多组独立的变更（修了 bug A、加了功能 B、重构了模块 C），怎么记录？
A: 每组独立变更在 PROGRESS.md 中各自一条 `###` 子标题，共享同一个 `## YYYY-MM-DD` 日期标题。在 PROGRESS-LITE.md 中也各占一行。顺序按重要性排（New Feature > Debug > Change > Build）。

### Q: CLAUDE.md 和 STRUCTURE.md 的区别？
A: CLAUDE.md 是**行为手册**（告诉智能体怎么做），STRUCTURE.md 是**空间地图**（告诉智能体文件在哪）。CLAUDE.md 可能有简化目录树，但完整文件级地图在 STRUCTURE.md。
