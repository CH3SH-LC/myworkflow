# 深度调研

**一次调研 = 一个可增长的知识库目录，不是一份报告。** 产物落在 `docs/research/<主题-slug>/`，按调研的逻辑要点切成多个 md 文件，可嵌套子目录、可续写、可修订。

## 触发

- **必须触发**：调研/研究/全面了解、技术选型与方案对比（"A vs B"）、需多来源验证的事实问题、查"XX 最新状况"。
- **不触发**：简单事实查询（直接搜索回答）、纯代码问题（走代码通道）、用户已有明确答案只需确认。

## 前置强制步骤

1. **禁止用自身知识替代搜索**——训练数据可能过时/有偏见，即使知道答案也必须实际搜索。
2. **锁定范围**：请求模糊 → AskUserQuestion 缩小（≤3 轮）；仍模糊 → 在总览页标注"范围基于以下假设：…"。
3. **声明不确定**：查不到的信息标注"信息缺口"，不编造。
4. **🔴 硬门禁——产物必须落盘为本地 .md 文件**，禁止仅对话输出；对话只给 ≤5 行摘要 + 目录路径，无例外。
5. **🔴 硬门禁——写入范围锁定 `docs/research/`（或其 fallback `./research/`）**，不得写入任何其他位置。

## 主线

**明确范围 → 划分逻辑骨架 → 建目录骨架 → 多源并行搜索 → 交叉验证 → 逐文件落盘 → 回写总览**；发现矛盾或可信度不足 → 补充搜索（聚焦）后回写对应文件。

## 产出结构规范

```
<项目根>/docs/research/<主题-slug>/
├── 00-总览.md              # 索引页：调研了什么 / 有哪几部分 / 结论摘要 / 变更记录
├── 01-<逻辑要点>.md        # 一个逻辑要点 = 一个文件
├── 02-<逻辑要点>.md
├── 03-<逻辑要点>.md
└── <子主题-slug>/          # 某个要点体量大 → 升格为子目录
    ├── 00-总览.md          # 子目录自己的索引
    ├── 01-<层面>.md
    └── 02-<层面>.md
```

命名规则：

- `<主题-slug>` / `<子主题-slug>`：英文 kebab-case（如 `vector-database-selection`），**稳定**，不随调研轮次变化。
- 文件编号两位递增，编号即阅读顺序；索引页固定 `00-`。
- 每个 `NN-<要点>.md` 头部固定三行：**调查的问题 / 结论一句话（含可信度）/ 最后更新日期**。

三个必备要素（缺一即不合格）：**有总览索引页、按逻辑要点分文件、支持子文件夹嵌套**。

### `00-总览.md` 结构

```markdown
# 调研：<主题>
> 首次调研 YYYY-MM-DD ｜ 最后更新 YYYY-MM-DD ｜ 轮次 N ｜ 来源总数 N

## 调研范围与假设
## 目录索引
| 文件 | 回答的问题 | 状态 | 最后更新 |
## 结论摘要
[每部分 1-2 句 + 可信度 + 指向文件]
## 变更记录
| 日期 | 变更 | 影响文件 |
## 信息缺口
```

## 单文件体量阈值

| 判据 | 动作 |
|------|------|
| 单文件 ≤ 300 行且 ≤ 12000 字符 | 正常交付 |
| 单文件 > 300 行 或 > 12000 字符 | **必须拆分**：该要点升格为子目录，按其内部二级逻辑切开 |
| 单文件 > 500 行 | **禁止交付**，无论内容多连贯 |
| `00-总览.md` > 150 行 | 索引页只留索引与摘要，细节下沉到分文件 |

拆分不是为了行数好看：**同一文件里出现两个能各自独立回答的问题，就该是两个文件。**

## 阶段 1：明确范围 + 逻辑骨架先行

**这是解决"大量调研最后只挤出一小份报告"的关键步骤，绝不允许跳过直入搜索。**

1. **解析用户意图**：主题 / 深度（概览→快速，学术级→完整流程）/ 时效性 / 约束（语言、地域、排除项）。
2. **锁定问题**（模糊时 AskUserQuestion 缩小，≤3 轮）：① 缩小主题 ② 确认深度 ③ 确认产出位置（`docs/research/` 还是 fallback `./research/`）。
3. **划分逻辑要点**——先不搜索，先产出「逻辑骨架表」：

   | # | 要回答的问题 | 产出文件 | 内容层面（写什么/不写什么） | 搜索维度 |
   |---|-------------|---------|--------------------------|---------|
   | 01 | 问题 A | `01-xxx.md` | 层面 1 / 层面 2 | 官方文档、社区、对比评测 |

   划分判据：
   - 一个要点 = **一个可以被单独回答的问题**，不是"一个章节标题"。
   - 要点数建议 3–8 个；少于 3 个说明没调研价值，多于 8 个考虑折叠为子目录。
   - 骨架阶段就要标出**哪个要点预计体量大**——预计会写很多的直接定为子目录，别等写完再拆。
4. **建目录骨架**：把骨架表落成真实文件——`00-总览.md`（含范围与索引表）+ 每个要点一个带标题的空壳文件。**先有文件，才有归属**，后续每条发现都有明确落点，从机制上消除"结尾压缩"。
5. **用户确认**骨架，或"直接开始"。
6. **出口**：核心问题一句话说清、逻辑骨架表已生成、目录骨架已建、用户已确认。

## 阶段 2：多源搜索（并行）

1. **设计搜索维度**（从以下选 ≥3 个；多源并行 → 派发子智能体）：
   官方文档 `<topic> official documentation`；社区讨论 `<topic> reddit/hackernews`；对比评测 `<A> vs <B> comparison`；学术/技术博客 `<topic> deep dive`；中文社区 `<主题> 实践 经验`；GitHub/开源 `<topic> github stars`；定价/成本 `<service> pricing`；负面/批评 `<topic> problems/issues`。
2. **每维度一个搜索子任务**：WebSearch ≥3 次不同关键词组合 → 选 3-5 个最相关来源 → WebFetch 全文 → 提取与骨架表相关的关键信息 → 输出 `来源 | URL | 关键发现 | 归属文件 | 可信度` 表 + 详细摘录。
   **摘录必须按「归属文件」分桶输出**，禁止交回一段笼统总结——否则又回到压缩成小报告的老路。
3. **可信度**：🟢 官方/权威/同行评议/数据可复现；🟡 知名博客/社区高赞/公司技术博客；🔴 个人博客/匿名/未注日期/明显偏见。
4. **出口**：≥3 维度并行、每维度 ≥2 个有效来源、总来源 ≥8、每个来源已标可信度、每条发现已指定归属文件。

## 阶段 3：交叉验证

1. **提取核心声明**为清单（声明 → 来源 A/B/C → 验证状态 → 归属文件）。
2. **分类处理**：
   - ✅ ≥2 独立来源确认 → 写入归属文件，标注来源。
   - ⚠️ 单一来源 → 写入但标"单一来源，未交叉验证"。
   - ❌ 来源矛盾 → **触发补充搜索**，聚焦矛盾点找第 3-4 个来源裁决。
   - 🔴 无来源 → 标"信息缺口"，在总览页「信息缺口」区登记。
3. **处理矛盾不选边站**：补充搜索聚焦矛盾；文中并列呈现各方观点及依据；给出基于方法论的判断但标"仅供参考"。
4. **出口**：核心声明全列入、每声明 ≥2 来源（或已标注单一/矛盾/缺口）、矛盾已补充搜索、缺口已标注。

## 阶段 4：逐文件落盘 + 总览回写

1. **逐要点写入**：用 Write/Edit 把分桶后的内容写进对应文件。正文每个事实性声明必须带来源标注（`[来源 #N]` 或内联链接 + 可信度）。**禁止把内容集中堆在总览页。**
2. **回写总览**：更新索引表「状态/最后更新」、结论摘要（每条 1-2 句 + 指向文件）、变更记录、信息缺口。
3. **双向一致性检查**：每个要点文件必须能被总览索引到；总览索引的每个文件必须真实存在（**悬空 + 孤儿双向检测**）。
4. **落盘后验证**：Glob/Read 确认目录结构完整、每个文件非空、来源清单完整（URL + 可信度 + 引用点）。
5. 对话中仅允许 ≤5 行摘要 + 目录路径。

> **🔴 落盘硬门禁**：产物必须写入 `docs/research/<主题-slug>/`（或 fallback `./research/<主题-slug>/`），禁止仅对话输出；**禁止写入该目录以外的任何位置**（含 `docs/design/`、`docs/information/`、项目根）。

### 更新式调研（同主题二次调研）

**必须更新已有目录，不得另起新目录**——`<主题>-v2`、`<主题>-2`、`<主题>-<日期>` 一律禁止。

| 情形 | 动作 |
|------|------|
| 出现新问题 | 新增 `NN-<要点>.md`（编号接续最大值），索引表补一行 |
| 已有结论被推翻 | 原地更新正文，文件顶部加一行：`> ⚠️ YYYY-MM-DD 更新：原结论"…"，现更正为"…"（来源）` |
| 结论被补充 | 原地扩写，页首「最后更新」同步 |
| 要点被废弃 | 文件保留，头部标 `> ⚠️ 已废弃（YYYY-MM-DD）：由 NN-xxx.md 取代`，索引表状态列同步 |
| 大范围重写 | 升格为子目录，原文件内容并入 `<子主题>/00-总览.md` |

无论哪种情形都要回写总览页「变更记录」——**只改分文件不改总览 = 更新未完成**。

## 与项目管理体系的衔接

- `docs/research/` 是新文档体系的一部分，回答「外部世界怎么说」；`docs/design/` 回答「做什么」，不得混写。
- **项目尚无 `docs/` 体系时**：AskUserQuestion 二选一——① 先走 `myworkflow:project-init` 建立文档体系，再落盘 `docs/research/`；② 就地建 `./research/<主题-slug>/`（fallback，且**不创建 `docs/`**）。不得代用户决定。
- **不建 index.json**——`docs/research/` 靠总览页 + 目录结构导航；索引只服务于 `design/` 与 `information/`。
- **经验沉淀归 `docs/information/`**：调研中得出的可复用经验，本技能**不直接写入**，只提示用户走 `myworkflow:project-maintain` 登记。
- 不主动改动项目既有文档（CLAUDE.md、GOAL、STATE、PROGRESS 等），本轮只产出 research 目录。

## 完成标志

- [ ] 逻辑骨架表已生成（每个要点对应明确的产出文件），且目录骨架已建
- [ ] ≥3 搜索维度并行执行，总来源 ≥8 个独立来源，每条发现已指定归属文件
- [ ] 核心声明已交叉验证（≥2 来源或已标注单一/矛盾/缺口）；矛盾已补充搜索且未选边站
- [ ] 产物位于 `docs/research/<主题-slug>/`（或 fallback `./research/<主题-slug>/`），未写入任何其他位置
- [ ] 含 `00-总览.md` 索引页；总览索引与磁盘文件双向一致（无悬空、无孤儿）
- [ ] 无单文件超阈值未拆分；体量大的要点已升格为子目录
- [ ] 更新式调研：更新已有目录而非新建，总览「变更记录」已回写
- [ ] 🔴 已落盘并 Read/Glob 验证文件存在且非空
- [ ] 对话仅 ≤5 行摘要 + 目录路径（未贴全文）

## 反绕过红线

- 跳过逻辑骨架直接开搜、最后把结果压成一段总览 → 本次调研作废重做。
- 只搜一个维度/一个关键词就"查完" → 覆盖面不足。
- 全部内容塞进 `00-总览.md`、分文件只是空壳 → 等价于退回单报告模式。
- 所有来源说法一致 → 可能同源互引，检查是否独立来源。
- 用自身知识代替搜索 / 把矛盾简化成"大家普遍认为" → 违规。
- 🔴 只在对话贴全文不写文件 → 硬门禁违规，先写文件再给摘要。
- 写入 `docs/research/` 之外的路径 → 越界违规。
- 同主题二次调研另起新目录 → 知识库碎片化，违规。
- 写完后未 Read/Glob 确认文件存在 → 可能写入失败。
