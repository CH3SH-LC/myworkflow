## 核心流程：骨架先行 → 多源验证 → 逐份落盘 → 总览回写

**何时加载**：要求深度调研、全面研究、多来源事实验证、方案对比或技术选型，且结论值得沉淀为可续写可更新的本地知识库目录。
**不加载**：简单事实查询、已明确的技术问题、用户已有答案只需确认；纯代码问题走开发流程。

**硬步骤**
1. **划骨架**：解析范围/深度/时效，把主题拆成「能被单独回答的问题」，每个问题=一份 `NN-<要点>.md`，体量大直接定为子目录 → 判据：骨架表含「问题 / 产出文件 / 检索维度」。
2. **建目录**：先把骨架落成真实文件——`00-总览.md` + 各要点文件（头部三行：调查的问题 / 一句话结论含可信度 / 更新日期）→ 判据：检索前目录已存在。
3. **多源检索**：`web_search` 换多组关键词、`web_fetch` 读原文，选互补维度（官方文档 / 社区 / 对比评测 / 负面批评）并行；每条发现记「来源 | URL | 关键发现 | 归属文件 | 可信度」并按归属文件分桶 → 判据：每条发现都有落点，禁止用自身知识替代检索。
4. **交叉验证**：核心声明逐条核对两个以上互相独立的来源；单一来源标注、矛盾聚焦补充检索找第 3–4 方裁决、无来源登记为信息缺口 → 判据：矛盾不选边站、缺口已登记。
5. **逐份落盘 + 回写**：用 `write` / `edit` 写入归属文件（事实性声明带来源），回写总览索引、结论摘要、变更记录；同主题二次调研就地更新同一目录，不另起新目录 → 判据：总览 ⇄ 磁盘双向一致（无悬空、无孤儿）。

**一个资料包一个 owner**：从检索到验收端到端负责，拒绝「检索 → 代写 → 审查」阶段接力；任一份结算即补位，未 ready 不派发。

**完成判据**：知识库目录已真实落盘，用 `glob` / `read` 核对总览存在、每份文件非空、来源与可信度齐全、双向一致；返回调用方的是简短结论 + 文件路径与来源指针等可核查证据。只贴对话不落盘、把内容堆进总览、另起 v2 目录都不算完成。

# 深度调研

**一次调研 = 一个可增长的知识库目录，不是一份报告。** 产物落在 `docs/research/<主题-slug>/`，按调研的逻辑要点切成多个 md 文件，可嵌套子目录、可续写、可修订。

## 触发

- **必须触发**：调研/研究/全面了解、技术选型与方案对比（"A vs B"）、需多来源验证的事实问题、查"XX 最新状况"。
- **不触发**：简单事实查询（直接检索回答）、纯代码问题（走代码通道）、用户已有明确答案只需确认。

## 铁律

1. **禁止用自身知识替代检索**：训练数据可能过时或有偏见，即使已经知道答案也要实际检索。用 `web_search` 换多组关键词检索，用 `web_fetch` 读原文，不凭印象下结论。
2. **结论必须落盘**：完整正文写进本地 .md 文件；对话里只给简短结论 + 关键证据指针 + 目录路径。只贴对话不落盘视为未完成。
3. **声明不确定**：查不到的信息标注「信息缺口」，不编造，不用"一般认为"掩盖分歧。
4. **默认落点**：`docs/research/<主题-slug>/`；项目没有 `docs/` 体系时可用 `./research/<主题-slug>/`；用户明确指定位置时以用户为准。本轮不主动改动项目既有文档。
5. **证据诚实**：区分「已核实（有来源）」与「推测/未核实」，不夸大，无证据不声称"验证通过"。

## 横向交付合约（核心组织方式）

以**资料包**为交付单元，不以流程阶段为单元。

- 一个「能被单独回答的问题」= 一个资料包 = 一份可独立交付的产物（一个 `NN-<要点>.md`，体量大时升格为子目录）。
- **每个资料包由一个 owner 端到端负责**：自己定检索维度 → 自己检索并读全文 → 自己写进归属文件 → 自己核对来源与可信度 → 自己修复 → 自己给出验收结论。
- **拒绝同一交付物的阶段接力**：不要「一批人只做检索 → 汇总者再写 → 另一个人再审查」这种把同一个资料包切给三个角色的排法；同一份产物换手即失去上下文。
- **横向重排建议**：把「先派 N 个研究员再统一汇总」改成「按独立问题域 / 资料包切分，每个包一个 owner 从检索到落盘一次做完」；只有在两个资料包之间确实存在依赖时才串接。
- **跨包引用可以，但必须标注来源与版本**：引用另一个资料包的结论时写清 `来源：NN-xxx.md@<版本/日期>`，不制造循环依赖。
- leader 负责全局集成（总览页、编号与命名、跨包一致性），但**与相关 owner 共同完成**，不撤走原来的人、换一个没有上下文的审查者来接管后半程。

## 事件驱动滚动补位

- 任何资料包一旦结算（完成 / 阻塞 / 待确认），**立即**补位下一个 ready 的资料包；不设全批屏障、不等"整层"全部完成，也不做全批统一等待。
- 慢资料包不阻塞其它 ready 项，同一时刻多个资料包可并行推进。
- **未 ready 不启动**：依赖未满足的资料包保持 ready 等工作项结算，不提前启动、不空等。
- **满额时明确拒绝并保持 ready（CAPACITY_FULL）**：并发已满就把新资料包标为 `CAPACITY_FULL` 并保持 ready，等有 owner 结算后再补位；不排队空等，也不用一次性旁路绕过上限。

## 主线

**明确范围 → 划分逻辑骨架 → 建目录骨架 → 多源检索 → 交叉验证 → 逐文件落盘 → 回写总览**；发现矛盾或可信度不足 → 聚焦补充检索 → 回写对应文件。

## 产出结构规范

```
<项目根>/docs/research/<主题-slug>/
├── 00-总览.md              # 索引页：调研了什么 / 有哪几部分 / 结论摘要 / 变更记录
├── 01-<逻辑要点>.md        # 一个逻辑要点 = 一个文件
├── 02-<逻辑要点>.md
├── 03-<逻辑要点>.md
└── <子主题-slug>/          # 某个要点体量大 → 升格为子目录
    ├── 00-总览.md          # 子目录自己的索引
    ├── 01-<层面>.md
    └── 02-<层面>.md
```

命名规则：

- `<主题-slug>` / `<子主题-slug>`：英文 kebab-case（如 `vector-database-selection`），**稳定**，不随调研轮次变化。
- 文件编号两位递增，编号即阅读顺序；索引页固定 `00-`。
- 每个 `NN-<要点>.md` 头部固定三行：**调查的问题 / 结论一句话（含可信度）/ 最后更新日期**。

三个必备要素（缺一即不合格）：**有总览索引页、按逻辑要点分文件、支持子文件夹嵌套**。

### `00-总览.md` 结构

```markdown
# 调研：<主题>
> 首次调研 YYYY-MM-DD ｜ 最后更新 YYYY-MM-DD ｜ 轮次 N ｜ 来源总数 N

## 调研范围与假设
## 目录索引
| 文件 | 回答的问题 | 状态 | 最后更新 |
## 结论摘要
[每部分 1-2 句 + 可信度 + 指向文件]
## 变更记录
| 日期 | 变更 | 影响文件 |
## 信息缺口
```

### 单文件体量参考

| 判据 | 建议动作 |
|------|---------|
| 单文件 ≤ 300 行且 ≤ 12000 字符 | 按现状交付 |
| 超过上述体量 | 该要点升格为子目录，按其内部二级逻辑切开 |
| 单文件 > 500 行 | 先拆分再交付：过长的单文件难以核查、难以续写 |
| `00-总览.md` > 150 行 | 索引页只留索引与摘要，细节下沉到分文件 |

拆分的实质判据不是行数好看：**同一文件里出现两个能各自独立回答的问题，就应当是两份文件。**

## 逻辑骨架先行

**这是解决"大量检索最后只挤出一小份报告"的关键，不要跳过直接开搜。**

1. **解析意图**：主题 / 深度（概览级→快速，学术级→完整流程）/ 时效性 / 约束（语言、地域、排除项）。
2. **只在真正改变结论的模糊点上提问**：用 `ask_user_question` 一次问清最少的必要问题（范围、深度、落点），不逐项打断。项目里查得到、或用合理假设就能推进的，不问，改在总览页「调研范围与假设」里写明假设。
3. **划分逻辑要点**——先不检索，先产出「逻辑骨架表」：

   | # | 要回答的问题 | 产出文件 | 内容层面（写什么/不写什么） | 检索维度 |
   |---|-------------|---------|--------------------------|---------|
   | 01 | 问题 A | `01-xxx.md` | 层面 1 / 层面 2 | 官方文档、社区、对比评测 |

   划分判据：
   - 一个要点 = **一个可以被单独回答的问题**，不是"一个章节标题"。
   - 要点数量以覆盖问题空间为准：能各自独立成文的就独立，互相重叠的合并；预计会写很多的**直接定为子目录**，别等写完再拆。
   - 骨架里就标出**哪个要点预计体量大**。
4. **建目录骨架**：把骨架表落成真实文件——`00-总览.md`（含范围与索引表）+ 每个要点一个带标题的文件。**先有文件，才有归属**，后续每条发现都有明确落点，从机制上消除"结尾压缩"。
5. **把骨架变成模块委托与成员计划**：leader 用 `team_mission_assign` 给每个资料包对应的模块下委托；**member 自己用 `team_plan_submit` 提交**（写清 `deliverable`、`outputs`、`writeScopes`、依赖 version+requires 与验收标准），再用 `team_dispatch_authorize` 授权；leader 用 `team_snapshot` 复核 ready 与容量。补位由常驻调度器执行。
6. **出口**：核心问题一句话说清、骨架表已生成、目录骨架已建、资料包已上板。

## 检索维度与来源可信度

1. **设计检索维度**（从以下选互补的几类；多路并行 → 把每份资料包提交为工作项，由模块成员端到端检索与落盘）：
   官方文档 `<topic> official documentation`；社区讨论 `<topic> reddit/hackernews`；对比评测 `<A> vs <B> comparison`；学术/技术博客 `<topic> deep dive`；中文社区 `<主题> 实践 经验`；GitHub/开源 `<topic> github stars`；定价/成本 `<service> pricing`；负面/批评 `<topic> problems/issues`。
2. **每个检索子任务**：`web_search` 换多组关键词各检索一次 → 选最相关的若干来源 → `web_fetch` 读全文 → 提取与骨架表相关的关键信息 → 输出 `来源 | URL | 关键发现 | 归属文件 | 可信度` 表 + 详细摘录。
   **摘录必须按「归属文件」分桶输出**，不要交回一段笼统总结——否则又回到压缩成小报告的老路。
3. **可信度**：🟢 官方/权威/同行评议/数据可复现；🟡 知名博客/社区高赞/公司技术博客；🔴 个人博客/匿名/未注日期/明显偏见。
4. 同一结论尽量来自**两个及以上互相独立的来源**；所有来源口径完全一致时，先怀疑同源互引。
5. **出口**：互补维度并行执行、每个来源已标可信度、每条发现已指定归属文件。

## 交叉验证

1. **提取核心声明**为清单（声明 → 来源 A/B/C → 验证状态 → 归属文件）。
2. **分类处理**：
   - ✅ 多独立来源确认 → 写入归属文件，标注来源。
   - ⚠️ 单一来源 → 写入但标"单一来源，未交叉验证"。
   - ❌ 来源矛盾 → **聚焦矛盾点补充检索**，找第 3-4 个来源裁决。
   - 🔴 无来源 → 标"信息缺口"，在总览页「信息缺口」区登记。
3. **处理矛盾不选边站**：补充检索聚焦矛盾点；文中并列呈现各方观点及依据；给出基于方法论的判断但标"仅供参考"。
4. **出口**：核心声明全部列入、每条已标状态、矛盾已补充检索、缺口已登记。

## 逐文件落盘 + 总览回写

1. **逐要点写入**：用 `write` / `edit` 把分桶后的内容写进对应文件。正文每个事实性声明必须带来源标注（`[来源 #N]` 或内联链接 + 可信度）。**不要把内容集中堆在总览页。**
2. **回写总览**：更新索引表「状态/最后更新」、结论摘要（每条 1-2 句 + 指向文件）、变更记录、信息缺口。
3. **双向一致性检查**：每个要点文件必须能被总览索引到；总览索引的每个文件必须真实存在（**悬空 + 孤儿双向检测**）。
4. **落盘后自查**：用 `glob` / `read` 确认目录结构完整、每个文件非空、来源清单完整（URL + 可信度 + 引用点）。

### 更新式调研（同主题二次调研）

**必须更新已有目录，不得另起新目录**——`<主题>-v2`、`<主题>-2`、`<主题>-<日期>` 一律禁止。

| 情形 | 动作 |
|------|------|
| 出现新问题 | 新增 `NN-<要点>.md`（编号接续最大值），索引表补一行 |
| 已有结论被推翻 | 原地更新正文，文件顶部加一行：`> ⚠️ YYYY-MM-DD 更新：原结论"…"，现更正为"…"（来源）` |
| 结论被补充 | 原地扩写，页首「最后更新」同步 |
| 要点被废弃 | 文件保留，头部标 `> ⚠️ 已废弃（YYYY-MM-DD）：由 NN-xxx.md 取代`，索引表状态列同步 |
| 大范围重写 | 升格为子目录，原文件内容并入 `<子主题>/00-总览.md` |

无论哪种情形都要回写总览页「变更记录」——**只改分文件不改总览 = 更新未完成**。

## 与文档体系的衔接

- `docs/research/` 回答「外部世界怎么说」；`docs/design/` 回答「做什么」，不得混写。
- **项目尚无 `docs/` 体系时**：可选 ① 先走 `skill(name="myworkflow-project-init")` 建立文档体系，再落盘 `docs/research/`；② 就地建 `./research/<主题-slug>/`（不创建 `docs/`）。用户能决定就让用户选；不能等时按 ② 推进并在总览页写明这一假设，不停摆。
- **不建 index.json**——`docs/research/` 靠总览页 + 目录结构导航。
- **经验沉淀归 `docs/information/`**：调研中得出的可复用经验，本技能**不直接写入**，只提示用户走 `skill(name="myworkflow-project-maintain")` 登记。
- 不主动改动项目既有文档，本轮只产出 research 目录。

## 阻塞与超时

阻塞处理顺序：

1. 记录确切失败信息、已尝试路径、影响范围、仍可做的事。
2. 查本机已装服务、源码、现成工具与当前权限。
3. 能写适配器 / 接口 / 本地桥接补齐的，就地补齐。
4. 局部阻塞先把其它 ready 资料包做完，并把 blocker 精确挂到受影响的资料包上。
5. 确实需要外部账号、人工决策或无法获得的资源，才标记 `needs_user`，并给出已尝试路径与最小下一步。

超时处理：先判断**进展与可恢复性**（是否已产出部分内容、能否从断点续跑、是否只是变慢），把「状态未知 / 已暂停」与「真正失败」严格分开——**超时不等于失败**，先恢复或续跑，确认是真失败后再重排或换 owner。

不设"试三次就结束"这类固定次数，也不无预算地对同一失败反复重试；权限拒绝不可绕过，记录后交给用户。

## 用户授权边界

- 用户已授权任务内的可逆开发（检索、建目录骨架、写归属文件）直接做，不重复询问。
- 审批与扩权只有用户入口；模型侧没有等价工具，也不代用户决定越权事项。
- 只在**真正改变决策且项目里查不到**时才用 `ask_user_question` 提问，一次把问题问清。

## 证据诚实与结果分层

- 区分「已核实 / 有来源」与「推测 / 未核实」；不夸大，无证据不声称"验证通过"。
- 返回给调用方（parent）的只有：**简短结论 + 可核查的 evidence / artifact 引用**（文件路径 + 关键行或来源编号 + 版本/日期）。
- 原始材料、检索摘录、长表格留在归属文件或子会话里，不进摘要。
- 摘要必须含：来源、版本、遗漏、不确定性、未完成项；未核实的内容明确标注。

## 完成标志

- [ ] 逻辑骨架表已生成（每个要点对应明确的产出文件），且目录骨架已建
- [ ] 互补检索路径并行执行，每个来源已标可信度，每条发现已指定归属文件
- [ ] 核心声明已交叉验证（多独立来源，或已标注单一/矛盾/缺口）；矛盾已聚焦补充检索且未选边站
- [ ] 产物位于 `docs/research/<主题-slug>/`（或约定 fallback），未写入无关位置
- [ ] 含 `00-总览.md` 索引页；总览索引与磁盘文件双向一致（无悬空、无孤儿）

## 反绕过红线

- 跳过逻辑骨架直接开搜、最后把结果压成一段总览 → 本次调研作废重做。
- 只搜一个维度、一个关键词就"查完" → 覆盖面不足。
- 全部内容塞进 `00-总览.md`、分文件只是空壳 → 等价于退回单报告模式。
- 所有来源说法一致 → 可能同源互引，检查是否独立来源。
- 用自身知识代替检索 / 把矛盾简化成"大家普遍认为" → 违规。
- 只在对话贴全文不写文件 → 先写文件再给摘要。
- 写入 `docs/research/` 之外的无关路径 → 越界违规。
- 同主题二次调研另起新目录 → 知识库碎片化，违规。
- 写完后未用 `glob` / `read` 确认文件存在 → 可能写入失败。
