# 任务拆解与派发（L3 拆分契约）

## 工作级别：L3 智能体团队

本技能是三级协作模型中的 **L3 智能体团队**拆分契约。

- **L1 单智能体（solo）**：单一不可再分交付物、单文件小改、一次回答闭环、纯问答；不建团队、不下 mission、不派 leaf。
- **L2 子智能体（subagent）**：≥2 个平铺、无依赖的小交付物；用 `subagent` 一口气派发回收（见「myworkflow:lightweight-dispatch」）。
- **L3 智能体团队（team）**：多域协作、交付物之间存在接口/依赖、需要持续负责人、需要并发推进与失败补位。**本技能只服务 L3**：先把项目横切成可独立交付的产物边界，再由 leader 下 mission、member 域自治，禁止按阶段接力。

## 团队角色与职责（leader / member / leaf）

- **leader**：只做四件事——**定目标与边界、建团队、下模块委托（mission）、监督与验收裁量**。不亲自产出交付物、不写业务文件、不逐批派活、不替成员拆叶子任务。leader 把**产物边界**下成 mission，成员内部顺序由 member 自己决定。
- **member**：持久存在的**域 owner**，必须具备独立目标意识。收到「目标 + 边界 + 输入 + 验收」后：自己规划（plan）→ 自己授权派发 → 自己验收结算 → 自己修复，**端到端完成一整件事**（调查→实现→自检→修复→验收）。只对自己域负责，跨域接口先约定。
- **leaf**：fresh 上下文的最小任务包执行者，一次实现并自检，交回真实产物与证据。**leader 与 member 都可以启动 leaf；leaf 不能再开 leaf，也不能创建同级成员**。
- **谁能开 leaf**：leader 可以（按已定产物边界直接派最小任务包）、member 可以（在自己域内自行 plan 后派）；leaf 不可以。任何一方都不得把「一个交付物的阶段」拆成多次 leaf 接力。

## 横向切分原则：一个交付物一个 owner

L3 只做**横向切分**，切分维度是**可独立交付的产物**（模块 A / 模块 B / 对象 1..N / 证据包 1..N），不是工序阶段。

- **一个交付物一个 owner**：每份产物有且只有一个 owner（member 或 leaf），由该 owner 端到端负责实现、自检与交付。
- **接口先于派发**：跨产物的接口（文件路径、导出签名、数据结构、验收命令）在派发前写进契约；同层产物并行，跨层产物等待前置产物就绪。
- **leader 不代拆**：leader 只下 mission（目标/边界/输入/验收），不替 member 拆 leaf；member 若判断需要再切，只能继续横向切产物。
- **数量边界**：派发给独立执行者的产物 2–12 份；超过 12 份说明切分粒度过细，应合并；少于 2 份说明不需要 L3。

## 禁止阶段接力（硬规则）

**定义**：一个交付物内部，禁止按时间/工序阶段（前→中→后）拆成多个独立窗口或智能体接力。

| 违规（禁止） | 合法（允许） |
|---|---|
| 「调研 → 设计 → 实现 → 审查」四个阶段各派一个执行者接力 | 大项目按**可独立交付的产物**横切成模块 A / 模块 B / 模块 C，各自端到端 |
| 同一功能的「先写接口 → 再写实现 → 再补测试」分三个窗口 | 一个 owner 一次做完自己的整个交付物（含它的测试与自检） |
| leader 把 member 的活再按阶段拆成多次 mission | leader 下的是**产物边界**，member 自己决定内部顺序 |
| 先派「调研 leaf」，等它交回再派「实现 leaf」 | 两个产物无依赖就并行；有依赖说明它们是一份交付物的阶段，应合并给同一 owner |

**判定话术**：如果拆出来的每一份「单独交给别人也不成为一个可用成果」，就是阶段接力，**违规**；如果每份都能独立交付、独立验收，才是横向切分，**合法**。

**两个常见绕过不算合法**：① **审查 / 汇总 / 接口文档 / 测试报告不是独立交付物**——它们是同一交付物的工序产物，不得作为横向切分的产物；② **同一交付物跨轮次串行接力**（第一轮 A 做一半、第二轮 B 接着做）同样违规，必须**一个 owner 一次做完**。

**违反时的行为**：**拒绝派发**并要求重排为横向切分；已发现阶段接力时立即停止该批派发、退回重切，不允许用「先跑起来再说」绕过。

## 触发

本技能在判定为 **L3** 后使用；L1 直接做，L2 走「myworkflow:lightweight-dispatch」。

- **显式触发**（用户主动要求）：用户说"拆成子任务/并行处理/分给多个智能体/并行化/同时做/分别做/任务拆解/先拆再派发/并行派发/一起做/都做/把这个任务拆开并行执行"；一次请求中描述了多项互不依赖的工作（如"帮我创建 A、B、C 三个文件"）。
- **隐式触发**（agent 主动判断，满足任意 1 条即触发评估）：
  1. 任务涉及**多个产出物**（文件、章节、设计稿、报告、数据表……不限于代码）
  2. 任务描述中存在**可自然分离的子目标**（逻辑上可拆分即满足，不要求产出物数量已确定）
  3. 预估任务需要 **≥3 个独立步骤**（独立步骤 = 产生独立中间产出物且可被后续步骤直接引用的步骤；仅产生内存中间值的步骤不计）
  4. 用户请求中描述了多项工作（即使只用"和/还有"连接，未用显式并行关键词）
- **不触发**：单一原子操作（改一行字/查一个数/问一个事实）→ 直接做；步骤间存在**运行时数据依赖**（后一步需要前一步的运行时输出作为输入，而非仅依赖其产出文件/类型定义）→ 不拆，串行执行；简单问答/搜索/解释；用户只要求 1 个产出物且该产出物不可再分。
- **核心心态**：本 skill 是**前置评估器**——agent 接到任何非平凡任务时先调本 skill 评估复杂度，再决定拆解并行还是直接执行。分析结果可以是"不需要拆解，直接做"——这也是合法输出，**但仅限 L1 场景（单文件或纯问答）**；单个交付物但改动 ≥2 文件属 L2，不在此出口。宁可多触发一次评估，也不错失一个可并行的任务。
- 已在进行的拆解任务，用户说"调整粒度/合并某两个任务" → 回到第二步，不走完整流程。

## 前置强制步骤

> **核心原则：合约先于执行。** 接口合约是子任务之间的"法律文件"——先定义，后派发。

1. **读取项目上下文**：了解已有代码结构、技术栈、文件布局。如果项目有 CLAUDE.md，读取了解项目约定。
2. **确认需求清晰度**：如果用户需求中存在模糊点，先用 AskUserQuestion 追问（最多 3 轮）。

## 执行流程

### 第一步：需求分析

读取用户需求，识别隐含的子目标和约束；检查项目上下文（已有代码结构、技术栈、文件布局）；需求不清晰 → AskUserQuestion 追问（最多 3 轮，每次一个问题）；将需求压缩为一句话核心目标 + 关键约束列表。

### 第二步：按可独立交付的产物横向切分（模块 / 对象 / 证据包）

将需求按**可独立交付的产物**横向切分（模块、对象、证据包），禁止按工序阶段切。对每个候选单元用三个标准判断：

- **职责单一性**：这个单元只做一件事吗？
- **依赖隔离性**：这个单元是否可以不等待其他单元的结果就开工？
- **接口可定义性**：这个单元的输出能否精确描述（文件路径、导出签名）？

用拓扑排序分层：第 0 层（depends_on 为空）→ 全部可并行；第 1 层（仅依赖第 0 层产物）；第 N 层 → 后续层。

**约束**：
- 最少 2 个、最多 12 个子任务。**超过 12 个 → 强制阻断**，拒绝生成合约，提示用户合并任务。
- **少于 2 个 → 强制阻断**，但阻断前先确认：第一步分析是否真的判定了需要拆解？（如果判定"不需要拆解"，应已在第一步出口结束本 skill。如果到达此步但只有 0-1 个子任务，说明第一步拆解判定有误——回第一步重新评估，输出"评估结论：此任务无需拆解，建议直接执行（仅限 L1：单文件或纯问答；多文件单个交付物按 L2 处理）"。）
- 每个子任务必须有至少一个确定的输出文件。**例外**：纯副作用任务（如数据库迁移、通知发送、配置变更）允许 `outputs: []`，但 description 必须标注 `[副作用任务]` 前缀，且 verification 至少包含一个可验证的检查项（如 `test_passes` 或手动验证步骤）。
- 依赖关系不能形成环。

**合约生成自动验证**（写入 task-contract.yaml 之前必须执行）：
1. **任务数量检查**：tasks 列表 <2 → 阻断，提示任务不需要拆解；>12 → 阻断，提示合并。
2. **依赖有效性检查**：每个 `depends_on` 中的 task-id 必须在 tasks 列表中存在 → 不存在的引用阻断。
3. **依赖环检查**：对 depends_on 图执行拓扑排序，无法生成合法拓扑序 → 阻断，报告环路径。
4. **输出路径唯一性检查**：收集所有 `outputs[].file`，有重复路径 → 阻断，报告冲突。
5. **自引用检查**：每个 task 的 depends_on 不能包含自己的 task-id（task-3 不能依赖 task-3）。

### 第三步：定义接口合约

自动验证通过后，写入 `.task-manifest/task-contract.yaml`。合约格式用 YAML。字段结构：

```yaml
project: {项目名}
generated: "{ISO 时间戳}"
tasks:
  - id: {task-id}
    description: {任务描述}
    depends_on: []            # 依赖的 task-id 列表，第 0 层为空
    inputs:                   # 输入文件
      - file: {路径}
        section: {章节}        # 可选
        description: {用途}
    outputs:                  # 输出文件（副作用任务可留空 outputs: []）
      - file: {路径}
        type: {typescript-module | ...}
        exports:
          - name: {导出名}
            signature: "{签名——其他子任务引用该接口的唯一依据}"
    verification:
      - file_exists: "{路径}"
      - export_matches: "{导出名}"
      - test_passes: "{命令}"   # 副作用任务用
```

**完整示例**（2 任务，含依赖关系）：

```yaml
project: user-auth-system
generated: "2026-07-10T14:30:00Z"
tasks:
  - id: build-shared-types
    description: 定义认证系统所需的全部共享 TypeScript 类型
    depends_on: []
    inputs:
      - file: docs/api-spec.md
        section: "Data Models"
        description: 认证相关的数据模型定义
    outputs:
      - file: src/auth/types.ts
        type: typescript-module
        exports:
          - name: Session
            signature: "interface Session { id: string; userId: string; expiresAt: Date; token: string }"
          - name: AuthResult
            signature: "type AuthResult = { success: true; session: Session } | { success: false; error: string }"
    verification:
      - file_exists: "src/auth/types.ts"
      - export_matches: "Session"
      - export_matches: "AuthResult"

  - id: run-db-migration
    description: "[副作用任务] 执行数据库迁移脚本，将 user 表升级到 v2 schema"
    depends_on: [build-shared-types]
    inputs:
      - file: src/auth/types.ts
        description: 需要知道最新的类型定义以验证迁移兼容性
    outputs: []  # 纯副作用任务，无产出文件
    verification:
      - test_passes: "npx prisma migrate deploy --name user-v2"
```

**合约规则**：每个 output.file 必须是确定的路径（不允许通配符）；每个 output.export 的 signature 是其他子任务引用该接口的唯一依据；depends_on 中引用的 task-id 必须在 tasks 列表中已存在，不可自引用，不可形成环。

### 第四步：生成任务拓扑（给人看）

写入 `.task-manifest/任务拓扑.md`：依赖拓扑图（文本）、并行批次表、接口耦合点标注、风险标注。

```markdown
# 任务拓扑 — {项目名}
## 并行批次表
| 批次 | 层级 | 任务 | 说明 |
| 第0批 | 0 | {task-id} | 无依赖，可立即启动 |
| 第1批 | 1 | {task-id} | 依赖第0批产出 |
| 第2批 | 2 | {task-id} | 依赖第1批产出 |
## 接口耦合点
| 输出任务 | 输出文件 | 被依赖的任务 |
## 风险标注
| 风险 | 级别 | 说明 |
| 共享类型变更 | 中 | types.ts 被多个下游依赖，变更需通知所有依赖方 |
| 接口耦合 | 低 | 签名已在合约中确认 |
| 单点阻塞 | 中 | 链式依赖，任一任务延期直接影响下游 |
```

**批次执行说明**：第 0 批可同时启动所有第 0 层任务；第 1 批等待第 0 批产出就绪后启动；第 N 批等待第 N-1 批产出就绪后启动。

### 第五步：生成 mission 与 leaf 任务包

**leader 只下 mission**（目标 / 边界 / 输入 / 验收），不替 member 拆 leaf；**member 收到 mission 后自己 plan、自己决定是否开 leaf**，leaf 任务包必须写全七项（目标、边界、输入证据路径、接口版本、输出位置、验收条件、失败政策）。为每个子任务生成 `.task-manifest/prompts/task-{id}.md`，模板包含：任务描述、依赖关系、输入文件表、输出接口表、验证标准、工作协议（引用「myworkflow:subagent-protocol」的 5 阶段）、约束。

```markdown
# 子任务：{task-id}
## 任务描述
{一句话——本任务的产出及其在系统中的位置}
## 依赖关系
- 依赖的任务：{...}
- 本任务产出被以下任务依赖：{...}
## 输入文件
| 文件 | 章节/位置 | 描述 |
## 输出接口
| 导出名 | 签名 |
## 验证标准
- [ ] 文件 {路径} 已存在
- [ ] 导出了 {name}
- [ ] 所有类型签名与合约完全一致
## 工作协议
请遵循「myworkflow:subagent-protocol」的 5 阶段工作规范：
1. 读取合约 + 确认输入：读取 task-contract.yaml 中你的条目和所有输入文件
2. 声明接口：先写 interface-declaration.md 承诺你的接口——声明先于实现
3. 产出实现：按声明逐项编码，每完成一个文件在声明中勾选
4. 自检：写 self-check.md，逐项核对，全部打勾才能进入下一步
5. 完成报告：写 completion.md，列出产出文件和自检结果
## 约束
- 只修改/创建本任务指定的输出文件，不修改其他模块
- 导出的签名必须与合约完全一致（下游任务依赖精确签名）
- 文件路径必须精确匹配：{路径}
```

### 第六步：用户审批

展示审批摘要：

> "共拆分为 {N} 个可独立交付的产物，分 {M} 个并行批次。第 0 批（{X} 个，可同时启动）：{task-id 列表}。审批通过后由 leader 按产物边界下 {N} 个 mission，各 owner 在自己域内端到端完成并自行决定是否开 leaf。是否批准？"

- **用户批准** → 进入第七步，按拓扑顺序派发。
- **用户拒绝或要求调整** → 回到对应步骤：粒度太细/太粗 → 回第二步（合并或拆分）；接口定义不对 → 回第三步（修改合约对应条目）；依赖关系有误 → 回第二步（调整 depends_on）后重新生成合约和拓扑；用户有新的约束 → 回第一步（重新分析需求）。调整后重新走第四、五、六步，直到用户批准才进入第七步。

### 第七步：下 mission / 启动 leaf

用户批准后按拓扑顺序推进：**leader 按产物边界下 mission**（目标+边界+输入+验收），**member 收到 mission 后自己 plan、授权并启动 leaf**；leader 也可以对已定的最小任务包直接启动 leaf。**leader 不得替 member 把 mission 拆成阶段任务**。向 leaf 派发时，prompt **必须**包含以下精确引用（直接复制，替换 {task-id}。**不可省略或改写此引用模板**——它确保 leaf 正确触发「myworkflow:subagent-protocol」）：

```
你必须遵循「myworkflow:subagent-protocol」。你的 task-id 是 {task-id}。
先读取 `.task-manifest/prompts/task-{task-id}.md` 了解任务，
再读取 `.task-manifest/task-contract.yaml` 找到你的合约条目，
然后严格按 5 阶段协议工作：阶段 1：读取合约+确认输入。先读取 `.task-manifest/prompts/task-{task-id}.md` 了解任务，再读取 `.task-manifest/task-contract.yaml` 找到你的合约条目，逐一读取 inputs 中的文件路径。阶段 2-5 声明接口→产出实现→自检→完成报告。
```

> **一致性约束**：本模板与 `skills/subagent-protocol/SKILL.md`「主智能体强制引用」小节中的同名模板必须**逐字一致**，修改其一时必须同步另一处。（用 slug `myworkflow:subagent-protocol` 而非中文显示名——技能寻址走目录名，中文名不参与寻址，写 slug 才能稳定触发。）

**派发失败降级**：单次派发失败 → 重试 1 次（间隔 5 秒）；仍失败 → 该产物由 owner（member）自己串行完成；owner 也无法完成 → 报告 leader 并列出未完成产物。L2 场景（无跨产物依赖）改用「myworkflow:lightweight-dispatch」，不走本 L3 流程。

## 后置更新步骤

1. 确认 `.task-manifest/` 目录已创建、用户已审批、所有任务包（mission / leaf 任务包）已生成，且每个产物有且只有一个 owner。
2. leader 下第 0 批 mission；各 member 在自己域内启动 leaf。
3. 监控所有子智能体的 completion.md：全部就绪后触发「myworkflow:integration-verify」；若派发后超 30 分钟仍有缺失则同样触发（集成验证会处理缺失场景）。
4. 收到子智能体的依赖超时报告后，立即检查依赖任务状态。如依赖方崩溃，不等 30 分钟立即触发集成验证与修正。
