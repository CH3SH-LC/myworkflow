## 核心流程：评估 → 横向切分 → 合约 → 提交与补位

**何时加载**：一次请求含多项产出物或可自然分离的子目标，且步骤间无运行时依赖。**不加载**：单一原子操作、简单问答、只有一个不可再分产出物、后一步依赖前一步输出（串行），或结论就是"不拆"（直接做）。

**硬步骤**
1. **评估**：读项目上下文，把需求压成一句话目标 + 约束，用多产出物/可分离子目标/独立中间产出三类信号判是否可拆 → 结论是"不需要拆"就在这里结束直接做，不套仪式。
2. **横向切分**：按 module / object / evidence-package 切分，每份一个 owner 端到端（调查→实现→自检→修复→验收），拒绝"调查→设计→审查"接力 → 依赖跨交付物且带 version + requires、无环，输出路径唯一，副作用要有可验证检查项。
3. **写合约**：把 owner/inputs/outputs/verification 落成合约，过依赖存在、无环、元数据完整、路径唯一、自检项齐全 → 任一不过就阻断并报出具体项。
4. **提交**：leader 建团队并用 `team_mission_assign` 下模块委托，**member 自己**用 `team_plan_submit` 提交、`team_dispatch_authorize` 授权；未 ready 不启动，满额保持 ready（CAPACITY_FULL）→ 调度器滚动补位，leader 不逐批派活。
5. **结算**：用 `team_snapshot` 看状态、`team_wait` 等事件，任一结算立即补位，超时只说明没有变化、不等于失败 → 修复由原 owner 收尾，全局集成由 leader 与相关 owner 共同完成。

**完成判据**：合约与工作项已提交、依赖与容量状态可查、每份交付物有真实产物与可核查证据（命令 + 退出码 + 产物路径或行号）；"不需要拆"同样是合格产出。只派人、只写清单、无证据声称通过都不算完成。
**不拆的边界**：「不拆」只适用于单一原子操作 / 单文件小改 / 一次回答闭环；若 ≥2 个可独立交付物或改动 ≥2 个文件，按角色段硬门槛必须建团队横向切开。

## 触发

### 显式触发（用户主动要求）

用户说"拆成子任务/并行处理/分给多个智能体/并行化/同时做/分别做/任务拆解/先拆再派发/并行派发/一起做/都做/把这个任务拆开并行执行"；一次请求中描述了多项互不依赖的工作（如"帮我创建 A、B、C 三个文件"）。

### 隐式触发（满足任意 1 条即进入评估）

1. 任务涉及**多个产出物**（文件、章节、设计稿、报告、数据表……不限于代码）
2. 任务描述中存在**可自然分离的子目标**（逻辑上可拆分即满足，不要求产出物数量已确定）
3. 任务含有**彼此独立的中间产出物**（该产出物能被后续步骤直接引用，而不是只存在于内存里的中间值）——不设任何数量门槛，够不够“独立交付”才是判据
4. 用户请求中描述了多项工作（即使只用"和/还有"连接，未用显式并行关键词）

### 不触发

- 单一原子操作（改一行字/查一个数/问一个事实）
- 简单问答、搜索、解释
- 只有一个产出物且该产出物不可再分
- 步骤间存在**运行时数据依赖**（后一步需要前一步的运行时输出作为输入，而非仅依赖其产出文件/类型定义）→ 不拆，串行执行

### 核心心态

本技能是**前置评估器**：接到任何非平凡任务先评估复杂度，再决定拆解并行还是直接执行。分析结果可以是"不需要拆解，直接做"——这也是合法输出。宁可多触发一次评估，也不错失一个可并行的任务。

**简单请求直接做**：能一次做完的事不要走完整仪式，用 todo_write 列几步就够。

已在进行的拆解任务，用户说"调整粒度/合并某两份交付物" → 回到拆解与合约步骤，不重走全流程。

## 第一步：需求分析

- 读项目上下文：已有代码结构、技术栈、文件布局；项目有 CLAUDE.md 就读，了解项目约定。
- 将需求压缩为一句话核心目标 + 关键约束列表。
- 只在**真正改变决策、且项目里查不到**时才用 ask_user_question 追问，一次一个问题；用户授权任务内的可逆开发不重复询问。

**判断出口**：若结论是"不需要拆解"，在这里结束，直接执行。

## 第二步：按可独立交付的产物切分（横向交付合约）

切分单元不是"阶段"，而是**交付物**：

| 交付物类型 | 说明 | 典型产物 |
| --- | --- | --- |
| module 模块 | 可单独编译/加载的功能单元 | 源文件、类型定义、导出签名 |
| object 对象 | 可独立完成与校验的实体 | 文档、章节、数据集、设计稿 |
| evidence-package 证据包 | 可独立核验的证据集合 | 调研结论 + 来源、测试报告、复现脚本 |

对每个候选交付物用三个标准判断：

- **职责单一性**：这份交付物只做一件事吗？
- **依赖隔离性**：它能否不等其他交付物的结果就开工（即依赖已发布）？
- **接口可定义性**：它的输出能否精确描述（文件路径、导出签名、可核查引用）？

**横向交付合约（硬要求）**

- 每份交付物由**一名 owner 端到端负责**：调查 → 实现 → 自检 → 修复 → 验收。
- 拒绝同一交付物的阶段接力：「背景调查 → 设计 → 检查」「计划 → 编码 → 审查」这类纵向串接必须横向重排。

| 原纵向接力 | 横向重排建议 |
| --- | --- |
| 背景调查 → 设计 → 检查（同一交付物） | 合成一份交付物，由一位 owner 包下调查 + 设计 + 检查 |
| 计划 → 编码 → 审查（同一交付物） | 按模块/对象/证据包切成多份交付物，每份各自计划 + 实现 + 自检 + 修复 + 验收 |
| 先建全局骨架，再由他人填肉 | 骨架作为公共接口交付物先行发布，其余交付物并行认领，接口用 version + requires 锁定 |
| 一人写、另一人补审查 | 审查并入 owner 的自检与验收；只有跨交付物的集成由 leader 与相关 owner 共同承担 |

**约束**

- 依赖只允许存在于**不同交付物之间**，且每条依赖必须写清 `version` + `requires`（`published-interface` 或 `verified-result`）。
- 依赖关系不能形成环。
- 每份交付物至少有一个确定的输出（文件路径或可核查引用）；纯副作用交付物允许 `outputs: []`，但 description 必须标注 `[副作用交付物]` 前缀，且 verification 至少包含一个可验证检查项（如 `test_passes` 或手动验证步骤）。
- 输出路径唯一：两份交付物不得写同一路径。

## 第三步：写交付合约

合约用 YAML，写到 `delivery-contract.yaml`（项目根或工作目录）；需要多人协作时，leader 用 `team_mission_assign` 把模块目标委托给模块成员，**由成员自己用 `team_plan_submit` 把合约里的每份交付物提交成自己拥有的 work**，再用 `team_dispatch_authorize` 授权派发；**不是**把它抄成待办清单，也不是 leader 替成员建工作项。

```yaml
project: {项目名}
generated: "{ISO 时间戳}"
deliverables:
  - id: {delivery-id}
    owner: {负责人的端到端责任人}
    kind: {module | object | evidence-package}
    description: {一句话——这份交付物是什么、在整体中的位置}
    depends_on:                # 只允许依赖其他交付物
      - id: {delivery-id}
        version: "{依赖的接口/结果版本}"
        requires: {published-interface | verified-result}
    inputs:
      - ref: {路径或可核查引用}
        description: {用途}
    outputs:                   # 纯副作用交付物可留空 outputs: []
      - file: {确定路径，不允许通配符}
        type: {typescript-module | markdown | dataset | ...}
        exports:
          - name: {导出名}
            signature: "{签名/接口描述——其他交付物引用该接口的唯一依据}"
    verification:
      - file_exists: "{路径}"
      - export_matches: "{导出名}"
      - test_passes: "{命令}"    # 副作用交付物至少要有这一类检查项
```

**完整示例**（两份交付物，含依赖）：

```yaml
project: user-auth-system
generated: "2026-07-10T14:30:00Z"
deliverables:
  - id: shared-auth-types
    owner: types-owner
    kind: module
    description: 定义认证系统所需的全部共享 TypeScript 类型
    depends_on: []
    inputs:
      - ref: docs/api-spec.md

        description: 认证相关的数据模型定义（章节 Data Models）
    outputs:
      - file: src/auth/types.ts
        type: typescript-module
        exports:
          - name: Session
            signature: "interface Session { id: string; userId: string; expiresAt: Date; token: string }"
          - name: AuthResult
            signature: "type AuthResult = { success: true; session: Session } | { success: false; error: string }"
    verification:
      - file_exists: "src/auth/types.ts"
      - export_matches: "Session"
      - export_matches: "AuthResult"

  - id: db-migration-user-v2
    owner: migration-owner
    kind: object
    description: "[副作用交付物] 执行数据库迁移，将 user 表升级到 v2 schema"
    depends_on:
      - id: shared-auth-types
        version: "1.0.0"
        requires: published-interface
    inputs:
      - ref: src/auth/types.ts
        description: 需要用最新类型定义验证迁移兼容性
    outputs: []                # 纯副作用交付物，无产出文件
    verification:
      - test_passes: "npx prisma migrate deploy --name user-v2"
```

**合约写出前的自动验证**（任一项不过就阻断并报告）：

1. **依赖有效性**：每个 `depends_on.id` 必须在 deliverables 列表中存在。
2. **依赖环**：对 `depends_on` 图执行拓扑排序，无法生成合法拓扑序 → 阻断，报告环路径。

3. **依赖元数据完整**：每条依赖都带 `version` 与 `requires`（仅允许 published-interface 或 verified-result），缺一即阻断。
4. **输出路径唯一性**：收集所有 `outputs[].file`，出现重复 → 阻断，报告冲突。
5. **自引用**：任何交付物的 `depends_on` 不得包含自己。
6. **副作用交付物**：`outputs` 为空的条目必须带 `[副作用交付物]` 前缀且 verification 非空。

## 第四步：交付拓扑与风险（给人看）

写一份 `交付拓扑.md`：依赖方向图（文本）、接口耦合点、风险标注。

> 依赖层级只说明先后顺序，**不产生批次屏障**：任何一份交付物的依赖满足就立刻开工，不必等同层其它交付物，也不做整层批次等待。

```markdown
# 交付拓扑 — {项目名}
## 依赖方向（DAG）
{delivery-a} ──1.0.0/published-interface──▶ {delivery-b}
{delivery-c} ──verified-result──▶ {delivery-d}
## 接口耦合点
| 上游交付物 | 输出接口/产物 | 被依赖的交付物 | 版本 |
## 风险标注
| 风险 | 级别 | 说明 |
| --- | --- | --- |
| 共享类型变更 | 中 | types.ts 被多个下游依赖，变更需 version bump 并通知所有依赖方 |
| 接口耦合 | 低 | 签名已在合约中确认 |
| 单点阻塞 | 中 | 链式依赖，任一交付物延期会顺延下游；可先做其它 ready 项 |
```

## 第五步：提交工作项与调度器补位

- **未 ready 不提交执行**。ready = 全部依赖已按合约发布（`published-interface` 表示接口已定且签名/版本可查，`verified-result` 表示结果已核实）且版本满足。未 ready 就留在队列，不做"先启动再等依赖"的投机动作，也不空等。
- **容量上限**：同时在跑的交付物数量有上限。满额时拒绝并让该交付物保持 ready（记录 `CAPACITY_FULL`），不排队空等，也不用一次性旁路绕上限。
- **提交方式（agent team 模型 · autonomy-v1）**：`team_define` 登记团队 → `team_member_create` 建**持续存在的模块成员**（写明责任与 `writeScopes`，默认 `fresh`）→ leader 用 **`team_mission_assign`** 下模块委托；**每份交付物由 member 自己用 `team_plan_submit` 提交**为它拥有的 work，再用 `team_dispatch_authorize` 授权。**leader 不逐批派活**：授权后由常驻调度器按 ready 与容量补位。
- **owner 是 member，执行者是 child**：member 用 `team_dispatch_authorize` 授权、`team_subagent_start` 定向启动自己的 continuable 执行者、`team_work_report` 结算（回执带 `attemptId`+`leaseEpoch`，不匹配只归档），最后用 `team_work_verify` 按验收条件核验。
- **事件驱动滚动补位**：任一工作项结算，调度器立即补位下一项 ready 工作项，不等同批其它任务；无全批屏障、无整层等待；慢任务不阻塞其它 ready 项。
- 成员当前 turn 停止或 pane 被隐藏都不影响成员与其队列；leader 用 `team_snapshot` 看状态、`team_wait` 等变化（不轮询）、`team_interrupt` 按范围停止（`turn` / `members` / `team`）。
- 同一交付物的后续修复继续由**原 owner** 收尾，不换人。

工作项简报表（提交给成员的自包含说明；成员再据此给自己执行者最小任务包）：

```markdown
# 工作项：{delivery-id}
## 交付目标
{一句话——本交付物的产出及其在整体中的位置}
## 依赖
- 依赖的交付物：{id} @ {version}（{published-interface | verified-result}）
## 输入 / 输出
| 引用或产物 | 说明 |
## 验收标准
- [ ] 产物 {路径} 已存在
- [ ] 导出了 {name}，签名与合约完全一致

- [ ] {test_passes 命令} 通过，或手动验证步骤已完成
## 边界
- 只写本工作项 outputs 指定的文件/产物；`writeScopes` 只是提醒，重叠由调度器串行化
- 端到端负责：调查 → 实现 → 自检 → 修复 → 验收，不把同一交付物切成阶段转交他人
```

## 第六步：边做边结算

- 观测用 `team_snapshot`（ready / 在飞 / 容量 / 诊断）与 `team_wait`（先登记等待再核对，不忙轮询）；超时只表示这段时间没有变化，不重复提交同一交付物。
- 结算动作：`produced` → 调度器立即补位；`failed` → 按阻塞处理顺序把 blocker 精确挂到受影响的工作项；需要用户决策 → 汇总并给出最小下一步。
- **同一 owner 收尾修复**：自检不通过、验收失败的修复由原 owner（member）完成；不撤走前面的人、换一个没有上下文的审查员接管后半程。
- **全局集成由 leader 与相关 owner 共同负责**：leader 跑验收命令、核对接口 version 与 requires、清点未完成项；相关 owner 在场解释与修复自己的交付物。
- 迟到回执（`leaseEpoch` 不匹配）只归档为迟到结果，不覆盖新版本；怀疑回执丢失时用 `team_recover` 对账。

## 超时与阻塞处理

**超时先判断进展与可恢复性**；「状态未知/暂停」与「真正失败」严格分开，**超时不等于失败**。

| 现象 | 判断 | 动作 |
| --- | --- | --- |
| 有**验收意义**的产物/状态推进（产物按验收更新、work 状态前进、验收通过、依赖解锁） | 仍在推进 | 继续等待或缩短观测间隔，不打断 |
| 无进展但可恢复 | 状态未知/暂停 | **member** 用 `team_message` 向该 owner 索取状态并给出最小下一步；**leaf** 用 `team_ask_owner` 向自己的 owner 求助 |
| owner 确认不可恢复 | 真正失败 | 由原 owner 收尾修复，或把该交付物重新指派给掌握上下文的成员 |
| 依赖方阻塞 | 局部阻塞 | 把 blocker 精确挂到受影响交付物，先做其它 ready 项 |

**阻塞处理顺序**：

1. 记录确切失败、已尝试路径、影响范围、仍可做的事。
2. 查已装服务、源码、现成工具、当前权限。
3. 能写适配器/接口/本地桥接补齐的，就补齐。
4. 局部阻塞先做其它 ready 项，并把 blocker 精确挂到受影响交付物。
5. 确实需要外部账号、人工决策或无法获得的资源，才标记 needs_user，并给出已尝试路径与最小下一步。

不得固定"试三次就结束"，也不得无预算无限重试同一失败；权限拒绝不可绕过。

## 授权与提问边界

- 用户授权任务内的可逆开发不重复询问。
- 审批与扩权只有用户入口，模型没有等价工具；需要审批时说明原因，由用户决定。
- 只在真正改变决策且项目里查不到时才 ask_user_question，一次一个问题。

## 证据与结果分层

- **证据诚实**：区分「已核实/有来源」与「推测/未核实」；不夸大；没有证据就不声称"验证通过"。
- **结果分层**：简短结论 + 可核查的 evidence/artifact refs 进 parent，原始材料留在文件或子会话。
- 摘要包含：来源、版本、遗漏、不确定性、未完成项。

**具体行动路径**（不盲重试、不绕过权限）：
- **同错第二次**：先记指纹（code/message/失败命令），只改**一个**条件（输入/参数/版本/权限来源/调用方）再试；指纹没变不重跑同一个失败。
- **权限或写入被拒**：由**原 owner 一次性定位**（哪个进程、哪个 scope、哪条路径被拒），不绕过权限、不让模型分段转抄规避；结论写进 blocker。
- **真实接线缺失**：保留已完成成果 + 明确"未接线"证据（缺哪条依赖/接口没暴露/哪个进程没加载），标 `source-complete` 但**未接入**，不得谎报上线。

## 完成标志

- [ ] 需求已分析，是否需拆解已判定（"不需要拆解"是合法结论；简单请求用 todo_write 列几步即可）
- [ ] 交付合约已写出：每份交付物一个 owner，端到端负责
- [ ] 依赖无环，且每条依赖带 version + requires（published-interface 或 verified-result）

## 高并发执行入口

用户的限制优先。若用户禁止拆分完整任务，同一负责人从调查到完整开发一直负责，不把调查、开发、检查交给不同的人。简单任务直接做；允许并行时只按独立可交付模块横向拆分。

1. 先用 team_snapshot 读取已有 team、member、workId、planRevision、writerEpoch 与容量，原 owner 续作已有交付物，不能为“提高并发”新建同义任务。
2. leader 只分配模块委托；member 自己 team_plan_submit、team_dispatch_authorize。Host 只调度已授权且依赖就绪的工作；需要定向启动时用 team_subagent_start，不与自动派发重复投递。
3. 真实 running、reserved、unknown、历史占位、ownerSessions 分列。没有原生 turn 证据就不报真实并发。配置值、队列长度和窗口数量都不是实测吞吐。
4. 调度滚动补位，不等整批；测试门槛独立：完整开发或用户约定的大块产出完成后统一测试。测试未跑的产物不能标 accepted，verified-result 依赖不能提前放行。
5. 超高并发或容量调整前，按索引依次读取“容量与资源预算”“滚动调度与共享写入”“故障恢复与上下文”“逐级压力验收”。provider 配额未知时不提高并发；不要把方案当成已经生效的配置。

本方案属于 myworkflow。工作台只承载现有执行工具与状态，不再复制一份并发指导。

## 容量与资源预算

先区分：总任务量 N、准备好但未启动的队列 Q、活跃执行 L、模型在途请求 P、父成员占槽 M、恢复余量 R、交互余量 I。1000 个排队任务不等于 1000 并发。

准入上限取最小值：C = min(原生激活上限减 M/R/I，Host 激活上限减 M/R/I，全局叶子上限，provider 已核实请求上限，机器/工具资源预算，已稳定压测上限)。现存预留和未知状态也保守占槽；新增启动数再减去这些占用，并受每成员/每团队公平额度限制。无效、过期、缺失的预算记 unknown，不当成无限容量。

2026-10-18 本机快照：Host=40，R=3，I=2，叶子=30，provider=null。5 个父成员时最多是 30 个叶子的配置算术，尚无 30 并发实测证明；100+ 不能靠这套配置承担。

百级目标前先验证原生 maxActiveSubagents 与 Host 同步配置、provider 配额、费用和限流、内存/CPU/磁盘/网络、工具连接池。多进程并不绕过 provider 共享配额。需要分片时按独立项目/账号/数据域设置单写者与全局请求预算，不能让两个 Host 同时写一个状态库。

可用本包 src/concurrency-policy.js 的 assessConcurrency 做只读预算评估。它只给准入建议和缺失项，不改配置、不启动任务。

## 滚动调度与共享写入

各模块负责人维护有限 ready 队列和工作包。队列为空且仍有需求时由原 owner 补充完整交付项；禁止 leader 逐批手工填槽。启动前重新核对 planRevision、依赖版本、授权、写入范围、全局资源与当前租约；只对一个 work 做一次原子预留。

调度验收必须覆盖：tick 执行期间收到的事件在 tick 结束后至少再处理一次；单个慢/挂起的启动请求不阻塞其它已就绪工作；启动 RPC 有超时且结果 unknown 不重放；队列尚有 ready 且尚有容量时能继续填充，不能只启动 maxStartsPerTick 后长期停住。出现缺陷时记录原调度器待修项，不能用额外轮询派发器制造双重启动。

源码中共享状态用锁与 CAS 保护，但 writeScopes 不是操作系统隔离。并发开发优先独立目录/worktree；共享入口、依赖清单、锁文件、数据库迁移由明确单写者归并。后续模块依赖已发布的接口版本，不等待无关模块，不伪造 verified-result。

开发可持续滚动；达到全部开发或用户约定的产出门槛后再统一测试。测试结果回原 owner 修复，不换人为同一交付物接力；最终由原负责人共同完成跨模块集成。

## 故障恢复与上下文

相同错误指纹、相同输入/权限/版本不循环重试；429 或 provider 过载降低目标并发，遵守 Retry-After，使用有上限的指数退避和抖动。超时只说明没有及时得到结果，不等于任务失败。

每次副作用绑定 workId、planRevision、attemptId、leaseEpoch 和幂等键。未知启动/投递先只读核对原 session、产物及回执；不得换 ID 再发。迟到旧租约回执只归档，不覆盖新版本。重启先对账、再回收确定失效的预留；保留 produced 成果、原 owner 与原 work 身份，不清空库重做。

下游已接受的版本要可追踪，修复追加修订，不能覆盖证据。输入不足由 leaf 用 team_ask_owner 回报，只有真正改变决策且本地不可查的事项才升级给用户。

上下文只含当前目标、边界、必要输入路径/摘要、接口版本与验收条件；详细证据落盘按需读。不要给每个执行者复制全体聊天、全仓库或全量工具 schema。汇总只读增量与有界缓存，读取失败保留 unknown 和上次时间；监控本身不应吞掉模型/磁盘容量。

## 逐级压力验收

这是一份待执行的验收方案，不是已经发生的压力测试。先完成本轮完整开发与修复，再统一测试。选择隔离的真实代表性工作负载（短/长、工具密集、共享资源、依赖链、限流、故障恢复），保留输入规模、版本、预算与随机种子。

在配额/成本/机器条件齐备时，按 4→8→16→24→30 升档；每档至少 30 分钟且不少于 100 个完整交付。只有经过原生/Host/监控范围扩容并重新确认 provider 配额后，才计划 48→64→100。每档升档以已完成证据为准，不同时把档位数字全部派发。

记录 native turn 起止与 session 映射推导真实重叠峰值、稳定时长，分列 owner、leaf、reserved、unknown；统计每分钟完整交付数、排队/启动/执行/补位延迟 P50/P95/P99、429/失败/重试、RSS、CPU、磁盘、费用。配置和 mocked scheduler 测试不能证明真实模型吞吐。

安全性硬门槛：0 重复副作用、0 越权写入、0 回执/产物丢失、0 假完成、恢复后身份与产物版本一致。可用性目标先冻结（例如成功率≥99%、补位P95≤5秒、交互P95≤10秒）；这些是建议目标，不是现有能力承诺。连续两档吞吐不增或延迟/错误恶化就降回最后稳定档。

通过断网、429、进程中断、CAS 冲突、过期租约、慢启动等注入后仍正确对账，才报告该实测上限；其它档位一律未验证。
