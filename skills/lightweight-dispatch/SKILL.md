# 轻量级派发（L2 子智能体操作规程）

## 工作级别：L2 子智能体

本技能是三级协作模型中的 **L2 子智能体**操作规程。

- **L1 单智能体（solo）**：单一不可再分交付物、单文件小改、一次回答闭环、纯问答；当前上下文直接做完，不建团队、不下 mission、不派 leaf。
- **L2 子智能体（subagent）**：**一个可独立完整执行的交付单元**——明确输入、明确产出、可独立验收（常见形态是 ≥2 个**平铺、无依赖**的小交付物）；不需要跨回合持续负责人；结果可一次性回收。形态：主智能体直接派 `subagent`，**一个执行者端到端做完**（调查→实现→自检→修复），交回真实产物与证据。**L2 的本质是「可独立验收的完整交付单元」，不是「小任务」的同义词。**
- **L3 智能体团队（team）**：**大型、长程任务**——切成若干**相互独立**的部分，模仿真人团队「各自独立工作 → 沟通 → 整合」；判据仍是接口/依赖、需要跨回合持续负责人、需要多批推进与补位。**不要因为「任务大」就建团，要因为「需要持续负责人与并行独立交付」才建团。** 形态：建团队，leader 定目标边界并下 mission，member 域自治端到端，leaf 执行最小任务包（leaf 不能再开 leaf）。**关键等价关系：团队里的每个 member 相当于一个 L2**（领域级的 L2）。

**升级到 L3 的判据（与「myworkflow-task-router」同一组，任一命中即升级，改用「myworkflow-task-dispatch」+「myworkflow-subagent-protocol」）**：出现跨交付物接口/依赖（含「A 产出 → B 引用」、需另一子任务按精确签名对接）；需要跨回合持续负责人；需多批推进与补位；需要并发调整与验收裁量。

- **member 之间可直接沟通**：member 与 member 可直接相互发消息，**不经过 leader 中转**（任务切分不可能完美，交叉/重叠/依赖靠直接沟通解决）；横切后出现交叉/依赖靠沟通解决而不是拆阶段。
- **member 与 leaf 的区别**：leaf/subagent **寿命绑定具体任务**（做完即结束，职责=一个具体任务，只能与派发者沟通）；member **长期存在**（可睡眠唤醒复用、跨任务保留知识，职责=一个领域，可直接与其它 member/leader 沟通，**member 相当于一个 L2**）。

## 禁止阶段拆分（硬规则）

一个交付物内部**禁止**按时间/工序阶段拆成多个子智能体接力（例：「先搜→再写→再审」各派一人）。合法切分只有**横向切平铺**：拆出的每一份都必须是可独立交付、独立验收的小件。（下文「阶段拆分」与「阶段接力」同义，判违规口径一致）

| 违规（禁止） | 合法（允许） |
|---|---|
| 「调研 → 设计 → 实现 → 审查」四阶段各派一个子智能体接力 | 一次派 N 个互不依赖的小件（查 A、查 B、生成 C），各由一名执行者端到端做完 |
| 同一份报告「先写提纲 → 再写正文 → 再润色」分三次派发 | 每个执行者一次做完自己那份小件（含自检），直接交回可用结果 |
| 先派一个子智能体「调研」，再派另一个基于它的产出「实现」 | 两个子任务无依赖就并行；有依赖说明不是 L2，应升级 L3 |

**判定话术**：如果拆出来的每一份「单独交给别人也不成为一个可用成果」，就是阶段接力，违规；如果每份都能独立交付、独立验收，才是合法切分。横切后出现交叉/依赖，靠 **member 之间直接沟通**解决（L2 内则由执行者一次做完），不靠拆阶段。

## 触发

- **显式触发**（用户主动要求）：用户说"并行查/同时搜/分别做/一起生成/批量处理/每人一个/各做各的/轻量级派发/简单并行/快速派发"；一次请求中描述了多项同类工作（如"帮我查 A、B、C 三人的信息，每人写一段简介"）。
- **隐式触发**（agent 主动判断，满足**全部**条件）：任务可自然分割为 N 个同类子任务（N≥2）；子任务之间无依赖——每个可独立完成，不需要等待其他子任务的结果；每个子任务足够简单——单一目标，无需多步骤拆解，不需要接口合约；子任务之间修改的文件/资源不重叠（不会互相覆盖）。
- **不触发**：单一原子操作 → 直接做；子任务之间存在强依赖（B 需要 A 的运行时输出）→ 升级「myworkflow-task-dispatch」；任务复杂，需要结构化拆解和接口合约 → 升级「myworkflow-task-dispatch」；子任务会修改相同的文件 → 不能并行，需串行或合并。
- **升级规则**（第一步判断时发现任一信号 → 立即停止，升级到「myworkflow-task-dispatch」）：子任务之间存在"A 产出 → B 引用"的依赖关系；子任务需要修改同一批文件的不同部分（存在潜在的合并冲突）；任务的产出物需要精确定义的接口（下游模块依赖精确签名）；用户明确说"需要验收标准/需要接口合约"。
- **中间地带处理**：2-3 个相互独立但每个有 2-3 步的中等复杂度任务（既不满足"一步到位"也不满足"需要合约"）→ **默认使用本 skill**，但必须丰富子智能体的 prompt：至少包含①逐步子任务清单（每步一个可执行动作）②输入文件路径或关键输入内容③输出格式与验收方式；缺任一项视为 prompt 不完整，不得派发。只有在子任务产生跨任务依赖时才升级到重量级。

### L2 与 L3 的边界（与「myworkflow-task-dispatch」的分工）

| 判断维度 | 轻量级派发（本 skill） | 任务拆解与派发（重量级） |
|---------|----------------------|------------------------|
| 子任务关系 | 完全独立，无依赖 | 可能有分层依赖 |
| 拆解深度 | 不做拆解，直接平铺 | 拓扑排序 + 分层 |
| 接口定义 | 无需合约 | YAML 合约 + 签名 |
| 子智能体协议 | 简化指令（本文档内置） | 完整「myworkflow-subagent-protocol」5 阶段 |
| 验证 | 无需集成验证 | 需要「myworkflow-integration-verify」 |
| 元文件 | 无（不创建 .task-manifest/） | 完整元文件体系 |
| 典型任务 | "搜索 5 个人的 GitHub 主页" | "实现用户认证系统" |
| 子任务上限 | 建议 <= 12 | 硬限制 2-12 |

## 前置强制步骤

1. **理解任务**：确认用户需求确实可分解为 N 个同类独立子任务。
2. **轻量/重量判断**：按上表判断——如果发现依赖/复杂度信号，立即升级到「myworkflow-task-dispatch」。
3. **收集上下文**：读取每个子任务需要的输入文件/信息，确保子智能体有足够的上下文。

## 执行流程

### 第一步：判断与分类

分析用户任务，回答三个问题：
1. **是否可平铺**：能否将任务直接拆成 N 个"做同一类事、但输入不同"的子任务？
2. **是否无依赖**：每个子任务是否可以完全独立完成，不需要其他子任务的产出？
3. **是否足够简单**：每个子任务是否是"单一目标、一步到位"的类型？

三个问题全部 YES → 进入第二步。任一 NO → 升级到「myworkflow-task-dispatch」。

### 第二步：生成子任务列表

为每个子任务赋一个编号（1..N），写一句话描述：

```
子任务 1：{一句话描述}
子任务 2：{一句话描述}
...
子任务 N：{一句话描述}
```

**约束**：N 建议不超过 12（超过 12 个时提示用户确认，避免管理成本超过并行收益）；每个子任务描述必须具体、可执行（子智能体看完就知道做什么）；如果某个子任务需要额外上下文（如特定文件内容），在这一步收集好，写入该子任务的 prompt。

### 第三步：生成简化 Prompt 并并行派发

> **核心原则：一个子任务 → 一个执行者 → 一个精简 prompt；执行者端到端做完自己的小件（调查→实现→自检→修复），不是只做一道工序。**

```markdown
## 任务
{一句话描述}

## 上下文
{子智能体需要的项目背景、技术栈、相关文件路径}
{如果需要，粘贴关键输入内容——让子智能体不需要自己去猜}

## 产出要求
- {具体的产出物，如文件路径、文本内容、搜索结果}
- {格式要求，如 Markdown 表格、JSON、代码文件}

## 约束
- 只做本任务范围内的事，不要扩展范围
- {如果有不能修改的文件或不能做的事情，在这里写明}
- 完成后直接输出结果，不需要额外的声明/自检/完成报告文件

## 输出格式
完成后请以以下格式输出：
### 结果：成功 → {具体产出内容}；失败 → 填写"失败原因: [具体原因]"，不填产出内容
```

**派发方式**：将所有 N 个 Agent 调用放在同一条消息中发送，它们会并行执行。不要在消息间串行发送。

**超时预算（由主智能体持有，不写进子智能体 prompt）**：给每个子任务设一个超时预算——默认 **300 秒**；搜索/查询类可设为 **120 秒**；代码生成类可设为 **600 秒**。这是**主智能体侧的判定标准**，用于第四步收集结果与「部分超时」处理：超过该任务设定的预算仍未返回即判"超时"。Agent 工具没有 timeout 参数，子智能体也不会解析 prompt 里的超时行，所以这行写进 prompt 是无效指令——预算只在主智能体侧记账。批量派发时逐个任务记录预算，不要用统一阈值判定。预算只用于判定「未返回=超时」，不得据此在回合内 sleep / 轮询等待。

**与重量级 prompt 的区别**：不引用「myworkflow-subagent-protocol」；不要求写 interface-declaration.md / self-check.md / completion.md；不要求读取 task-contract.yaml（因为根本不存在）；prompt 内置了简化的输出格式约定（"结果：成功/失败"）。L2 不建团队、不下 mission；出现阶段拆分（即阶段接力）或跨产物依赖时立即升级 L3。

### 第四步：收集结果

收集本批执行者的返回（同一条消息并行派发后由工具回执一次性返回；**不得 sleep / 轮询等待**；超过该任务超时预算未返回 → 按「超时」标记）。对每个返回：
- **成功**：提取产出内容
- **失败**：记录失败原因（子智能体可能报告错误、超时、或找不到所需信息）
- **未返回**：超过该任务的超时预算仍未响应 → 标记为失败，原因记为"超时"

不需要走集成验证——各子任务独立，结果之间不互相依赖。

### 第五步：合并输出

将 N 个子任务的结果合并为统一的输出：

```markdown
## 轻量级派发结果
| # | 子任务 | 状态 | 结果摘要 |
|---|--------|:----:|---------|
| 1 | {描述} | ✅ | {一句话摘要} |
| N | {描述} | ❌ | {失败原因} |

### 详细结果
#### ✅ 子任务 1：{描述}
{完整产出内容}
#### ❌ 子任务 N：{描述}
**失败原因**：{原因}

### 统计
- 成功：{X}/{N} / 失败：{Y}/{N}
```

**失败处理决策**：

| 失败率 | 建议动作 |
|--------|---------|
| >50% | 建议审视是否应升级到「myworkflow-task-dispatch」 |
| ≤50% 且 ≥2 项 | 重试失败项 |
| 仅 1 项 | 人工补做或重试 |
| 全部超时 | 检查超时预算设置是否合理，考虑增大预算或拆分任务 |

- **失败项信息不重要**（如"搜索某人信息未找到"且该信息不是核心需求）→ 标注后继续。
- **失败项影响整体结论**（如"3 项失败导致无法做后续判断"）→ 在统计后添加"建议"段落，说明是否需要重试或人工介入。

## 失败处理

### 单个子任务失败
- 不阻塞、不重试其他子任务。
- 在合并输出中标记为 ❌ 并附失败原因。
- 如果用户对失败项有后续要求（如"重试子任务 3"），单独处理。

### 全部子任务失败
- 汇报所有失败原因，分析是否因为：任务描述不清 → 重新描述后重试；子智能体缺少必要上下文 → 补充上下文后重试；任务本质上不适合轻量级派发 → 升级到「myworkflow-task-dispatch」或自己直接做。

### 部分超时
- 超过**该子任务设定的超时预算**（未单独设定时按默认 300 秒，即 5 分钟）未返回的子智能体标记为"超时"。按任务逐个判定——搜索类预算 120 秒、代码生成类预算 600 秒的任务，各自按自己的预算判，不得一律用 5 分钟卡。
- 不影响已返回的结果——先合并已返回的结果，超时的单独标记。

## 完成标志

- [ ] 任务已判断为适合轻量级派发（三个问题全部 YES）
- [ ] N 个子任务列表已生成，每个描述具体可执行
- [ ] 每个子任务的简化 prompt 已准备好（含上下文和约束）
- [ ] 所有 Agent 调用在同一条消息中并行派发
- [ ] 所有子智能体已返回（或超时已标记）
- [ ] 合并输出已生成，包含成功/失败统计和详细结果
- [ ] 已确认没有把同一交付物按阶段拆成多个执行者接力（每份都可独立交付/验收）
- [ ] 如有失败项，已给出失败原因和建议
- [ ] 结果按证据口径交付：产物路径 + 关键命令 / exitCode（或 runId）+ sha256；无证据不算完成
