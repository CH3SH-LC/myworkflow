## 核心流程：三问定档 → 平铺切分 → 成员提交 → 结算合并

**何时加载**：N≥2 份同类小交付物、彼此无依赖、每份单一目标且不写同一批文件。**不加载**：单一原子操作、交付物之间有强依赖或需要精确接口合约（走 task-dispatch）、交付物会改同一批文件（合并成一份）。

**硬步骤**
1. **三问定档**：可平铺？无依赖？每份够简单？全部 YES 才继续；2–3 份各 2–3 步的中等复杂度默认本技能但把说明写细 → 出现"A 产出被 B 引用却无接口或已验证结果"、"改同一批文件"、"要精确签名"任一信号立即升级完整交付合约。
2. **平铺切分**：给每份可独立交付的产物编号，写清目标 / 输入路径 / 产出位置 / 验收 / 边界，每份一个 owner 端到端 → 无依赖不写 dependencies，有依赖必须带 version + requires；不设数量硬门槛，数量偏多时提示管理成本。
3. **成员提交**：已有模块成员就由**成员自己**用 `team_plan_submit` 提交、`team_dispatch_authorize` 授权，常驻调度器按 ready 与容量补位；没有成员且每件都很小就自己做完 → 不建空成员、不逐个写 per-交付物 prompt 派活、不写 delivery-contract.yaml 之类元文件，满额保持 ready（CAPACITY_FULL）。
4. **按结算推进**：每项结算当场判定成功 / 失败 / 状态未知，文件产物用 `read` 抽验关键点 → 超时先判进展与可恢复性，不忙轮询、不判早死；失败项由原 owner 收尾，不阻塞其它 ready 项，blocker 精确挂到受影响交付物。
5. **分层合并**：结论表 + 每项证据引用进 parent，原文留在文件或子会话 → 统计成功/未知/失败数，摘要含来源、版本、遗漏、不确定性、未完成项；失败率过高先回查是否退化成阶段接力。

**完成判据**：N 份交付物各有真实产物与可核查证据（路径、行号、命令与退出码），状态区分已核实与未核实；"用上团队"、文件非空、idle 都不算完成。

## 触发

- **显式触发**（用户主动要求）：用户说"并行查/同时搜/分别做/一起生成/批量处理/每人一个/各做各的/简单并行"；一次请求中描述了多项同类工作（如"帮我查 A、B、C 三人的信息，每人写一段简介"）。
- **隐式触发**（agent 主动判断，满足**全部**条件）：任务可自然分割为 N 个同类交付物（N≥2）；交付物之间无依赖——每个可独立完成，不需要等待其他交付物的结果；每个交付物足够简单——单一目标，无需接口合约；交付物之间不写同一批文件。
- **不触发**：单一原子操作 → 直接做；交付物之间存在强依赖（B 需要 A 的运行时输出）→ 改用「task-dispatch」类完整拆解技能；需要结构化拆解和接口合约 → 改用完整交付合约技能；交付物会修改相同的文件 → 合并成一份交付物。
- **升级规则**（判断时发现任一信号 → 立即停止本技能，改用完整交付合约）：交付物之间存在"A 产出 → B 引用"且没有可发布的接口或已验证结果；交付物需要修改同一批文件的不同部分（存在潜在的合并冲突）；任务的产出物需要精确定义的接口（下游模块依赖精确签名）；用户明确说"需要验收标准/需要接口合约"。
- **中间地带处理**：2-3 个相互独立、每个有 2-3 步的中等复杂度交付物（既不满足"一步到位"也不满足"需要合约"）→ **默认使用本技能**，但把每份交付物的说明写得更细（给出步骤指引与中间验收点）。只有在交付物之间产生跨交付物依赖时才升级。
- **本技能的定位**：它是**轻量工作项**的推进方式——不是"一条消息派一个子智能体"，而是把 N 份小交付物交给**已有的模块成员**，由**成员自己**用 `team_plan_submit` 提交、`team_dispatch_authorize` 授权，常驻调度器据此推进；没有成员或每件都很小时，自己直接做完。

### 与完整交付合约的边界

| 判断维度 | 轻量工作项（本 skill） | 完整交付合约（task-dispatch） |
|---------|----------------------|------------------------|
| 交付物关系 | 完全独立，无依赖 | 可能在交付物之间有依赖 |
| 拆解深度 | 不做拆解，直接平铺 | 拓扑排序 + 分层 |
| 接口定义 | 无需合约 | YAML 合约 + 签名 |
| 谁执行 | 已有模块成员认领；成员用自己的 `team_subagent_start` 起执行者 | 由模块成员端到端负责全流程 |
| 验证 | 各交付物自检；不撤走 owner 换审查员 | 独立集成验证 |
| 元文件 | 无（不创建清单类元文件） | 完整元文件体系 |
| 典型任务 | "搜索 5 个人的 GitHub 主页" | "实现用户认证系统" |
| 交付物数量 | 按需平铺；数量偏多时提示管理成本 | 由依赖拓扑决定 |

## 前置强制步骤

1. **理解任务**：确认用户需求确实可分解为 N 个同类独立交付物。
2. **轻量/完整判断**：按上表判断——发现依赖/复杂度信号立即升级到完整交付合约。
3. **收集上下文**：读取每个交付物需要的输入文件/信息，写进该工作项的说明，让成员不必去猜。
4. **决定执行方式**：已有模块成员（用 `team_snapshot` 看得到）→ 提交工作项；只有 leader 自己且每件都很小 → 直接做完，不为了"用上团队"而建空成员。

## 执行流程

### 第一步：判断与分类

分析用户任务，回答三个问题：
1. **是否可平铺**：能否将任务直接拆成 N 个"做同一类事、但输入不同"的交付物？
2. **是否无依赖**：每个交付物是否可以完全独立完成，不需要其他交付物的产出？
3. **是否足够简单**：每个交付物是否是"单一目标、一步到位"的类型？

三个问题全部 YES → 进入第二步。任一 NO → 改用重量级技能。

### 第二步：横向交付合约（切分与清单）

**横向切法**：按**可独立交付的产物**切分——module 模块 / object 对象 / evidence-package 证据包。每份交付物由一个 owner **端到端负责**：调查 → 实现 → 自检 → 修复 → 验收。

**拒绝阶段接力**：不得把同一个交付物切成"背景调查 → 设计 → 检查"或"计划 → 编码 → 审查"再各派一个人。发现这种拆法时，按下面的方式横向重排：

| 阶段接力（禁止） | 横向重排（推荐） |
|-----------------|-----------------|
| 先派 1 人做背景调查，再派 1 人设计，再派 1 人检查 | 每个交付物一个 owner，自己查背景、自己设计、自己自检 |
| 计划 / 编码 / 审查 三段各一个 owner | 一个 owner 负责一个完整交付物；审查由**同一 owner 收尾修复**，全局集成由 leader 与相关 owner 共同负责 |
| 全部调查做完再统一开工 | 每份交付物各自从调查开始，边结算边补位 |

**依赖规则**：依赖只允许存在于**不同交付物之间**，并且每个依赖必须写清 `version` + `requires`（published-interface 已发布的接口，或 verified-result 已验证的结果）。同一交付物内部不得写依赖；无依赖关系的交付物不得凭空标注依赖。不共享中间状态，不引用未发布的接口。

为每个交付物赋一个编号（1..N），写一句话描述：

```
交付物 1：{一句话描述} | owner: {谁} | 依赖: 无
交付物 2：{一句话描述} | owner: {谁} | 依赖: 交付物 1 (version 1.0, requires: published-interface)
...
交付物 N：{一句话描述} | owner: {谁} | 依赖: 无
```

**约束**：不做数量硬门槛，也不设固定上限或下限；数量偏多时提示用户管理成本可能超过并发收益，由用户决定是否继续平铺。每个交付物的说明必须具体、可执行（成员看完就知道做什么）；如果某个交付物需要额外上下文（如特定文件内容），在这一步收集好，写进该工作项的说明。已发布接口用 `write` 落到文件里再对外引用，不要只放在会话里。

### 第三步：提交轻量工作项（由调度器补位）

> **核心原则：一份交付物 → 一个 owner（模块成员）端到端负责；执行者是该 owner 自己用 `team_subagent_start` 启动的 continuable child。**

提交动作（agent team 模型）：

1. 没有受管团队时，leader 先 `team_define` 登记团队；没有成员时用 `team_member_create` 建模块成员（写明模块责任与 `writeScopes`），再用 `team_mission_assign` 下模块委托——**不要**为几件小事把每个交付物都变成一个成员，也不必把简单请求升级成完整仪式。
2. **成员自己**用 `team_plan_submit` 把每份交付物提交成自己拥有的 work：`title` / `deliverable` / `outputs` / `acceptance` / `writeScopes` / 依赖 `version` + `requires`。交付物之间无依赖就都不写 `dependencies`。
3. 成员用 `team_dispatch_authorize` 授权后，**由常驻 Host 调度器按 ready 与容量补位**：member 用 `team_subagent_start` 定向启动执行者、`team_work_report` 结算、`team_work_verify` 验收。leader **不逐批派活**，不写 per-交付物 prompt 去挨个"发出"。
4. 满额时调度器**拒绝并保持 ready**（`CAPACITY_FULL`），不排队空等、不用一次性旁路绕上限；成员当前 turn 停止或 pane 隐藏都不影响成员与队列。
5. 每份交付物的说明必须具体、可执行：目标、输入证据路径、产出位置与格式、验收标准、边界（不能改什么）。这就是"任务包"，由 owner 再拆给它自己的执行者。

**与完整交付合约的区别**：不要求写 `delivery-contract.yaml`、不要求接口声明 / 自检 / 完成报告等附加文件；交付物本身足够简单，owner 直接做完即可。

### 第四步：按结算推进（不轮询、不判早死）

**任一项结算就立即处理，不等同批其它项。** 每个工作项结算后当场判定，并把结果落到「已核实 / 推测 / 未核实」之一：

- **成功（`produced`）**：提取产出内容；若产物是文件，用 `read` 抽验关键点，作为证据引用。
- **失败（`failed`）**：记录确切失败原因（错误信息、已尝试路径、影响范围），进入下面的阻塞处理顺序。
- **未结算 / 状态未知**：用 `team_snapshot` 看该成员与工作项的当前状态，用 `team_wait` 等下一次变化（不忙轮询）；只有确认无法继续才判失败。**「状态未知/暂停」与「真正失败」严格分开，超时不等于失败**——状态未知的项如实保持原状并注明，不折算成失败。
- **迟到回执**：`attemptId` / `leaseEpoch` 不匹配的回执只归档为迟到结果，不覆盖新版本；怀疑回执丢失时用 `team_recover` 对账。

**阻塞处理顺序**（逐级递进，不跳级）：
1. 记录确切失败点、已尝试路径、影响范围、以及**在当前阻塞下仍可做的部分**；
2. 查已装服务、源码、现成工具、当前权限，确认是否只是没找对路径；
3. 能写适配器 / 接口 / 本地桥接补齐的，就地补齐，不把问题抛回用户；
4. 局部阻塞时先做其它 ready 项，并把 blocker 精确挂到受影响的交付物上（写明它卡在哪一步、解除条件是什么）；
5. 确实需要外部账号、人工决策或无法获得的资源，才标记 `needs_user`，并给出**已尝试路径与最小下一步**。

**不得**固定"试三次就结束"，也**不得**无预算地无限重试同一失败；权限拒绝不可绕过，不重试被拒操作。

**收尾与集成**：同一 owner 负责自己交付物的收尾修复，不撤走前面的人换一个无上下文的审查员。全局集成由 leader 与相关 owner **共同负责**。

**用户授权**：用户已在授权任务内的可逆开发动作，不重复询问；审批与扩权只有用户入口，模型没有等价工具。只在**真正改变决策且项目里查不到**时才用 `ask_user_question` 提问。

### 第五步：分层合并输出

结果分层：**简短结论 + 可核查的 evidence/artifact refs 进 parent**，原始材料留在文件或子会话里，不把大段原文倒进汇总。

```markdown
## 轻量工作项结果
| # | 交付物 | owner | 状态 | 置信 | 结果摘要 | 证据引用 |
|---|--------|-------|:----:|:----:|---------|---------|
| 1 | {描述} | {owner} | ✅ | 已核实 | {一句话摘要} | {文件路径:行 / 子会话} |
| 2 | {描述} | {owner} | ⏸ | 未核实 | {状态未知，仍在推进 / 已暂停} | {team_snapshot 观察到的状态} |
| N | {描述} | {owner} | ❌ | 已核实 | {确切失败点} | {尝试记录} |

### 详细结果
#### ✅ 交付物 1：{描述}
{结论 + 证据引用}
#### ⏸ 交付物 2：{描述}
**状态**：未知/暂停（不等于失败）—— {已观察到什么、下一步}
#### ❌ 交付物 N：{描述}
**确切失败点**：{原因} / **已尝试**：{路径} / **影响范围**：{哪些交付物受影响} / **仍可做**：{部分}

### 统计与摘要
- 成功：{X}/{N} ｜ 状态未知：{U}/{N} ｜ 失败：{Y}/{N}
- 摘要需含：来源、版本、遗漏、不确定性、未完成项
- 证据诚实：区分「已核实/有来源」与「推测/未核实」；不夸大，无证据不得声称"验证通过"
```

**失败处理决策**：

| 失败情况 | 建议动作 |
|----------|---------|
| 失败率 >50% | 审视交付物是否真的无依赖、切法是否退化成阶段接力 |
| 2 项以上且非全失败 | 按阻塞处理顺序逐项补齐，能自己补的就补，不整体重跑 |
| 仅 1 项 | 由该 owner 收尾修复；或人工补做 |
| 多项停在"状态未知/超时" | 先用 `team_snapshot` / `team_wait` 判断进展与可恢复性，再决定继续等或拆小该交付物；不把它当失败统计 |

- **失败项信息不重要**（如"搜索某人信息未找到"且该信息不是核心需求）→ 标注后继续。
- **失败项影响整体结论**（如"3 项失败导致无法做后续判断"）→ 在统计后添加"建议"段落，说明是否需要补齐或人工介入。

## 失败处理

### 单个交付物失败
- 不阻塞、不重试其他交付物；该项的 blocker 精确挂到受影响的交付物上。
- 在合并输出中标记为 ❌ 并附确切失败点与已尝试路径。
- 由**原 owner 收尾修复**；如果用户对失败项有后续要求（如"重试交付物 3"），单独处理。

### 全部交付物失败
- 汇报所有确切失败原因，分析是否因为：工作项说明不清 → 补充说明后重试；成员缺少必要上下文 → 补齐输入后重试；任务本质上不适合轻量提交 → 改用完整交付合约或自己直接做。

### 部分超时 / 状态未知
- 先判断进展与可恢复性：用 `team_snapshot` 看是否仍在推进、能否恢复；可恢复的继续等或补位别的 ready 项，不可恢复的才按失败处理。
- 不影响已返回的结果——先合并、先补位已返回留下的空位，超时/未知项单独标记，不判失败。

## 完成标志

- [ ] 任务已判断为适合轻量工作项（三个问题全部 YES）
- [ ] 交付物按可独立交付的产物横向切分，每份有一个端到端 owner，无阶段接力
- [ ] 跨交付物依赖已写清 version + requires（published-interface / verified-result）
- [ ] 每份交付物的说明已准备好（目标 / 输入 / 产出 / 验收 / 边界）
- [ ] 已由**成员自己**用 `team_plan_submit` 提交为工作项并 `team_dispatch_authorize` 授权；补位由常驻调度器执行，无全批屏障、无整层等待；满额时保持 ready
- [ ] 每项结算当场判定；超时先判进展与可恢复性，"状态未知/暂停"与失败分开
- [ ] 同一 owner 收尾修复；全局集成由 leader 与相关 owner 共同负责
- [ ] 分层输出已生成：parent 只留简短结论 + 可核查证据引用，原始材料留在文件或子会话
- [ ] 摘要含来源、版本、遗漏、不确定性、未完成项；无证据不声称"验证通过"
