## 核心流程：加载判定 → 五步闭环 → 完成判据

**何时加载**：创建/修改/删除代码或文件、加功能、重构、修 bug，或"继续做"且任务未完成。**不加载**：纯问答/阅读/搜索、只查不修的根因排查、纯文稿。单文件小改走精简路径：直接实现 + 一次真实验证；多文件按角色段门槛建团队。

**硬步骤（可裁剪但不跳验证）**
1. **读懂**：读项目指令与相关代码，复述目标/输入/输出/约束；只在改变决策且查不到时 `ask_user_question`。
2. **切分**：按可独立交付产物切 module/object/evidence-package，每份一个 owner 端到端；禁止"调查→设计→检查"接力；多交付物走 agent team（成员自 `team_plan_submit`/`team_dispatch_authorize`）。
3. **实现**：同一 owner 做完全部调查与实现；遇 bug 先定根因再改，不盲目试错；写测试/mock 前对照 references/testing-anti-patterns.md。
4. **真实验证**：真实命令启动、真实入口走通 happy path + 边界 + 回归；单测全过 ≠ 完成，mock 只证明合同。
5. **收尾**：失败按小/中/大回退回步骤 3/2/1，原 owner 修复复验；有 docs/ 走 project-maintain，需 commit/PR 走 github-collab。

**复用优先**：先复用已记事实、已解决错误与错误指纹，不重复调查、不重跑同一失败，按指纹的「改什么条件才重试」。

**沉淀（强制）**：同一命令第 2 次使用 → `scripts/<kebab>.mjs`（Node ESM、`--help`、exit 0/1/2）；收尾 → `node scripts/kb.mjs new ...` 落 `docs/knowledge/` 再补四段，不手写绕过 `kb.mjs check`。

**完成判据**：真实产物 + 可核查证据（命令 + exit code + 产物 sha/路径 + 入口走通记录），结论分层并标遗漏/不确定；只说不做、helper 单测、文档数量不算完成。

# 智能体闭环开发（DSH 版）

## 触发与豁免

- **触发**：创建/修改/删除代码或文件、加功能、重构、新增、改写；发现 bug 需修复；对话中途随口提出的产出需求；"继续/接着做"（本技能已加载且任务未完成时）。
- **不触发**：纯问答、文件阅读/搜索、纯格式化/注释、闲聊不写代码、纯根因排查（只查不修，走 `skill(name="myworkflow-root-cause-analysis")`）、纯文稿写作（走 `write-prose` / `polish-prose`）。
- **简单请求走精简路径**：改一行、改配置、改文案、单文件小修——直接实现 + 一次真实验证即可，不必走完整仪式。下面的阶段是**内部检查清单**，不是关卡；判断不清时按"需要清单"处理。

## 总原则

1. **横向交付合约**：按**可独立交付的产物**切分工作，每份交付物由一个 owner **端到端负责**：调查 → 实现 → 自检 → 修复 → 验收。禁止把同一份交付物拆成"背景调查 → 设计 → 检查"或"计划 → 编码 → 审查"的阶段接力（每个阶段换人，没人对成品负责）。
2. **事件驱动滚动补位**：任一项结算就立即补位，不等同批其它任务；没有全批屏障、没有整层等待；慢任务不阻塞其它已 ready 项。
3. **未 ready 不派发**：依赖未满足的任务不下发。容量满时**拒绝并保持 ready（CAPACITY_FULL）**，不排队空等，也不用一次性旁路绕过上限。
4. **同一 owner 收尾修复**：谁做的交付物谁修复。全局集成由 leader 与相关 owner **共同负责**，不撤走前面的人换一个没有上下文的"审查员"接管后半程。
5. **证据诚实**：区分「已核实 / 有来源」与「推测 / 未核实」；不夸大，不在没有证据时声称"验证通过"。
6. **不重复询问用户**：用户已授权任务范围内的可逆开发（改代码、写文件、跑本地命令）不必反复确认。审批与扩权只有用户入口，模型没有等价工具，也不存在"先取得许可再开工"的例行环节。

## 内部检查清单（原 5 阶段，降级为自检项）

### 检查项 1：需求理解
读项目指令文件（如 `CLAUDE.md`）与相关代码；复述核心目标 / 输入 / 输出 / 约束。
**只在真正改变决策、且项目里查不到答案时才提问**，且用 `ask_user_question`；项目里能查到的（命名、路径、既有约定）自己去查，不要问用户。
复杂或意图不明时用 `skill(name="myworkflow-req-clarify")`（本机已安装该技能时）。

### 检查项 2：交付切分与计划
产出分步清单 + 验证方案（**以真实用户身份描述怎么验证，不写空泛的"跑测试"**）+ 风险点。
切分依据是**可独立交付的产物**：
- `module` 模块（一个可编译/可加载的功能单元）
- `object` 对象（一类数据/实体的持有者与操作）
- `evidence-package` 证据包（一组同源结论及其来源、复现步骤）

**横向重排建议**：若发现计划里出现"同一交付物横跨多个人/多个阶段"，改成"一个交付物一个 owner 全流程"，把阶段接力改写为按产物切分的并列任务。

若项目根存在 `docs/GOAL.md`：先读 GOAL 确认开发本意、读 STATE 了解当前进度、读 `docs/design/index.json` 定位本次改动对应的 design 点。定位不到且性质是「新增功能 / 行为变更 / 新模块 / 接口变更 / 影响 ≥2 个模块」时，**先补齐 design 再动手**（这是准备项，由 `skill(name="myworkflow-project-maintain")` 执行，本技能不直接改 `index.json`）。bug 修复 / 重构 / 配置 / 文档 / 格式化可在 PROGRESS 条目里标注 `[Debug]` / `[Change]` 并写明"本次无 design（小场景豁免）"。

### 已记节点的定向查询批次与失败止损（E1）

- **一轮 = 一个有界批次**：既有结论 → `route`/`cluster`（5/30，`nextOffset`）→ `explain` 精确 graphKind/ID/端口（12）→ 必要 `recipe`/`enums`/`enum`（12）→ 实现。
- **再查三条件**：唯一缺语义/新证据/未试动作；否则复用已记事实与错误指纹。
- **失败止损**：同一失败最多 2 次，第二次换动作（重 grep 真实原文/换入口/上报 blocker）；同工具+同输入+同版本确定性失败不重发，先查错误指纹的"改什么条件才重试"。
- **只在相同条件阻止**：guard 按 工具+参数+会话/工作区+文件指纹/权限 判定；文件改动、权限修复、调用成功或超 TTL 自动失效，不需 nonce 绕过。
- **旧串编辑**：`old_string` 先 grep 真实原文；not found/multiple 不得原样重发。
- **上限与指针**：checkpoint evidence 最多 12 条、每条 400 字符；上下文只留 file:line/seq/runId/workId 指针。
- **完成门**：验收看真实调用链与真实产物；helper 单独成功/声明/文档不算完成。
- **阶段纪律**：全部开发完成前**禁止运行自测/单测/审计**；允许 read/grep/source 实现与真实工具执行，统一验收再测。

### 检查项 3：完整实现
1. 由**同一 owner** 完成"调查 → 完整实现"，不搞每改一行跑一轮的小步循环，也不因为"改了多个文件"就强制拆给不同的人。批量写、批量改是允许且推荐的。
2. 写测试或 mock 前对照 [测试反模式](references/testing-anti-patterns.md)。完整实现或约定的大块产出完成后**统一测试**；用户要求全部开发后再测时优先遵守。
3. **遇到 bug 不盲目改**：先用 `skill(name="myworkflow-root-cause-analysis")` 定位根因（只查不修）→ 按根因修复 → 继续。
4. **自检**：计划步骤全完成、无语法 / import 错误、批量测试全绿、边界与错误路径已覆盖。

多交付物并行时走 agent team 模型（autonomy-v1）：`team_define` 登记受管团队 → `team_member_create` 建**持续存在的模块成员**（写明模块责任与 `writeScopes`）→ leader 用 **`team_mission_assign`** 下模块委托；**work 由 member 自己用 `team_plan_submit` 提交**、用 `team_dispatch_authorize` 授权派发。之后常驻 Host 调度器**只启动成员已授权**的 work 并持续补位；member 用 `team_subagent_start` 定向启动自己的执行者、`team_member_inbox` 处理事件、`team_work_verify` 验收；leader 用 `team_snapshot` 看状态、`team_wait` 等变化、`team_interrupt` 按范围停止，不自己轮询派活。

### 检查项 4：真实验证
**核心原则：单测全过 ≠ 功能完成。** 单测测"代码按预期运行"，真实验证测"用户按预期使用"，缺一不可；**禁止仅用单元测试代替真实验证**。
- 达到用户约定的完整开发或大块产出门槛后**统一验证**一次即可（不必逐段反复验证）：真实命令启动、真实入口进入、真实数据走通。
- 覆盖：happy path + 边界 + 回归；关键用户路径逐条走（一般 ≥5 条，小改动可减少但必须走真实入口）。
- 需要独立视角时：**member 用 `team_message`** 请相邻成员增量复核；**leaf 无 `team_message` 权限，用 `team_ask_owner`** 向 owner 提出复核。复核**不是接力**：不接管后半程，发现问题回原 owner 修复。
- 专项验证可用 `skill(name="myworkflow-real-world-verify")`（本机已安装该技能时），传入：项目根目录/类型、变更概要、启动命令、测试命令、关键用户路径。

### 检查项 5：判断与持续修复

```
验证全过 → 收尾
有 ❌ → 小（几行可修）→ 回检查项 3
        中（动设计不改需求）→ 回检查项 2
        大（方向根本错）→ 回检查项 1
```

每个 ❌ 都必须处理，不允许降级跳过。**没有"轮数到了就停工"的规则**：修复循环由"是否仍在取得进展"决定。**不得固定"试三次就结束"，也不得对同一个失败无预算地无限重试**——每轮必须有新信息（新的报错、新的假设、新的排查面），否则按下面的阻塞处理走。

## 依赖、容量与阻塞

**依赖只允许存在于不同交付物之间**，同一交付物内部不设依赖。声明依赖时必须带 `version` + `requires`（`published-interface` 已发布接口，或 `verified-result` 已验证结果）；没有这两项就不算 ready。

提交与启动规则：
- 未 ready 的项不下发；满额时拒绝并保持 ready（`CAPACITY_FULL`）。
- 任一项**结算即补位**，不等同批其它任务，不做整批等待、不做逐层屏障。
- 慢任务挂起时，其它 ready 项照常推进。

**阻塞处理顺序（依次尝试，不要跳）**：
1. **记录**：确切的失败信息、已尝试的做法、影响范围、以及此时仍可做的部分。
2. **查**：已安装的服务/依赖、源码、现成工具、当前权限能做什么。
3. **补**：能写适配器、接口或本地桥接补齐的，就补上再继续。
4. **绕**：局部阻塞时先做其它 ready 项，并把 blocker **精确挂到受影响的那个交付物**上（不扩散到全任务）。
5. **上报**：确实需要外部账号、人工决策或无法获得的资源时，标记 `needs_user`，并给出**已尝试的路径**与**最小下一步**。权限被拒绝不可绕过，也不要用别的写法重试同一件事。

## 超时与失败判定

超时**不等于失败**。收到超时/中断先判断：是否有进展、是否可恢复。
- **状态未知 / 暂停**：进程被杀、连接断开、状态无法确认 → 标记未知，先探测实际状态（重跑探测命令、读产物、查任务板），再决定重试或换路径。
- **真正失败**：有确定的错误输出、可复现的失败路径、明确的失败原因。
两者严格分开，不要把"状态未知"写成"失败"，也不要把重复出现的确定性失败算作偶发超时。后台作业用 `job_list` / `job_output` / `job_kill` 跟踪，每个启动的作业都要有归属。

## 收尾与集成

1. **同一 owner 收尾修复**：验证中发现的问题由该交付物 owner 修完并复验；不换人接管。
2. **全局集成**由 leader 与相关 owner 共同完成；集成问题按交付物边界分派回对应 owner，而不是由一个新审查员从零接手。
3. **同步项目文档**（项目有 `docs/` 体系时）：走 `skill(name="myworkflow-project-maintain")` 的完成时流程（写 PROGRESS 条目、递增版本号、把 design 点置为「待验收」、刷新 STATE、校验 index）。**点状态只能由 project-maintain 置为「待验收」，「完成」只能由用户确认后置位。**
4. 需要提交远程（commit / PR / merge）时走 `skill(name="myworkflow-github-collab")`（本机已安装该技能时）。

## 证据与结果分层

- **给 parent 的**：简短结论 + 可核查的 evidence / artifact 引用（文件路径、命令、行号、message_id、任务 id）。
- **留在文件或子会话的**：原始材料（完整日志、长输出、逐条明细）。
- 摘要必须含：来源、版本、**遗漏与不确定项、未完成项**。没核实的不写"已验证"；只说"看起来对/推测"时要显式标注。

## 完成标志

- [ ] 需求已确认（或已判定为简单请求，走精简路径）
- [ ] 交付物按横向合约切分，每个交付物有唯一 owner 端到端负责（跨交付物依赖已带 version + requires）
- [ ] 准备项已完成（有 docs 体系时 design 已定位或已记录小场景豁免）
- [ ] 代码按计划完整实现（未做每行小步循环、未因文件数量多而无谓拆人）
- [ ] 真实验证已完成（真实入口 + happy path + 边界 + 回归），未仅用单测代替
- [ ] 所有 ❌ 已由原 owner 修复并复验；阻塞项已按顺序处理或标 `needs_user`（含已尝试路径与最小下一步）
- [ ] 结果已分层报告（结论 + 证据引用；来源/版本/遗漏/不确定性/未完成项）
- [ ] 项目文档已同步（有 docs 体系时）

## 元使用：审计模式

任务为审计或优化技能/插件时：明确审计目标与维度 → leader `team_member_create` 建相邻模块成员并用 `team_mission_assign` 下委托，**该成员自己** `team_plan_submit` 提交「审计」交付项、`team_dispatch_authorize` 授权后从新鲜视角审计 → 读回执，把 P0/P1 各项转为验证场景 → 由原 owner 持续修复，**P0/P1/P2 全部清零才停止**；清零前若卡在外部资源或人工决策上，标 `needs_user` 并给出已尝试路径与最小下一步，不因轮数到限而停止。

## 完整开发与统一验证

先读当前代码、项目约束和现有产物，定位真实根因与调用路径。能直接做的简单改动直接完成，不强制设计文档、脚手架或前置声明。

同一交付物的调查、开发、修复和验收由原 owner 连续负责；用户禁止拆分完整任务时不派给多个执行者。允许并发时只拆独立模块，并用 myworkflow-task-dispatch 核对已有团队、依赖、容量和授权。

一次完成完整实现，或达到用户明确接受的大块产出；全部开发后统一测试的要求优先，不以“可运行”或“写完一个文件”提前开测。开发中只做必要的读代码、输入核对和故障定位，保留待验证状态。

实现完成后统一执行与改动相称的回归和真实入口验收。测试不能照抄实现；mock 只能证明合同，不能冒充真实模型、客户端、网络或保存重开。失败回原 owner 修复，只针对实际变化或未解决问题补验。

成果应包括可用产物、必要的运行说明、实际验证证据和剩余边界。证据进已有任务回执，未验证、受阻和已完成分开，不用文档数量或日志数量代替进展。用户已授权的可逆工作不重复索要确认。
