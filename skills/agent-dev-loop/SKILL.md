## 触发场景

### 复杂度门控（先判断，再决定走完整流程还是快速通道）

在触发本 skill 后，第一步是判断任务复杂度：

| 复杂度 | 判定标准 | 走哪条通道 |
|--------|---------|-----------|
| **微小** | 单行/单表达式修改，改一个变量名、修一个拼写、加一行日志、改一个常量值。用户明确知道要改什么且改动不涉及逻辑变化 | **快速通道**：一句话确认→直接修改→快速验证→报告完成 |
| **简单** | 单文件内的函数/方法修改，修复一个明确的 bug（知道原因），添加一个简单字段/属性 | **标准通道**：走完整 5 阶段，阶段 1-2 可精简（不需要模板，口头确认即可） |
| **中等** | 跨文件修改、新增一个完整功能、重构一个模块 | **完整通道**：走完整 5 阶段，阶段 1 必须输出需求确认，阶段 2 必须输出计划并获批准 |
| **复杂** | ≥2 个独立模块、需要多个子智能体并行、架构级变更 | **完整通道 + 拆解派发**：阶段 3 必须调用任务拆解与派发 |

> **通道升降级**：任何阶段发现复杂度被高估或低估时可以切换通道。升级（如快速→标准）无需特别记录。降级（如标准→快速）必须在验证报告中记录降级原因。循环中的修复始终在当前通道内执行，不因单个修复简单而切换回快速通道。
> **用户要求精简**：用户说"直接做，不用走流程"不是不触发——skill 仍触发，但阶段 1-2 可精简（口头确认即可），阶段 4-5 不可跳过。

### 必须触发（满足任意一条——即使请求只有几个字）

1. 用户要求**创建**新功能、新文件、新模块（如"加个登录""写个工具函数""新建一个页面"）
2. 用户要求**修改**现有代码、重构、功能开发中附带的 bug 修复（独立的 bug 修复任务请用 Bug修复与验证）
3. 用户说"帮我做""实现一下""改一下""加一个""写一个""这里能不能""把这个改成"
4. 用户在对话中途**随口提出**任何需要产出或修改代码的需求——不需要等用户说"开始开发"，即使已经聊了很多轮
5. 用户描述了一个需要**产出代码/文件**的需求（即使没有明确说"开发"或"实现"）
6. 任何涉及 `Write`、`Edit` 工具对项目代码进行的修改（简单格式化/注释除外）
7. 用户说"继续""接着做""然后呢"且上一轮对话中本 skill 已被触发且任务未完成

### 不触发（反例）

- 纯信息问答（"这个框架怎么用""解释一下这段代码"）
- 文件阅读/搜索（"帮我找到 X 在哪里""看看这个文件"）
- 简单格式化/注释修改（不改变行为）
- 闲聊/讨论方案（用户明确说"先讨论，不写代码"）

### 与其他 skill 的层级关系

本 skill 是**外层元工作流**，内部阶段调用其他 skill。以下 skill 均为 myworkflow 技能包内置：

| 关联 skill | 调用时机 | 关系 | 不可用时的降级方案 |
|-----------|---------|------|------------------|
| **Bug修复与验证** | 不调用（互斥） | 纯 bug 修复任务优先用 Bug修复与验证；本 skill 仅处理功能开发中附带的小修复 | — |
| **大项目初始化 / 大项目工作维护** | 与开发流程并行 | 互补——管理 CLAUDE.md/PROGRESS.md 等文档体系。本 skill 管理开发流程 | 手动维护项目文档 |
| **需求澄清** | 阶段 1（需求不清晰时） | 探索意图和方案（硬门禁+多方案+落盘+可视化） | 自行分析需求，用 AskUserQuestion 澄清 |
| **需求澄清** | 阶段 2（中等/复杂任务） | 如有未解决的方案选择，委托需求澄清做多方案对比 | 手写计划（用阶段 2 模板） |
| 任务拆解与派发（ARIS 生态） | 阶段 3（复杂任务） | 拆解和派发并行子任务。如果不可用，直接按计划逐步实现 | 用 Agent 工具手动并行 |
| 子智能体执行协议（ARIS 生态） | 阶段 3 间接 | 由任务拆解与派发自动引用，本 skill 不直接调用 | Agent prompt 中手写工作规范 |
| 集成验证与修正（ARIS 生态） | 阶段 3 间接 | 由任务拆解与派发自动触发 | 手动检查接口合规性 |
| **反谄媚** | 阶段 4 | 验证时的行为准则——确保不自我欺骗、不跳过验证 | 保持警觉，逐项对照验证报告 |
| **Github协作** | 后置更新步骤 | 代码完成并验证通过后，如需提交到远程仓库，调用 Github协作完成 commit/PR/merge | 手动执行 git 命令 |
| **根因定位与全面排查** | 阶段 2（用户排查后传入） | 输入 ← | 排查报告可用于阶段 2 计划制定 | 自行分析根因 |

> **循环边界说明**：本 skill 的"3 轮完整循环"（阶段 5）和集成验证与修正的"3 轮修正"是**不同层级**的循环。集成验证与修正的修正循环发生在阶段 3 内部（只针对单个子任务的接口合规性），本 skill 的循环是宏观闭环。只有从阶段 5 回到阶段 1/2/3 才算本 skill 的一轮循环。

## 推荐要素

## 前置强制步骤

> **核心原则：闭环优于速度。** 跳步做快 = 返工做慢。宁可多花 30% 时间一次做对，不要花 300% 时间反复修补。

1. **识别任务类型**：判断是新增、修复、重构、修改，还是**审计/优化 skill**。如果是审计 skill → 阶段 3-5 自动适配为"派子智能体审计→读报告→有问题则循环"模式（详见文末「元使用：审计模式」）。如果需求模糊 → 进入阶段 1 时必须追问清楚
2. **检查项目上下文**：读取 CLAUDE.md、相关代码文件，了解技术栈和约定
3. **确认没有跳过**：如果发现自己正在想"这个简单，直接写代码就行"→ 这正是需要本 skill 的时刻

## 目标

确保智能体在每次开发任务中走完整闭环：理解需求 → 制定计划 → 执行实现 → 真实验证 → 问题循环。禁止跳步，禁止伪验证（仅跑单元测试），禁止发现问题后不回头修复。

## 执行流程

### 快速通道（微小任务）

> 适用：单行/单表达式修改——改变量名、修拼写、加一行日志、改常量值。用户明确知道要改什么。

1. **一句话确认**：复述你要改什么（如"把 `MAX_RETRY` 从 3 改成 5"），等用户确认（一个"对"字即可）
2. **直接修改**：用 Edit 工具完成改动。如果修改过程中发现涉及范围超出预期（需要改多个文件、改接口签名等）→ 立即升级到标准通道，从阶段 1 重新开始
3. **快速验证**：检查改动后的代码语法正确、逻辑一致、没有破坏调用方。如果是运行时行为 → 实际运行一次确认
4. **报告完成**：告诉用户改了什么、验证结果

快速通道跳过阶段 1-5 的完整模板和审批流程，但**不可跳过验证**。

**快速通道升级**：如果在快速验证中发现改动引发了连锁问题（调用方出错、类型不兼容、测试失败等），立即升级到标准通道——已有确认仍有效，从阶段 1 补充影响范围确认后走完整流程。不要反复在快速通道内修补。

### 阶段 1：需求理解

**目标**：在写任何代码之前，确保完全理解了用户想要什么。

**按复杂度调整深度**（参考上方「复杂度门控」表）：

| 复杂度 | 阶段 1 怎么做 |
|--------|-------------|
| **简单** | 口头复述需求（2-3 句话），用户确认即可。不用模板。模糊点超过 1 个时追问，否则直接进入阶段 2 |
| **中等** | 使用下方需求确认模板，用户确认后进入阶段 2 |
| **复杂** | 使用完整模板 + 优先调用「myworkflow:req-clarify」探索方案（硬门禁澄清 + 多方案对比）。模糊点必须全部澄清后才能进入阶段 2 |

**强制步骤**：

1. **读取上下文**：读取项目的 CLAUDE.md、相关代码、配置文件。不了解项目就开工 = 盲人摸象
2. **复述需求**：用你自己的话复述用户的需求，包含：
   - 核心目标（一句话）
   - 输入/输出是什么
   - 涉及哪些文件/模块
   - 有哪些约束条件
3. **识别模糊点**：主动找出需求中不清晰的地方。如果存在以下任一情况 → 用 AskUserQuestion 追问（最多 3 轮，每次一个问题）：
   - 用户没指定技术方案但你发现有多种选择
   - 用户没说明边界条件（空输入怎么办、大数据量怎么办、失败怎么办）
   - 用户的需求存在内在矛盾
   - 你不知道某些关键文件的位置或现有接口
4. **如果需求复杂或用户意图不明确**：调用「myworkflow:req-clarify」来探索方案（硬门禁 + 多方案对比 + 落盘）。不要自己猜——澄清成本远低于返工成本
5. **输出需求确认**：将确认后的需求总结为一段话 + 约束清单，向用户展示并等待确认。用户说"对"之后再进入阶段 2

**需求确认模板**：

```
## 需求确认

**核心目标**：[一句话描述]

**输入**：[用户提供什么 / 数据从哪来]

**输出**：[最终产出什么 / 用户能看到什么]

**涉及范围**：[哪些文件/模块会被修改或创建]

**约束条件**（外部限制）：
- [技术栈限制 / 性能要求 / 兼容性要求]

**边界条件**（输入数据的极端情况）：
- 空输入 → [如何处理]
- 异常输入 → [如何处理]
- 大数据量 → [如何处理]

以上理解是否正确？确认后我将制定详细计划。
```

**质量检查**：在进入阶段 2 之前，问自己：
- 我能向一个不了解这个项目的人解释清楚这个需求吗？
- 我知道完成后"成功"是什么样子吗？
- 我知道哪些东西不需要做吗（范围边界）？

### 阶段 2：计划制定

**目标**：将确认后的需求转化为可执行的详细计划。

**强制步骤**：

1. **判断复杂度**（参考上方「复杂度门控」表，不要重新定义）：
   - **微小** → 走快速通道（见上方），不进入本阶段
   - **简单** → 手写简要计划即可（不需要完整模板，说清楚步骤+验证即可）
   - **中等** → 按下方计划模板手写；如有方案选择疑虑，委托「myworkflow:req-clarify」做多方案对比
   - **复杂** → 必须输出完整计划模板。先委托「myworkflow:req-clarify」对比方案并落盘，再基于选定方案制定计划。标注"阶段 3 将使用任务拆解与派发"

2. **制定计划**，计划必须包含：
   - **分步执行清单**：每一步做什么、产出什么文件
   - **依赖关系**：哪些步骤必须先完成
   - **接口定义**：如果涉及多个模块，模块之间的接口是什么
   - **验证方案**：完成后的验证方法（不能只写"跑测试"——必须写清楚如何以用户身份验证。详见阶段 4）
   - **风险点**：哪里可能出错，出错了怎么办

3. **判断是否需要拆解派发**：
   - 满足条件（≥2 个独立模块且模块间接口可明确定义，子目标可分离）→ 在计划中标注"阶段 3 将使用任务拆解与派发"
   - 不满足 → 标注"阶段 3 将直接实现"

4. **展示计划并获取批准**：
   - 向用户展示计划摘要（步骤数、产出文件列表、验证方案）
   - 用户批准后进入阶段 3
   - 用户要求修改 → 调整计划后重新展示
   - **不可跳过批准步骤**——计划是用户和你的"合同"

**计划模板**（简单任务可精简）：

```
## 实施计划

### 步骤清单
1. [步骤名称] → 产出: [文件路径] — [简述]
2. ...

### 依赖关系
- 步骤 1 无依赖，可立即开始
- 步骤 2 依赖步骤 1 的 [具体产出]

### 验证方案
- [具体的验证步骤，以用户身份描述]
- 例如："打开浏览器访问 /login，用 test@example.com / password123 登录，检查是否跳转到 /dashboard 且显示用户名"

### 风险点
- [风险] → 应对: [措施]
```

### 阶段 3：执行实现

**目标**：严格按照计划实现，不走偏、不偷懒。

**强制步骤**：

1. **判断执行方式**：
   - 如果计划中标注了"使用任务拆解与派发"且该 skill 可用 → 调用「myworkflow:task-dispatch」skill，走完整的流程。派发后等待子智能体完成，然后调用「myworkflow:integration-verify」进行集成验证
   - 如果计划中标注了"使用任务拆解与派发"但该 skill 不可用 → 手动并行：(a) 按计划中的步骤清单将任务分为独立子任务；(b) 为每个子任务写一个 Agent prompt，包含任务描述、输入文件、期望输出文件、接口签名；(c) 用 Agent 工具并行派发；(d) 所有子智能体完成后手动检查接口一致性（对照计划中的接口定义逐项核对）
   - 如果没有使用任务拆解与派发 → 直接按计划逐步实现

2. **实现过程中的约束**：
   - **严格按计划执行**：不擅自增加计划外的功能（scope creep）
   - **每完成一步检查一步**：对照计划的验证方案逐项确认
   - **遇到计划未覆盖的情况**：停下来，更新计划，获取用户确认后再继续
   - **如果使用子智能体**：确保每个子智能体的 prompt 中包含对「myworkflow:subagent-protocol」的引用

3. **TDD 微循环（RED-GREEN-REFACTOR）**

> **这是微观层面的单元/集成测试——关注代码正确性，不等同于阶段 4 的宏观真实验证。**

每完成一个实现步骤（或一个函数/模块）时，按以下 TDD 微循环执行：

**RED：先写失败的测试**

- 在写任何实现代码之前，先写出该步骤的测试用例
- 测试必须覆盖：正常输入 → 期望输出、边界条件（空/null/极值）、错误路径
- 运行测试 → **必须看到测试失败**（红色）——如果测试直接通过，说明测试本身有问题（没测到东西，或功能已经存在）

**GREEN：写最小实现让测试通过**

- 只写让当前测试通过的最少代码——不过度设计
- 运行测试 → 全部绿色
- 如果多个测试同时失败 → 先修复最简单的那个

**REFACTOR：重构优化**

- 测试全部通过后，审视代码质量：
  - 是否有重复代码可以抽取？
  - 变量/函数命名是否清晰？
  - 逻辑结构是否可读？
- 重构时保持测试绿色——重构一步，跑一次测试
- 不要在此阶段添加新功能（那是下一轮 RED 的事）

**TDD 微循环的节奏**：

```
RED（写测试→失败）→ GREEN（最小实现→通过）→ REFACTOR（优化→仍通过）
                                                            │
                                                            ▼
                                        下一个实现步骤 ──→ RED...
```

**TDD 适用范围**：

| 产物类型 | TDD | 说明 |
|---------|:---:|------|
| 新增函数/方法/类 | ✅ 必须 | 先写测试，再写实现 |
| 被修改的逻辑 | ✅ 必须 | 先补齐已有测试，再修改代码 |
| 配置文件、文档、静态资源 | ⚠️ 跳过 | 无法自动测试，直接进入阶段 4 真实验证 |
| 副作用任务（数据库迁移、部署脚本） | ⚠️ 替代 | 写"验证清单"替代自动化测试 |

**TDD 出口条件**：当前实现步骤的所有测试全部绿色（通过），且代码已重构满意 → 进入下一实现步骤或进入步骤 4（实现完成后的自检）。

#### TDD 顺序为何重要——常见借口的回应

| 借口 | 回应 |
|------|------|
| "写完再测也一样" | 写完代码后你被实现细节锚定，测试会验证"代码做了什么"而非"应该做什么"。先写测试→测试描述需求；后写测试→测试描述实现。两者不同。 |
| "我已经手动测试了所有边界" | 手动测试不可重复、不可审计、不可自动化。下次任何人改了代码，你的手动测试等于不存在。 |
| "删掉重写的代码太浪费" | 沉没成本谬误。已经投入的时间不影响未来。留着有问题的代码比删掉重写更贵。 |
| "TDD 太教条，务实就是灵活" | "务实"通常意味着"跳过难的测试只写简单的"。TDD 是防止跳过难测试的硬约束。 |
| "后写测试精神上一样" | 顺序改变产出。先写测试→代码天然可测试；后写测试→需要在不可测试的代码上打补丁。这是因果。 |

> 完整的测试反模式手册见：`references/testing-anti-patterns.md`

4. **实现完成后的自检**：
   - 所有计划步骤已完成
   - 所有 TDD 测试通过（绿色）
   - 代码没有明显的错误（语法、类型、import 路径）
   - 如果使用了任务拆解与派发 → 集成验证报告已生成，所有模块通过

5. **集成烟雾测试**（仅当使用了任务拆解与派发时执行）：
   > 集成验证与修正只检查了接口合约合规性（"声明是否匹配"），不检查集成后的系统能否真的协同工作。本步骤填补这个空白。
   - (1) 确认所有子任务产出文件的最终路径，确保它们在同一项目中可互相引用
   - (2) 按数据流方向列出模块调用链（如：请求 → 路由 → 业务逻辑 → 数据库 → 响应）
   - (3) 构造一个跨越所有模块的最小输入（最简单的 happy path 请求）
   - (4) 判断产物类型：**可运行项目**→实际执行端到端流程，记录每个模块的输入/输出；**不可运行产物**（库、配置、文档）→手动追溯调用链，确认每个接口引用处的签名/类型/路径与合约一致
   - 如果烟雾测试失败 → 不要直接进入阶段 4，先定位是哪个模块的问题，回到阶段 3 修复对应子任务
   - 如果烟雾测试通过 → 进入阶段 4 进行完整的真实验证

### 阶段 4：真实验证（核心阶段）

> **这是本 skill 最关键的阶段。绝大多数智能体在这一步偷懒——跑几个单元测试就说"完成了"。这是不可接受的。**

**核心原则：你必须以真实用户的身份，实际使用你构建的东西，观察它的行为，收集真实数据，据此判断是否成功。**

#### 前置条件：所有 TDD 测试通过

> **在进入阶段 4 之前，必须确认阶段 3 中编写的所有 TDD 测试全部通过（绿色）。**
> 如果有任何 TDD 测试失败 → 回到阶段 3，完成 TDD 微循环后再进入阶段 4。

**TDD vs 真实验证的区别**：

| 维度 | TDD（阶段 3 微循环） | 真实验证（阶段 4） |
|------|---------------------|-------------------|
| **测什么** | 代码正确性——函数返回值、类型匹配、边界处理 | 用户体验——实际运行、交互流程、视觉效果 |
| **怎么测** | 自动化测试用例（单元/集成测试） | 启动应用 → 手动操作 → 观察行为 |
| **谁在测** | 代码（断言） | 你（真实用户视角） |
| **关注点** | 逻辑有没有 bug、接口对不对 | 用起来顺不顺、功能完不完整 |
| **失败意味着** | 代码实现有误 | 用户体验不达标（即使所有 TDD 测试通过） |

**核心原则**：TDD 测试通过 ≠ 功能完成。TDD 测的是"代码按预期运行"，真实验证测的是"用户按预期使用"。两者缺一不可。

**禁止行为**：
- ❌ 只运行项目中已有的单元测试就说"通过"
- ❌ 只检查文件是否存在、导出是否正确
- ❌ 写一个简单的测试脚本只测 happy path
- ❌ 用 `curl` 发一个请求看到 200 就认为 API 正常
- ❌ 只看代码逻辑推断"应该没问题"

**必须做到**：

#### 第一步：确定验证场景

根据需求类型选择验证方式：

| 需求类型 | 验证方式 | 不可接受的方式 |
|----------|----------|---------------|
| Web API | 用 curl/Postman 发真实请求，覆盖：正常请求、边界值、异常输入、并发（如果适用）。检查响应体、状态码、响应时间 | 只测一个 200 OK |
| 前端页面 | 实际描述页面行为：打开什么 URL、点击什么按钮、输入什么数据、看到什么结果。如果无法启动浏览器，则描述完整的交互流程并用截图/HTML 验证 | 只检查组件是否渲染 |
| CLI 工具 | 在终端实际运行，传不同参数，检查 stdout/stderr/exit code | 只跑 `--help` |
| 库/模块 | 写一个真实的调用脚本，模拟真实使用场景，检查返回值 | 只检查导出是否存在 |
| 数据处理 | 用真实数据（或接近真实的数据）跑一遍，检查输出 | 只检查函数签名 |
| 配置文件 | 实际加载/解析配置，用该配置启动系统（或模拟加载），验证系统行为符合配置意图 | 只检查 YAML/JSON 语法 |
| 文档/说明书 | 以目标读者的身份通读全文，检查：逻辑是否通顺、步骤是否可跟随、示例是否可运行、术语是否一致 | 只检查拼写和 markdown 语法 |
| 静态资源 | 实际在目标环境中加载（浏览器打开图片、字体渲染、图标显示），检查尺寸、清晰度、兼容性 | 只检查文件是否存在 |
| 代码修改（无独立运行入口） | 找到所有调用方，逐一确认行为未退化；如果可构造最小复现场景则实际运行一次 | 只检查修改的函数本身 |

**混合类型任务**（如 API + 数据库 + 前端，或 CLI + 配置文件 + 文档）：不要只选一种验证方式。每种产出类型独立验证后，再做一次端到端串联验证——模拟用户从头到尾完整使用一次的流程。各类型独立通过但串联失败 = 验证不通过。

#### 第二步：执行验证

1. **准备验证环境**：
   - **可运行项目**（Web 应用、CLI 工具、脚本）：确保项目能正常构建和启动。如果启动失败 → 这就是第一个要修复的问题
   - **不可运行产物**（文档、配置、静态资源、库模块）：确保产物可被目标消费者正确加载/阅读/解析。如果文件格式错误或无法被目标工具打开 → 第一个要修复的问题
2. **happy path 测试**：按预期使用流程走一遍
3. **边界测试**：
   - 空输入 / 空列表 / null / undefined
   - 超大输入 / 超长字符串
   - 特殊字符 / 非 ASCII 字符
   - 并发请求（如适用）
4. **错误路径测试**：
   - 网络失败
   - 权限不足
   - 资源不存在
   - 格式错误
5. **回归检查**：列出所有可能受影响的已有功能/调用方，逐一确认未被破坏。方法：用 Grep 搜索被修改的函数名/类型名/配置键在所有源文件中的引用；检查 import 关系和类型定义的使用者。如果改动涉及共享模块（工具函数、类型定义、配置文件）→ 必须检查所有已知调用方

**回归测试的 TDD 验证模式**（用于 bug 修复附带的回归测试，硬门禁）：
1. 写回归测试 → 运行（确保通过——此时尚未回退修复）
2. **回退修复代码** → 运行回归测试 → **必须失败**
3. 如果回退后测试仍然通过 → 这个测试没有真正覆盖被修复的 bug，重写测试
4. 恢复修复代码 → 运行 → 通过
6. **记录结果**：对每个测试场景，记录输入、期望输出、实际输出（贴出命令原始输出或截图，**禁止**用"符合预期""返回正常"等概括性描述代替证据）、是否通过

#### 第三步：输出验证报告

```
## 验证报告

### 测试环境
- 产物类型：[可运行项目 / 文档 / 配置文件 / 静态资源 / 库模块 / 其他]
- 准备状态：[构建成功/启动成功/文件可读取/格式正确] 或 [失败—具体错误]

### Happy Path
| 场景 | 输入 | 期望 | 实际 | 结果 |
|------|------|------|------|------|
| [场景名] | [输入] | [期望] | [实际] | ✅/❌ |

### 边界测试
| 场景 | 输入 | 期望 | 实际 | 结果 |
|------|------|------|------|------|
| [场景名] | [输入] | [期望] | [实际] | ✅/❌ |

### 错误路径
| 场景 | 输入 | 期望 | 实际 | 结果 |
|------|------|------|------|------|
| [场景名] | [输入] | [期望] | [实际] | ✅/❌ |

### 回归检查
| 已有功能/调用方 | 是否受影响 | 验证方式 | 结果 |
|--------------|-----------|---------|------|
| [功能名] | 是/否 | [验证方式] | ✅/❌ |

### 总体判断
- ✅ 全部通过 → 进入阶段 5（完成）
- ❌ 存在问题 → 进入阶段 5（问题循环）
```

### 阶段 5：判断与循环

**目标**：根据验证结果决定是完成还是回头修复。

```
验证报告 → 全部通过？
              │
              ├── 是 → 🎉 完成。向用户报告结果
              │
              └── 否 → 有问题需要修复
                        │
                        ▼
                  问题严重程度？
                   │
                   ├── 小问题（单文件修改即可修复）
                   │    → 回到阶段 3（执行实现），修复后重新验证
                   │
                   ├── 中等问题（需要重新设计部分逻辑）
                   │    → 回到阶段 2（计划制定），更新计划后重新执行
                   │
                   └── 大问题（需求理解有误 / 方案根本性错误）
                        → 回到阶段 1（需求理解），重新理解需求
```

**严重程度校准示例**（避免主观判断偏差——对照此表决定回退到哪个阶段）：

| 严重程度 | 典型场景 | 回退到 |
|---------|---------|--------|
| **小** | 验证发现一个 API 返回了错误的状态码（404 而非 200），路由配置写错了——改一行即可 | 阶段 3 |
| **小** | 边界测试发现空输入时没有返回默认值，加一个 if 判断即可 | 阶段 3 |
| **中** | 验证发现登录流程整体可走通，但 token 刷新逻辑有设计缺陷——需要改多个函数和文件 | 阶段 2 |
| **中** | 两个模块的接口定义在实现时偏离了计划，需要重新设计交互方式 | 阶段 2 |
| **大** | 验证发现整个功能用起来体验很差——用户真正想要的是批量操作，但你做成了逐条操作 | 阶段 1 |
| **大** | 实现到一半发现技术方案根本行不通（如选型错误），需要换方案重新理解约束 | 阶段 1 |

> **快速判断口诀**：改几行代码就能修 = 小（回阶段3）。要动设计但不改需求 = 中（回阶段2）。做的事和用户想要的不一样 = 大（回阶段1）。

**循环规则**：
- **不允许"差不多就行"**：每一个 ❌ 的验证项都必须被处理
- **不允许降级处理**：不能把 ❌ 改成 ⚠️ 然后跳过
- **最多 3 轮完整循环**：如果 3 轮后仍有问题 → 停下来，向用户报告情况，请求指导。不要无限循环
- **每次循环必须留下记录**：在验证报告中追加"第 N 轮修复"章节，记录修了什么、结果如何
- **循环边界**：详见上方「与其他 skill 的层级关系」中的循环边界说明
- **循环中的修复始终在当前通道内执行**：不要在循环中因某个修复"看起来很简单"而切换回快速通道。快速通道仅用于初始判定，一旦进入标准/完整通道，循环修复也在此通道内执行

**循环记录模板**：

```
## 第 N 轮修复（追加在验证报告末尾）

### 发现的问题
- [问题 1]：验证场景 [场景名] 失败，期望 [X] 实际 [Y]

### 修复内容
- [修改了什么文件，做了什么改动]

### 修复后重新验证
- [场景名]：重新测试 → ✅/❌
```

## 常见错误

| 错误 | 为什么错 | 正确做法 |
|------|---------|---------|
| 看到需求直接写代码 | 没理解就写 = 大概率返工 | 先走阶段 1-2，确认后再动手 |
| 用"跑通了单元测试"代替真实验证 | 单元测试 ≠ 用户使用。测试通过但用户用不了 = 失败 | 阶段 4 的验证方式 |
| 验证发现小问题，手动改一下然后说"修好了"但没重新验证 | 改动可能引入新问题 | 任何修改后必须重新走验证 |
| 计划太粗略（"实现登录功能"就一行） | 没有分步 = 没有检查点 | 拆到可独立验证的粒度 |
| 跳过需求确认直接做 | 你以为的需求不一定是用户要的 | 阶段 1 的复述和确认 |
| 验证只走 happy path | 真实用户不会只用 happy path | 边界测试 + 错误路径 + 阶段 4 第二步 |
| 第 3 轮循环后仍然修不好但不说 | 用户不知道你在死循环 | 3 轮后必须上报，请求指导 |
| 把应该拆解的大任务自己一个人串行做 | 浪费时间和上下文 | 判断是否触发任务拆解与派发 |
| 对微小改动走完整 5 阶段流程 | 改一个变量名要用户审批两次，浪费用户时间 | 走快速通道：一句话确认→改→验证→报告 |

## 危险信号 — 停下重新检查

- 你脑子里出现了"这个简单，直接做就行" → 正是需要走流程的时候
- 你在阶段 4 只跑了 `npm test` 或 `pytest` → 这不是真实验证
- 验证报告全是 ✅ 但你其实没实际运行任何东西 → 你在造假
- 你发现一个问题，手动改了代码，但没回阶段 4 重新验证 → 可能引入新 bug
- 你跳过阶段 2 直接写代码，结果发现写到一半不知道下一步是什么 → 没有计划 = 迷失
- 用户的需求你只能复述原话，不能用自己语言解释 → 你没理解，需要追问
- 阶段 3 中你发现计划不够细，但硬着头皮继续 → 停下来更新计划

## 元使用：审计模式（自动循环——禁止手动等待）

> 审计模式是本 skill 在特定场景下的适配变体，不改变 skill 的核心定位。仅在审计/优化 skill 时使用。

当任务是对 skill 进行审计/优化时，本 skill 的 5 阶段闭环**自动适配为审计循环**：

| 标准阶段 | 审计模式适配 |
|---------|-------------|
| 阶段 1：需求理解 | 明确审计目标（哪个 skill）、审计维度、通过标准 |
| 阶段 2：计划制定 | 编写子智能体的审计 prompt（包含审计维度、输出格式要求） |
| 阶段 3：执行实现 | **派子智能体执行审计**（不是自己审计——作者的盲区只有新鲜视角能发现）。子智能体的审计报告 = 本阶段的产出 |
| 阶段 4：真实验证 | 读取子智能体的审计报告。报告中 P0/P1/P2 各项 = 验证场景。**零发现 = 验证通过**；有任何 P0/P1 = 验证不通过 |
| 阶段 5：判断循环 | 见下方自动循环决策表 |

### ⚠️ 自动循环规则（强制执行，不可跳过）

**核心禁令：修复完一轮后，绝对不允许停下来问用户"还需要继续吗？"或等待用户确认。** 这是最常见的违反行为——修复完就说"第 N 轮完成，还需要继续吗？"→ 这是错误的。正确做法是修复完立即自己判断并进入下一轮。

**自动循环决策表**（阶段 5 完成后立即对照此表，无需用户输入）：

| 本轮结果 | 下一动作 | 何时停止 |
|---------|---------|---------|
| 有 P0 | 立即修复 → 自动回到阶段 3 重审 | — |
| 无 P0，有 P1 | 立即修复 → 自动回到阶段 3 重审 | 连续 3 轮 P1 递减且最后一轮 ≤2 个 P1 |
| 无 P0/P1，仅 P2 | 评估是否值得再修一轮 | 连续 3 轮全 P2 且递减 → 停止并报告 |
| 零发现 | 停止并报告 ✅ | — |

**停止条件**（满足任一条即停止，向用户报告最终结果）：
1. 审计报告零发现（P0=P1=P2=0）
2. 连续 3 轮递减且仅剩 P2（已无实质问题）
3. 已达 3 轮完整循环——无论结果如何都停止，向用户报告进展

**自动循环执行流程**：
```
阶段 5 判断 → 对照决策表
  ├─ 需要继续 → 立即执行修复（不等待用户）
  │              → 修复完成后立即回到阶段 3（派子智能体重审）
  │              → 子智能体返回报告后进入阶段 4
  │              → 阶段 4 读取报告后进入阶段 5
  │              → 重复判断...
  └─ 满足停止条件 → 向用户报告最终结果
```

**违规自检**（每次阶段 5 结束时问自己）：
- [ ] 我是否在等待用户说"继续"？→ 如果是，违规！立即对照决策表自动执行
- [ ] 我是否在问用户"还需要继续吗？" → 如果是，违规！自己判断
- [ ] 本轮有 P0/P1 但我没有自动开始修复？→ 如果是，违规！立即修复
