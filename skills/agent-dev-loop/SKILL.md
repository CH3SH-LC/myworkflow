## 触发

- **必须触发**：创建/修改/删除代码或文件、加功能、重构、新增、改写；对话中途随口提出的产出需求；"继续/接着做"（本 skill 已触发且任务未完成时）。
- **不触发**：纯问答、文件阅读/搜索、纯格式化/注释、闲聊不写代码、独立 bug 修复（走「Bug修复与验证」）。

## 复杂度门控

先判断复杂度，再决定走哪条通道：

| 复杂度 | 判定 | 通道 |
|--------|------|------|
| 微小 | 单行/单表达式改动（变量名/拼写/日志/常量），用户明确知道改什么 | 快速通道 |
| 简单 | 单文件内修改，已知原因的小改动 | 标准通道：完整 5 阶段流程，阶段1-2 可口头确认但流程不省 |
| 跨文件/标准 | 跨文件修改、新增完整功能、重构模块 | 完整流程 + **必须**派发子智能体（task-dispatch） |
| 架构级 | ≥2 独立模块、架构变更 | 完整流程 + 拆解派发 |

- 任何阶段可升降级通道；循环中的修复始终在当前通道内执行，不因单次修复简单而切回快速通道。
- 用户说"直接做"：阶段1-2可精简为口头确认，**阶段4-5不可跳过**。

## 目标

每次开发走完整闭环：**需求理解 → 计划制定 → 执行实现 → 真实验证 → 问题循环**。禁止跳步、禁止伪验证（仅跑单测）、禁止发现问题后不回头修复。

## 前置强制步骤

1. 识别任务类型（新增/修复/重构/审计 skill——审计走文末「审计模式」）。
2. 读取 CLAUDE.md 与相关代码，了解技术栈与约定。
3. 需求模糊 → 进入阶段1必须追问清楚，不要猜。

## 快速通道（微小任务）

1. **一句话确认**：复述要改什么（如"把 MAX_RETRY 从 3 改成 5"），用户确认即可。
2. **直接修改**：超范围（改多个文件/改接口）→ 立即升级标准通道，从阶段1重来。
3. **快速验证**：语法正确、逻辑一致、未破坏调用方；运行时行为则实际运行确认。
4. **报告完成**。

**验证不可跳过。**

## 标准/完整通道

**主线**：阶段1 需求理解 → 阶段2 计划制定 → 阶段3 执行实现 → 阶段4 真实验证 → 阶段5 判断与循环（验证不通过则回退修复）。

### 阶段1：需求理解

写任何代码之前，确保完全理解需求。按复杂度定深度（简单口头复述确认；中等用模板；复杂优先 `req-clarify`）。

1. **读取上下文**：CLAUDE.md、相关代码、配置。
2. **复述需求**：核心目标、输入/输出、涉及文件、约束条件。
3. **识别模糊点**，存在以下任一情况用 AskUserQuestion 追问（**最多 3 轮，每次一问**）：技术方案有分歧、边界条件不明、需求内在矛盾、关键文件/接口位置未知。
4. **复杂或意图不明** → 调用 `Skill("myworkflow:req-clarify")` 深度澄清（硬门禁+多方案对比）。不要自己猜——澄清成本远低于返工。
5. **输出需求确认**并等用户确认后再进阶段2。

需求确认模板：
```
## 需求确认
核心目标：[一句话]
输入：[数据从哪来]   输出：[最终产出]
涉及范围：[哪些文件/模块]
约束条件：[技术栈/性能/兼容性]
边界条件：[空输入/异常/大数据量如何处理]
以上理解是否正确？
```

### 阶段2：计划制定

1. 按复杂度定深度：简单→口头计划；中等→用模板；复杂→先 `req-clarify` 多方案对比，计划中标注"阶段3用拆解派发"。
2. 计划必须包含：**分步执行清单**（每步做什么/产出什么）、**依赖关系**、**接口定义**（多模块时）、**验证方案**（写清如何以用户身份验证，不能只写"跑测试"）、**风险点**。
3. 判断是否拆解派发：**跨文件任务，或**≥2 独立模块且接口可明确定义 → 必须标注"阶段3用任务拆解与派发"（派发子智能体）；仅单文件内小改动 → 标注"直接实现"。
4. **展示计划并获用户批准**——计划是用户与你的契约，不可跳过。

计划模板（简单任务可精简）：
```
## 实施计划
### 步骤清单
1. [步骤] → 产出: [文件] — [简述]
### 依赖关系
- 步骤2 依赖步骤1 的 [产出]
### 验证方案
- [以用户身份的具体验证步骤，如"打开浏览器访问 /login 用 test@x.com 登录，检查跳转"]
### 风险点
- [风险] → 应对: [措施]
```

### 阶段3：执行实现

1. **按计划执行**：标注拆解 → 调 `Skill("myworkflow:task-dispatch")` 派发并行子任务，完成后调 `Skill("myworkflow:integration-verify")`；直接实现 → 逐步执行。
2. **约束**：严格按计划，不擅自加计划外功能（scope creep）；每完成一步对照验证方案检查；遇到计划未覆盖的情况 → 停下更新计划、获用户确认后再继续。
3. **TDD 微循环**（微观正确性，≠阶段4宏观真实验证）：
   - **RED**：先写失败的测试（覆盖正常/边界/错误路径），运行必须见红——测试直接通过说明没测到东西；
   - **GREEN**：写最小实现让测试通过，不过度设计；
   - **REFACTOR**：保持绿色下重构（抽重复、理命名），不加新功能。
   - 适用范围：新增/修改逻辑**必须 TDD**；配置/文档/静态资源跳过；副作用任务（迁移/部署脚本）写验证清单替代。
4. **实现完成自检**：计划步骤全完成、TDD 全绿、无语法/类型/import 错误。
5. **集成烟雾测试**（仅拆解派发时）：按数据流方向列模块调用链，构造跨全模块的最小 happy path 输入——可运行项目则实际端到端执行，不可运行产物则手动追溯调用链核对接口一致；失败 → 定位模块回阶段3修复，通过 → 进阶段4。

### 阶段4：真实验证（核心阶段）

> 最关键的阶段。绝大多数智能体在这里偷懒——跑几个单元测试就说"完成了"，不可接受。**必须当真实用户实际使用你构建的东西。**

1. **硬门禁**：先调用 `Skill("myworkflow:real-world-verify")`，传入：项目根目录/类型、变更概要、启动命令、测试命令、关键用户路径（≥5条）。
2. **前置条件**：阶段3所有 TDD 测试全绿；有失败则回阶段3补完再进阶段4。
3. real-world-verify 覆盖：环境就绪→全量测试→用户路径验证→异常边界→回归→验证报告。返回 ❌ → 进阶段5；返回 ✅ → 完成。
4. **核心原则：TDD 全过 ≠ 功能完成。** TDD 测"代码按预期运行"，真实验证测"用户按预期使用"，两者缺一不可。

### 阶段5：判断与循环

```
验证全过 → 完成
有 ❌ → 按严重程度回退：
  小（改几行可修）→ 回阶段3，修复后重新验证
  中（动设计不改需求）→ 回阶段2，更新计划
  大（做的事≠用户想要的 / 方案根本性错）→ 回阶段1，重新理解需求
```

循环规则：
- 每个 ❌ 都必须处理，不允许"差不多就行"，不允许把 ❌ 降级成 ⚠️ 跳过。
- **最多 3 轮完整循环**，3 轮后仍有问题 → 停下向用户报告、请求指导。
- 每轮在验证报告末尾追加「第 N 轮修复」记录（发现的问题/修复内容/重验结果）。

### 后置步骤

1. 确认验证报告已产出（对话中即可）、所有 ❌ 已修复或已上报。
2. 向用户报告最终结果。
3. 如需提交远程（commit/PR/merge）→ 调用 `Skill("myworkflow:github-collab")`。

### 完成标志

- [ ] 需求已确认（简单=口头；中/复杂=用户明确"对"）
- [ ] 计划已获批准
- [ ] 代码已按计划产出（含集成烟雾测试，如适用）
- [ ] 阶段4真实验证完成（happy path + 边界 + 错误路径 + 回归）
- [ ] 所有 ❌ 已循环修复（≤3轮）
- [ ] 最终结果已报告用户

## 元使用：审计模式

任务为审计/优化 skill 时，5 阶段自动适配为审计循环：
- 阶段1：明确审计目标（哪个 skill）、审计维度、通过标准
- 阶段2：编写子智能体的审计 prompt（维度+输出格式）
- 阶段3：**派子智能体审计**（不自己审——作者盲区只有新鲜视角能发现），其报告=本阶段产出
- 阶段4：读报告，P0/P1 各项=验证场景，零发现=通过，有 P0/P1=不通过
- 阶段5：自动循环决策

**自动循环（强制，不可等待用户）**：修复完一轮**禁止**停下来问"还需要继续吗"——立即对照下表自动进入下一轮：

| 本轮结果 | 下一动作 | 何时停止 |
|---------|---------|---------|
| 有 P0 | 立即修复 → 回阶段3重审 | — |
| 无 P0，有 P1 | 立即修复 → 回阶段3重审 | — |
| 仅 P2 | 立即修复 → 回阶段3重审（P2 也是漏洞，必须修） | — |
| 零发现 | 停止并报告 ✅ | — |

停止条件：零发现（P0=P1=P2 全为 0）/ 已达 3 轮上限。**P0/P1/P2 全部必须修复，不允许留任何漏洞出循环。**
