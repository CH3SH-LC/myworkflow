## 核心流程：判定文件夹类型 → 建六文档体系 → 指派单写者

**何时加载**：用户要初始化项目 / 建立文档体系 / 建 AGENTS.md / 搭项目骨架，或进入既无 AGENTS.md 也无 CLAUDE.md 且将长期开发的文件夹。**不加载**：已有规则文件与 `docs/` 的日常维护（走 project-maintain）、单文件脚本、临时工具、只读浏览、纯问答。

**硬步骤**
1. **判定类型**：按仓库证据数信号（`.git`/构建清单/测试/CI/多源码目录），≥2 即定性 → 判据：两组都 ≥2 且查不到证据才 `ask_user_question`，不代选。
2. **分叉落地**：常规文件夹只新建或追加规则文件三节，**绝不建 `docs/`**；项目文件夹先 glob 扫现状、确认根目录与可量化 GOAL → 判据：GOAL 拿不到数字/阈值就留空标「待用户确认」，不编造。
3. **生成文档**：顺序 `AGENTS.md → STRUCTURE.md → docs/GOAL、PROGRESS、STATE → design/information/research/other` → 判据：六个文档各只回答一个问题，模板占位符全部替换。
4. **建两个 index.json**：design 与 information 各一份，点号四态封闭枚举、evidence 为空不得置「待验收」→ 判据：可解析、file 能在磁盘定位。
5. **指派单写者**：`STATE.md`、两个 `index.json`、PROGRESS 版本号行只由一人写，其余人提变更请求 → 判据：报告写明 owner 与请求路径。

**优先级与红线**：同目录 `AGENTS.md` 优先于 `CLAUDE.md`；既有 `CLAUDE.md` 原样保留，末尾追加一行指针。写入白名单仅 `AGENTS.md`/`CLAUDE.md`/`STRUCTURE.md`/`docs/**`；不搬迁、不删除既有文件。

**完成判据**：六文档与两个 index 齐备可解析、单写者已公布、零搬迁、验证清单 8 项全过；证据=文件回读 + index 解析输出 + 白名单自查。

# 项目文档初始化

## 触发

- **必须触发**：用户要求初始化项目 / 建立文档体系 / 创建或补建规则文件 / 搭建项目骨架；进入一个既没有 `AGENTS.md` 也没有 `CLAUDE.md` 的文件夹，并准备在这里长期开发。
- **隐式触发**：规则文件不存在，但扫描发现 ≥5 个源文件分布在 ≥2 个目录，且用户本轮明确要在该处持续开发 → 主动建议初始化，不默默等待。
- **不触发**：已有规则文件与 `docs/` 体系的项目（走 skill(name="myworkflow-project-maintain")）、单文件脚本、临时小工具、只读浏览、纯问答。

## 目标

一次把文档体系建对。目标不是「生成几个文件」，而是让后续每个智能体都能**按问题查表定位**，不必判断「这条内容该写哪」。

### 规则与地图（顶层，位于项目根）

| 文件 | 回答 | 谁可写 |
|------|------|--------|
| `AGENTS.md`（DSH 原生，首选） | **怎么工作**（规则） | 单写者 / leader |
| `CLAUDE.md`（旧项目兼容） | 同上，同目录优先级低于 `AGENTS.md` | 单写者 / leader |
| `STRUCTURE.md` | **东西在哪**（地图） | 单写者 |

### 六个文档各回答一个问题

| 文件 / 目录 | 回答 | 内容性质 | 谁可写 |
|------|------|---------|--------|
| `docs/GOAL.md` | **为什么做**（长期目标 + 量化验收） | 用户所有 | **仅用户批准可改**，智能体只能提议 |
| `docs/design/` | **做什么**（需求与设计） | 需求 | 该交付物的 owner |
| `docs/PROGRESS.md` | **做了什么**（追加式） | 历史 | owner 追加；版本号行归单写者 |
| `docs/STATE.md` | **现在在哪**（刷新式） | 快照 | **单写者**（见下节） |
| `docs/information/` | **学到了什么**（经验条目） | 经验 | 条目 owner |
| `docs/research/` | **外部世界怎么说** | 外部材料 | 调研 owner |

> `docs/` 是项目开发过程的文档区，不是文件收容所。旧体系的 `PROGRESS-LITE.md` 在新体系中**取消**，职能由 `docs/PROGRESS.md` 的条目区继承。

## 规则文件：AGENTS.md 与 CLAUDE.md 的优先级

`AGENTS.md` 是 DSH 原生规则文件；`CLAUDE.md` 仅为**兼容旧项目**而保留（含项目里已有的 `CLAUDE.md` 与手工维护的 `CLAUDE.md`）。

写入与识别规则：

1. **首选目标**是 `<root>/AGENTS.md`；只有项目明确只用 `CLAUDE.md` 时才写 `CLAUDE.md`。
2. 项目里**已有** `CLAUDE.md` → **保留原样**（可读、可作参考），不删不改既有内容；新建 `AGENTS.md` 时在 `CLAUDE.md` 末尾**追加一行**指向 `AGENTS.md`（`> 本项目的现行规则以同目录 AGENTS.md 为准`）。
3. **同目录并存**：`AGENTS.md` 优先于 `CLAUDE.md`。两者冲突时按 `AGENTS.md` 执行。
4. **不同目录**：就近目录优先。读取顺序是从当前工作文件所在目录逐级向上找，取**最近**的一份规则文件；同级内 `AGENTS.md` 优先于 `CLAUDE.md`。
5. 例：在 `<root>/src/api/` 工作时，依次看 `src/api/AGENTS.md` → `src/api/CLAUDE.md` → `src/AGENTS.md` → `src/CLAUDE.md` → `<root>/AGENTS.md` → `<root>/CLAUDE.md`，命中即停。
6. 报告中必须写明：本轮**新建/沿用了哪个规则文件**，以及项目里是否存在被兼容的 `CLAUDE.md`。

## 单写者：STATE 与 index

**单写者文件清单**（同一时刻只允许一个 owner 写入）：

- `docs/STATE.md`
- `docs/design/index.json`
- `docs/information/index.json`
- `docs/PROGRESS.md` 头部的**版本号行**（版本号单一权威源，其他文件只能引用它）

**怎么指派**：

1. leader 用 `team_mission_assign` 把「状态维护」委托给模块成员，**由该成员自己用 `team_plan_submit` 提交**（`writeScopes` 写清上面四个路径）；
2. owner 默认由 leader 兼任，或指派给**掌握全局上下文**的那位成员（没有该成员时先 `team_member_create`）；改派时新提交一条工作项并说明上下文来源，不让无上下文的人接管该交付物。
3. 该 owner 负责：把各成员提交的变更请求核实后写入、维护 index 与 STATE 的一致性、收尾修复。**同一交付物的收尾修复由原 owner 完成**，不换一个没有上下文的接手人。
4. 其他成员**只能提交变更请求**，不得直接写这四个位置。请求一条消息说清：目标文件 / 点号或条目号 / 请求的变更 / 证据 / 依据版本；单写者核实后写入并回执。
5. 状态冲突时以 index 为准修正正文表格；版本号冲突以代码清单 `version` 为准并在 `STATE.md` 列出差异。

## 横向交付合约（团队协作时）

**按可独立交付的产物切分**，不按文件、不按阶段切分。文档体系里的交付物单元是：一份 design 主题文件 + 它的 index 条目、一份 information 主题文件 + 它的 index 条目、一个 research 证据包、`AGENTS.md` 定稿、`STRUCTURE.md` 地图、STATE/PROGRESS 维护。

- 每份交付物由**一个 owner 端到端负责**：调查 → 写入 → 自检 → 修复 → 验收。
- **拒绝同一交付物的阶段接力**：不出现「背景调查 → 设计 → 检查」，也不出现「计划 → 编码 → 审查」由三个人分段接管。同一份交付物的上下文必须留在同一个 owner 手里。
- 横向重排建议：

| 错误切分（纵向接力） | 横向重排（按交付物） |
|------|------|
| A 只查资料 → B 只写文档 → C 只做检查 | 一个 owner 负责一份 design/信息/调研交付物，自查后交验收 |
| 一人统一改 `docs/` 全部文件 | 每份主题文件归其 owner；STATE / index 归单写者 |
| 先全员铺 `docs/design/` 再统一补 index | 每份 design 与它的 index 条目由同一 owner 一次做完，单写者合并 |

### 事件驱动滚动补位

- 任一项**结算就立即补位**，不等同批其它任务；无全批屏障、无整层等待（不要「等这一层全部完成再进下一层」）。
- 慢任务不阻塞其它 ready 项：阻塞发生时先做其它 ready 的交付物。
- **未 ready 不派发**；容量满时**拒绝并保持 ready**（`CAPACITY_FULL`），不排队空等，也不用一次性旁路绕开上限。
- 依赖**只允许存在于不同交付物之间**，并要求写明 `version` + `requires`（`published-interface` 或 `verified-result`）；同一交付物内部不许拆成依赖链。
- 全局集成由 **leader 与相关 owner 共同负责**。

### 超时与阻塞

- 超时先判断**进展与可恢复性**；「状态未知 / 暂停」与「真正失败」严格分开——**超时不等于失败**。
- 不得写死「试三次就结束」，也不得无预算地对同一失败无限重试；权限拒绝不可绕过。
- **阻塞处理顺序（五步）**：
  1. 记录确切失败、已尝试的动作、影响范围、仍然可做的部分。
  2. 查已装服务、源码、现成工具、当前权限——先确认手上有什么。
  3. 能写适配器 / 接口 / 本地桥接就补齐。
  4. 局部阻塞先做其它 ready 项，并把 blocker 精确挂到受影响的交付物上。
  5. 确实需要外部账号、人工决策或无法获得的资源时，才标记 `needs_user`，并给出**已尝试路径与最小下一步**。

### 用户授权与提问

- 用户已授权任务范围内的**可逆开发不重复询问**（写 `docs/**`、追加日志、生成模板都属可逆）。
- 审批与扩权只有用户入口，模型没有等价工具。
- **只在真正改变决策、且项目里查不到**时才用 ask_user_question；能从仓库证据读出来的，不问。
- 不可逆操作（删除、搬迁、大段覆盖既有内容）先说明影响，取得用户明确授权后再做。

### 证据诚实与结果分层

- 区分「已核实 / 有来源」与「推测 / 未核实」，不夸大，绝不无证据声称「验证通过」。
- 结果分层：简短结论 + 可核查的 evidence / artifact 引用进 parent；原始材料留在文件或子会话里。
- 摘要必须含：来源、版本、遗漏、不确定性、未完成项。

## 防破坏护栏（五条，任何写入前先读一遍）

1. **写入白名单**：只允许 write/edit `<root>/AGENTS.md`、`<root>/CLAUDE.md`、`<root>/STRUCTURE.md`、`<root>/docs/**`（`<root>` = 本轮确认的文件夹根）。白名单之外的文件一律不动；确需改动先向用户说明原因。
2. **docs/ 准入**：只放本项目开发过程产生的文档。判断是一个单点事实核查：**「这份文档是这次开发中写出来的吗？不是 → 原地不动」**。禁止把项目里既有的资料、素材、参考文档搬进 `docs/`。
3. **扫描目的限定**：扫描只为「看清现状」，**扫描结果不得作为搬迁依据**。任何移动先列逐项计划（源路径 → 目标路径 → 原因）。
4. **迁移只做「复制 + 归档」，不删除**；根目录旧文件默认原样保留。删除是不可逆操作，必须逐文件取得用户明确授权。
5. **覆盖保护**：写入前目标已存在必须先 read；优先用 edit 追加而不是整文件覆盖；确需改写既有内容时，在完成报告里列出改了哪些行、原值是什么。

## 主线（六步，按顺序执行，不是审批关卡）

```
步骤0 判定文件夹类型 ─[常规]→ 步骤1 只登记规则文件 → 报告
                     ─[项目]→ 步骤2 收集信息 + 确认 GOAL → 步骤3 生成文件 → 步骤4 两个 index.json → 步骤5 验证与报告
```

### 步骤 0：判定「项目文件夹 vs 常规文件夹」（任何写入之前）

先用**仓库证据**自行判定，判定依据要记录在报告里；判定不消耗用户提问额度。

| 项目信号（≥2 即偏项目） | 常规信号（≥2 即偏常规） |
|------|------|
| 有 `.git/` 且已有提交历史 | 以资料/文档/素材为主（pdf/docx/xlsx/图片/视频占比高） |
| 有依赖或构建清单：`package.json`/`pyproject.toml`/`requirements.txt`/`go.mod`/`Cargo.toml` | 无构建清单、无测试、无 CI |
| 有测试目录或测试框架配置（`tests/`、`*.test.*`、`pytest.ini`） | 文件命名多为日期/主题/编号，无代码组织痕迹 |
| 有 CI 配置（`.github/workflows/`、`.gitlab-ci.yml`） | 已被编号分类体系管理（如 `D:\CH3SH\1.xxx / 2.xxx` 树） |
| 有 ≥2 个源码目录（`src/` 之外还有实质代码目录） | 用户从未声明开发目标，只是「往这里放东西」 |
| 用户已声明要「做出什么」并给出验收标准 | 存在大量与本次无关的历史文件 |

- 项目信号 ≥2 → 项目文件夹；常规信号 ≥2 → 常规文件夹。
- 单侧命中即可推进；**只有两组都 ≥2、且项目里确实查不到能定性的证据时**，才用 ask_user_question 把两列信号逐条摆出来让用户拍板，不代选。

### 步骤 1：常规文件夹分支（只登记规则文件）

> **绝对禁止**：在常规文件夹里创建 `docs/`、GOAL.md、PROGRESS.md、design/ 等任何项目文档体系。创建 = 毁坏用户的文件夹。

- 规则文件**不存在** → 新建，内容仅三节：`## 本目录性质（常规文件夹）`、`## 目录工作约定`、`## 变更记录`。
- 规则文件**已存在** → 只允许在文件末尾**追加**这三节，**禁止改写、重排、删除任何既有内容**。若同名小节已存在，只在 `## 变更记录` 下追加一行（日期 + 做了什么），不重复追加整节。
- 已存在的 `CLAUDE.md` 与 `STRUCTURE.md` 保留原样（可读、可作参考，但不改不删）；新建 `AGENTS.md` 时在 `CLAUDE.md` 末尾追加一行指针。
- 报告一句话：判定为常规文件夹，只登记规则文件，未创建 `docs/`，未移动任何文件。

### 步骤 2：项目文件夹 — 收集信息与确认 GOAL

1. **确认项目根**：向上查找 `.git` / 构建清单；不明确就问用户，别猜。
2. **扫描现状**（glob + pwsh 目录树）：为 STRUCTURE.md 与信号判定取事实，**不作搬迁依据**。
3. **提取事实**：`package.json`（名称/技术栈/version）、`README.md`（定位）、`.git/config`、`.env`（端口）。
4. **确认 GOAL**：问清「最终验收是什么」，必须拿到**可量化判据**（数字 / 阈值 / 分母 / 什么算不达标）。用户答不上来就逐条提议让用户选，**不要替用户写死目标**；宁可留空并标「待用户确认」，也不要编造。

### 步骤 3：生成文件（模板）

生成顺序：`AGENTS.md → STRUCTURE.md → docs/GOAL.md → docs/PROGRESS.md → docs/STATE.md → docs/design/ → docs/information/ → docs/research/ → docs/other/`。

**3.1 `<root>/AGENTS.md`**

```markdown
# [项目名称] 工作区指令
> 本文件是 DSH 原生规则文件；同目录若同时存在 CLAUDE.md，以本文件为准。
## 每次工作的固定流程
**每次新会话开始时，先调用 skill(name="myworkflow-project-maintain")。** 它引导你：
1. 读本文件（规则）→ 2. 读 `docs/STATE.md`（现在在哪）→ 3. 读 `docs/PROGRESS.md` 条目区（最近做了什么）
4. 读 `docs/GOAL.md` 与 `docs/design/index.json`（要做什么、做到哪）→ 5. 工作完成后回到该 skill 的完成时流程，同步文档
> 不要跳过。文档体系的价值取决于每一次工作都留下记录。
## 当前项目
正在开发 **[项目名称]**（一句话定位）。为什么做见 `docs/GOAL.md`。
## 工作规则
1. **先设计后开发**：改动只做 `docs/design/` 中已写明的点；新增功能 / 行为变更 / 新模块必须先生成 design，没有 design 不动手。bug 修复 / 重构 / 配置 / 文档 / 格式化允许豁免，但须在 PROGRESS 条目标注「本次无 design（小场景豁免）」；判断不清时默认按「需要 design」处理。
2. **验收口径**：只有用户明确说「确认没问题 / 可以了 / 通过了 / 我验收通过」才能把点置「完成」；**用户没说话 = 还没验收**，只能停在「待验收」。
3. **文档同步**：每次变更后同步 `docs/PROGRESS.md`、`docs/STATE.md`、`docs/design/index.json`，必要时 `STRUCTURE.md`。
4. **单写者**：`docs/STATE.md`、两个 `index.json`、PROGRESS 的版本号行只有状态 owner 可写；其他人提交变更请求。
5. **不许搬运**：`docs/` 只放本项目开发过程产生的文档；项目里既有的资料、素材、参考文档原地不动。
## 工作区目录结构
[实际目录树，逐行注释用途；细节见 STRUCTURE.md]
## 目录结构更新规则
仅当根目录（顶层）新增 / 删除 / 重命名目录或文件、新增子项目、核心规则变化时更新本文件目录树；子目录内文件增删由 STRUCTURE.md 管理。
```

**适配要点**：占位符必须替换为实际结构；小型项目（<20 文件）保持简洁；特殊规则（如「改 `.ts` 后必须 build」）追加在「工作规则」之后；**「每次工作的固定流程」一节不可删除**。

**若项目已有 `CLAUDE.md`**：不动其既有内容，只在末尾追加 `> 现行规则以同目录 AGENTS.md 为准`；只在项目明确只用 `CLAUDE.md` 时，才把上面的模板写进 `CLAUDE.md`。

**3.2 `<root>/STRUCTURE.md`**（保留在项目根目录，不在 docs/ 下）

```markdown
# [项目名称] 项目结构
> 最后更新：YYYY-MM-DD　新增、删除、重命名文件或目录时必须同步更新本文件。
---
## 顶层结构
[项目根]/

├── CLAUDE.md              # 旧项目兼容规则（同目录优先级低于 AGENTS.md；无则不存在）
├── STRUCTURE.md           # 本文件（东西在哪）
├── src/                   # 源代码
└── docs/                  # 开发文档区：GOAL.md 为什么做（仅用户批准可改）｜STATE.md 现在在哪（刷新式，单写者）
                           #   PROGRESS.md 做了什么（条目区 + 版本记录区）｜design/ 做什么（含 index.json）｜

## [每个主要子目录的结构]
src/  →  index.ts 入口 ／ components/ UI 组件 ／ utils/ 工具函数
## 当前核心事实
- 运行时：Node.js 22；包管理器：pnpm；测试框架：Vitest；默认端口：3000
```

**关键原则**：按重要性分层（顶层 → 主要子目录 → 更深层）；注释写**用途**不照搬文件名；与实际文件系统 100% 一致。「当前核心事实」从配置提取（`.nvmrc`/`.python-version`/`go.mod`/`package.json engines`、lock 文件、依赖中的测试框架、`.env` 的 PORT），**不编造**。

**3.4 `<root>/docs/PROGRESS.md`**（双层 + 版本号）

```markdown
# [项目名称] 开发进度
> **版本：0.1.0**（本行为版本号单一权威源，其他文件只能引用它；由状态 owner 维护）
> 双层结构：**条目区**（做了什么，最新在最上，每条一行，带版本号）+ **版本记录区**（每版本一段：问题/根因/修改/验证）
> 版本号是两层的 join key。归档：条目区触顶后最老内容移入 `docs/other/progress-archive-YYYY.md`。
---
## 条目
## YYYY-MM-DD
- [New Feature][v0.1.0] 一句话做了什么（严格一行，不写「为什么」）
- [Debug][v0.1.0] ……
---
## 版本记录
### v0.1.0 — YYYY-MM-DD
**问题 / 动机**：（背景与意图）
**根因**：（仅 bug 修复需要：为什么发生、为什么之前没发现、为什么这样修）
**修改**：`路径/文件` — 改了什么；对应 design 点号 `design-01-P1`
**验证**：（真实跑到的命令与结果，不写「已测试」）
```

标签：`[New Feature]` 新增 / `[Debug]` 修复 / `[Change]` 重构优化 / `[Build]` 构建部署；同日多条按此顺序排。

**版本号 a.b.c**（初始值：空体系 `0.0.0`；已有可运行产物 `0.1.0`；有 `package.json` 等代码清单的 `version` 时以代码清单为准）：

| 位 | 语义 | 递增条件 | 谁定 |
|----|------|---------|--------|
| a | 大版本 | `0` = 未成熟测试期；正式发布 0→1；此后仅完整项目的大变动 | **用户** |
| b | 小版本 | 新增功能 / 功能增强 / 新增模块 | owner 自动 |
| c | debug | 修 bug、重构、性能微调、文档配置调整 | owner 自动 |

> 一次会话至多递增一次（取最高语义）；不产生版本的工作不递增；与代码清单 `version` 不一致时，在版本记录区显式记一行并在 `STATE.md` 列出。递增与写入由状态单写者执行（日常走 skill(name="myworkflow-project-maintain")）。

**3.6 `<root>/docs/design/design-01-<主题>.md`** — 是交付物单元（正文 + 它的 index 条目同一 owner 一次做完）。四节**背景 / 需求 / 验收标准 / 点清单**必须齐全并写到可执行；内容明显偏薄（例如不足 20 行）通常说明需求没写清，而不是「项目小」。

```markdown
# design-01：<主题>
> 状态：进行中 / 已完成 / 已废弃　创建：YYYY-MM-DD　最后更新：YYYY-MM-DD
> 上游：`docs/GOAL.md`　本文件只管「做什么」，不管「怎么写」。
## 背景
[为什么做这一块：对应 GOAL 的哪条判据、当前缺口是什么]
## 需求
- 需求 1：…
## 验收标准
- [可验证判据：什么算做成、怎么验、什么条件下算不达标]
## 点清单
| 点号 | 内容 | 状态 | 证据 | 备注 |
|------|------|------|------|------|
| design-01-P1 | … | 未开发 | | |
| design-01-P2 | … | 未开发 | | |
> 状态为四态封闭枚举：`未开发` / `阻塞` / `待验收` / `完成`。**「开发中」不写进本表**，它由 `docs/STATE.md` 承载。
> 权威索引是 `docs/design/index.json`；本表的点号与状态必须与 index 完全一致，冲突时按 index 修正本表。
## 不做的事
- [明确排除项，防止范围漂移]
```

> **design 内容禁令**：只放需求 / 功能 / 设计。**禁止写具体代码方案**——不写函数签名、数据结构、算法步骤、目录布局。design 是「要什么」，不是「怎么实现」。

**3.8 `<root>/docs/research/`、`<root>/docs/other/`**

- `research/`：调研产生的证据包（evidence-package），**不建 index.json**，靠日期 + slug 文件名检索；允许按调研要点建子文件夹。
- `other/`：兜底，**严格准入**——只有确实不属于上述任何一类、且**确实是本次开发产生的**文档才放这里；准入提问仍是那一句「这份文档是这次开发中写出来的吗？不是 → 原地不动」。归档文件命名为 `progress-archive-YYYY.md`。

### 步骤 4：两个 index.json（schema 与示例）

> **单写者**：两个 `index.json` 建成后只由状态 owner 写入；本步骤负责建出初始文件，后续状态变更一律走变更请求。

**`docs/design/index.json`** 字段：根级 `schema_version`（固定 1）/ `project` / `updated` / `status_enum`（固定四态）；`designs[]` 每项含 `id`（与文件名前缀一致）、`file`（相对 `docs/design/` 的文件名，必须能在磁盘定位）、`title`、`created`、`updated`、`goal_check`（GOAL 回望那一行的原文）；`points[]` 每项含 `id`（如 `design-01-P1`，全局唯一）、`design`、`file`（必须等于其 `designs[].file`）、`title`、`status`（四态枚举之一）、`evidence`（可指认的证据：验证输出、命令与结果、截图路径）、`updated`、`note`（如「历史文档补登记」）。

```json
{
  "schema_version": 1, "project": "CoCo", "updated": "2026-09-15",
  "status_enum": ["未开发", "阻塞", "待验收", "完成"],
  "designs": [
    { "id": "design-01", "file": "design-01-用户登录.md", "title": "用户登录", "created": "2026-09-15", "updated": "2026-09-15", "goal_check": "GOAL 回望：本 design 与 GOAL 的「登录流程可用」一致" }
  ],
  "points": [
    { "id": "design-01-P1", "design": "design-01", "file": "design-01-用户登录.md", "title": "支持手机号 + 验证码登录", "status": "待验收", "evidence": "pnpm vitest run tests/login.test.ts → 8 passed；手工走通验证码登录进入首页", "updated": "2026-09-15", "note": "" },

    { "id": "design-01-P2", "design": "design-01", "file": "design-01-用户登录.md", "title": "记住登录状态 7 天", "status": "未开发", "evidence": "", "updated": "2026-09-15", "note": "" }
  ]
}
```

**`docs/information/index.json`** 字段：根级同上（以 `entries[]` 取代 `designs`/`points`）；`entries[]` 每项含 `id`（如 `info-001`，与正文条目号一致）、`file`（相对 `docs/information/`）、`title`（一句话结论）、`tags`（标签数组，用于筛选）、`summary`（2–3 句展开，够判断「要不要点开」）、`created`、`updated`。

```json
{
  "schema_version": 1, "project": "CoCo", "updated": "2026-09-15",
  "entries": [
    { "id": "info-001", "file": "information-01-构建与测试.md", "title": "构建前必须先跑代码生成，否则 TS 类型缺失", "tags": ["构建", "测试"], "summary": "直接 pnpm build 会因缺失生成代码报类型错误；正确顺序是先 pnpm gen 再 pnpm build。", "created": "2026-09-15", "updated": "2026-09-15" }
  ]
}
```

**状态判定四条硬规则**（建库即生效，后续由状态单写者执行）：

> 未开发 / 阻塞 / 待验收 / 完成 四态封闭枚举，**「开发中」不写进 index**——它由 `docs/STATE.md` 承载。

> `evidence` 为空的点不得置「待验收」。必须有可指认的证据（验证输出、命令与结果、截图路径），不接受「已测试」这类无证据表述。

> 除非用户在本轮对话中明确说出「确认没问题 / 可以了 / 通过了 / 我验收通过」，否则状态只能停留在「待验收」。禁止以「我已经验证过」「测试全绿」为由自行置为「完成」。**用户没说话 = 还没验收。**

> 置「阻塞」必须写具体原因（卡在哪、缺什么、依赖谁）；只写「没做完」不许置阻塞。

## 常见问题

- **用户说不清 GOAL？** 逐条提议让用户选，不替用户写死；宁可留空并标「待用户确认」，也不要编造目标。
- **文件夹里已有一堆旧文档？** 原地不动；用户明确要求迁移时按「复制 + 归档，逐项列计划」执行，删除另需明确授权（日常维护走 skill(name="myworkflow-project-maintain")）。
- **半新半旧（有 CLAUDE.md 无 docs/）？** 判为项目文件夹后按步骤 3 补齐；新建 `AGENTS.md` 并在 `CLAUDE.md` 末尾追加一行指针；已存在文件先 read 再定补写还是追加。
- **项目里同时有 AGENTS.md 和 CLAUDE.md，内容冲突？** 同目录取 `AGENTS.md`；目录不同取离当前工作文件最近的一份；冲突点在报告里列出，不擅自删改 `CLAUDE.md`。
- **多个成员同时要改 STATE / index？** 谁都不是单写者——向状态 owner 发变更请求（目标文件 / 点号 / 变更 / 证据 / 依据版本），由 owner 核实后写入。
