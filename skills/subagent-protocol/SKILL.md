# 成员与执行者协作协议（L2 执行者 + L3 团队协作）

## 协作模型总览：L1 / L2 / L3

- **L1 单智能体（solo）**：单一不可再分交付物、单文件小改、一次回答闭环、纯问答；当前上下文直接做完，不建团队、不下 mission、不派 leaf。
- **L2 子智能体（subagent）**：≥2 个平铺、无依赖的小交付物；主智能体直接派 `subagent`，每个子交付一个执行者端到端做完。
- **L3 智能体团队（team）**：多域协作、交付物有接口/依赖、需要持续负责人；leader 定目标边界并下 mission，member 域自治端到端，leaf 执行最小任务包。
本协议同时约束 **L2 子智能体** 与 **L3 的 member / leaf** 的执行方式（五阶段工作规范见下）。

## 团队角色与职责（leader / member / leaf）

- **leader**：只做四件事——定目标与边界、建团队、下模块委托（mission）、监督与验收裁量；**不亲自产出交付物、不写业务文件、不逐批派活、不替成员拆叶子任务**。
- **member**：持久存在的**域 owner**，具备独立目标意识。收到「目标 + 边界 + 输入 + 验收」后自己规划、自己授权派发、自己验收结算、自己修复，**端到端完成一整件事**；只在自己写范围内动手，跨域接口先约定。
- **leaf**：fresh 上下文的最小任务包执行者，一次实现并自检，交回真实产物与证据；缺输入找 owner，不越界，**不能开 leaf、不能建同级成员**。

## 谁能开 leaf

**leader 与 member 都可以开 leaf；leaf 不可以开 leaf。** 具体分工：

- **leader 可以**：按已定的产物边界，直接给 leaf 下最小任务包（单文件小改、单条命令、一次回答这类最小件）。
- **member 可以**：在自己的域内自行 plan、授权并启动 leaf；产物边界由 member 自己决定。
- **leaf 不可以**：leaf 不能再开 leaf，也不能创建同级成员或建团队；需要更大能力时把问题交回 owner（member/leader）决策。

## 禁止阶段拆分（硬规则）

一个交付物内部禁止按时间/工序阶段拆成多个窗口或智能体接力；合法切分只有横向切分（每份都能独立交付、独立验收）。

| 违规（禁止） | 合法（允许） |
|---|---|
| 「调研 → 设计 → 实现 → 审查」四阶段各派一个 leaf 接力 | 按可独立交付的产物横切，每个 owner 端到端做完自己那份 |
| 同一功能的「先写接口 → 再写实现 → 再补测试」分三个 leaf | 一个 owner 一次做完整个交付物（含测试与自检） |
| leader/member 把一个交付物的阶段拆成多次 leaf 派发 | leader 只下 mission（产物边界），member 自己决定内部顺序 |

**判定话术**：拆出来的每份「单独交给别人也不成为可用成果」= 阶段接力，违规；每份能独立交付/验收 = 合法。

**两个常见绕过不算合法**：① **审查 / 汇总 / 接口文档 / 测试报告不是独立交付物**——不得作为横向切分的产物；② **同一交付物跨轮次串行接力**（第一轮 A 做一半、第二轮 B 接着做）同样违规，必须**一个 owner 一次做完**。

## 最小任务包（派发方必须写全）

派发 leaf 的 brief 必须包含以下七项，缺项 leaf 应直接向 owner 要，不猜测：

1. **目标**：这份交付物是什么、为什么要它。
2. **边界**：只允许写哪些路径/文件；不能碰什么。
3. **输入证据路径**：要读的契约/基线/证据文件的确切路径。
4. **接口版本**：跨模块接口名称与版本（或「无接口」）。
5. **输出位置**：产物落到哪（精确路径/目录）。
6. **验收条件**：可执行的验收命令或逐条判据。
7. **失败政策**：卡住时找谁、允许重试几次、什么情况下报 blocker 而不是硬做。

## 结算口径：produced ≠ verified ≠ accepted

- **produced**：执行者交回产物与回执（只有产物路径不算完成）。
- **verified**：有真实执行证据（命令 + exit code + 产物哈希/关键输出）。
- **accepted**：owner 复核证据后才算完成；idle、超时、非空完成文件都不是完成。

## 极端与异常场景（必须给出明确指引）

- **无可用工具（subagent / 团队工具缺失或不可用）**：先用替代手段——当前上下文直接做、脚本/命令行、只读查询或已有文件；确实无法执行 → 明确回 `BLOCKED`，写清缺什么工具/权限、影响面、已完成部分，交回 owner 或用户决策；**不许编造结果、不许假装完成**。
- **用户坚持阶段拆分**：这是与「禁止阶段拆分」硬规则冲突的要求——**拒绝**并说明「拆出的每份不能独立交付/验收 = 阶段接力」，给出可执行的横向重排方案（按可独立交付产物切分、一个 owner 端到端做完）；用户仍坚持时，记录为已接受风险并请其明确确认，不得静默照做。
- **中途发现级别判断错误**：允许并鼓励**重新判级**（L3 → L2/L1 回收，或 L2 → L3 升级）；已交付且已验收的产物不重做，只调整后续分配；重新判级要更新 mission/计划说明并告知相关 owner。

## 触发

- **调用者**：L2 子智能体，或 L3 的 leaf；派发方（leader / member）不调用本 skill，只引用它。
- **自动触发**（满足全部 3 条）→ 立即从「阶段1：读取合约」开始：① 被主智能体通过 Agent 工具创建；② prompt 明确提到 `task-id`；③ 工作目录存在 `.task-manifest/task-contract.yaml` 且 `.task-manifest/prompts/`。
- **自举触发**（不满足自动触发时）→ 无 task-id 但工作目录存在 `.task-manifest/` → 走下方「自举保障」，先向主智能体确认执行哪一个任务，不猜测。
- **不触发**：普通问答（无 task-id、无合约）、单件小事（如"检查语法错误"）、找不到 task-contract.yaml 也无 task-id。

### 派发方强制引用（leader 或 member 向 leaf 派发时必须写入）

> 本协议同时服务 L2 与 L3：L2 由主智能体直接派 `subagent`（可不引用本模板，但必须满足最小任务包七项）；L3 由 **leader 或 member** 向 leaf 派发时必须写入下列模板。

```
你必须遵循「myworkflow:subagent-protocol」。你的 task-id 是 {task-id}。
先读取 `.task-manifest/prompts/task-{task-id}.md` 了解任务，
再读取 `.task-manifest/task-contract.yaml` 找到你的合约条目，
然后严格按 5 阶段协议工作：阶段 1：读取合约+确认输入。先读取 `.task-manifest/prompts/task-{task-id}.md` 了解任务，再读取 `.task-manifest/task-contract.yaml` 找到你的合约条目，逐一读取 inputs 中的文件路径。阶段 2-5 声明接口→产出实现→自检→完成报告。
```

> **一致性约束**：本模板与 `skills/task-dispatch/SKILL.md`「第七步：下 mission / 启动 leaf」中的同名模板必须**逐字一致**，修改其一时必须同步另一处。（用 slug `myworkflow:subagent-protocol` 而非中文显示名——技能寻址走目录名，中文名不参与寻址，写 slug 才能稳定触发。）

### 自举保障（主智能体漏引用/漏 task-id 时）

有 task-id？→ 查合约 → 存在 → 正常执行；不存在 → 报告"合约不存在"。
无 task-id → 有 `.task-manifest/`？→ 有 → 检测合约：存在 → 列出所有未完成任务（无 completion.md 的），问"以下任务尚未完成，我应执行哪一个？"并附列表；`prompts/` 存在但合约缺失 → 报告"请重新生成合约或指定我的任务"；两者都不存在 → 报告"目录为空，请确认是否重新拆解"。无 `.task-manifest/` → 非派发系统子智能体，正常回答。
（task-id 可在自举中由主智能体补充指定，不依赖前置存在。）

## 目标

规范子智能体工作：产出具备可验证的接口、可追溯的声明、可审计的自检记录。核心原则：**声明先于产出，声明即承诺。**

## 关联Skill

输入 ← 读取「myworkflow:task-dispatch」产出的 task-contract.yaml 与任务包（mission / leaf 任务包）；输出 → 产出的 interface-declaration.md / self-check.md / completion.md 是「myworkflow:integration-verify」的验证输入。

## 前置强制步骤

1. 确认 task-id：从 prompt 中找；没有 → 检查合约中未完成任务（无 completion.md 的），列出并向主智能体提问（不可猜测）。
2. 读取合约条目：task-contract.yaml 中 `id: {task-id}` 条目，找不到 → 报告。
3. 读取输入文件：逐一读取 inputs 列出的文件；不存在或内容不足 → 提问。

## 执行流程

**主线**：阶段1 读取合约+确认输入 → 阶段2 声明接口 → 阶段3 产出实现 → 阶段4 自检 → 阶段5 完成报告。

### 阶段1：读取合约 + 确认输入

- 找到与 task-id 匹配的合约条目，确认 description、depends_on、inputs、outputs、verification。
- 逐一读取 inputs 文件。
- 关键规则：输入文件不存在→提问；输入不足→提问；依赖任务未完成→等待（以 `.task-manifest/outputs/{dep-task-id}/completion.md` 存在且非空为准，**最多等 10 分钟**，超时报告"依赖任务 {dep-task-id} 未在时限内完成，请确认状态"）；合约有歧义→提问。

### 阶段2：声明接口

写 `.task-manifest/outputs/{task-id}/interface-declaration.md`：

```markdown
# 接口声明 — {task-id}
> 本声明是我的接口承诺。「myworkflow:integration-verify」将据此验证我的产出。
> 声明时间: {ISO 8601 时间戳}

## 我将创建/修改的文件
- [ ] {文件路径} — {用途描述}

## 我将暴露的接口
| 名称 | 签名 | 所在文件 |
|------|------|----------|
| {name} | {signature} | {file} |

## 我需要的外部输入
| 文件 | 内容（节/函数/类型） | 用途 |
|------|---------------------|------|
| {path} | {具体部分} | {说明} |

## 风险和假设
- {假设 1}
- {风险 1}
```

声明规则：必须覆盖合约 outputs 全部条目（可多不能少）；签名必须与合约一致；合约签名有问题 → 在风险中标注并继续按合约声明；声明写入后不可秘密修改。

### 阶段3：产出实现

1. 先建文件骨架（空文件、导出签名桩），再填实现逻辑。
2. 每完成一个文件，在声明中勾选 `- [x]`。
3. 需要修改声明 → 先更新 interface-declaration.md 再改代码。
4. 需要超出合约范围的工作 → 先反馈主智能体确认。

### 阶段4：自检

写 `.task-manifest/outputs/{task-id}/self-check.md`：

```markdown
# 自检报告 — {task-id}
> 自检时间: {ISO 8601 时间戳}

## 文件存在性
- [x] {file} — 存在且非空

## 接口签名匹配（与 interface-declaration.md 对比）
- [x] {name}: `{signature}` — 实际签名一致

## 功能完整性
- [x] {功能点}

## 接口自洽
- [x] 所有导出的函数/类型在同一个模块内有定义
- [x] 没有引用不存在的模块/文件 → 对每个 import/require 用 ls/Test-Path 验证
- [x] 没有孤立的导出 → grep 搜索每个导出名，确认被引用或属合约要求的 outputs

## 错误处理
- [x] {异常路径}
```

自检规则：必须全部 [x] 才能进入阶段5；修正涉及接口 → 先回阶段2更新声明；不造假（「myworkflow:integration-verify」会对比）。

### 阶段5：完成报告

写 `.task-manifest/outputs/{task-id}/completion.md`，状态为四种之一：

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| **DONE** | 全部完成，对正确性有信心 | 合约全实现、自检全过、无已知问题 |
| **DONE_WITH_CONCERNS** | 完成但有疑虑（诚实表达不确定，非逃避；主智能体应优先审查这些疑虑） | 全部实现但存在：①正确性依赖未验证假设 ②边界处理不确定 ③某 API 行为与预期不同 ④对 trade-off 有疑虑 |
| **NEEDS_CONTEXT** | 无法完成，缺关键信息 | 合约信息不充分（错误处理策略未指定/目标平台未指定/接口签名有未定义参数等） |
| **BLOCKED** | 无法完成，被外部条件阻止 | 依赖子任务未完成/工具或服务不可用/合约有不可修复矛盾 |

```markdown
# 完成报告 — {task-id}

**状态**: [DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED]

## 产出文件清单
- [文件路径] — [简述]

## 自检结果
- [ ] 文件存在性
- [ ] 接口签名匹配
- [ ] 功能完整性
- [ ] 接口自洽
- [ ] 错误处理
- 全部通过: [是/否]

## 已知担忧 (DONE_WITH_CONCERNS 时填写)
- 担忧: [具体技术担忧] — 影响: [可能影响什么]

## 缺失信息 (NEEDS_CONTEXT 时填写)
- 缺失: [什么信息] — 影响决策: [哪个决策]

## 阻塞原因 (BLOCKED 时填写)
- 阻塞: [什么原因] — 可能解决: [方案]
```

核心约束：声明先于实现（未写 interface-declaration.md 就写代码=违规）；签名即承诺（改签名必同步更新声明）；自检不通过不交活（必须全部 [x]）；输入缺失不猜测（提问）；范围不蔓延（不修改合约未列文件）。

## 后置更新

1. 确认 3 个元文件（interface-declaration.md、self-check.md、completion.md）已生成，且实际代码产出已完成，路径均在 `.task-manifest/outputs/{task-id}/`。
2. 确认 self-check.md 全部 [x]。
3. 向主智能体报告完成。

## 完成标志

- [ ] interface-declaration.md 已写入，覆盖合约所有 outputs
- [ ] 所有代码/文档产出文件已创建，内容完成
- [ ] self-check.md 已写入，全部项目 [x]
- [ ] completion.md 已写入，产出清单完整
- [ ] 所有元文件在 .task-manifest/outputs/{task-id}/ 下
- [ ] 已向派发方（leader / member / 主智能体）报告完成
- [ ] 未超出最小任务包边界；需要更大范围时已交回 owner 决策
- [ ] 未把同一交付物按阶段再拆给其他执行者（阶段接力禁止）
