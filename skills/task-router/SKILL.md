## 反绕过红旗清单

> 当你发现自己正在想以下任一念头——停下来。这正是需要先进行任务分类的时刻。以下 12 条来自真实对话中最常见的绕过模式。

| 红旗念头 | 现实 |
|---------|------|
| "这只是个简单问题" | 问题不分简单复杂——先分类。简单问题的分类只需 2 秒。 |
| "我需要先了解更多上下文" | 分类在读任何文件之前。不了解任务类型就无法确定需要什么上下文。 |
| "让我先探索一下代码库" | 探索方向取决于任务类型。先分类→再按分类指引探索。 |
| "我直接看一下文件就行" | 看文件之前要知道为什么看。分类告诉你目的是什么。 |
| "我应该先问问用户" | 分类是提问的前置步骤——不同类型任务需要问不同的问题。 |
| "我记得这个 skill 的内容" | skill 在演化。当前版本可能不同于你的记忆。 |
| "这不需要走正式流程" | 分类≠走完整流程。分类只是路由——简单任务被路由到快速通道。 |
| "这个 skill 太重了，不适合小事" | 本 skill 就是路由+返回。开销≈0。怕重的是下游 skill——由分类决定通道。 |
| "用户没有明确说要用 skill" | 用户不需要知道 skill 名字。所有请求走分类入口——这是门禁，不是选项。 |
| "让我先做这一件事，然后补分类" | 先做=先不做。分类没有成本——现在就分类。 |
| "这很明显是代码编写任务" | 明显≠已确认。代码编写分：新功能/修 bug/重构/加测试——需细分路由。 |
| "我只是在回答代码相关的问题" | 回答=解释=不改代码？分类为"其它任务"直接答。需要改代码？分类为"代码编写"。先分才知道。 |

### 红旗自检

每次收到用户请求后、开始任何操作前，快速过：
- [ ] 我正在想"这个简单/明显/不需要分类"吗？→ 看第 1/11 条
- [ ] 我正在想"先做 X，再分类"吗？→ 看第 10 条
- [ ] 我正在想"我直接读文件/搜索/探索"吗？→ 看第 2/3/4 条

## 目标

作为所有任务的公共入口，完成三件事：
1. **判断任务类型**（五分类）
2. **细化需求**（启发式多轮提问 → 结构化报告）
3. **按类型路由执行**（调用对应的执行 skill）

## 执行流程

### 步骤 1：判断任务类型

根据用户请求判断属于以下哪一类：

| # | 分类 | 关键信号 | 下一步 |
|---|------|---------|--------|
| 1 | **代码编写** | 写代码、改代码、重构、修 bug、新建项目、加功能 | → 步骤 2 细化需求 → 步骤 3.1 |
| 2 | **文稿撰写** | 写文档、写报告、润色文本、去 AI 味、翻译 | → 步骤 2 细化需求 → 步骤 3.2 |
| 3 | **深度调研** | 需要多源搜索 + 交叉验证 + 综合报告 | → 步骤 2 细化需求 → 步骤 3.3 |
| 4 | **专项工作** | 写小说、学习笔记、数据可视化等有专用 skill 的领域 | → 步骤 2 细化需求 → 步骤 3.4 |
| 5 | **其它任务** | 简单小提问、闲聊、无法归类 | → 直接回答 |

**判断原则**：
- 不确定时 → 用 AskUserQuestion 问用户（一句话："你是要做 X 还是 Y？"）
- 多项匹配 → 选最接近的那个
- 完全不匹配 → 「其它任务」

### 步骤 2：细化需求

> 注：步骤 2 执行内联轻量澄清；复杂需求时升级调用 Skill('myworkflow:req-clarify')。
>
> **适用于分类 1-4。分类 5（其它任务）跳过此步骤。**

1. 读取项目上下文（CLAUDE.md、相关代码等）
2. 逐轮启发式提问：每次一个问题，2-4 个选项，覆盖目标 → 范围 → 约束 → 边界
3. 生成结构化需求报告：
   - 核心目标（一句话）
   - 输入/输出
   - 涉及范围（新建/修改/不涉及）
   - 约束条件（技术/性能/兼容性）
   - 边界条件（空输入/异常/大数据量）
   - 技术方案（可选，复杂任务时提供）
   - 验证标准（怎么判断做完了/做对了）
4. 用户确认报告后进入步骤 3

**提问规则**：
- 每次只问一个问题，不要一次抛出一堆
- 优先给选项（2-4 个），让用户点选
- 最多 5 轮总提问
- 用户说"直接做"→ 精简但至少确认核心目标 + 输出形式

### 步骤 3：按类型执行

#### 3.1 代码编写

```
先判断：是否为新项目？
  ├─ 是（文件夹为空 / 无 CLAUDE.md / 无任何包管理配置文件（package.json、pyproject.toml、go.mod、Cargo.toml、Gemfile 等））
  │   → Skill("myworkflow:project-init")
  │   → 初始化完成后，回到本流程继续
  └─ 否 → 判断子类型：
      ├─ 功能开发/重构/加功能 → Skill("myworkflow:agent-dev-loop")
      ├─ 修 bug/报错/异常/不工作 → Skill("myworkflow:bug-fix-verify")
      ├─ 排查根因/深度排查 → Skill("myworkflow:root-cause-analysis")
      └─ 提交代码/创建 PR/合并 → Skill("myworkflow:github-collab")
```

**关键**：新项目必须先初始化四文件体系，再进入开发闭环。

#### 3.2 文稿撰写

```
判断用户需求：
  ├─ 已有文本需去 AI 味/润色 → Skill("myworkflow:humanizer-zh")
  ├─ 需要从零撰写内容 → 先直接撰写初稿，再询问是否需要 humanizer-zh 润色
  └─ 纯翻译 → 直接翻译，再询问是否需要 humanizer-zh 润色
```

#### 3.3 深度调研

```
→ Skill("myworkflow:deep-research")
```

传入步骤 2 确认的调研问题和范围。

> ⚠️ 如果「myworkflow:deep-research」skill 不可用，手动执行：多源搜索 → 交叉验证 → 综合报告。

#### 3.4 专项工作

```
先扫描：上下文中的「专项 Skills」清单，找匹配的专用 skill
  ├─ 有匹配 → 调用对应的 Skill("myworkflow:xxx")
  └─ 无匹配 → 降级为「需求澄清 → 直接执行」
```

**已知专项映射**（示例，以实际扫描结果为准）：

|------|---------|

#### 3.5 其它任务

直接回答用户请求，不走需求澄清和执行路由。

### 步骤 4：确认完成

向用户汇报：
- 判定为什么类型
- 路由到了哪个 skill
- 预计的后续流程

**汇报格式**：向用户报告时遵循以下结构——
- 📂 判定类型：[代码编写/文稿撰写/深度调研/专项工作/其它任务]
- 🛤️ 路由到：[skill 名称]
- 📋 后续流程：[一句话说明接下来会发生什么]

## 常见场景速查

| 用户说 | 分类 | 路由 |
|--------|------|------|
| "帮我加个登录" | 代码编写 | 需求澄清 → 智能体闭环开发 |
| "报错了 TypeError: ..." | 代码编写 | Bug修复与验证 |
| "新建一个 React 项目" | 代码编写 | 大项目初始化 → 智能体闭环开发 |
| "帮我把这段去 AI 味" | 文稿撰写 | humanizer-zh |
| "写一篇技术博客" | 文稿撰写 | 需求澄清 → 撰写 → humanizer-zh |
| "调研一下 Next.js vs Nuxt" | 深度调研 | 深度调研 |
| "帮我找到根因 / 深度排查" | 代码编写 | 根因定位与全面排查 |
| "提交代码 / 创建 PR / 推送到远程" | 代码编写 | Github协作 |
| "写小说第三章" | 专项工作 | 扫描技能 → 具体写作 |
| "这段代码什么意思" | 其它任务 | 直接回答 |
| "hello" | 其它任务 | 直接回答 |

## 注意事项

- 本 skill 是**路由器 + 需求澄清器**，不是一个单纯的 router
- 分类不确定时 → 问用户，不要猜
- 代码编写类**禁止**跳过步骤 2（需求澄清）直接写代码
- 专项工作的 skill 清单由 Hook 在会话启动时注入——以注入清单为准，不要硬编码
