# 任务分类速查

会话入口是 hook：它在启动时注入任务分类概念与阶段链。本表是**备用速查**，用于两种场合——拿不准归哪类时，或长会话内切换任务类型、上下文里已经堆了很多别的东西时。

## 第一步：判定工作级别（L1 单智能体 / L2 子智能体 / L3 团队）

先判级别，再判类别：级别决定「谁来做、怎么协作」，类别决定「加载哪个技能」。

- **L1 单智能体（solo）适用**：单一不可再分交付物、单文件小改、一次回答闭环、纯问答。形态：当前上下文直接做完，**不建团队、不下 mission、不派 leaf、不建 goal**。判据：出现「≥2 个可独立交付物」或「改动 ≥2 个文件」即不再属于 L1。
- **L2 子智能体（subagent）适用**：≥2 个平铺、无依赖的小交付物；不需要跨回合持续负责人；结果可一次性回收。形态：直接派 `subagent`，每个子交付一个执行者**端到端做完自己的小件**（调查→实现→自检→修复），交回真实产物与证据。升级判据：出现跨交付物接口/依赖、需要持续负责人、需要多轮补位 → L3。
- **L3 智能体团队（team）适用**：多域协作、交付物之间存在接口/依赖、需要持续负责人、需要并发推进与滚动补位。形态：建团队，按角色分工（见下一条）。
- **L3 角色**：**leader** 只做四件事——定目标与边界、建团队、下模块委托（mission）、监督与验收裁量；不亲自产出交付物、不写业务文件、不逐批派活、不替成员拆叶子任务。**member** 是持久存在的域 owner：收到「目标+边界+输入+验收」后自己规划、自己授权派发、自己验收结算，端到端完成一整件事。**leaf** 是 fresh 上下文的最小任务包执行者，一次实现并自检后交回产物与证据；**leader 与 member 都可以启动 leaf，leaf 不能再开 leaf**。
- **禁止阶段拆分（硬规则）**：一个交付物内部不得按时间/工序拆成多个窗口或智能体接力（如「调研→设计→实现→审查」各派一人）。合法切分只有**横向切分**：拆出的每一份都能独立交付、独立验收。

## 第二步：按交付物形态选类别（速查表）

| 请求类型 | 走 |
|---|---|
| 代码 / 改文件 / 重构 | `Skill("myworkflow:agent-dev-loop")` |
| 文稿 / 从零写作 | `Skill("myworkflow:write-prose")` |
| 文稿 / 润色 / 改写 / 去 AI 味 | `Skill("myworkflow:polish-prose")` |
| 深度调研 | `Skill("myworkflow:deep-research")` |
| 疑似专项任务 | 查 `config/special-skills.json` → 命中则调用对应 skill |
| 简单问答 / 其它 | 直接回答 |

## 级别与技能的对照

- **L1**：不加载协作类技能，当前上下文直接做完。
- **L2**：加载 `Skill("myworkflow:lightweight-dispatch")`（L2 子智能体操作规程）。
- **L3**：加载 `Skill("myworkflow:task-dispatch")`（L3 拆分契约）+ `Skill("myworkflow:subagent-protocol")`（协作协议）。

## 不在这张表里的技能

以下技能不参与任务分类，但在上表任一流程中都可能被调用：

- **工具性**：`req-clarify`（需求澄清）、`anti-sycophancy`（质疑准则）、`lessismore`（输出克制）、`registry-maintain`（注册表维护）
- **协作与执行**：`task-dispatch`、`lightweight-dispatch`、`subagent-protocol`、`integration-verify`
- **项目管理**：`project-init`、`project-maintain`
- **代码细节**：`root-cause-analysis`、`real-world-verify`、`github-collab`

## 完成判据

- [ ] 已给出**工作级别 + 理由**（L1/L2/L3 与命中的判据）
- [ ] 已按交付物形态选定类别并加载对应技能
- [ ] 级别与动作一致：L1 不派发、L2 平铺派发、L3 建团队并下 mission
- [ ] 若发生切分，已确认每份都能独立交付、独立验收（无阶段接力）
