## 核心流程：症状定位 → 5 Whys → 数据流逆向 → 全面扫描

**何时加载**：bug 要定位根因而非改表面症状、同一 bug 反复复发、用户要求「找根因 / 深度排查 / 全面扫描同类问题 / 还有没有别的地方」。**不加载**：简单事实查询、根因一目了然的语法拼写错误、纯功能开发与重构、根因已确认只需动手修。

**硬步骤**
1. **症状收集与分类**：整理错误原文、堆栈、复现步骤、预期 vs 实际 → 判据：定位到出错点文件:行号并读出上下文，症状归入崩溃/错误输出/性能超时/数据损坏/竞态五类。
2. **5 Whys 追问**：每层「因为」必须有代码或日志证据，问到外部系统或物理限制为止 → 判据：标出「修复这一层即可消除所有上层症状」的根因层；技术根因与流程根因都记录。
3. **数据流逆向**：从出错点向上游画每个变换点的数据进出 → 判据：用 ★★★ 标出最先出现坏数据的源头；各变换点都正确、唯独出错点错，则根因在出错点逻辑本身。
4. **假设-验证循环**：写可证伪假设「若根因是 X 的 Y 逻辑，则预测 Z 成立」，设计证伪实验并实跑 → 判据：≥1 假设通过证伪、≥2 个独立证据支撑；被推翻回第 2/3 步，不无预算重复同一失败实验。
5. **全面扫描同类**：先提 bug 模式（误用/变换缺失/边界遗漏/时序依赖/防护缺失），再按 ≥3 个维度搜（同调用点/同字段/同结构/同链路/对称逻辑/防御缺口）→ 判据：结果全部分类（同类确认/高概率/相似/潜在/防御缺口）并落盘。

**专项分叉**：竞态、插桩、Bisect、防御纵深、flaky 统计置信度按症状类型从 detail 取用，不预先全读；flaky 偶发必算统计置信度，禁止「跑三次没挂就算过」。

**证据分层**：区分「已核实 / 有来源」与「推测 / 未核实」；交给 parent 的是简短结论 + 可核查引用，原始材料留在文件里。

**完成判据**：根因有证据、扫描覆盖 ≥3 维度且无遗漏、报告与交接清单（直接修改 + 回归清单）已落盘；开发任务内同一 owner 修完并做真实验证，证据=命令输出/日志/代码行号。

## 触发与边界

- **触发**：开发闭环中遇到 bug 需要定位根因而非直接改表面症状；用户要求"找根因 / 深度排查 / 为什么出现这个 bug / 全面扫描同类问题 / 还有没有别的地方有这问题"；同一 bug 修多次仍复发。
- **不触发**：简单事实查询（直接 grep）；根因一目了然（明显语法/拼写错误）；纯功能开发/重构；已确认根因只需动手修。
- **与开发闭环的关系**：排查产出可直接喂给下游修复执行（可配合 `skill(name="myworkflow-agent-dev-loop")`）。排查结论要与被排查代码在同一交付物内闭环，不要只交出一份"诊断书"就撤手。

## 定位目标

抵达真正根因（非表面症状）+ 动手前找全所有受影响位置（非只修一处）。

**排查与修复同属一个责任人**：开发任务内由同一 owner 端到端走完"调查 → 实现 → 自检 → 修复 → 验收"，不把同一份交付物拆成"背景调查→设计→检查"或"计划→编码→审查"的多人阶段接力。只有用户明确表示"我只要排查结论、先别改"时，才止于报告并交付交接清单。

## 核心原则

- 不找到根因不停止追问；不扫完全局不下结论。
- 每一层"因为"必须有代码/日志证据，禁止猜测。
- 直觉可能是对的，但必须经过验证。
- 证据充分即可给出修复方向，不必等所有步骤走完；六步可交错、可回退，不是关卡。

## 主线（六步，可交错）

### 第 1 步：症状收集与分类
1. 整理信息：错误原文/堆栈/复现步骤/预期 vs 实际/git log/环境/日志。缺失较多且确实影响排查方向时，用 `ask_user_question` 一次性补全关键项。
2. 症状分类：🔴 崩溃异常 / 🟠 错误输出 / 🟡 性能超时 / 🟢 数据损坏 / 🔵 竞态不稳定。
3. 定位出错点：文件:行号（或少量候选），读出错代码上下文。
4. 🔵 → 启动技术 A；回归型（之前好现在坏）→ 启动技术 C。

### 第 2 步：5 Whys 深度追问
- 每层"因为"必须有证据；问到不能再问为止（通常 3-7 层，停止于外部系统/物理限制）；不跳过代码层、数据层。
- 区分技术根因与流程根因，都记录。
- 标注最深层 ← 根因：修复这一层即可消除所有上层症状。
- 出口：每层有证据、已标根因层。

### 第 3 步：数据流逆向追踪
- 从出错点向上游绘制数据流，标注每个变换点的数据进出与检查结果。
- 用 ★★★ 标记最先出现坏数据的变换点（= 数据层根因）。
- 数据在所有变换点都正确、唯独出错点错 → 根因在出错点逻辑本身。
- 策略：正向 / 逆向（默认）/ 二分法（链路很长时）/ 并行追踪（把每条分支作为**独立交付项**交给模块成员走受管派发；不建团队时自己逐条追）/ 插桩（→技术 B）。
- 出口：数据流图分层清晰、坏数据源头已标记；多个变换点"不确定" → 启动技术 B。

### 第 4 步：假设-验证循环（科学方法）
- 形成**可证伪**假设："如果根因是 X 位置的 Y 逻辑，则预测 Z 应成立"。
- 设计**证伪实验**（试图证明它错，而非证实）——抵抗确认性偏差。
- 执行：实际运行看结果，不推理。✅ 通过证伪 → 可信；❌ 推翻 → 回第 2/3 步；⚠️ 不确定 → 更精确实验。
- 多次推翻且无新进展时停下检查是否遗漏关键信息，并升级判断：可能架构性问题 / 第三方依赖 bug / 用户信息有误。**不得无预算地重复同一个失败实验，也不设"试三次就结束"这类固定次数。**
- flaky 偶发 → 技术 E 统计置信度。
- 出口：≥1 假设经证伪实验确认，≥2 个独立证据支撑（非同一文件/日志）。

### 第 5 步：全面性扫描
- 提取 bug 模式：函数/API 误用、数据变换缺失、条件/边界遗漏、配置/环境差异、时序/顺序依赖、校验/防护缺失。
- 多维度搜索，**≥3 个维度**（禁止单个 grep 就说"找全了"）：相同函数调用点 / 相同字段 / 相同逻辑结构 / 相同调用链 / 相同作者提交 / 相反对称逻辑 / 防御性缺口。
- 分类：🔴 同类确认 / 🟠 同类高概率 / 🟡 相似中概率 / 🔵 潜在低概率 / ⚫ 防御缺口。
- 出口：模式提取 ≥2 维度、搜索 ≥3 维度、全部已分类、扫描结果已落盘。

### 第 6 步：输出与交接
- 产出报告（7 节）：症状摘要 / 根因因果链 / 数据流分析 / 根因确认（证据 + 可信度 + 专项技术使用）/ 全面扫描结果 / 交接清单 / 已知局限。
- 交接清单必须可直接执行：直接修改列表 + 回归清单（症状摘要 → 根因确认 → 交接清单三段是下游必读）。
- 用户只要排查时，报告即终态；开发任务内则同一 owner 继续修完，修复后用 `skill(name="myworkflow-real-world-verify")` 做真实验证才算完成。

## 横向交付与滚动协作

- **按可独立交付的产物切分**：以 module 模块 / object 对象 / evidence-package 证据包为单位分工，每份交付物由一个 owner 端到端负责（调查→实现→自检→修复→验收）。切分线落在交付物边界上，不落在流程阶段上。
- **横向重排建议**：若现有安排是"先全线背景调查，再统一设计，再统一检查"，或"计划→编码→审查"三段接力，改为按交付物横向切开、各自端到端闭环。
- **事件驱动滚动补位**：任一项结算，常驻 Host 调度器立即补位下一项**已授权**的 work，不等同批其它任务；无全批屏障、无整层等待；慢任务不阻塞其它 ready 项。用 `team_snapshot` 看 ready 与容量、`team_wait` 等变化（不轮询）；需要多人并行排查时，leader 用 `team_mission_assign` 下模块委托，由成员自己 `team_plan_submit` + `team_dispatch_authorize` 把每份独立排查提交并授权。
- **未 ready 不派发**：依赖未就绪时不要提前启动、不要空等；满额时明确拒绝并保持 ready 状态（CAPACITY_FULL），既不用排队空等，也不用一次性旁路绕过上限。
- **超时语义**：超时后先判断进展与可恢复性，「状态未知 / 暂停」与「真正失败」严格分开，超时不等于失败。
- **依赖只允许存在于不同交付物之间**，并要求标注 version + requires（published-interface 已发布接口，或 verified-result 已核实结果）。
- **收尾修复由原 owner 负责**；全局集成由 leader 与相关 owner 共同承担，不撤走前面的人、换成没有上下文的审查员来接后半程。

## 阻塞处理顺序

出现阻塞时按顺序处理，不要停在原地：

1. **记录确切失败**：失败现象、已尝试路径、影响范围、当前仍可做的部分。
2. **查现成资源**：已装服务、源码、现成工具、当前权限能覆盖的范围。
3. **能补就补**：可写适配器 / 接口 / 本地桥接的，就地补齐打通。
4. **局部阻塞先绕**：先推进其它 ready 项，并把 blocker 精确挂到受影响的交付物上（谁被挡、挡在哪一步）。
5. **确实需要外部账号、人工决策或无法获得的资源**时，才标记 needs_user，并给出已尝试路径与最小下一步。

权限拒绝不可绕过；同一失败不无预算地反复重试，也不固定"试几次就结束"。

## 授权与提问

- 用户已授权任务内的可逆开发不重复征求批准；审批与扩权只有用户入口，模型没有等价工具。
- 只在**真正改变决策且项目里查不到**时才用 `ask_user_question` 提问。

## 专项排查技术库（从对应步骤分叉的可选深度工具）

### A. 竞态条件排查（🔵 类 / 偶发 / 并发）
1. 事件顺序重建：列出并发操作与共享资源，对比正常 vs 异常时间线，找脏读/覆盖。
2. 时序图分析：标注竞态窗口。
3. Interleaving 分析：枚举导致异常的操作交错序列。
4. 条件轮询替代盲等：任意 timeout → 用 `waitFor(条件,{timeout,interval})` 而非 `sleep()`。见 [references/condition-based-waiting.md](references/condition-based-waiting.md)。

### B. 插桩调试（多个变换点不确定 / 多组件断裂）
1. 组件边界插桩：每边界记录「进/出」，运行一次对比哪层"出"与预期不符。
2. 二分法：长链路中间插检查点，每轮缩半。
3. 环境/配置传播验证：每层检查环境变量的接收/使用/传递。

### C. Bisect 二分定位（回归型 bug）
- `git bisect start` → `bad HEAD` → `good <版本>` → `git bisect run <验证脚本>` → `log` → `reset`。
- 需 UI/特殊环境 → 手动二分：`git log --oneline <good>..<bad>` → 中间 commit 实测 → 缩至 1-2 提交 → `git show`。
- 产出：引入提交 SHA + diff + 变更行。

### D. 防御性排查（外部输入 / 多层系统）
1. 穷举异常输入（null/空串/格式错/超长/XSS/路径遍历），逐层追踪处理方式。
2. 边界穷举：数值（0/-1/MAX/溢出）、集合（空/单元素/大量）、状态转移、时间边界。
3. 多层校验缺口：校验是否只在单层存在。
4. 防御纵深四层模型：L1 入口验证 / L2 业务逻辑验证 / L3 环境守卫 / L4 调试插桩——问"哪一层能阻止此 bug"，缺失则补哪层。见 [references/defense-in-depth.md](references/defense-in-depth.md)。

### E. Flaky test 分析（偶发失败 / 修复置信度）
- **统计显著性判定（核心）**：估算原始失败率 P_fail（≥20 次历史运行），所需连续通过 N = log(α)/log(1−P_fail)。50%→7 次；30%→13；10%→44；5%→90。**禁止"跑了 3 次没挂就算过"。**
- 失败模式聚类：≥2 种不同失败模式 → 多个独立根因，各自独立假设-验证。
- 环境因素隔离：时间依赖（固定时钟）/ 执行顺序（shuffle）/ 外部服务（mock）/ 随机数（固定种子）/ 异步时序 / 资源竞争 / 数据污染，逐一排除实验。

## 证据与结果分层

- **证据诚实**：区分「已核实/有来源」与「推测/未核实」，不夸大，不在无证据时声称"验证通过"。
- **结果分层**：简短结论 + 可核查的 evidence/artifact 引用进 parent；原始材料留在文件或子会话中。
- **摘要要素**：来源、版本、遗漏、不确定性、未完成项都要写清。

## 完成标志

- [ ] 六步关键出口达成：因果链每层有证据；数据流坏源头已标记；≥1 假设经证伪验证 + ≥2 独立证据；扫描 ≥3 维度并全部分类
- [ ] 报告 7 节完整，交接清单（修改列表 + 回归清单）已填写，已知局限已标注
- [ ] flaky 已按技术 E 算统计置信度
- [ ] 专项技术产出已整合进报告对应章节
- [ ] 用户只要排查 → 已交付报告即收尾；开发任务内 → 同一 owner 已修完并完成真实验证
