## 触发

- **必须触发**：Bug修复与验证 步骤 ② 调用本 skill 进行深层根因追踪 + 全面性扫描；用户直接说"帮我找到根因/深度排查/为什么会出现这个 bug/全面扫描同类问题"；用户说"还有没有别的地方有这个问题/帮我找全/扫描一下类似 bug"；同一个 bug 被修了 2 次以上仍然复发（说明没找到根因）；用户说"这个 bug 的根本原因是什么/数据是在哪里变坏的"。
- **不触发**：用户只想知道一个简单事实（"这个变量在哪定义的"→ 直接 grep）；根因一目了然（明显语法/拼写错误——由 bug-fix-verify 步骤 ② 的轻量分析例外处理）；纯功能开发/重构/代码审查（走闭环开发）；用户已确认根因只需修（直接走 bug-fix-verify 步骤 ③）。
- 由 bug-fix-verify 调用 → 接收其步骤 ① 产出的 5 项细节，排查完成后将报告交回；用户直接调用 → 排查完成后建议走 bug-fix-verify 进行修复。

## 目标

确保每次排查都抵达真正的根因——而非停留在表面症状。确保修复前已找全所有受影响的代码位置——而非只修一处、遗漏一片。**本 skill 只排查不修复**——修复是 Bug修复与验证 → 智能体闭环开发 的职责。

## 前置强制步骤

> **不找到根因不停止追问。不扫完全局不下结论。** 表面修复 = 掩盖症状；深层根因 = 彻底解决。单一修复 = 按下葫芦浮起瓢；全面扫描 = 一网打尽。

1. **接收 bug 上下文**：由 bug-fix-verify 调用 → 接收其步骤 ① 已产出的 5 项细节（复现步骤、预期vs实际、环境、日志、频率）。用户直接调用 → 先用 1 轮快速提问了解症状。
2. **确认不跳过深度追问**：脑中闪现"这很明显就是 X 的问题"——这正是需要本 skill 的时刻。直觉可能是对的，但必须经过验证。
3. **禁止急于修复**：完成全部 6 个阶段之前，不提出修复建议。排查和修复分离——修代码是 bug-fix-verify → 智能体闭环开发 的事。

## 执行流程

**主线**：阶段1 症状收集与分类 → 阶段2 5 Whys 深度追问 → 阶段3 数据流逆向追踪 → 阶段4 假设-验证循环 → 阶段5 全面性扫描 → 阶段6 输出与交接。假设被推翻 → 回阶段 2 或 3。

> **专项技术定位**：五项专项排查技术（A-E）不是独立阶段——它们是可选深度工具，在特定条件满足时从对应阶段分叉进入（见「专项排查技术库」）。阶段 3/5 可派只读子智能体并行探索不同追踪路径或搜索维度。

### 阶段 1：症状收集与分类

> 把用户提供（或 bug-fix-verify 传入）的 bug 信息整理为结构化症状档案。不满足于表面描述——收集所有可用的客观证据。

#### 第一步：信息收集清单

逐项确认以下信息是否可用：

| 信息项 | 状态 | 来源 |
|--------|------|------|
| 错误信息原文（非转述） | ✅/❌/⚠️部分 | [谁提供的/从哪读取的] |
| 完整堆栈跟踪（含行号） | ✅/❌/⚠️部分 | [...] |
| 稳定复现步骤 | ✅/❌/⚠️偶发 | [...] |
| 预期行为 vs 实际行为 | ✅/❌ | [...] |
| 最近相关变更（git log） | ✅/❌ | [...] |
| 环境信息（OS/版本/配置） | ✅/❌ | [...] |
| 相关日志 | ✅/❌ | [...] |

缺失项 ≤2 → 可继续。缺失项 ≥3 → 先用 AskUserQuestion 补充关键信息（最多 2 轮）。回归型 bug（"之前好现在坏"）需精确定位引入提交 → 用技术 C（Bisect 二分定位）。

#### 第二步：症状分类

根据症状特征将 bug 归入一个主类别：

| 类别 | 特征 | 排查重点 |
|------|------|---------|
| 🔴 崩溃/异常 | 抛出错误、进程退出、panic、segfault | 阶段 3——追踪异常触发条件 |
| 🟠 错误输出 | 不崩溃但返回值/显示内容错误 | 阶段 3——追踪数据从哪步变错 |
| 🟡 性能/超时 | 慢、卡顿、超时、内存泄漏 | 阶段 3——追踪瓶颈与资源消耗链 |
| 🟢 数据损坏 | 数据静默变错、持久化后无法读取 | 阶段 3——追踪数据写入和变换链路 |
| 🔵 竞态/不稳定 | 偶发、时序相关、并发、不可稳定复现 | 阶段 2——多问几层"为什么偶发"；属并发/竞态 → 技术 A |

#### 第三步：精确定位出错点

- 从堆栈/错误信息中提取确切的 **文件:行号**。
- 读取出错代码及其上下文（上下各 30 行）。
- 用户没有提供错误信息 → 根据症状描述 Grep 关键词，定位到 1-3 个候选文件。

**阶段 1 出口条件**：信息收集清单已填写（缺失项 ≤2）；症状已归入主类别；出错点已定位到文件:行号级别（或 ≤3 个候选）；出错代码上下文已读取；🔵 类已确认是否启动技术 A；回归型已确认是否启动技术 C。

### 阶段 2：5 Whys 深度追问

> **本 skill 区别于其他排查方法的标志性阶段。** 5 Whys 不是"问 5 次为什么就停"——而是问到不能再问为止。每一层"因为"必须基于代码证据，不能基于猜测。

#### 追问规则

| 规则 | 说明 |
|------|------|
| **每层"因为"必须有证据** | 不能写"因为可能是 X"——必须基于代码/日志/测试结果 |
| **问到不能再问为止** | 通常 3-7 层。停止条件：答案涉及外部系统（第三方 API、硬件）或已达物理/数学限制 |
| **不跳过任何一层** | 从"为什么返回 500"不能直接跳到"因为架构不好"——中间必须经过代码层、数据层 |
| **区分技术根因和流程根因** | Why 1-4 通常是技术层；Why 5+ 可能进入流程/架构层。两者都要记录 |
| **标记最深层** | 在因果链中标注"← 这是根因。修复这一层即可消除所有上层症状" |

#### 因果链记录模板

每完成一轮 5 Whys，记录为结构化因果链：

```
## 因果链 — [bug 简述]

症状（What）: [一句话——用户看到了什么]

Why 1: [直接原因]
  ├── 证据: [代码位置 / 日志行 / 测试结果]
  └── 如果是这层的问题: [只修这里的话，bug 还会不会复发？]

Why 2: [底层原因]
  ├── 证据: [...]
  └── ...

Why N: [根因] ← 根因
  ├── 证据: [...]
  └── 修复这一层即可从根本上消除症状

Why N+1: [系统性原因——如适用]
  ├── 证据: [...]
  └── 说明: [为什么系统设计/流程使得此类 bug 必然发生]
```

**示例**（登录"网络错误"）：症状=显示"网络错误" → Why1 因为 API 返回 500（证据：Network 面板/日志）→ Why2 因为 `AuthController.login()` 抛 NullPointerException（证据：堆栈指向 :47）→ Why3 因为 `findByEmail(email)` 返回 null（证据：代码——用户不存在时返回 null 而非 Optional.empty）→ Why4 因为 DB 查不到该 email（证据：email 存旧格式，登录传新格式）→ Why5 因为迁移脚本统一转小写但前端没做 `.toLowerCase()`（证据：git log + 代码对比）→ Why6 部署流程允许前后端独立发布、无合约测试保证兼容性（根因层面：流程缺陷使此类错误必然发生）。

**阶段 2 出口条件**：因果链至少追问到 Why 3；每层"因为"都有代码/日志证据支撑（不是猜测）；已标注最深根因层；根因指向外部系统 → 已记录并准备跳过阶段 3-4（无法追踪外部系统数据流）。

### 阶段 3：数据流逆向追踪

> 从出错点出发，向上游追溯数据的完整流动路径，精确定位**数据是在哪一步变坏/丢失/变错的**。

#### 第一步：绘制数据流图

从出错点开始，向上游追溯每一步数据变换（转换/过滤/校验/存储/传递——不做任何事也是"传递"），标注每个变换点的数据进出与检查结果：

```
用户输入 → [变换点1 前端表单→JSON] 检查: email 是否规范化？❌ 没有 .toLowerCase()
  → [变换点2 HTTP→后端路由] 检查: 中间件是否修改 email？无
  → [变换点3 Controller→Service→Repository] 检查: 是否有大小写转换？❌
  → [变换点4 Repository→SQL] SQL: WHERE email = '...' 检查: 是否大小写不敏感？❌
  → [出错点] 查询返回空 → null → NullPointerException
  ★★★ 坏数据源头: [变换点1]——前端未做 .toLowerCase()（或 [变换点4]——SQL 应使用 LOWER()/CI 排序规则）
```

#### 第二步：标注每个变换点的检查结果

对每个变换点回答：1) 这个变换点做什么？2) 进入和离开时的数据分别是什么（能取真实数据则用真实数据）？3) 数据在这里是否已经不正确了？4) 如果此处正确，下一步在哪变坏的？

#### 第三步：标记坏数据源头

用 ★★★ 标记**最先**出现坏数据的变换点——这就是数据层面的根因位置。如果数据在所有变换点都正确、唯独在出错点出错 → 根因在出错点本身的逻辑，不需要再向上追溯。

#### 数据流追踪策略

| 策略 | 适用场景 | 做法 |
|------|---------|------|
| 正向追踪 | 知道输入、不知道输出为何错 | 从输入开始逐步执行，观察每步数据变化 |
| 逆向追踪（默认） | 知道出错点、不知道坏数据从哪来 | 从出错点向上游追溯，检查每个变换点的输入输出 |
| 二分法 | 变换链很长（10+ 步） | 在链路中间插检查点，先定坏数据在前半段还是后半段 |
| 并行追踪 | 多条数据流汇聚到出错点 | Agent 派多个只读子智能体，每个追踪一条分支 |
| 插桩调试 | 多个变换点"不确定"，或需精确定位多组件断裂点 | 在组件边界插入诊断日志/断点 → 技术 B |

**阶段 3 出口条件**：数据流图已绘制（至少覆盖出错点上游 3 层）；每个变换点检查结果已记录；坏数据源头已用 ★★★ 标记；源头在外部系统 → 已标注，阶段 4 调整为"已知局限"；≥2 个变换点"不确定" → 已考虑启动技术 B。

### 阶段 4：假设-验证循环

> **本 skill 的"科学方法"阶段。** 不要相信第一个假设——设计实验来证伪它。只有经得起证伪尝试的假设才是可信的根因。

#### 第一步：形成假设

基于阶段 2/3 的发现，用一句话精确表述根因假设：

```
我认为根因是 [X 位置的 Y 逻辑]，
因为 [证据 A + 证据 B]。
如果这个假设正确，那么 [可观察的预测 C] 应该成立。
```

**好的假设必须可证伪**：

| 坏的假设（不可证伪） | 好的假设（可证伪） |
|---------------------|-------------------|
| "可能是环境问题" | "如果根因是环境问题，在 staging（同配置）也应能复现" |
| "代码写得不好" | "如果根因是 `getUser()` 没 null 检查，传入 null 时应抛 TypeError" |
| "数据库有问题" | "如果根因是 email 大小写不匹配，用 LOWER() 包装查询后 bug 应消失" |

#### 第二步：设计证伪实验

对每个假设设计**证伪实验**——试图证明它错误，而非证明正确。先写出"如果这个假设是错的，我应该看到什么现象"，再设计实验。这样可以抵抗 LLM 天然倾向寻找确认性证据的偏差。

| 假设 | 证伪实验 | 假设正确预测 | 假设错误预测 |
|------|---------|------------|------------|
| 根因是前端未做 toLowerCase | 前端加 toLowerCase → 重测 | bug 消失 | bug 仍在 |
| 根因是 SQL 大小写敏感 | 手动执行 LOWER() 查询 | 返回用户 | 仍不返回 |

#### 第三步：执行验证并判定

1. **执行**：实际运行代码、查询数据库、查看日志——不要推理，要亲眼看到结果。
2. **判定**：✅ 假设通过证伪尝试 → 可信度↑；❌ 被推翻 → 回阶段 2 或 3 重新形成假设；⚠️ 不确定 → 设计更精确实验。无法设计实验 → 标注"无法验证"，降为 🟡 中等可信度。

#### 第四步：多假设竞争（如有）

并发设计实验、并行验证多个假设，按"最容易验证"顺序执行：不改代码验证 > 改测试代码 > 改源码 > 部署到其他环境。

**推翻次数警告**：1 个被推翻 → 正常，形成第 2 个；2 个被推翻 → 停下，检查是否遗漏关键信息（回阶段 1 补充）；3+ 个被推翻 → **升级**：可能是架构性问题、第三方依赖 bug、或用户提供的信息有误。生成"假设推翻报告"交回 bug-fix-verify，建议重新审视 bug 描述或考虑外部因素。

**偶发/flaky**：症状为测试偶发失败或不可稳定复现时，仅一次验证实验不足以确认根因——需要统计显著性判定，见技术 E。

**阶段 4 出口条件**：≥1 个根因假设经证伪实验验证；确认的假设有 ≥2 个独立证据支撑（证据来源不能是同一个文件或同一条日志）；被推翻的假设已记录推翻原因和证据；3+ 假设被推翻 → 已生成"假设推翻报告"并建议升级；根因指向外部系统 → 已标注"已知局限"；偶发/flaky → 已按技术 E 评估置信度。

### 阶段 5：全面性扫描

> **找到根因只完成一半。另一半：确保代码库中没有其他地方存在同样或类似的 bug。** 一个 bug 的出现通常意味着一个模式被错误地使用了多次。

#### 第一步：提取 bug 模式

从阶段 4 确认的根因中，提取可搜索的 bug 模式：

| 模式维度 | 提取方法 | 示例 |
|---------|---------|------|
| 函数/API 误用 | 出错的函数调用签名 | `findByEmail(email)` 未处理 null → 搜所有 `findByEmail` 调用点是否都做了 null 检查 |
| 数据变换缺失 | 应该做但没做的数据操作 | `email.toLowerCase()` 缺失 → 搜所有 email 比较/查询处是否规范化 |
| 条件/边界遗漏 | 缺失的 if 判断或边界条件 | 缺少 `if (result == null)` → 搜所有 DB 查询返回值的使用点 |
| 配置/环境差异 | 不一致的配置或环境假设 | 开发不区分大小写但生产区分 → 搜所有大小写敏感的字符串比较 |
| 时序/顺序依赖 | 错误的调用顺序或竞态 | 先渲染后取数据 → 搜所有在 async 外使用 await 结果的代码 |
| 校验/防护缺失 | 缺少输入校验或边界防护 | 未对用户输入规范化 → 搜所有外部输入入口是否有前置校验 |

#### 第二步：多维度搜索

**不允许只用一个 grep 就说"找全了"——每个维度可能发现不同的结果。至少使用 3 个维度。**

- **维度1 相同函数/API 调用**：搜出错函数名/方法名/API 路径的所有调用点，检查每个调用点的返回值处理、参数传入、错误处理。
- **维度2 相同数据结构/字段**：搜同一数据字段/变量的所有使用点，检查是否做了同样的数据假设。
- **维度3 相同逻辑结构/代码模式**：搜结构相似的代码（即使函数名不同）——同一设计模式多个实现、复制粘贴代码、模板生成文件。Grep 关键语法结构（`if.*== null`、`.then(`、`await.*catch`）→ 上下文窗口分析相似性。
- **维度4 相同调用链**：搜 A→B→C 整条调用链是否在其他上下文同样组装。用 Agent 派只读子智能体探索不同调用路径。
- **维度5 相同开发者/提交**：git blame 找出错代码作者，搜同作者同期修改是否有类似模式。`git log --author="name" --since="date" --oneline`。
- **维度6 相反/对称逻辑**：如果 bug 是"X 情况下应做 Y 但没做"，搜 X 的相反/对称情况——很多 bug 成对出现。
- **维度7 防御性缺口分析**：检查校验逻辑是否只在单层存在（输入层/中间层/输出层）。假设每个输入都是异常的 → 校验是否在所有层都存在？只在某层 → 记录为 ⚫ 防御缺口，连同 🔴🟠 类 bug 一同报告。防御缺口的修复建议属 bug-fix-verify 职责，本 skill 只识别和报告。

#### 第三步：分类和优先级

| 分类 | 定义 | 处理建议 |
|------|------|---------|
| 🔴 同类 bug（确认） | 完全相同的根因导致的可复现异常 | 必须与主 bug 一同修复 |

## 专项排查技术库

> 五项深度工具。它们不是独立阶段——从对应阶段分叉进入的可选方法。每项描述：何时触发、如何执行、产出什么。

### 技术 A：竞态条件排查

**触发条件**（满足任意一条即启动）：症状分类为 🔵 竞态/不稳定；bug 偶发、不可稳定复现（复现率 <50%）；与并发操作相关（多线程/多进程/异步事件/定时器）；同样的输入有时正常有时异常；加 sleep/延迟后 bug 行为改变。

**执行方法**：
1. **A1 事件顺序重建**：列出 bug 场景中所有并发的操作/事件和共享资源（变量/文件/DB 连接），确定可能的执行顺序。对比正常时间线 vs bug 触发时间线——找出脏读（B 在 A 写入完成前读到旧值）或覆盖（B 基于旧值算出结果覆盖 A 的写入）。
2. **A2 时序图分析**：绘制并发组件交互时序图，标注关键事件顺序依赖和竞态窗口。
3. **A3 Interleaving 分析**：枚举关键操作的指令交错序列，列出所有导致异常的交错。例：A1 检查缓存 → A2 缓存未命中查库 → A3 回填缓存；B1 删除缓存。异常交错 A1→B1→A2→A3 = A 在 B 删缓存后查到旧数据并回填，缓存变脏。
4. **A4 条件轮询替代盲等**：如果 bug 涉及任意 timeout（`sleep(1000)`、`setTimeout(..., 5000)`），分析是否可用事件驱动等待替代。盲等（脆弱）：`await sleep(5000); checkResult()`——慢机器不够、快机器浪费。条件轮询（可靠）：`await waitFor(() => result !== undefined, {timeout: 30000, interval: 200})`——条件满足立即返回，绝不盲等。详见 [references/condition-based-waiting.md](references/condition-based-waiting.md)。

**产出**：事件顺序对比（正常 vs 异常）、时序图（标注竞态窗口）、Interleaving 异常序列、竞态假设（哪个操作序列导致不一致）、条件轮询替代建议。

### 技术 B：插桩调试

**触发条件**（满足任意一条即启动）：数据流图有 ≥2 个变换点"不确定"；需精确定位多组件系统断裂点（前端→API→Service→DB）；错误信息不包含足够位置信息（"内部错误"/"未知异常"）；怀疑环境/配置传播在某层丢失。

**执行方法**：
1. **B1 组件边界插桩**：在每个组件边界插入诊断日志/断点，记录「进」和「出」。对每个边界记录：进 = 方法调用参数/HTTP 请求，出 = 方法返回值/HTTP 响应。运行一次收集所有边界日志 → 对比哪一层的"出"与预期不符。插桩示例（排查完成后移除）：`console.log('[DIAG] Layer: API→Service | In:', JSON.stringify(params)); const result = service.doSomething(params); console.log('[DIAG] Layer: API→Service | Out:', JSON.stringify(result));`
2. **B2 二分法缩小范围**：变换链较长（5+ 步）时在链路中间插入检查点，每轮缩小一半（8 步链最多 3 轮定位，16 步链最多 4 轮）。
3. **B3 环境/配置传播验证**：对每一层检查——接收了哪些环境变量/配置？使用了哪些、值与预期一致？传递给下一层时是否遗漏或覆盖？

**产出**：组件边界数据对比表（每边界的"进"与"出"）、精确定位的断裂组件 + 断裂点前后数据差异、二分法缩小后的最小可疑区间、环境/配置传播异常层。

### 技术 C：Bisect 二分定位

**触发条件**（满足任意一条即启动）：回归型 bug（"之前好现在坏"）；有可用 git 历史；不确定由哪次提交引入；有 ≥2 个候选提交范围需缩小。

**执行方法**：
1. **C1 git bisect 自动化**（存在可自动执行的验证方式时）：
```bash
git bisect start
git bisect bad HEAD          # 标记当前版本为坏
git bisect good v2.1.0       # 标记已知好的版本（如上次发布 tag）
git bisect run ./scripts/verify-fix.sh   # 或: git bisect run npm test -- --testPathPattern="failingTest"
git bisect log               # 自动定位到引入 bug 的 commit
git bisect reset             # 结束 bisect（必须，避免留在 detached HEAD/bisect 状态）
```
2. **C2 脚本化验证**：编写自动执行验证脚本——测试失败 exit 1（bad）、通过 exit 0（good）。例：`npm run build || exit 1; npm test -- --testPathPattern="login" || exit 1`。
3. **C3 手动 bisect**（需 UI 操作/特定环境时）：`git log --oneline <good>..<bad>` 取候选 → 二分检出中间 commit → 手动测试 bug 是否存在 → 存在则 bad=mid、不存在则 good=mid → 重复至范围缩小到 1-2 个提交 → `git show <bad_commit>` 看 diff。

**产出**：引入 bug 的提交 SHA、完整 diff（变更内容、文件列表）、提交信息（作者、时间、关联 issue）、引入 bug 的具体变更行。

### 技术 D：防御性排查

**触发条件**（满足任意一条即启动）：bug 涉及外部输入（用户输入/API 请求/文件上传/消息队列）；根因与输入校验缺失或边界条件遗漏相关；系统有多个层级（前端→后端→数据库/多层微服务）；修复可能只在单层进行——需评估上下游是否同样脆弱。

**执行方法**：
1. **D1 假设输入异常（穷举异常值）**：对 bug 相关的每个关键输入接口，穷举异常值：null/undefined、空串、格式错误（"not-an-email"）、超长（1 万字符）、XSS（`<script>`）、路径遍历（`../../etc/passwd`）、null byte 注入。对每个异常值，追踪从入口到出错点的完整路径，记录每层如何处理（校验/转换/忽略/崩溃）。
2. **D2 边界条件穷举**：数值边界（0/-1/1/MAX_INT/溢出）、集合边界（空数组/单元素/大量）、状态转移边界（初始→重复初始化、终态→再次触发、非法状态）、时间边界（epoch、过期临界、时间回拨）。
3. **D3 多层校验缺口分析**：检查校验逻辑是否在所有层都存在——而非仅依赖某一层。例：前端 HTML5 type=email（有格式校验）、网关 API 无校验直接透传（🔴 全缺）、Service 仅不为 null（🟠 格式缺）、DB 参数化查询（✅）。结论：前端可被 curl/脚本绕过，畸形输入直通 Service——需至少在 API 或 Service 层加校验。
4. **D3.1 防御纵深四层模型**（排查到 bug 时问"从哪一层能阻止它"）：

| 层级 | 名称 | 做什么 | 设计问题 |
|------|------|--------|---------|
| L1 | 入口点验证 | API 边界拒绝非法输入（类型/格式/范围） | "如果调用方传了 null？" |
| L2 | 业务逻辑验证 | 确保数据对当前操作有意义（状态前置/业务规则） | "如果状态不是 ACTIVE？" |
| L3 | 环境守卫 | 防止在错误上下文执行危险操作（测试环境不连生产 DB） | "如果在错误上下文被调用？" |
| L4 | 调试插桩 | 捕获足够上下文用于取证（关键变量/调用栈/时间戳） | "如果 bug 在生产中发生，有什么诊断信息？" |

   L1 被绕过 → 加强入口验证；L2 缺失 → 增加前置条件检查；L3 没考虑 → 增加环境检查；L4 缺失 → 增加诊断日志。案例：生产误发测试邮件——L1 地址合法无法拦截、L2 用户状态 ACTIVE 无法拦截、L3 缺失（没检查运行环境）、L4 缺失（不知道哪封邮件从何触发）→ 根因 L3，修复 = 发送前检查环境 + L4 加环境标识日志。

**产出**：异常输入穷举表、边界条件覆盖检查表、多层校验缺口清单（⚫）、攻击面排序（🔴 无任何校验 > 🟠 单层校验 > 🟡 校验不完整）。

### 技术 E：Flaky test 分析

**触发条件**（满足任意一条即启动）：bug 表现为测试偶发失败、不可稳定复现；修复后的验证——需判断"真修好了还是恰好这次没触发"；同一个测试多次运行结果不一致。

**执行方法**：
1. **E1 统计显著性判定**：**核心原则——不是"跑了 3 次没挂就算过"**。估算原始失败率 P_fail（收集 ≥20 次历史运行数据），所需连续通过次数 N = log(α)/log(1−P_fail)，α 为可接受误判概率（建议 0.01）。快速判定表：

| 原始失败率 | 需要连续通过次数 | 判定 |
|-----------|:-------------:|------|
| 50%（每次都有机会挂） | 7 | 跑 7 次全过 → 可信 |
| 30%（3 次里挂 1 次） | 13 | 跑 13 次全过 → 可信 |
| 10%（10 次里挂 1 次） | 44 | 跑 44 次全过 → 可信 |
| 5% | 90 | 跑 90 次全过 → 可信 |
| < 5%（极稀有） | 100+ | 增加日志 + 标记"低置信度" |

2. **E2 失败模式聚类**：收集多次失败日志，按错误类型聚类（如超时 3/5、500 错误 1/5、空指针 1/5）。≥2 种不同失败模式 → 可能存在多个独立根因，每种模式需要独立的假设-验证。
3. **E3 环境因素隔离**：逐一排除常见 flaky 根因，每个因素设计一个排除实验：时间依赖（固定时钟 mock Date.now/sinon fakeTimers）→ 根因是时间逻辑；执行顺序依赖（--shuffle）→ 测试间共享状态未清理；外部服务（mock 固定数据）→ 外部服务不稳定；随机数（固定随机种子）→ 对随机值隐式依赖；异步时序（sync flush）→ 竞态条件（→ 同时用技术 A）；资源竞争（--runInBand/-j 1）→ 并行执行资源冲突；数据污染（每测试前重建 DB/清理状态）→ 前一个测试的副作用。

**产出**：原始失败率估算 + 所需连续通过次数 N、失败模式分类（可能揭示多个独立根因）、环境因素隔离实验矩阵、flaky 修复置信度评估（🟢 高/🟡 中/🔴 低——基于统计判定）。
