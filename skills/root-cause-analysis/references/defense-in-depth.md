# 防御纵深四层模型

让 bug 在结构上不可能发生——不只是修复它。

## 四层框架

| 层级 | 名称 | 做什么 | 设计问题 |
|------|------|--------|---------|
| L1 | 入口点验证 | API边界拒绝非法输入（类型/格式/范围检查） | "如果调用方传了 null？" |
| L2 | 业务逻辑验证 | 确保数据对当前操作有意义（状态前置条件/业务规则） | "如果用户状态不是 ACTIVE？" |
| L3 | 环境守卫 | 防止在错误上下文中执行危险操作 | "如果在错误上下文被调用？" |
| L4 | 调试插桩 | 捕获足够上下文用于取证（关键变量/调用栈/时间戳） | "如果发生在生产，有什么诊断信息？" |

## 使用方式

排查到 bug 时，不只修复——追问：从哪一层能阻止？

- L1 被绕过 → 加强入口验证（类型/范围/格式检查）
- L2 缺失 → 增加业务层前置条件检查
- L3 没考虑 → 在危险操作前加环境检查
- L4 缺失 → 增加诊断日志，下次出问题不再盲飞

## 案例

```
Bug：生产环境误发测试邮件给真实用户

L1 入口：邮件地址合法 → 无法拦截
L2 业务：用户状态 ACTIVE → 无法拦截 —— 到此防不住
L3 环境：[缺失] 未检查运行环境——测试环境应拒绝发送
L4 插桩：[缺失] 未记录触发上下文——不知道哪封从何来

根因：L3 缺失。修复 = 发送前加环境检查 + L4 加环境标识日志
```

## 设计即防御

在功能开发时就用四层框架审查设计——不要等 bug 出现后再补：

1. 对于每个外部输入 → L1 如何拒绝非法输入？
2. 对于每个业务操作 → L2 前置条件是什么？
3. 对于每个有副作用的操作 → L3 环境上下文是否正确？
4. 对于每个关键数据转换 → L4 是否记录了足够的诊断信息？
