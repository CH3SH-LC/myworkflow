# 需求澄清

## 定位

通用信息收集与决策辅助工具——任何需要用户补充信息、需求细化、或方案决策的场景都可调用。**谁调用就返回给谁**（不强制返回任务分类入口）。禁止递归（调用方本身在澄清时不得再调本 skill）。

## 硬门禁

需求未被确认前，**禁止写任何代码、产出任何内容、或调用执行类 skill**。即使项目很小也必须走完澄清流程——"简单项目恰是未检查假设造成最多返工的地方"。简单需求的报告可以短（几句话），但 MUST 生成并获用户确认。用户说"直接做"不是绕过硬门禁的理由——至少确认核心目标 + 输出形式，并在报告中标注"用户要求精简，以下为基于假设的需求"。

## 清晰度最低标准

需求"清晰"须同时满足三项，任一项不满足即进入澄清循环：

| # | 维度 | 检查问题 |
|---|------|---------|
| 1 | 目标 | 能一句话描述最终产出物？最终用户能看到/用到什么？ |
| 2 | 上下文 | 涉及哪些文件/模块/系统？有什么前置条件？ |
| 3 | 约束 | 技术栈/性能/兼容性限制？明确不能做什么？ |

- 三项全满足 → 跳过澄清循环，直接方案生成。
- 用户说"直接做" → 仍至少确认目标+输出形式，标注假设。

## 执行流程

### 阶段 1：读取上下文

读取项目 CLAUDE.md、PROGRESS.md、相关代码/配置，了解技术栈与已有约定。

### 阶段 2：硬门禁检查

对照「清晰度最低标准」三项逐一检查请求。三项全满足 → 先做阶段 2.5 再跳方案生成；任一项不满足 → 进入澄清循环。

### 阶段 2.5：多子系统检测

需求描述 ≥2 个独立子系统（如"做一个平台，含聊天、存储、计费"）→ **先不逐项澄清**，告知用户"需求涉及 N 个子系统，建议拆成 N 个子项目逐个推进"，帮其排定优先级从核心开始；用户坚持一次全做 → 警告范围过大风险但尊重决定。

### 阶段 3：澄清循环（核心）

**多轮启发式提问**，逐项补齐清晰度三项：
- **允许多问**——一轮可以把若干个模糊点合并提问，不必每轮只问一个；
- 但**每个问题都必须有价值**：它的答案要能实际改变后续方案或产出；
- 一律用 `AskUserQuestion` 提供 2-4 个选项，**不用纯文本提问**；
- 优先补齐**目标 → 上下文 → 约束**；同一维度的多个点可合并到一轮里问；
- 逐轮直到三项全满足；超过 5 轮仍有模糊点 → 报告中标注"以下为未确认假设"列项让用户批量确认。
- 效率提示：用户已通过对话/表单提供足够信息则跳过对应提问。

**"有价值"的判据**：这个问题的答案会不会改变我接下来做什么？**会 → 问；不会（只是走流程、只是确认已知信息、只是让澄清显得充分）→ 不问。**

**反模式（禁止）**：问的答案不影响任何后续动作（为问而问，哪怕一次只问一个也是噪声）；用纯文本而非 `AskUserQuestion` 提问；猜意图后直接动手（猜错=全部返工）；用户说"随便"就跳过（给出默认选项确认）；"太简单不需要澄清"（简单项目是返工重灾区）；用"你觉得呢"代替具体选项。

### 阶段 4：方案生成与对比

非平凡需求必须生成 **≥2 个**可行方案；只有一种技术路径则从"实现粒度"拆分（最小可行版 vs 完整版 / 快速版 vs 稳健版）。**YAGNI**：生成方案时主动删除不必要功能——去掉后还能满足核心目标就删。

- **平凡判定**（可跳过阶段4直接出简版报告）：单行改动不改逻辑、纯查询、纯格式化、变量重命名。
- **非平凡判定**：新建文件/跨文件修改、架构或设计选择、有多种可行实现路径 → 非平凡。

每个方案含：思路、优点、缺点、适用场景、预估工作量。用对比表展示后 `AskUserQuestion` 让用户选择；都不满意 → 问不满意的点重新生成；可合并方案 A/B 优点生成方案 D。

### 阶段 5：可视化（按需）

按类型生成 ASCII 图，判定规则：涉及 ≥3 组件/服务/模块交互 → 架构图；数据经 ≥3 次转换 → 数据流图；有明确状态切换（≥3 状态）→ 状态转换图。纯文本/简单 CRUD/单文件修改 → 跳过。

### 阶段 6：生成需求报告

输出结构化报告：
```
## 需求报告：<主题>
核心目标：[一句话]
原始需求：[用户原话，保留完整上下文]
澄清要点：[Q→A 列表；无需澄清则标注"需求已清晰"]
输入：[数据/来源]    输出：[最终产出物]
涉及范围：[新建/修改/不涉及 各列出]
约束条件：[技术/性能/兼容性]
边界条件：[空输入/异常输入/大数据量 如何处理]
方案对比：[阶段4表格，平凡可省略]
可视化：[ASCII图，无则写"不适用"]
验证标准：[怎么判断做完了/做对了]
潜在风险：[...]
```

### 阶段 7：报告自检

展示前做 4 项自检并修复：占位符扫描（TBD/TODO/待定）；内部一致性（如约束说 PostgreSQL 但方案用了 MongoDB）；范围聚焦（是否混入无关内容）；歧义检查（能有两种理解的表述改单一明确）。修完即继续，不需重审。

### 阶段 8：落盘

落盘位置取决于当前文件夹的性质：

| 情形 | 落盘位置 |
|------|---------|
| **项目文件夹**且已有 `docs/` 体系 | 需求文档即 design——**交 `myworkflow:project-maintain` 登记为 design**；本技能不直接写 `docs/design/index.json`（该文件的写入单点归 project-maintain） |
| 项目文件夹但尚无 `docs/` 体系 | 提示用户走 `myworkflow:project-init`；用户选择跳过则落到 `<当前目录>/docs/design-<slug>.md` |
| **常规文件夹**（非项目） | 落到 `<当前目录>/<slug>-需求报告.md` |

slug 用英文小写+连字符（如 `user-login-flow`）。目录不存在自动创建；写入失败则输出到对话并标注"落盘失败（原因：XXX）"。文件开头附加元信息：生成日期、调用方、澄清轮次、选定方案、决策理由。

### 阶段 9：用户确认

展示报告摘要（核心目标+选定方案+关键决策）等用户确认。"对"→完成；"XX 需改"→修改重确认；"换方案"→回阶段 4。报告是后续开发的**合同**，执行 skill 以报告为准。

### 阶段 10：返回调用方

返回时显式带上报告文件完整路径。**谁调用就返回给谁**：task-router 调用→回到路由表；agent-dev-loop 调用→回其阶段 1；project-maintain 调用→回其 design 补齐流程；其他→回对应 skill。

## 完成标志

- [ ] 硬门禁检查完成（三项最低标准均已评估）
- [ ] 多子系统检测完成（如涉及，已拆解并排定优先级）
- [ ] 澄清循环完成（提问均有价值且用 AskUserQuestion，或用户确认"直接做"并标注假设）
- [ ] 非平凡需求已生成 ≥2 方案对比并经用户选择
- [ ] 按需生成可视化图（架构/数据流/状态机）
- [ ] 需求报告已生成（含全部 section）并自检通过
- [ ] 报告已按当前文件夹性质落到正确位置（项目内交 project-maintain 登记 / 常规文件夹就地落盘）
- [ ] 用户已确认报告
- [ ] 已返回调用方
