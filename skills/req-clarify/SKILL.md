# 需求澄清 v3

## 定位

本 skill 是一个**通用信息收集与决策辅助**工具。它不是一个固定工作流步骤——任何需要用户信息补充、需求细化、或方案决策的场景，都可以调用它。

**谁可以调用**：
- 任务分类入口（三步工作流中的需求细化）
- 智能体闭环开发（开发过程中需要用户确认方案选择）
- Bug修复与验证（需要用户补充 bug 细节、确认修复策略）
- 深度调研（需要用户确认调研方向和范围）
- 任何其他 skill，只要需要用户输入或决策

**出口**：完成澄清后，返回**调用方**——谁调用，就返回给谁。不强制返回任务分类入口。

> ⚠️ **禁止递归**：如果调用方本身正在执行需求澄清流程，不允许再次调用本 skill。

| 关联 Skill | 关系 | 说明 |
|-----------|------|------|
| **任务分类入口** | 调用方 | 三步工作流中步骤 2 调用本 skill 细化需求 |
| **智能体闭环开发** | 调用方 | 阶段 1/2 中需求不清晰时调用本 skill |
| **Bug修复与验证** | 调用方 | 步骤 ① 中收集 bug 细节时调用本 skill |
| **深度调研** | 调用方 | 调研范围不清晰时调用本 skill |

---

<HARD-GATE>
需求未被确认前，**禁止**写任何代码、产出任何内容、或调用任何执行类 skill。

这不是可选的。"简单"项目恰恰是未检查的假设造成最多返工的地方。即使项目很小，也必须走完澄清流程。简单需求的报告可以短（几句话），但 MUST 生成并获用户确认。

用户说"直接做"不是绕过硬门禁的理由——至少需要确认核心目标 + 输出形式，并在报告中标注"用户要求精简，以下为基于假设的需求"。
</HARD-GATE>

## 清晰度最低标准

一个需求被认为是"清晰"的，必须同时满足以下三项：

| # | 维度 | 含义 | 检查问题 |
|---|------|------|---------|
| 1 | **目标** | 用户想要达成什么？ | 能用一句话描述最终产出物吗？最终用户能看到/用到什么？ |
| 2 | **上下文** | 在什么环境/项目中执行？ | 涉及哪些文件/模块/系统？有什么前置条件？ |
| 3 | **约束** | 有什么限制条件？ | 技术栈限制？性能要求？兼容性要求？明确不能做什么？ |

**判定规则**：
- 三项全部满足 → 跳过澄清循环，直接进入方案生成（阶段 4）
- 任一项不满足 → 强制进入澄清循环（阶段 3），逐项补齐
- 用户说"直接做" → 仍然至少确认目标 + 输出形式，标注假设

## 执行流程

### 阶段 1：读取上下文

1. 读取项目的 CLAUDE.md（如果存在）
2. 读取 PROGRESS.md 了解项目进度与状态
3. 读取相关代码/配置文件
4. 了解当前项目状态、技术栈、已有约定

### 阶段 2：硬门禁检查

对照「清晰度最低标准」三项，逐一检查用户请求：

```
清晰度检查清单：
□ 目标明确？（能一句话说清最终产出物）
□ 上下文清楚？（知道在哪个项目、涉及哪些文件）
□ 约束条件有？（技术限制、性能要求、不做什么）
```

- 三项全部满足 → 先执行阶段 2.5（多子系统检测），再根据阶段 2 规则判断是否跳至阶段 4。
- 任一项不满足 → 进入阶段 3（澄清循环）

### 阶段 2.5：多子系统检测

在开始逐项澄清之前，先评估需求范围：

- 如果用户需求描述了 ≥2 个独立子系统（如"做一个平台，包含聊天、文件存储、计费、数据分析"），**先不要进入逐项澄清**。
- 立即告知用户："你的需求涉及 N 个独立子系统：A、B、C。每个子系统需要独立的需求澄清和设计方案。建议先拆解为 N 个子项目，逐个推进。"
- 帮助用户排定优先级，从最核心的子系统开始。
- 如果用户坚持一次性全部做 → 警告范围过大风险，但尊重用户决定，继续进入阶段 3。

### 阶段 3：澄清循环

> ⚡ 效率提示：如果用户已通过其他方式（对话中直接说明、已填写的表单等）提供了足够信息，跳过对应的提问。阶段 4 的方案选择与阶段 9 的确认应合并在同一轮 AskUserQuestion 中（如果适用）。

**核心规则**：
- 每次只问一个问题，使用 `AskUserQuestion` 提供 2-4 个选项
- 每轮只针对一个不满足的维度
- 优先补齐"目标" → 再补"上下文" → 最后补"约束"
- 逐轮进行，直到三项全部满足
- 超过 5 轮仍有模糊点 → 在报告中标注"以下为未确认假设"，列出假设项让用户批量确认

**第一轮：确认目标**
- 核心目标是什么？（一句话）
- 最终用户能看到/用到什么？

**第二轮：确认上下文**
- 涉及哪些文件/模块？
- 有哪些不需要做的？（明确边界）

**第三轮：确认约束**
- 技术限制？（必须用什么/不能用什么）
- 性能要求？兼容性要求？

**后续轮次（按需）**：每轮只追问一个模糊点，直到清晰度标准三项全部满足。

**反模式（严格禁止）**：
| 错误做法 | 为什么不对 |
|---------|-----------|
| 一次抛出 3 个问题 | 用户困惑，通常只答一个，其余被忽略 |
| 猜测用户意图然后直接动手 | 猜错 = 全部返工 |
| 用户说"随便"就跳过 | 至少给出默认选项让用户确认 |
| "这个太简单了不需要澄清" | 简单项目是返工重灾区——假设不核对就出错 |
| 用"你觉得呢"代替具体选项 | 开放式问题增加用户负担，降低回答质量 |

### 阶段 4：方案生成与对比

> **适用于所有非平凡需求。** 平凡需求（单行配置修改、变量改名、简单信息查询、纯格式化）可跳过此阶段，直接进入阶段 6 生成简化报告。

**"非平凡"的判定**（按优先级判断——先检查是否落入平凡例外，再检查是否非平凡）：
- **先判定平凡（可直接跳过阶段4）**：仅涉及单行改动（不改逻辑）、纯查询、纯格式化、变量重命名 → 平凡
- **以下情况为非平凡**（即使满足上述平凡条件，只要涉及以下任一项就是非平凡）：
  - 涉及新建文件或涉及跨文件修改 → 非平凡
  - 涉及架构/设计选择 → 非平凡
  - 有多种可行的实现路径 → 非平凡

**多方案生成规则**：
- 必须生成 **≥2 个**可行方案
- 如果只有一种技术路径，则从"实现粒度"维度拆分：最小可行版 vs 完整版 / 快速版 vs 稳健版
- 每个方案包含：思路、优点、缺点、适用场景、预估工作量
- 复杂方案展开细节；简单方案一句话即可，但不能没有

**方案生成原则**：
- **YAGNI 原则**——在生成每个方案时，主动检查并删除不必要的功能。问自己：如果去掉这个功能，方案还能满足核心目标吗？能就去掉。

**对比表格格式**：

```
| 维度 | 方案 A：[名称] | 方案 B：[名称] | 方案 C：[名称]（如有）|
|------|---------------|---------------|---------------------|
| 思路 | [核心思路一句话] | [核心思路一句话] | [核心思路一句话] |
| 优点 | [列出 2-3 个] | [列出 2-3 个] | [列出 2-3 个] |
| 缺点 | [列出 2-3 个] | [列出 2-3 个] | [列出 2-3 个] |
| 适用场景 | [什么情况下最合适] | [什么情况下最合适] | [什么情况下最合适] |
| 预估工作量 | [人时/人天] | [人时/人天] | [人时/人天] |
| 推荐 | ⭐ 推荐 / — | ⭐ 推荐 / — | ⭐ 推荐 / — |
```

- 对比表展示后，使用 `AskUserQuestion` 让用户选择方案（选项即为各方案名称 + 简要说明）
- 如果用户都不满意 → 询问用户不满意的点 → 重新生成方案或调整已有方案
- 用户可要求"把方案 A 和方案 B 的优点合并" → 生成方案 D

### 阶段 5：可视化（按需）

当图表比文字更高效时，生成 ASCII 可视化图。按需求类型选择：

**架构级需求 → ASCII 架构图**：
```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   前端 SPA    │────▶│  BFF 层      │────▶│  微服务集群   │
│   React      │     │  Node.js     │     │  Go / Rust   │
└──────────────┘     └──────────────┘     └──────────────┘
```

**数据流需求 → ASCII 数据流图**：
```
用户请求 → [认证中间件] → [参数校验] → [业务逻辑] → [数据持久化] → [响应]
                │                            │
                ▼                            ▼
           [401 拦截]                   [事务回滚]
```

**状态机需求 → ASCII 状态转换图**：
```
  ┌──────────┐  submit  ┌──────────┐  approve  ┌──────────┐
  │  草稿    │─────────▶│  审核中   │─────────▶│  已发布   │
  └──────────┘          └──────────┘          └──────────┘
       ▲                      │                      │
       │ reject          reject│                      │ archive
       │                      ▼                      ▼
  ┌──────────┐          ┌──────────┐          ┌──────────┐
  │  已驳回  │◀─────────│  已驳回   │          │  已归档   │
  └──────────┘          └──────────┘          └──────────┘
```

**判定规则**：
- 涉及 ≥3 个组件/服务/模块的交互 → 生成架构图
- 数据经过 ≥3 次转换/处理/传递 → 生成数据流图
- 有明确的状态切换逻辑（≥3 个状态）→ 生成状态转换图
- 纯文本编写、简单 CRUD、单文件修改 → 跳过可视化

### 阶段 6：生成需求报告

整合所有信息，输出结构化需求报告。报告格式如下：

```
## 需求报告：<主题>

### 核心目标
[一句话说清要达成什么]

### 原始需求
[用户最初的原话，保留完整上下文]

### 澄清要点
- Q1: [问题] → A: [回答]
- Q2: [问题] → A: [回答]
（如无澄清则标注"无需澄清，需求已清晰"）

### 输入
- 用户提供的数据/信息
- 数据来源

### 输出
- 最终产出物（文件/功能/文档/其他）
- 用户能看到的/用到的

### 涉及范围
- 新建: [文件列表，无则写"无"]
- 修改: [文件列表，无则写"无"]
- 不涉及: [明确排除的内容]

### 约束条件
- 技术限制: [...]
- 性能要求: [...]
- 兼容性: [...]

### 边界条件
- 空输入 → [如何处理]
- 异常输入 → [如何处理]
- 大数据量 → [如何处理]

### 方案对比
[阶段 4 的对比表格，平凡需求可省略]

### 可视化
[阶段 5 的 ASCII 图，无则写"不适用"]

### 验证标准
- 怎么判断"做完了"？
- 怎么判断"做对了"？

### 潜在风险
- [风险 1]
- [风险 2]
```
	
### 阶段 7：报告自检

在展示给用户之前，对生成的需求报告进行 4 项自检：

1. **占位符扫描**：搜索 "TBD"、"TODO"、"待定"、"未确定"——如果有，替换为具体内容或标注为"待用户确认"
2. **内部一致性**：检查报告各部分之间是否存在矛盾（如：约束中说"必须用 PostgreSQL"但方案描述中用了 MongoDB）
3. **范围聚焦**：报告是否聚焦于用户的核心需求？是否混入了无关内容？
4. **歧义检查**：报告中是否存在可以有两种不同理解的表述？如果有，澄清为单一明确的表述

修复所有发现的问题。不需要重新审查——修完就继续。

### 阶段 8：落盘

将报告写入 `docs/information/` 目录：

- **目录**：项目根目录下的 `docs/information/`（不存在则自动创建）
- **失败处理**：如果目录创建失败或写入失败（权限不足/磁盘满），将报告直接输出到对话中并标注"落盘失败（原因：XXX），以下为对话内报告"
- **文件名**：`YYYY-MM-DD-<slug>.md`
  - slug 从需求主题提取，使用英文小写 + 连字符
  - 示例：`2026-07-13-user-login-flow.md`、`2026-07-13-bugfix-null-pointer.md`
- **文件内容**：阶段 6 的完整报告，并在文件开头附加元信息：

```
# 需求澄清报告：<主题>

> **生成日期**：YYYY-MM-DD
> **调用方**：<任务分类入口 / 智能体闭环开发 / Bug修复与验证 / 其它 skill 名>
> **澄清轮次**：<N 轮>
> **选定方案**：<方案 X>（如有）
> **决策理由**：<为什么选这个方案>
```

### 阶段 9：用户确认

展示报告摘要（核心目标 + 选定方案 + 关键决策），等待用户确认。用户可能：
- "对，就这样" → 进入阶段 10
- "XX 需要改" → 修改报告对应部分 → 重新确认
- "换个方案" → 返回阶段 4 重新对比

报告作为后续开发的"合同"——后续执行 skill 以报告为准，不得偏离。

### 阶段 10：返回调用方

返回调用方时，在返回信息中显式带上报告文件的完整路径。调用方通过该路径直接读取报告。

- 如果是「myworkflow:task-router」调用的 → 返回任务分类入口，继续其步骤 3（按类型路由执行）
- 如果是「myworkflow:agent-dev-loop」调用的 → 返回闭环开发，进入阶段 2（制定计划）
- 如果是「myworkflow:bug-fix-verify」调用的 → 返回 Bug 修复流程，继续后续步骤
- 如果是其他 skill 调用的 → 返回对应 skill 继续执行
- **核心原则：谁调用，就返回给谁。不强制返回任务分类入口。**

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 一次问 3 个问题 | 每次只问一个，用 AskUserQuestion 给 2-4 个选项 |
| 猜用户意图后直接动手 | 用 AskUserQuestion 确认后再行动 |
| 报告缺边界条件 | 必须覆盖空/异常/大数据量三种情况 |
| 用户说"直接做"就跳过澄清 | 硬门禁不可跳过——至少确认核心目标 + 输出形式 |
| 只给一个方案 | 非平凡需求必须 ≥2 个方案；只有一种路径则拆"最小版 vs 完整版" |
| 方案对比缺维度 | 每个方案必须含：思路/优点/缺点/适用场景/预估工作量 |
| 忘记落盘 | 报告确认后写入 `docs/information/` 才算完成 |
| 架构/数据流/状态机需求不给图 | 对应类型需求必须生成 ASCII 可视化 |
| 强行返回任务分类入口 | 谁调用就返回给谁，不自己决定出口 |
| 报告写成实现方案 | 报告是"要做什么"不是"怎么做"——实现细节留给执行 skill |

## 完成标志

- [ ] 硬门禁检查已完成（三项最低标准均已评估）
- [ ] 多子系统检测已完成（如涉及多子系统，已帮助用户拆解并排定优先级）
- [ ] 如有缺失，澄清循环已完成（≥1 轮提问，或用户确认"直接做"并标注假设）
- [ ] 非平凡需求已生成 ≥2 个方案对比
- [ ] 方案已通过 AskUserQuestion 让用户选择（或用户确认跳过方案对比）
- [ ] 按需生成了 ASCII 可视化图（架构/数据流/状态机）
- [ ] 需求报告已生成（包含全部 section：目标 → 原始需求 → 澄清 → 输入/输出 → 范围 → 约束 → 边界 → 方案 → 可视化 → 验证 → 风险）
- [ ] 报告自检已完成（占位符/内部一致性/范围聚焦/歧义四项检查均通过）
- [ ] 报告已落盘到 `docs/information/YYYY-MM-DD-<slug>.md`
- [ ] 用户已确认报告
- [ ] 已返回调用方（不强制为任务分类入口）
