## 核心流程：先查项目 → 只问改变决策的问题 → 需求报告

**何时加载**：需求模糊、缺目标/上下文/约束，用户要在 ≥2 条互斥技术路径间做方案对比与选择，或产出物形态未定。
**不加载**：纯问答、日常修复与常规实现、目标与输出形式已明确的实现；队列调度与可逆开发步骤不包装成审批节点。

**硬步骤**
1. **先查项目**：用 `glob` 摸目录、`grep` 找配置与约定、`read` 读入口文档与相关代码，先列假设清单 → 判据：查得到的都不去问用户，只把确实查不到且改变决策的列进待问清单。
2. **判清晰度**：目标（一句话说清产出物）、上下文（涉及文件/模块/前置条件）、约束（技术栈/性能/兼容性/不能做什么）三项逐项核对 → 判据：三项全满足就直接进方案，不再发问。
3. **只问会改变决策的**：每个问题先自查「会改变我接下来做什么吗、项目里查得到吗、用户说过吗」，用 `ask_user_question` 给 2–4 个具体选项，按 目标→上下文→约束 一轮问清 → 判据：不为问而问、不猜意图直接动手；用户说「随便」就给带默认值的选项，剩余模糊点写成「未确认假设」。
4. **方案对比**：非平凡需求给 ≥2 个可行方案（思路/优点/缺点/适用场景/预估工作量）并列表对比，YAGNI 删掉非必要功能；涉及 ≥2 个独立子系统先建议拆成子项目 → 判据：由用户选，不替他拍板；平凡改动可跳过对比。
5. **报告 + 确认落盘**：产出需求报告（目标/输入输出/范围/约束/边界/横向交付切分/验证标准/风险/未确认假设/证据与来源），展示前做占位符、内部一致性、范围、歧义四项自检，确认后即为开发合同 → 判据：按文件夹性质落盘并带完整路径返回，每份交付物一个 owner，依赖写 version + requires。

**完成判据**：需求报告已确认并落盘（项目内交 project-maintain 登记，常规文件夹就地落盘），澄清点与未确认假设标注清楚；证据=报告路径 + Q→A 记录 + 四项自检结果；只发问不出报告、报告含占位符都不算完成。

# 需求澄清

## 定位

通用信息收集与决策辅助。**谁调用就返回给谁**（不强制回到某个固定入口）。禁止递归：调用方本身正在澄清时，不得再调本技能。

核心不是"走完澄清流程"，而是**只补齐真正会改变下一步行动的缺失信息**。澄清是减少返工的手段，不是开工前的审批关卡：队列调度、日常修复、常规实现、可逆的开发动作都不需要用户逐项批准。

## 唯一提问标准：会改变决策，且项目里查不到

提问前逐条自查，任一为"否"就不进入提问：

1. **会改变决策吗**——这个答案会不会改变我接下来做什么？不会（只是在走过场、只是确认已知信息、只是让澄清显得充分）→ 不问。
2. **项目里查得到吗**——用 glob / grep / read 查项目入口文档（如 CLAUDE.md、README、AGENTS.md、PROGRESS.md）、目录结构、配置、依赖清单、已有代码与文档。查得到 → 自己查，不占用用户。
3. **用户已经说过吗**——对话或已给材料里已经提供的，直接采用，不重复问。

### 该问 / 不该问 对照表

| 情形 | 处理 |
|------|------|
| 最终产出物形态未定（脚本 / 服务 / 文档 / 一次性分析），且项目里看不出来 | **问**，给 2–4 个具体选项 |
| 关键约束缺失且无法从项目推断：目标平台、必须兼容的旧系统、外部账号与权限、预算或时间硬限制 | **问** |
| 存在 ≥2 条互斥技术路径且代价差异明显（自建服务 vs 复用现成脚本；最小可行版 vs 完整版） | **问**，附对比 |
| 需求里的歧义词会改变实现（"实时"、"批量"、"多用户"、"同步/异步"） | **问** |
| 不可逆或高影响决策：删数据、改对外接口、改公共约定、花钱、发布 | **问**，并说明影响面 |
| 答案能从仓库、配置、依赖或既有文档查到 | **查**，用 glob / grep / read，不问 |
| 队列调度：先做哪一项、并发多少、批次多大 | 不问，按 ready 情况自行调度 |
| 日常修复、常规实现、可逆开发步骤：改文案、补测试、局部重构、加日志、跑格式化 | 不问，直接做 |
| 请用户确认进度、确认已知信息、批准下一步 | 不问 |
| "以后可能用得上"但不影响当前实现的备选项 | 不问，写成假设 |
| 权限不足或需要扩权 | 只有用户入口能授权，模型没有等价工具；说明所需权限与最小下一步，由用户操作；不得绕过权限拒绝 |

提问用 ask_user_question，提供 2–4 个选项，不用纯文本提问。

## 清晰度最低标准

需求"清晰"须同时满足三项，任一项不满足才针对该项澄清：

| # | 维度 | 检查问题 |
|---|------|---------|
| 1 | 目标 | 能一句话描述最终产出物？最终用户能看到或用上什么？ |
| 2 | 上下文 | 涉及哪些文件 / 模块 / 系统？有什么前置条件？ |
| 3 | 约束 | 技术栈 / 性能 / 兼容性限制？明确不能做什么？ |

三项全满足 → 直接进入方案与报告，不再发问。

## 执行流程

### 1. 先读上下文（能用工具解决的一律不问）

用 glob 摸目录结构，用 grep 定位配置、约定与相关符号，用 read 读关键文档与代码，先形成候选假设清单；只把"确实查不到、且会改变决策"的项列进待问清单。

### 2. 多子系统检测

需求涉及 ≥2 个独立子系统（如"做一个平台，含聊天、存储、计费"）→ 先不逐项澄清，告知用户"涉及 N 个子系统，建议拆成 N 个子项目、按可独立交付的产物逐个推进"，并帮其排定优先级从核心开始；用户坚持一次全做 → 说明范围风险但尊重决定。

### 3. 提问：一次只问必要的

- 优先顺序：**目标 → 上下文 → 约束**；同一维度内的多个模糊点合并到一次提问里。
- 一轮只推进当前必须的分叉；只有前一答案产生新的、真正影响实现的歧义时，才发起下一次提问。
- 不设固定轮数。一旦判断继续提问不再改变决策，就把剩余模糊点整理成"未确认假设"清单，随报告让用户批量确认。
- 用户说"随便 / 你定" → 给出带默认值的选项让其确认，不替其默默决定。
- 用户说"直接做" → 采用最小假设集开工，在报告开头标注"基于假设"，不把提问变成开工前的批准节点。

**反模式（禁止）**：为问而问；用纯文本而非 ask_user_question 提问；猜意图后直接动手（猜错就是全部返工）；"太简单不需要澄清"；用"你觉得呢"代替具体选项；把调度、常规实现或可逆开发步骤包装成审批节点；同一问题反复追问。

### 4. 方案生成与对比

非平凡需求给出 ≥2 个可行方案；只有一条技术路径时，从"实现粒度"拆分（最小可行版 vs 完整版 / 快速版 vs 稳健版）。**YAGNI**：主动删除不必要功能——去掉后仍满足核心目标就删。

- **平凡判定**（可跳过方案对比，直接简版报告）：单行改动不改逻辑、纯查询、纯格式化、变量重命名。
- **非平凡判定**：新建文件、架构或设计选择、有多种可行实现路径。

每个方案含：思路、优点、缺点、适用场景、预估工作量。用对比表展示后由用户选择；都不满意 → 问清不满意的点重新生成；可合并方案 A/B 的优点生成方案 D。

### 5. 可视化（按需）

按类型生成 ASCII 图：涉及 ≥3 组件 / 服务 / 模块交互 → 架构图；数据经 ≥3 次转换 → 数据流图；有明确状态切换（≥3 状态）→ 状态转换图。纯文本、简单 CRUD、单文件修改 → 跳过，写"不适用"。

### 6. 交付切分：横向交付合约

需求报告必须把工作切成**可独立交付的产物**：module（模块）、object（对象 / 实体）、evidence-package（证据包）等，每份交付物由**一个 owner 端到端负责**（调查 → 实现 → 自检 → 修复 → 验收）。

- 拒绝阶段接力：不要"背景调查 → 设计 → 检查"或"计划 → 编码 → 审查"式的，让同一份交付物在多个人之间交接。若需求天然被这样描述，给出横向重排建议（按交付物切，而不是按工序切）。
- 交付物之间才允许有依赖，且依赖要写清 **version + requires**，requires 的类型是 published-interface（已发布接口）或 verified-result（已核实结果）；同一交付物内部不设跨人依赖。
- 后续执行期的调度约定（写进报告，便于调用方遵守）：任一项结算就立即补位，不等同批其它任务；无全批屏障、无整层等待；慢任务不阻塞其它 ready 项；**未 ready 不派发**；容量已满时拒绝并保持 ready（CAPACITY_FULL），不排队空等，也不用一次性旁路绕开上限。
- 收尾修复由**同一 owner** 承担；全局集成由 leader 与相关 owner 共同负责，不撤走前面的人、换成没有上下文的审查者。

### 7. 阻塞与超时处理

澄清或落地中遇到阻塞，按此顺序处理：

1. 记录确切失败、已尝试的动作、影响范围、以及仍然可做的事；
2. 查已装服务、源码、现成工具与当前权限；
3. 能写适配器 / 接口 / 本地桥接补齐的，就补齐；
4. 局部阻塞先做其它 ready 项，并把 blocker 精确挂到受影响的那个交付物上；
5. 确实需要外部账号、人工决策或无法获得的资源，才标记 needs_user，并给出已尝试路径与最小下一步。

不得固定"试三次就结束"，也不得无预算地重复同一个失败动作；权限拒绝不可绕过。

超时处理：**先判断进展与可恢复性**，把"状态未知 / 暂停"与"真正失败"严格分开——超时不等于失败，不要用超时直接判定失败。

### 8. 生成需求报告

```
## 需求报告：<主题>
核心目标：[一句话]
原始需求：[用户原话，保留完整上下文]
澄清要点：[Q→A 列表；无需澄清则写"需求已清晰"]
输入：[数据/来源]    输出：[最终产出物]
涉及范围：[新建 / 修改 / 不涉及 各列出]
约束条件：[技术/性能/兼容性]
边界条件：[空输入 / 异常输入 / 大数据量 如何处理]
横向交付切分：[交付物清单 + 每份的唯一 owner + 交付物间依赖(version + requires)]
调度与补位：[ready 判定、结算即补位、CAPACITY_FULL 处理]
方案对比：[第 4 节表格，平凡可省略]
可视化：[ASCII 图，无则写"不适用"]
验证标准：[怎么判断做完了 / 做对了]
潜在风险：[...]
未确认假设：[...]
证据与来源：[已核实项及其来源；推测项单列并标注"未核实"]
```

结果分层：给调用方与用户的应是**简短结论 + 可核查的 evidence / artifact 引用**；原始材料留在文件或子会话里。摘要须含来源、版本、遗漏、不确定性、未完成项。区分"已核实 / 有来源"与"推测 / 未核实"，不夸大，不在无证据时声称"验证通过"。

### 9. 报告自检

展示前做 4 项自检并就地修复：占位符扫描（TBD / TODO / 待定）；内部一致性（约束说 PostgreSQL 却在方案里用 MongoDB）；范围聚焦（是否混入无关内容）；歧义检查（能有两种理解的表述改单一明确）。修完即继续，不需再审一轮。

### 10. 落盘

落盘位置取决于当前文件夹性质：

| 情形 | 落盘位置 |
|------|---------|
| **项目文件夹**且已有 `docs/` 体系 | 需求文档即 design——交 skill(name="myworkflow-project-maintain") 登记为 design；本技能不直接写 `docs/design/index.json`（该文件的写入单点归 project-maintain） |
| 项目文件夹但尚无 `docs/` 体系 | 提示用户走 skill(name="myworkflow-project-init")；用户选择跳过则落到 `<当前目录>/docs/design-<slug>.md` |
| **常规文件夹**（非项目） | 落到 `<当前目录>/<slug>-需求报告.md` |

slug 用英文小写加连字符（如 `user-login-flow`）。目录不存在自动创建；写入失败则输出到对话并标注"落盘失败（原因：XXX）"。文件开头附元信息：生成日期、调用方、澄清次数、选定方案、决策理由。

### 11. 确认与返回

展示报告摘要（核心目标 + 选定方案 + 关键决策），由用户确认："对"→完成；"XX 需改"→修改并重确认；"换方案"→回第 4 节重新对比。

确认只针对会改变产出的内容；报告一旦确认即为后续开发的**合同**，执行方以报告为准，此后常规实现步骤不再反复请求批准。返回调用方时显式带上报告文件完整路径。

## 完成标志

- [ ] 已先查项目（glob / grep / read），查得到的都没去问用户
- [ ] 清晰度三项（目标 / 上下文 / 约束）均已评估
- [ ] 多子系统检测完成（如涉及，已给出拆分与优先级建议）
- [ ] 提问都通过 ask_user_question 且每条都会改变决策；剩余模糊点已列为未确认假设并标注
- [ ] 非平凡需求已给出 ≥2 个方案对比并经用户选择
- [ ] 报告已含横向交付切分（每份交付物一个 owner、依赖写 version + requires）
- [ ] 按需生成可视化图（架构 / 数据流 / 状态机）
- [ ] 报告已按当前文件夹性质落到正确位置（项目内交 project-maintain 登记 / 常规文件夹就地落盘）
- [ ] 自检 4 项通过；已核实的与未核实的证据分开标注
- [ ] 报告已确认，并已带完整路径返回调用方
