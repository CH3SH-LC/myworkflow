## 核心流程：跑全量测试 → 走真实用户路径 → 证据判定

**何时加载**：整体开发完成后的验收、大批量产出的集中验收、bug 修复或根因定位后的复核、提交/合并前自检。**不加载**：纯文档或纯配置修改、无代码变更的讨论、每改一行就前置的碎片门禁。

**硬步骤**
1. **环境就绪**：用 pwsh 真跑启动命令并记录耗时与关键日志 → 判据：程序真起来（监听端口/help/编译可访问）；起不来即本项未通过，读完整错误日志给最小下一步，而不是放弃验证。
2. **跑全量测试**：执行项目定义的全量命令（`npm test`/`pytest`/`go test ./...`）→ 判据：报总数-通过-失败-跳过与通过率，100% 才进下一步；**只跑单测或只挑几个文件不算验收依据**。
3. **走真实用户路径**：按六类通道（happy path/次要路径/入口/权限/数据/状态）列出不少于 5 条，逐条实操 → 判据：每条有期望 vs 实际 + 证据，不允许只写文字描述。
4. **异常与回归**：补空输入、非法输入、重复操作、未授权、资源不存在、断网等边界，再对受影响功能逐项回归 → 判据：至少覆盖空输入、非法输入、未授权访问；受影响功能逐个记 ✅/❌。
5. **出报告**：结论 + 数据，不给空泛结论 → 判据：明确 ✅/❌，附命令、统计、证据路径；确定性验证与真机/模型观察分栏记录，模拟结果标注为模拟。

**判定规则**：任一步未通过 → 列未通过项（期望 vs 实际 + 证据）回产出该交付物的 owner 修复后重验；超时先判进展与可恢复性，超时 ≠ 失败；无测试套件则手动验证全部通道，纯库 / 纯 API 项目用示例程序或逐端点调用代偿。

**记录分野**：确定性验证（可复现命令、测试、接口调用）与真实桌面 / 模型验收分栏记录；用模拟、桩件、脚本回放得到的结果必须标注为模拟，不得冒充真实完成。

**完成判据**：全量测试 100%、所有通道与异常均有证据、回归全绿、报告含具体数据；禁止无证据声称「验证通过」，证据=命令 + exit code + 输出片段。

## 定位

本技能是所有编程类技能共用的**验收判定标准**：回答「这个产物在真实环境下真的能用吗」。

**核心原则：你不是在「检查代码」，你是在「使用产品」。像真实用户一样运行、点击、输入、观察。不允许站在代码外面指指点点。**

与横向交付合约的关系：每份可独立交付的产物（module 模块 / object 对象 / evidence-package 证据包）由一个 owner 端到端负责（调查 → 实现 → 自检 → 修复 → 验收），本技能是该 owner 的自检标准与集中验收标准，**不是阶段接力里的一环**。拒绝「背景调查 → 设计 → 检查」「计划 → 编码 → 审查」这类对同一交付物的阶段接力；一旦发现这种切分，给出横向重排建议：按可独立交付的产物切分，让同一个 owner 走完全程，本技能负责其收尾判定。

加载方式：`skill(name="myworkflow-real-world-verify")`。

## 触发

- **需要执行**：整体开发完成后的验收；大批量产出后的集中验收；bug 修复后的复核；根因定位后的修复复核；提交 / 合并前自检。
- **不执行**：纯文档修改、纯配置修改、无代码变更的讨论。
- **执行时机**：在整体开发完成、或已形成明确的大批量产出后**集中执行**。不要每改一行就跑一轮，也不要把验证当成每次小改的前置门禁。
- **两类记录分开**：确定性验证（可重复复现的命令、测试、脚本、接口调用）与真实桌面 / 模型验收（真人操作界面、真实模型输出的观察）分别记录、分别给证据；用模拟、桩件或脚本得到的结果**必须标注为模拟，不得冒充真实完成**。

**红旗自检（开始前必读）**：

| 念头 | 纠正 |
|------|------|
| 「跑几个测试就差不多了」 | 测试测代码，本流程测产品，两者不等价 |
| 「改动很小肉眼看看就行」 | 改了代码就要走真实路径，没有「改动小」豁免 |
| 「系统太复杂无法完整跑起来」 | 把能跑的部分真实跑起来；跑不起来的部分如实记录并说明原因 |
| 「跑全量太慢了」 | 慢也比上线后出问题快；但按下方超时语义处理，不无预算空等 |
| 「看日志 / 输出就够了」 | 用户看的是页面、CLI 输出、文件结果，要模拟用户操作 |
| 「之前已经验证过了」 | 每次改动后重新取证据，上次通过 ≠ 这次通过 |

## 执行流程

### 步骤 0：接收参数

项目根目录、项目类型（Web 应用 / CLI 工具 / 库 / 前端 SPA / 后端 API / 全栈 / 脚本 / 其他）、本次变更概要（改了什么、影响哪些功能）、主入口与启动命令、测试命令、用户关键路径。

### 步骤 1：环境就绪检查

> **程序启动不起来 = 这一项没通过。**

1. 用 `pwsh` 执行启动命令，确认程序正常启动（server 监听端口、CLI 输出 help、SPA 编译成功可访问）。
2. 启动失败 → 用 `read` 读取完整启动错误日志，输出关键错误行，标记未通过，同时给出最小下一步；这是要优先修的问题，而不是放弃验证的理由。
3. 启动成功 → 记录启动耗时与关键日志行（截取前 20 行）作为证据。

**不可接受的「就绪」**：没实际执行（「启动命令看起来没问题」）；执行了但没等完全启动就判断「应该起来了」；端口被占用 / 编译报错仍声称环境就绪。

**超时与失败语义（严格区分）**：命令超时时，先判断**进展**与**可恢复性**——查看输出、日志、进程、产物是否有推进；「状态未知 / 暂停」与「真正失败」严格分开，**超时不等于失败**。可恢复就继续观测或换一种观测方式；确认不可恢复才记为失败，并写清确切的失败现象、已尝试的路径、影响范围、仍可做的部分。

### 步骤 2：全量测试（确定性验证）

> **跑全量，不是挑几个文件跑。跑完报告统计数据，不能只说「通过了」。**

| 项目类型 | 命令 |
|---------|------|
| Node.js | `npm test` |
| Python | `pytest` |
| Go | `go test ./...` |
| Rust | `cargo test` |

**规则**：必须执行项目定义的全量测试命令（不是挑几个测试文件）。无测试套件 → 跳过**本**步骤，直接进步骤 3 改为手动验证（不豁免，见下方「豁免条件」）。

**报告统计数据**：

```
## 全量测试结果
| 总测试数 | 通过 | 失败 | 跳过 | 耗时 | 通过率 |
### 失败测试详情（如有）：[测试名]: [错误信息摘要]
```

**判定**：通过率 100% → 进步骤 3；< 100% → 列出所有失败测试与错误摘要，标记未通过并进入修复回路（见「修复回路与阻塞处理」）；有跳过 → 列出跳过项与原因，判断是否掩盖了问题。

> 只跑单元测试 / 只跑部分测试文件，不能作为验收依据；测试全绿也不等于真实用户路径可用。

### 步骤 3：用户视角端到端验证（核心步骤）

> **以真实用户的身份，走完所有关键路径。不允许只测 happy path。**

#### 3.1 列出所有用户通道

根据项目类型和本次变更，列出用户可能走的**所有通道**（覆盖下列类型，通常不少于 5 条；明显更少说明想得不够全面，重新列举）：

| 通道类型 | 示例 |
|---------|------|
| 主要 happy path | 用户最常用的完整操作流程 |
| 次要路径 | 不常用但合法的替代操作方式 |
| 入口变化 | 不同 URL / 命令参数 / 输入来源 |
| 权限变化 | 不同角色（管理员 / 普通用户 / 未登录） |
| 数据变化 | 空数据 / 单条 / 大量数据 / 特殊字符 |
| 状态变化 | 首次使用 / 重复使用 / 中断恢复 |

#### 3.2 逐条验证每条通道

对每条通道：1) 描述用户操作（「打开页面 X → 输入 Y → 点击 Z → 看到 W」）→ 2) 实际执行（启动浏览器 / 运行命令 / 调用接口）→ 3) 观察结果 → 4) 对比期望 → 5) 记录证据（终端输出 / 截图 / HTTP 响应 / 文件输出——不允许只用文字描述）。

#### 3.3 异常与边界路径

> **happy path 通过 ≠ 功能完成。用户不会只走 happy path。**

| 场景 | 验证内容 |
|------|---------|
| 空 / 缺失输入 | 不填必填字段直接提交 → 有合理提示？崩溃？ |
| 非法输入 | 输入超长字符串 / 注入类字符 / 特殊字符 → 是否正确拒绝？ |
| 重复操作 | 快速连续点击提交 → 是否重复创建？ |
| 后退 / 刷新 | 表单填写一半刷新或后退 → 数据是否合理处理？ |
| 未授权访问 | 未登录直接访问需登录 URL → 是否正确跳转？ |
| 资源不存在 | 访问不存在的 ID / 路径 → 404 还是 500？ |
| 超时 / 断网 | 请求中切断网络 → 有合理提示？崩溃？ |

#### 3.4 真实桌面 / 模型验收记录（与 3.2、3.3 分开成节）

只能由真人 / 真机观察才能得出的结论（界面交互观感、真实模型输出质量、桌面端行为）单独记录，注明观察者、时间、环境与版本；用 mock、桩件、脚本回放得到的结果标注「模拟」，不得写成真实完成。范围未覆盖的，写「本次未覆盖」，不能当作没有问题。

### 步骤 4：回归检查

> **你改了 A，可能坏了 B。必须检查所有可能受影响的已有功能。**

1. 识别影响面：列出本次变更可能影响的所有已有功能 / 模块。
2. 逐项验证：对每个可能受影响的功能走一遍核心流程。
3. 记录结果：

```
## 回归检查
| 已有功能 | 是否受影响 | 验证方式 | 验证结果 |
| [功能A] | 是——共享[模块] | 执行[操作]→观察[结果] | ✅/❌ |
| [功能B] | 否——独立模块 | 用 grep 确认无交叉引用 | ✅ |
```

### 步骤 5：输出验证报告

> **报告必须有具体数据。不允许「验证通过」四个字代替。**

```markdown
## 真实验证报告

### 环境就绪
- 启动命令：`[命令]` / 启动结果：✅ 成功 / ❌ 失败 / 启动耗时：[N]s
- 关键日志：
  ```
  [前 20 行启动日志]
  ```

### 全量测试（确定性验证）
- 命令：`[命令]` / 总数-通过-失败-跳过：[N]/[N]/[N]/[N] / 通过率：[N]%
- 失败详情：[列表或「无」]

### 用户通道验证（共 [N] 条）
| # | 通道描述 | 期望结果 | 实际结果 | 证据 | 判定 |
|---|---------|---------|---------|------|------|
| 1 | [用户操作流程] | [期望] | [实际] | [日志/截图/输出] | ✅/❌ |

### 异常/边界验证（共 [N] 条）
| # | 异常场景 | 期望行为 | 实际行为 | 证据 | 判定 |
|---|---------|---------|---------|------|------|
| 1 | [空输入/非法输入/重复操作...] | [期望] | [实际] | [日志/截图] | ✅/❌ |

### 真实桌面/模型验收
- 观察者 / 时间 / 环境与版本：[填写]
- 结论与证据：[填写]；模拟部分已标注为模拟

### 回归检查
| 已有功能 | 验证方式 | 结果 |
|---------|---------|------|
| [功能名] | [怎么验证的] | ✅/❌ |

### 总体判定
- ✅ 通过 —— 测试、用户通道、异常场景、回归检查均通过，且有证据
- ❌ 未通过 —— 未通过项：[列表 + 期望 vs 实际 + 最小下一步]

### 证据附件
- [截图/日志/命令/文件路径；每条结论对应可核查的引用]

### 未完成与不确定项
- [遗漏范围、未核实推断、待补验证]
```

**结果分层**：给上游 / 调用方只回**简短结论 + 可核查的 evidence / artifact 引用**（文件路径、命令、日志行、证据编号）；原始材料留在文件或子会话中，不要整段回灌。摘要必须包含来源、版本、遗漏、不确定性与未完成项。

## 判定规则

**通过条件（全部满足才算通过）**：

- [ ] 步骤 1：程序主入口启动成功（或已明确记录不可启动的确切现象与影响范围）
- [ ] 步骤 2：全量测试通过率 100%（无测试套件 → 手动验证全部用户通道取代）
- [ ] 步骤 3：所有用户通道全部 ✅ 且各有证据
- [ ] 步骤 3：异常 / 边界场景覆盖到位（至少覆盖：空输入、非法输入、未授权访问）
- [ ] 步骤 4：所有受影响的已有功能回归检查 ✅
- [ ] 步骤 5：验证报告包含具体数据（非空泛描述），确定性验证与真实验收分别记录
- [ ] 证据诚实：区分「已核实 / 有来源」与「推测 / 未核实」，未覆盖范围已写明

**修复回路与阻塞处理（按顺序执行）**：

| 情况 | 处理 |
|------|------|
| 任一步骤未通过 | 输出未通过项清单（期望 vs 实际 + 证据），回到产出该交付物的 owner 处修复后重新验证 |
| 无法启动程序 | 最高优先级——先定位并修复启动问题；把确切失败现象与影响范围记录清楚 |
| 测试通过率 < 100% | 列出失败测试 → 修复后重新验证 |
| 通道覆盖不足 | 补齐通道并重新取证据 |
| 异常场景未覆盖 | 补充异常验证 |
| 报告无具体数据 | 补充证据后重新提交结论 |
| 超时 / 状态未知 | 先判断进展与可恢复性；「暂停、状态未知」不算失败，给出继续观测或恢复的最小下一步 |

**遇到阻塞时的处理顺序**：

1. 记录确切的失败现象、已尝试的操作、影响范围、仍然可以做的部分。
2. 查已装服务 / 依赖、源码、现成工具、当前权限，确认是否已有可用能力。
3. 能写适配器 / 接口 / 本地桥接补齐的，先补齐。
4. 局部阻塞时，先做其它 ready 的交付物，并把 blocker 精确挂到受影响的交付物上。
5. 确实需要外部账号、人工决策或无法获得的资源时，才标记 `needs_user`，并给出已尝试的路径与最小下一步。

不得固定「试三次就结束」，也不得无预算无限重试同一失败；权限拒绝不可绕过，被拒绝的操作不要换一种写法重试。

**豁免条件（严格受限）**：

- 无测试套件 → 手动验证所有用户通道 + 所有异常场景（步骤 3 工作量翻倍）。
- 无法启动（纯库项目）→ 全量测试 100% 通过 + 写一个使用该库的示例程序并验证其输出。
- 无用户界面（纯后端 API）→ 逐条调用所有 API 端点，验证响应体 / 状态码，并保留原始响应作为证据。

## 与团队协作的衔接

- **横向交付合约**：按可独立交付的产物切分（module 模块 / object 对象 / evidence-package 证据包），每份交付物由一个 owner 端到端负责（调查 → 实现 → 自检 → 修复 → 验收）；依赖只允许存在于不同交付物之间，并要求 **version + requires**（published-interface 或 verified-result）。
- **事件驱动滚动补位**：任一项一结算（完成 / 失败 / 阻塞）就立即补位下一项并跑它的验证，不等同批其它任务；无全批屏障、无整层等待；慢任务不阻塞其它 ready 项的验证与推进。
- **未 ready 不派发**：依赖未就绪的任务不启动、不空等；容量满时返回 `CAPACITY_FULL` 并保持该任务 ready，等有空位再派，不用一次性旁路绕过上限。
- **同一 owner 收尾修复**：验证发现的问题回到产出该交付物的 owner 手里修，修完由他重新取证据；全局集成由 leader 与相关 owner 共同负责，不撤走前面的人、换一个没有上下文的审查员接管后半程。
- **用户授权与询问**：用户已授权任务内的可逆开发不重复询问；审批与扩权只有用户入口，模型没有等价工具。只在真正改变决策、且项目里查不到答案时才用 `ask_user_question` 提问。
- **可用协作工具（autonomy-v1）**：lead 用 `team_mission_assign`（模块委托，不产生可调度项）、`team_member_create`、`team_snapshot`、`team_interrupt`、`team_layout`，**不替成员写 work/plan**；member 用 `team_plan_submit`（自己提交自己拥有的 work，`planRevision` CAS）、`team_dispatch_authorize`（授权派发）、`team_plan_cancel`（取消未来派发）、`team_subagent_start`（定向启动自己的执行者）、`team_member_inbox`（处理自己的事件）、`team_work_verify`（按验收条件核验）、`team_message`、`team_wait`、`team_recover`；leaf 用 `team_work_report`（交回结果）、`team_ask_owner`（**只向自己的 owner** 求助/回报）——`team_message` 对 leaf 不可用。文件用 `read`、`write`、`edit`、`glob`、`grep`；终端用 `pwsh`；查资料用 `web_search`、`web_fetch`；另有 `todo_write`、`present`、`job_list`、`job_output`、`job_kill`、`workflow`。

## 证据诚实

- 区分「已核实 / 有来源」与「推测 / 未核实」，不夸大，不无证据声称「验证通过」。
- 每条结论挂可核查引用：命令、文件路径与行号、日志片段、接口响应、证据编号。
- 图片、语音、文件正文、链接正文未实际读取时，必须说明未读取。
- 未覆盖的范围写明「本次未覆盖」，不能默认「没有问题」；模拟、桩件、回放结果标注为模拟。
