## 定位

本 skill 是 myworkflow **所有编程 skill 的验证门禁**。不通过本 skill = 不允许进入下一步（提交/合并/标记完成）。

**核心原则：你不是在"检查代码"，你是在"使用产品"。像真实用户一样运行、点击、输入、观察。不允许站在代码外面指指点点。**

## 触发

- **强制调用（不可跳过）**：
  - 智能体闭环开发 阶段4 开始时 → 返回 ✅ 进阶段 5，❌ 进阶段 5 问题循环
  - Bug修复与验证 步骤④ 审查时（验证子智能体修复）→ ✅ 审查通过，❌ 步骤⑤ 循环
  - 根因定位与全面排查 的修复验证环节 → 回修复步骤
  - Github协作 提交前自检 → 不允许提交
- 不触发仅限：纯文档修改、纯配置修改、无代码变更的讨论。
- **红旗自检（开始前必读）**："跑几个测试就差不多了"→ 不，TDD 测试测代码，本 skill 测产品，两者不等价；"改动很小肉眼看看就行"→ 改了代码就必须跑，没有"改动小"豁免；"系统太复杂无法完整跑起来"→ 把能跑的部分跑起来，跑不起来说明你根本不了解它；"跑全量测试太慢了"→ 慢也比上线后出 bug 快；"看日志/输出就够了"→ 用户不看日志，用户看页面/CLI 输出/文件结果，模拟用户操作；"之前已经验证过了"→ 每次改动后重新验证，上次通过 ≠ 这次通过。

## 执行流程

### 步骤 0：接收调用参数

调用方传入：项目根目录、项目类型（Web应用/CLI工具/库/前端SPA/后端API/全栈/脚本/其他）、本次变更概要（改了什么、影响哪些功能）、主入口/启动命令、测试命令、用户关键路径（≥3 条）。

### 步骤 1：环境就绪检查（硬门禁）

> **程序启动不起来 = 验证不通过。没有任何借口。**

1. 启动程序主入口：执行启动命令，确认程序正常启动（server 监听端口、CLI 输出 help、SPA 编译成功可访问）。
2. 启动失败 → 这是第一个要修复的问题：输出完整启动错误日志，标记 ❌，立即返回调用方。
3. 启动成功 → 记录启动耗时、关键日志行（截取前 20 行）作为验证证据。

**不可接受的启动验证**：没实际执行（"启动命令看起来没问题"）；执行了但没等完全启动就判断"应该起来了"；端口被占用/编译报错仍声称"环境就绪"。

### 步骤 2：全量测试套件（硬门禁）

> **跑全量，不是挑几个文件跑。跑完报告统计数据，不能只说"通过了"。**

按项目类型执行正确的全量测试命令：

| 项目类型 | 命令 |
|---------|------|
| Node.js | `npm test` |
| Python | `pytest` |
| Go | `go test ./...` |
| Rust | `cargo test` |

**规则**：
- 必须执行项目定义的全量测试命令（不是挑几个测试文件）。无测试套件 → 跳步骤 3（不豁免，改手动验证）。超时默认 5 分钟，大型项目可延长。

**报告统计数据**：
```
## 全量测试结果
| 总测试数 | 通过 | 失败 | 跳过 | 耗时 | 通过率 |
### 失败测试详情（如有）：[测试名]: [错误信息摘要]
```

**判定**：通过率 100% → ✅ 进步骤 3；<100% → ❌ 列出所有失败测试，标记不通过，返回调用方；有跳过 → ⚠️ 列出跳过的测试及原因，判断是否掩盖问题。

### 步骤 3：用户视角端到端验证（硬门禁）

> **最核心步骤。以真实用户的身份，走完所有关键路径。不允许只测 happy path。**

#### 3.1 列出所有用户通道

根据项目类型和本次变更，列出用户可能走的**所有通道**（**至少 5 条**；少于 5 条 → 想得不够全面，重新列举）：

| 通道类型 | 示例 |
|---------|------|
| 主要 happy path | 用户最常用的完整操作流程 |
| 次要路径 | 不常用但合法的替代操作方式 |
| 入口变化 | 不同 URL/命令参数/输入来源 |
| 权限变化 | 不同角色（管理员/普通用户/未登录） |
| 数据变化 | 空数据/单条/大量数据/特殊字符 |
| 状态变化 | 首次使用/重复使用/中断恢复 |

#### 3.2 逐条验证每条通道

对每条通道：1) 描述用户操作（"打开页面 X → 输入 Y → 点击 Z → 看到 W"）→ 2) 实际执行（启动浏览器/运行命令/调用 API）→ 3) 观察结果 → 4) 对比期望 → 5) 记录证据（终端输出/截图/HTTP 响应/文件输出——不允许只用文字描述）。

#### 3.3 异常与边界路径（强制）

> **happy path 通过 ≠ 功能完成。用户不会只走 happy path。**

对每条用户通道，至少验证以下异常场景：

| 场景 | 验证内容 |
|------|---------|
| 空/缺失输入 | 不填必填字段直接提交 → 有合理提示？崩溃？ |
| 非法输入 | 输入超长字符串/SQL 注入/特殊字符 → 是否正确拒绝？ |
| 重复操作 | 快速连续点击提交 → 是否重复创建？ |
| 后退/刷新 | 表单填写一半刷新或后退 → 数据是否合理处理？ |
| 未授权访问 | 未登录直接访问需登录 URL → 是否正确跳转？ |
| 资源不存在 | 访问不存在的 ID/路径 → 404 还是 500？ |
| 超时/断网 | 请求中切断网络 → 有合理提示？崩溃？ |

### 步骤 4：回归检查

> **你改了 A，可能坏了 B。必须检查所有可能受影响的已有功能。**

1. 识别影响面：列出本次变更可能影响的所有已有功能/模块。
2. 逐项验证：对每个可能受影响的功能走一遍核心流程。
3. 记录结果：
```
## 回归检查
| 已有功能 | 是否受影响 | 验证方式 | 验证结果 |
| [功能A] | 是——共享[模块] | 执行[操作]→观察[结果] | ✅/❌ |
| [功能B] | 否——独立模块 | Grep 确认无交叉引用 | ✅ |
```

### 步骤 5：输出验证报告

> **报告必须有具体数据。不允许"验证通过"四个字代替。**

```markdown
## 🔍 真实验证报告

### 环境就绪
- 启动命令：`[命令]` / 启动结果：✅ 成功 / ❌ 失败 / 启动耗时：[N]s
- 关键日志：
  ```
  [前 20 行启动日志]
  ```

### 全量测试
- 命令：`[命令]` / 总数-通过-失败-跳过：[N]/[N]/[N]/[N] / 通过率：[N]%
- 失败详情：[列表或"无"]

### 用户通道验证（共 [N] 条）
| # | 通道描述 | 期望结果 | 实际结果 | 证据 | 判定 |
|---|---------|---------|---------|------|------|
| 1 | [用户操作流程] | [期望] | [实际] | [日志/截图/输出] | ✅/❌ |

### 异常/边界验证（共 [N] 条）
| # | 异常场景 | 期望行为 | 实际行为 | 证据 | 判定 |
|---|---------|---------|---------|------|------|
| 1 | [空输入/非法输入/重复操作...] | [期望] | [实际] | [日志/截图] | ✅/❌ |

### 回归检查
| 已有功能 | 验证方式 | 结果 |
|---------|---------|------|
| [功能名] | [怎么验证的] | ✅/❌ |

### 总体判定
- ✅ 全部通过 —— 所有测试、所有通道、所有异常场景、所有回归检查均通过
- ❌ 不通过 —— 以下项目未通过：[列表 + 期望 vs 实际]

### 证据附件
- [如有截图/日志文件，附上路径]
```

## 判定与阻断规则

**通过条件（全部满足才算通过）**：
- [ ] 步骤 1：程序主入口启动成功
- [ ] 步骤 2：全量测试通过率 100%（无测试套件 → 手动验证全部用户通道取代）
- [ ] 步骤 3：所有用户通道（≥5 条）全部 ✅
- [ ] 步骤 3：异常/边界场景全部 ✅（至少覆盖：空输入、非法输入、未授权访问）
- [ ] 步骤 4：所有受影响的已有功能回归检查 ✅
- [ ] 步骤 5：验证报告包含具体数据（非空泛描述）

**阻断规则**：

| 情况 | 处理 |
|------|------|
| 任一步骤 ❌ | 返回调用方，附验证报告"未通过项目清单" |
| 无法启动程序 | 最高优先级——先修复启动问题 |
| 测试通过率 < 100% | 列出失败测试 → 修复后重新验证 |
| 用户通道 < 5 条 | 拒绝通过——必须覆盖更多通道 |
| 异常场景未覆盖 | 拒绝通过——补充异常验证 |
| 验证报告无具体数据 | 拒绝通过——补充证据后重新提交 |

**豁免条件（严格受限）**：
- 无测试套件 → 手动验证所有用户通道 + 所有异常场景（步骤 3 工作量翻倍）。
- 无法启动（纯库项目）→ 全量测试 100% 通过 + 写一个使用该库的示例程序并验证其输出。
- 无用户界面（纯后端 API）→ 用 curl/Postman 逐条调用所有 API 端点，验证响应体/状态码。
