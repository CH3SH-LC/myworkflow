# Skill：章节审查 — 单个已完成章节的质量检查

> **⚡ 连续工作流**：此 skill 是「myworkflow:写前审查 → myworkflow:具体写作 → myworkflow:章节审查」自动链的最后一环。由具体写作自动调用，审查通过后**自动推进到下一章的写前审查**。详见底部「连续工作流规则」。

## 触发场景
- 每次写完一章后（由「myworkflow:具体写作」自动触发）
- 对已审查但被退回修改的章节再次检查

## 必需要素
- 章节正文已在 `正文/` 中完成
- 细纲可查阅（对照基准）
- 本章涉及的人物设定和设定文件可查阅
- **指南/风格定位.md**：审查时必须对照本书专属的风格要求、禁忌、特殊规则——偏离指南的问题和偏离设定的问题同等对待

## 推荐要素
- 最近一次**全书一致性审查**的发现记录（如有）

## 前置强制步骤

> **核心原则：指南文件是本书的"宪法"。** 章节审查不仅要检查设定一致性和写作质量，更要检查本章是否符合本书的专属风格和禁忌要求。

1. **读取本书指南文件**：读取 `指南/` 文件夹下所有文件，逐条对照本章正文：
   - `指南/风格定位.md` — 本章的情绪基调、文风、人物互动是否符合定位？
   - `指南/核心卖点.md` — 本章是否保持了差异化定位？
   - `指南/书籍禁忌.md` — 本章正文是否触犯任一条？
   - `指南/AI记忆卡片.md` — 快速确认本章未遗漏关键约束
   - `指南/特殊设定约束.md` — 本章涉及的设定是否满足特殊约束？
   → 如果本章有违反指南的内容 → 标注为"指南违规"，必须修改
   
2. **读取 CLAUDE.md**：了解当前创作状态、上一章审查状态、待处理问题

3. **读取本章正文和对照材料**：读取 `正文/第XX章-*.md`（本章正文）、`大纲/细纲/{事件名}-细纲.md`（对照细纲）、本章涉及的角色文件和设定文件

4. **个性化调整审查标准**：
   - 如果指南要求"轻松幽默为主" → 本章如果出现过于沉重的段落，审查时应标注
   - 如果指南要求"战斗时切换严肃" → 检查战斗场景的情感基调
   - 如果指南有明确的字数/结构规则 → 直接作为审查标准

---

## 目标
对刚写完的单章进行审查，确保其与细纲、人物、设定一致，并达到写作质量标准。

**不通过 → 修改 → 重新审查本节 → 直到通过。**

---

## 执行流程

### 第一步：阅读对照材料

- `大纲/细纲/{事件名}-细纲.md`（对照本章）
- `设定/` 中涉及的设定文件（通过 `设定/索引.md` 定位）
- `角色/` 中涉及的人物设定
- `指南/风格定位.md`（本书专属参考）
- 最近一次**全书一致性审查**的发现记录（如有）——全局问题可辅助判断本章问题是否为系统性问题

### 第二步：逐项审查

---

#### 审查项一：细纲一致性

- [ ] **章节类型一致**：本章实际内容类型是否与细纲中标注的 `章节类型`（战斗类/日常类/过渡类/组合）一致？
  - 细纲标注"战斗类"，本章是否确实以战斗为主体？
  - 细纲标注"过渡类"，本章是否负载了信息增量（而非空洞的时间流逝）？
  - 细纲标注"日常类"，本章是否以人物互动和性格展现为核心？
  - 细纲标注组合（如"过渡+战斗"），各部分比例是否大致符合细纲规划？
  - 偏差合理（写出来发现某种类型更适合本章）→ 允许，但需同步更新细纲的章节类型
- [ ] 本章内容与细纲一致？
  - 偏差合理（比原计划更好）→ 允许，但需更新细纲
  - 偏差不合理（偏离了主线）→ 修改正文或调整细纲

---

#### 审查项二：人物一致性

- [ ] **行为塑造四维落地**：人物的动作/语言/神态/行为逻辑是否匹配角色文件中定义的四维行为塑造（阶段C+）？——本章至少各维度有一个特征落地（与具体写作的要求一致）
- [ ] **多标签融合正确**（如适用）：多标签人物的副标签激活后，是否只在主标签底色上渗透纹理（非完全切换人格）？
- [ ] **外貌与服饰一致**：本章描写的外貌/服饰特征是否来自角色文件的设计（阶段B+），而非临时编造？
- [ ] **人物塑造技法落地**（对应具体写作六项技法）：①出场定型法——新登场人物的第一印象是否用2-3个细节锁定？②习惯标记法——已有人物的标志性习惯是否在关键场景中自然复用？③对比凸显法——同一事件中不同角色的反应差异是否明显？④侧面烘托法——其他角色的反应是否间接塑造了目标人物？⑤成长可视化——人物状态变化是否与上一章自然延续？⑥外貌神态动作法——外貌是否在动作中带出、神态是否用微表情替代形容词？
- [ ] 所有出场人物行为符合人设（不降智）
- [ ] 人物能力和等级在设定范围内
- [ ] 人物关系没有无故变化
- [ ] 本章人物状态与上一章结尾衔接（伤势/情绪/物品）
- [ ] 人物不可能知道的信息没有出现在对话/心理中

---

#### 审查项三：设定一致性

- [ ] 力量体系使用正确（等级名称、升级规则）
- [ ] 世界观元素一致（地理、历史、势力）
- [ ] 专有名词使用正确（定义、效果）
- [ ] 无新旧设定矛盾
- [ ] 如有新设定——是否已写入设定文件和索引？

---

#### 审查项四：写作质量

**步骤 0（强制 — 不可跳过）：运行自动化检测脚本**

> 本章正文文件路径 = `正文/第XX章-{章节标题}.md`（即第一步中读取的正文文件）。
>
> 执行以下命令，一次性完成全部 17 项机械性文本检查：
> ```bash
> python "$HOME/.claude/plugins/webnovel-studio/tools/chapter_check.py" 正文/第XX章-xxx.md --format json
> ```
>
> **结果处理（必须执行）**：
> - 任何 `passed=false` 的项 → 根据 `matches` 数组逐处修改正文
> - 以下硬性规则项 `passed=false` → **必须修改后重新运行脚本确认通过**，不得跳过：
>   - `word_count`（字数不足）— 补充核心场景，不得灌水
>   - `shi`（"是"字判断句超限）— 删改至 ≤2 处
>   - `not_but`（"不是…而是…"违规）— 全部改写
>   - `compare_ruyi`（"和…一样…"违规）— 全部改写
>   - `en_punct`（英文标点侵入）— 全部替换
>   - `em_dash`（破折号超限）— 保留 ≤1 处
>   - `quotes`（引号格式错误）— 全部替换
>   - `ellipsis`（省略号格式错误）— 全部替换
>   - `punct_hierarchy`（标点层级违规：句号过多/逗号不足）— 逐段修改，将能用逗号连接的短句合并，句号仅保留于段落收束和强转折处
> - 其余项 `passed=false` → 逐处审查，修改或在审查报告中注明豁免理由
> - 全部 `passed=true` → 跳过下方"所有类型必检"中的机械性清单项，直接审查人工判断项（结尾钩子、人物、情绪等）
>
> ⚠️ **脚本未返回全部 `passed=true` 之前，不得进入第三步「综合评定」。**

**步骤 1：根据本章类型聚焦重点**（类型来源：细纲 `章节类型` 字段）：

| 本章类型 | 优先检查 |
|---------|---------|
| **战斗类** | 战斗交互感 + 展示而非告知 + 短段短句节奏 + 篇幅是否在类型范围内（小战斗半章~1章/常规1~3章/大高潮3~5章） |
| **日常类** | 对话是否符合人设 + 是否有灌水 + 轻松但不轻浮 + 是否以人物塑造为核心 |
| **过渡类** | **信息负载检查**（是否有信息增量而非空洞的时间流逝？）+ 逻辑衔接是否自然 + 篇幅是否控制在半章~1章 + **人物塑造不因过渡而中断**（过渡中是否仍有至少一个角色展示了性格细节？） |
| **组合**（如"过渡+战斗"） | ①过渡部分是否负载了信息增量（而非空洞过渡）？②过渡部分是否自然引出核心部分（因果关联，非硬接）？③核心部分是否得到了足够的篇幅展开（不被过渡挤占）？④两部分比例是否大致符合细纲规划？ |

> **写作子类型**（经营/探索/突破）不作为独立类型审查——它们出现在战斗/日常/过渡章中，审查时关注相应的写作质量（如突破章的爽点是否到位、探索章的信息增量是否足够），但类型一致性以细纲标注的结构类型为准。

**所有类型必检**：
- [ ] **字数达标**：本章正文字数 ≥ 2500字。低于此标准 → ❌ 不通过，必须补足。注意：凑字数灌水同样不通过
- [ ] **结尾钩子（非收束式）**：本书为连载，每一章都不是完整的故事。结尾必须用钩子"开启"下一章，禁止任何形式的"关闭"本章。详见下方「审查项四-附3：结尾审查」
- [ ] **关键语言规则抽检**（每章至少抽检以下六项中的四项）：
  - 是否有"不是…而是/是/只是…""没有…而是…"等转折句式？（铁律禁止）
  - 是否有"和……一样……""跟……一样……"等比较句式？（铁律禁止——全章"一样/不一样/同样/相同/不同/类似/似的/近似/无异/没什么两样/没什么不同"等近义词合计≤3次）
  - 正文是否为纯文本（无Markdown标记、无破折号（超过硬性上限1处））？
  - 是否有对比/比较手法（"与……不同""相比之下""而……却……"等）在叙述中出现？（铁律禁止——对比框架必须删除，直接呈现）
  - 是否有不必要的比喻/暗喻（"像…""仿佛…""似乎…""…似的"）可改用白描？一节内是否超过1个比喻？
  - 叙述中"是"字判断句（A是B / A就是B / 这便是… / 那正是… / 这才是… 等）是否 ≤2 处？（对话口语/客观事实/强调句"是…的"不计，≥3处 → ❌ 不通过，除非用户批准）
- [ ] **标点符号审查（每章必检）**：
  - 全角中文标点检查：是否出现英文半角 `,` `.` `?` `!` `:` `;` `"` `'` `()` 等替代中文全角标点？省略号是否正确使用"……"（非 `...` 或 `。。。`）？引号是否为全角弯引号？
  - 中英文/数字混排检查：中文与西文/数字之间是否有半角空格？
  - 标点层级检查：是否优先用逗号连接句子（一段之内句号不过多、文气不断裂）？句子内部是否用"，"分隔（无乱用顿号替代逗号）？顿号"、"是否仅用于极小的并列分割（少用）？
  - 排版禁则扫查：行首是否出现禁则字符？行末是否出现前一半符号？破折号/省略号是否在行尾断裂？
- [ ] 无灌水内容（灌水≠凑字数——2500字是底线，但用废话凑出来的2500字同样不通过）
- [ ] 无说明书式对话
- [ ] 无过度整活

**铺垫章累计检查**：
- [ ] 向前回溯：本章及上一章是否均为铺垫位置？→ 如果是，本章必须有一个小高潮或至少一次明显的情绪波动（本章不通过则回到具体写作补充情绪波动）

**常见问题速查**：
- 结尾拖着总结段 → 删除，用钩子替代
- 结尾出现"夜色渐深""他陷入沉思""明天一定会更好"等收束语 → 全部删除
- 角色说出不可能知道的信息 → 改对话
- 战斗变成"对波"或"喊技能名" → 增加动作细节和交互
- 展示不足，旁白过多 → 关键情绪改神动/动作呈现
- 字数不足2500字 → 检查是否有该展开却一笔带过的场景，补足后重审
- 过渡章纯时间流逝无信息增量 → 补充环境描写/角色对话/线索发现
- 组合章过渡与核心脱节 → 过渡中的信息必须自然引出核心事件
- 中文段落出现英文半角标点（`,` `.` `?` 等）→ 全部替换为中文全角标点（，。？）
- 省略号写成"..."或"。。。"→ 替换为"……"
- 中英文/数字之间无半角空格（"使用Python"）→ 加空格（"使用 Python"）
- 引号用英文直引号 `"..."` → 替换为全角弯引号"…"
- 行首出现逗号/句号/顿号等禁则字符 → 手动断行回避
- 破折号或省略号在行尾断裂 → 整体移至下一行
- 句号过多（一段超过 3 个句号，或全章逗号:句号 < 2:1）→ 逐句检查，能用逗号合并的短句改为逗号连接。逗号总数接近句号总数 = AI 又犯了"每句都用句号结尾"的默认坏习惯
- 顿号替代逗号（动作序列用顿号连接）→ 顿号仅用于词/短语并列，动作承接用逗号
- "是"字判断句超过2处 → 删改至 ≤2 处，或逐处向用户申请批准

#### 审查项四-附1：小高潮验证

> 如果本章在细纲中被标注为所属小事件的"核心"或大事件的"小高潮"（见细纲 `小事件概览` 表和 `所属小事件` 字段），额外检查以下项：

- [ ] **篇幅突出**：本章篇幅是否明显长于同事件内的其他章？小高潮战斗是否**至少跨2章**？（单章战斗无法承担小高潮的情绪重量和展开空间——如果小高潮只有1章 → ❌ 不通过）
- [ ] **情感强度**：本章是否在情绪上达到了该大事件内的最高点？（爽/感动/愤怒释放——至少一种情绪达到峰值）
- [ ] **剧情分量**：本章是否推动了该大事件的核心冲突走向解决？（小高潮不是"又一场战斗"，而是"决定性的一场"）
- [ ] **读者体验**：读完本章后，读者是否会觉得"这段值了"？

> 如果以上四项中有两项以上不满足 → ⚠️ 标注为"小高潮力度不足"，建议增强该章的情感强度或篇幅。

#### 审查项四-附2：大高潮验证

> 如果本章所属大事件在本卷完整大纲的 `大事件列表` 中被标注为 ⭐大高潮事件，则在完成小高潮验证的基础上，额外以更高标准检查：

- [ ] **全卷最高点**：本章情感强度是否达到了**全卷**的最高点？（不仅是该大事件的最高点——大高潮是全卷读者记忆的锚点）
- [ ] **全卷核心冲突**：本章是否推动了**全卷核心冲突**的解决？（大高潮不是"又一场重要的战斗"，而是"这一卷最重要的事在此时了结或转折"）
- [ ] **篇幅绝对突出**：本章篇幅是否**显著长于**本卷其他所有章节？（大高潮应有足够的展开空间——不能和其他章长度持平）
- [ ] **记忆点明确**：读完本章，读者能否给出一个清晰的"这一卷最值得记住的场景"？（如果答案模糊 → 大高潮力度不足）

> 以上任一项不满足 → ❌ 标注为"大高潮力度不足"，必须增强后重新审查。大高潮是分卷的"存在理由"——力度不足的大高潮 = 读者记不住这一卷。

---

#### 审查项四-附3：结尾审查（连载铁律）

> **核心原则：本书是连载，每一章都不是完整的故事。** 结尾的唯一作用是制造"然后呢？"的追读冲动——"开启"下一章，而非"关闭"本章。任何让读者觉得"这章讲完了，可以放下"的结尾都是失败的结尾。

**第一步：绝对禁止的结尾（出现任一项 → ❌ 不通过）**

| 禁止类型 | 具体表现 | 为什么必须删 |
|---------|---------|------------|
| **总结式** | "这一天的经历让他明白……" / "回顾这一章……" / 任何对本章内容的概括 | 连载不需要总结——读者刚看完，不需要你复述一遍 |
| **收束式** | "夜色渐深，一切归于平静" / "他带着满足沉沉睡去" / 环境描写收束全章 | 环境收束 = 告诉读者"今天结束了，关灯睡觉"——读者真的会关掉 |
| **展望式** | "明天的路还很长……" / "他相信一切都会好起来的" / "未来充满了无限可能" | 这是"作者觉得该收尾了"的信号，读者感受到的是"本章已完结" |
| **感悟式** | "他陷入沉思……" / "或许这才是真正的……" / 角色对本章事件的内心总结 | 角色替读者总结 = 剥夺读者的思考空间 = 阅读体验终止 |
| **口号式** | "他一定会变得更强！" / "从今天起，他再也不会……" / 决心宣言 | 网文读者对口号免疫——喊得越响，读者关得越快 |
| **闭环式** | 本章开头的问题在本章结尾彻底解决 / "到此为止，这件事告一段落" | 记住：这一章不是完整故事。闭环 = 没有追读理由 |
| **安静收尾** | 角色独自安静地坐着/躺着 / 无人说话的场景收束 / "他一个人站在窗前" | 安静 = 能量归零。读者跟着安静下来，然后就……关掉了 |
| **拖沓式** | 钩子抛出后又加了2-3行解说/抒情/环境描写 | 拖沓 = 钩子已失效——读者已经得到"解答"，不需要追读了 |
| **补充式** | 钩子句后再追加"但他知道/他意识到/这意味着/或许……" | 补充 = 钩子被稀释——写完钩子立刻断章，不追加任何文字 |

**第二步：正确的结尾替代方案**

| 删除的坏结尾 | 替换为 |
|------------|-------|
| "夜色渐深，他沉沉睡去" | 他刚闭眼，门外传来急促的敲门声 |
| "这一天的收获真不少" | 他清点收获时，在某件物品底部发现了一个不该出现在这里的标记 |
| "明天又是新的一天" | 他计划好明天的行程——但他不知道，有人已经在明天等着他了 |
| "他陷入沉思，思考着未来的方向" | 他用一句话/一个动作/一个新发现打断自己的沉思 |
| "他相信一切都会好起来的" | 刚放下心，某个细节让他猛然意识到事情没那么简单 |

**第三步：结尾自问（审查者用）**
- 删掉结尾最后一段，下一章能直接接上吗？→ 能 = 结尾有效，不能 = 结尾在"关闭"
- 读者读到最后一段会问"然后呢？"还是"嗯，讲完了"？→ 前者 = 合格，后者 = 不合格
- 如果我在这章结尾放下手机去睡觉，明天还记得回来看吗？→ 不记得 = 钩子太弱
- 这个结尾是在"回答"本章的问题，还是在"提出"新的问题？→ 回答 = 关闭（❌），提问 = 开启（✅）

## 常见错误

| 错误 | 为什么错 | 正确做法 |
|------|---------|---------|
| 审查通过太快（每一项都扫一眼打√） | 扫一眼≠审查——人物降智、设定矛盾、说明书语往往藏在行文中 | 每个审查项至少给20秒，关键人物的对话段落必须逐句读 |
| 偏差合理但忘了更新细纲 | 后期回看细纲与正文不一致，不知道哪个是对的 | 偏差合理→同步更新细纲，标注"正文优于原细纲" |
| 收到❌不通过后只改了标出来的问题 | 一个地方出问题往往有连锁效应——只改一点其他处矛盾更明显 | 修改后检查受影响的相关段落 |
| 有条件通过的小问题连续三章标注但不修复 | 条件通过的保护伞让问题合法化——"先记着"变成"永远不会改" | 连续三章标注同样类型的问题→必须优先修复再开新章 |
| 审查人物只看"有没有降智"，不核对四维行为塑造 | "降智"是极端情况——大多数人物问题是"动作/语言/神态与角色文件定义的特征不一致"而非降智 | 审查时打开角色文件，逐一对比关键场景中人物的动作/语言/神态/决策是否匹配四维塑造设计 |
| 不检查章节类型是否与细纲标注一致 | 细纲标注"战斗类"但正文只打了半章嘴炮 → 读者期待的战斗没发生 | 审查项一必须核对章节实际内容类型是否匹配细纲的 `章节类型` 字段 |
| 过渡章不检查信息负载 | 过渡沦为"在路上"的流水账，读者跳过不读 | 过渡章必须检查是否有信息增量（世界观/角色关系推进/线索/伏笔） |
| 不验证小高潮力度 | 细纲标注为小高潮的章，写出来和其他章没区别 → 大事件没有情绪爆发点 | 小高潮章额外检查篇幅/情感强度/剧情分量/读者体验四项 |
| 不验证大高潮力度 | 完整大纲标注为⭐大高潮事件的章写完后与其他小高潮章没区别 → 读者记不住这一卷 | 大高潮章额外以更高标准检查：全卷最高点/全卷核心冲突/篇幅绝对突出/记忆点明确 |
| 只看写作质量不看人物/设定一致性 | 写得再漂亮的章节，人物崩了整章就是废稿 | 人物一致性和设定一致性优先于写作质量 |
| 跳过内容合规审查 | 违规内容一旦发布，轻则章节屏蔽，重则全书下架甚至追责 | 合规审查与写作质量同等重要，特别是战斗描写和情感描写的边界 |
| 不检查字数 | "感觉差不多2500字" → 感觉不准，实际可能只有1800 | 用工具统计实际正文字数，低于2500 → ❌不通过 |
| 灌水凑字数 | 用废话撑到2500字 → 比字数不足更差，既水又暴露功底 | 字数不足时补该展开的场景（情绪高潮/心理斗争/战斗细节），不是加废话 |
| 结尾出现"总结""收束""展望" | 连载每一章都不是完整故事——读者不需要你帮他们总结本章 | 结尾唯一作用：制造"然后呢？"。自查9类禁止结尾清单，触犯任一项 → ❌不通过 |
| 结尾钩子与主线无因果 | "全章99%平淡种田，末段突然有人叛变" → 天降神钩，读者被侮辱智商 | 钩子从本章情节中自然生长，不从天而降 |
| 跳过标点符号审查 | 中文段落混入英文标点、省略号写成"..."、中英文挤在一起——读者一眼看出文本不专业 | 标点符号审查为每章必检项，不可跳过 |
| 标点违规当成"小问题"忽略 | "不就是几个逗号嘛"——累积到第10章时全书视觉质量严重下降 | 标点规范是排版底线——每章必检且出现即改 |

## 危险信号 — 停下先处理

- 用户问"能不能先写下一章，同时改这一章" → 不行。并行修改和写作的后果是两个都做不好，且新章可能要回头再改
- 本章审查的❌问题与上一章审查的❌问题是同一类型 → 不是单章问题，是系统性问题，可能需要回调人物设计或明确设定
- 审查中发现正文有"等下再补"的标注 → 等下永远不会来——要么现在补要么删掉标注
- 用户说"这次不审查了直接看下一章" → 拒绝。未审查章不能进入写前审查（闭环链路断裂）
- **审查项四未运行自动化检测脚本** → 脚本是审查项四的步骤 0（强制步骤），不可跳过。必须先运行 `python "$HOME/.claude/plugins/webnovel-studio/tools/chapter_check.py"` 拿到 JSON 结果，再继续后续审查。跳过脚本直接打勾 = 审查无效
- 脚本返回 `failed` 但审查者未要求修改 → 硬性规则项（字数/禁止句式/标点）的 `failed` 必须修改正文 + 重新运行脚本确认。不允许"先记录以后再改"
- 发现可能踩线的违规内容 → 立即指出并提供修改建议，标注为 ❌ 不通过。合规问题零容忍
- 本章字数不足2500字但用户说"这章内容就这么多，写不长" → 不是写不长，是该展开的场景没展开。回到细纲检查本章是否有核心冲突/情绪场景被压缩了
- 连续两章结尾都是同一类型的收束语（如连续两章都"夜色渐深"） → 系统性结尾问题，不是偶然。回到具体写作的断章13式重新选钩子
- 细纲标注"战斗类"但正文战斗篇幅不足半章 → 类型偏差——要么正文该扩充战斗，要么细纲该改类型
- 细纲标注"过渡类"但过渡内容全部是"赶路/移动/等待"无信息增量 → 过渡章在凑章数，回到具体写作补充信息负载
- 被标注为小高潮的章写完和其他章长度/情感强度没区别 → 小高潮名存实亡，回到具体写作增强该章
- 被标注为⭐大高潮事件的章写完后与其他小高潮章没区别 → 大高潮名存实亡，读者记不住这一卷。回到具体写作以全卷最高标准增强
- 扫查正文时发现多处英文半角标点（`,` `.` `?` `"` 等）→ 标点规范系统性违规——全章搜索半角标点替换为中文全角标点后再提交审查
- 中英文/数字之间大面积缺少半角空格 → 排版规范系统性违规——全章逐处补空格
- 一段之内句号超过 5 个，频繁断句 → 文气断裂——逐个句号尝试替换为逗号，合并碎片化短句为逗号连接的长句流。仅段落末尾和强转折处保留句号
- 搜索全章"是"字判断句 ≥3 处 → "是"字句超量——保留最重要2处，其余改动作/白描，或逐处向用户申请批准
