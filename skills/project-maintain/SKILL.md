# 项目工作维护

## 触发

- **必须触发**：CLAUDE.md 要求每次会话先调用本 skill；用户说"更新进度 / 同步文档 / 记录工作 / 维护文档 / 更新 design"；本轮产生了代码或文件变更。
- **续接触发**：用户说"继续 / 接着做 / 下一步"，或会话压缩、重启、换会话后接手既有项目 → 先按「续接与恢复」对账，不凭对话记忆。
- **隐式触发**：工作目录有 CLAUDE.md 且 `docs/` 存在；某次改动需要补 design；在一个旧四文件体系项目里开始工作。
- **不触发**：目标文件夹没有 CLAUDE.md（先走「myworkflow-project-init」）、纯问答、纯阅读、本轮无任何文件改动。

## 目标

让文档成为工作的副产品而不是额外负担。**两个调用时机分工不同**：进入时（动手前）读文档知上下文 + 过开工门禁；完成时（验证通过后）强制同步文档 + 校验无遗漏。

**"这条内容该写哪"是查表动作，不是判断题**：CLAUDE.md 怎么工作 ／ STRUCTURE.md 东西在哪 ／ `docs/GOAL.md` 为什么做（仅用户批准可改）／ `docs/design/` 做什么 ／ `docs/PROGRESS.md` 做了什么 ／ `docs/STATE.md` 现在在哪 ／ `docs/information/` 学到了什么 ／ `docs/research/` 外部世界怎么说。

**易混场景的落位判据**（照查，别自己发明）：

| 手上这条内容 | 写哪 | 为什么 |
|------|------|--------|
| "这个点还没做完 / 正在做" | `docs/STATE.md` | index 只有四态，**"开发中"不是状态** |
| "为什么当初要这么设计" | 对应 design 的「背景」节 | 设计动机属于需求侧，不属于进度 |
| "上次踩过的坑 / 用户明说过不要 XX" | `docs/information/` | 跨会话的经验资产 |
| "我调研了三个方案，选了这个" | `docs/research/`（由 myworkflow-deep-research 落盘） | 外部世界的论据 |
| "今天改了哪几个文件" | `docs/PROGRESS.md` | 发生过的事实，追加式 |
| "这个项目不接受任何联网依赖" | `CLAUDE.md` 工作规则 | 长期规则，不是一次性经验 |

## 两个调用时机（分工不同）

| 时机 | 做什么 |
|------|--------|
| **进入时**（动手前） | 阶段 0 体系识别 → 阶段 1 读文档 → 阶段 2 开工门禁 |
| **完成时**（验证通过后） | 阶段 3 补 design（如需要）→ 阶段 4 强制同步 → 阶段 5 校验 |

进入时不做门禁就动手 = 项目漂变的起点；完成时不同步 = 下一次会话从零开始猜。

## 主线（6 阶段）

```
阶段0 体系识别与迁移 → [进入时] 阶段1 读文档 → 阶段2 开工门禁 → 阶段3 design 维护
                     → [完成时] 阶段4 强制同步 → 阶段5 四类校验 → 摘要
```

**任何写入前先过的三条护栏**（与 myworkflow-project-init 同源）：写入白名单只允许 `<root>/CLAUDE.md`、`<root>/STRUCTURE.md`、`<root>/docs/**`；`docs/` 只收**本次开发产生**的文档（判据：「这份文档是这次开发中写出来的吗？不是 → 原地不动」）；覆盖超过 20 行既有内容前必须展示 diff 摘要并获确认。

### 阶段 0：体系识别与旧体系迁移

进入一个文件夹时，先用 Glob/Read 判定它属于哪一类：

| 现象 | 判定 | 处理 |
|------|------|------|
| CLAUDE.md + `docs/{GOAL,STATE,PROGRESS}.md` + `docs/design/index.json` | **新体系** | 直接进阶段 1 |
| 根目录 CLAUDE.md + PROGRESS.md + PROGRESS-LITE.md + STRUCTURE.md（无 GOAL/STATE） | **旧体系** | 走下方迁移三选一 |
| 旧四文件与部分 `docs/` 文件并存 | **半迁移** | 走迁移三选一，缺什么补什么 |
| 有 CLAUDE.md、无 `docs/`，且是常规文件夹 | **常规文件夹** | 只读 CLAUDE.md 的工作约定与变更记录；**绝不创建 `docs/`** |
| 没有 CLAUDE.md | **无体系** | 提示用户先走「myworkflow-project-init」，不要在这里擅自建体系 |

检测到**旧体系 / 半迁移**时，用 ask_user_question 给三选一：

- **现在迁移**：按下表做迁移计划，逐项列给用户确认后执行。
- **暂不迁移**：本次按旧体系记录（写 PROGRESS.md / PROGRESS-LITE.md）；**每次会话只提示一次，不反复骚扰**。
- **永久不改**：在 CLAUDE.md 末尾追加一行标记 `> 本项目不迁移文档体系（用户决定 YYYY-MM-DD）`，此后识别到该标记直接跳过提示。

迁移计划表（**只做"复制 + 归档"，不移动、不删除**；根目录旧文件默认原样保留）：

| 旧文件 | 去向 | 处理 |
|------|------|------|
| `PROGRESS-LITE.md` | `docs/PROGRESS.md` 条目区 | 复制条目并补 `vX.Y.Z`；无法判断版本的填 `v0.0.0` 并在 `note` 标注 |
| `PROGRESS.md` | `docs/PROGRESS.md` 版本记录区 | 复制为历史段落，原文保留 |
| `STRUCTURE.md` | **原地保留** | 新体系仍在项目根目录，不移动 |
| `CLAUDE.md` | 原地改写「每次启动会话的强制步骤」一节 | 先 Read 并展示 diff 摘要，其余内容不动 |
| 旧 `docs/` 里的资料文档 | **原地不动** | 禁止为了"整齐"搬进 `docs/` |

> **禁止为填满 `index.json` 而给历史文档凭空补状态。** 拿不准的不确定一律填「未开发」，`note` 写"历史文档补登记"。历史文档不是本次开发的产物，它的状态无从考证——编一个状态比留空有害得多。

### 阶段 1：工作前 — 读文档知上下文

- **必须读**：CLAUDE.md（规则）；`docs/STATE.md`（现在在哪）；`docs/PROGRESS.md` 条目区（最近做了什么）。
- **按需读**：`docs/GOAL.md`（为什么做，判断本次改动是否偏航）；`docs/design/index.json`（要做什么、做到哪）；STRUCTURE.md（找文件时）；`docs/information/index.json`（踩过的坑、用户偏好）。
- **大文件不要整读**：PROGRESS 版本记录区用 Grep 定位（`grep -A 50 "## 2026-09-15" docs/PROGRESS.md`）。

### 阶段 2：开工门禁（与 myworkflow-agent-dev-loop 的接口）

> 动手前先回答一句：**本次改动对应 `docs/design/index.json` 里的哪个点号？**
> - 能指出点号 → 放行，记下点号，收尾时更新它的状态。
> - **新增功能 / 行为变更 / 新模块 → 必须先补 design**，没有 design 不动手（回阶段 3）。
> - bug 修复 / 重构 / 配置 / 文档 / 格式化 → **允许豁免**，但必须在 PROGRESS 条目标注「本次无 design（小场景豁免）」。
> - 判断不清 → **默认按"需要 design"处理**。

> `index.json` 的写入**只由本技能执行**。`myworkflow-agent-dev-loop` 及其他技能不得直接改 `index.json`，避免格式漂移。

### 阶段 3：design 维护（新建 / 补齐）

1. **编号**：现有 `design-NN-<主题>.md` 最大编号 +1，两位数字（`design-01`、`design-02`）。文件名与 `id` 前缀必须一致。
2. **硬下限 ≥20 行**，必须含 **背景 / 需求 / 验收标准 / 点清单** 四节；点号形如 `design-01-P1`，全局唯一。
3. **内容禁令**：只放需求 / 功能 / 设计。**禁止写具体代码方案**——不写函数签名、数据结构、算法步骤、目录布局。design 是"要什么"，不是"怎么实现"。
4. **GOAL 回望（硬门禁）**：

> 补齐或新建 design 后，必须输出一行：**「GOAL 回望：本 design 与 GOAL 的「<命题>」一致 ／ 冲突点为 <X>」**（`<命题>` 取自 `docs/GOAL.md` 的验收判据原文）。
> 发现冲突 → **立即停下**，用 ask_user_question 让用户在「修改 GOAL」与「修改 design」之间二选一。**禁止自行选择、禁止标注"暂不处理"、禁止先写下去再说。**

5. **写 index**：新 design 写入 `designs[]`（含 `goal_check` 那一行原文），点写入 `points[]`，初始状态一律 `未开发`、`evidence` 为空字符串。

### 阶段 4：工作后 — 强制同步（验证通过后立即执行，不可推迟）

按 4.1 → 4.6 顺序执行，全部落地才算完成。

**4.1 条目区（`docs/PROGRESS.md`）**：新条目插在条目区最上（日期标题下），**每条严格一行**，不写"为什么"：`- [标签][vX.Y.Z] 一句话做了什么`。标签集合：`[New Feature]` / `[Debug]` / `[Change]` / `[Build]`；同日多条按此顺序排。豁免场景在行尾补「（本次无 design，小场景豁免）」。

```markdown
## 条目

## 2026-09-15
- [New Feature][v0.2.0] 登录支持手机号 + 验证码（design-01-P1）
- [Debug][v0.2.0] 修复会话过期后 401 未跳转登录页（design-01-P3）
- [Change][v0.2.0] 格式化 hooks 目录（本次无 design，小场景豁免）
```

**约束**：每条严格一行——条目区的价值是让人一次读几百条；只写"做了什么"不写"为什么"，根因留给版本记录区。坏例：`- 修复了一个 bug`（三个月后谁也看不懂）。

**4.2 版本号（仅当项目有明确版本策略或用户要求时）**：版本号属于用户 / 项目策略，智能体**不擅自递增**；单次改动默认不改版本号，只有项目有明确版本策略或用户明确要求时才更新。有策略时：存在代码清单（如 `package.json`）的 `version` 则以代码清单为准，否则以 `docs/PROGRESS.md` 头部为准；两者不一致必须显式记一行，并在 `docs/STATE.md` 列出差异。

| 位 | 语义 | 递增条件 | 谁决定 |
|----|------|---------|--------|
| a | 大版本 | 项目版本策略定义（如正式发布 0→1、大变动）；无策略时仅用户明确要求 | **用户 / 项目策略** |
| b | 小版本 | 项目版本策略定义（如新增功能 / 模块）；无策略时不递增 | **用户 / 项目策略** |
| c | debug | 项目版本策略定义（如修 bug、重构、文档调整）；无策略时不递增 | **用户 / 项目策略** |

> 智能体**不擅自递增**：单次改动默认不改版本号；项目有明确版本策略或用户要求时才按策略更新（一次改动至多一次）。无版本策略的项目不检查也不推进版本号。若存在 `package.json` 等代码清单的 `version`，以代码清单为准，与 PROGRESS 头部不一致时必须显式记一行，并在 `docs/STATE.md` 列出差异。

**4.3 版本记录区**：追加本版本一段，含 **问题/动机 → 根因（仅 bug 修复需要）→ 修改（文件清单 + 对应 design 点号）→ 验证（命令 + exitCode/退出码，或产物路径/sha256；不接受「已测试」类表述）**。条目区与版本记录区靠版本号 join。

```markdown
### v0.2.0 — 2026-09-15
**问题 / 动机**：会话过期后 API 返回 401，前端未拦截，把 401 当正常数据显示 "undefined"。
**根因**：axios 拦截器只处理 200/201/404/500，401 落到 default 分支；该拦截器上次重构时移入 AuthContext 时遗漏 401 case；测试期 token 有效期 7 天，从未触发过期。
**修改**：`src/api/interceptors.ts` 新增 401 case（清 token 并跳转 /login）；`src/api/interceptors.test.ts` 新增 2 个测试。对应 design-01-P3。
**验证**：pnpm vitest run（48 files, 312 tests）通过；手工清除 cookie 刷新确认跳转登录页。
```

**根因怎么写**：不只说现象（"少一行代码"），要追问"为什么少？什么时候少的？为什么之前没暴露"——指向流程问题、假设错误、测试覆盖不足。这正是未来智能体最需要的上下文。

**4.4 `docs/design/index.json` 状态流转**（四条硬门禁，逐条执行）：

> 未开发 / 阻塞 / 待验收 / 完成 四态封闭枚举，**"开发中"不写进 index**——它由 `docs/STATE.md` 承载。

> `evidence` 为空的点不得置「待验收」。必须有可指认的证据（命令 + exitCode/退出码、产物路径或 sha256），不接受"已测试"这类无证据表述。

> 除非用户在本轮对话中明确说出"确认没问题 / 可以了 / 通过了 / 我验收通过"，否则状态只能停留在「待验收」。禁止以"我已经验证过""测试全绿"为由自行置为「完成」。**用户没说话 = 还没验收。**

> 置「阻塞」必须写具体原因（卡在哪、缺什么、依赖谁）；只写"没做完"不许置阻塞。

流转规则：`未开发 → 待验收`（agent，需真实验证通过且 evidence 非空）；`未开发 → 阻塞`（agent，必须写具体原因）；`待验收 → 完成`（**仅用户**）；`完成 → 待验收`（agent 发现回归）。同步更新 `points[].updated`，并保持 design 文件里的点清单表与 index 一致。

**4.5 `docs/STATE.md` 刷新**：更新"最后刷新"日期、当前版本、正在做、卡住的、下一步、等用户验收——**只写现在，不写历史**。自检判据：**「文件里是否出现 3 条以上上周的内容？是 → 你把 PROGRESS 的历史抄进来了」**，删掉重写。

**4.6 `docs/information/` 与静态文件**：本次学到了值得记住的事（试错结论、用户偏好、环境事实、坑）→ 在对应主题文件追加条目（`info-NNN`）并同步 `docs/information/index.json`；无新知识则不写、不凑。STRUCTURE.md 仅在新增/删除/重命名文件或目录时更新（只改内容不更新）；CLAUDE.md 仅在根目录结构、核心规则、子项目变化时更新。

### 阶段 5：校验 — 四类检查，缺一不可

**5.1 index.json 三处一致校验**

- **悬空检测**：`designs[].file` 与 `points[].file` 的每一项都必须能在 `docs/design/` 下 Glob 定位到；定位不到 = 悬空，修正。
- **孤儿检测**：`docs/design/` 下实际 `.md` 文件集合与 index 的 `file` 集合**必须完全相等**——多一个（孤儿文件未登记）或少一个（悬空条目）都算失败。
- **状态一致性抽查 ≥3 个 design 文件**：逐个文件比对点清单表的点号、状态、证据与 index 是否逐点一致；不一致按 index 修正文件（index 是权威源）。

**5.2 变更覆盖检查（git / 无 git）**

```bash
# Bash：覆盖有历史 commit / 仅一个 commit / 无 commit 三种情况
(git rev-parse --verify HEAD >/dev/null 2>&1 && git diff --name-only HEAD~1 2>/dev/null) || git status --short
```

**非 git 项目**（上面两条命令都失败）→ 以**本会话 Write/Edit 记录 + 文件 mtime**（`Get-ChildItem -Recurse | Where-Object LastWriteTime -gt <开工时间>`）为准，禁止凭记忆列变更。

确保每个变更文件都在 PROGRESS 版本记录区有记录。局限：只查最近一次提交——一次会话多次独立提交时用 `git log --oneline` 手动比对；**git 不可用**时改用本会话 Write/Edit 记录 + PROGRESS 条目 / STATE + 文件 mtime 等磁盘事实核对，**禁止凭对话记忆**。

**5.3 日期与版本检查**：PROGRESS 条目区有今天的日期标题？若项目有版本策略，确认头部版本号与代码清单一致（无策略则不检查）？STATE.md 的"最后刷新"是今天？

**5.4 输出摘要**（有遗漏已补正时用 `⚠️ 已补正` 标记）：

```
📋 文档同步完成：
✓ PROGRESS.md — 条目区 +1 条（vX.Y.Z），版本记录区 +1 段
✓ design/index.json — design-01-P1 → 待验收（等用户确认）
✓ STATE.md — 已刷新
✓ information/index.json — 无需更新
✓ STRUCTURE.md / CLAUDE.md — 无需更新
```

## 项目规模适配

| 规模 | 文件数 | 处理 |
|------|--------|------|
| 小型 | <20 | 条目一句话；根因一句话；STRUCTURE 只写顶层 + 1 层；design 保持最小四节 |
| 中型 | 20–100 | 标准条目；bug 必写根因；STRUCTURE 顶层 + 2 层 |
| 大型 | 100–500 | 完整条目（全写根因）；STRUCTURE 顶层 + 3 层 + 核心事实；design 按模块分文件 |
| 超大型 | >500 | 根与子项目各自维护一套 `docs/`；本技能在每个子项目根目录下分别执行 |

## 完成标志

- [ ] 体系已识别（新 / 旧 / 半迁移 / 常规 / 无体系），旧体系已给三选一或已读到"永久不改"标记
- [ ] 阶段 2 开工门禁已过：每个改动都能指到点号，或已标注「本次无 design（小场景豁免）」
- [ ] 需要 design 时已补齐：≥20 行、四节齐全、无代码方案、GOAL 回望那一行已输出且无未决冲突
- [ ] PROGRESS 条目区 + 版本记录区已同步；若项目有版本策略，版本号语义与一致性已核对（无策略则不改版本号）
- [ ] `index.json` 状态流转符合四条硬门禁（无"开发中"、无空 evidence 的待验收、无用户原话不许置完成、阻塞有具体原因）
- [ ] STATE.md 已刷新且未混入历史
- [ ] 阶段 5 四类校验全过（悬空 / 孤儿 / 状态抽查 ≥3 个 design 文件 / git 覆盖）
- [ ] 摘要已输出，未移动或删除任何既有文件

## 常见问题

- **改一行也要记录？** 独立有意义的变更——记；连续小改动合并成一条。
- **忘了实时记录？** 用 `git log --oneline` 回顾今天的变更补写（**无 git 项目**改用本会话改动清单 + 文件 mtime，禁止凭记忆编造），阶段 5.2 会发现遗漏。
- **用户没验收就催着走？** 状态停在「待验收」，并在摘要里明确写出"等用户确认"——不要沉默地留在待验收，也不要替用户点完成。
- **PROGRESS 太大？** 先读条目区，需要细节用 Grep 定位；条目区触顶后把最老内容移入 `docs/other/progress-archive-YYYY.md`。
## 续接与恢复（接手 / 继续既有项目）

用户说「继续 / 接着做 / 下一步」，或会话压缩、重启、换会话后接手既有项目时：**先对账再动手**，禁止凭对话记忆假设"应该做完了"。

1. **从磁盘事实重建上下文**（只读）：`docs/GOAL.md` 目标 → `docs/STATE.md` 现在在哪 → `docs/PROGRESS.md` 条目区（最近做了什么）与版本记录区 → `docs/design/index.json` 各点状态 → `git log`（**无 git 项目跳过**，改用 PROGRESS / STATE / 回执）、运行记录、上一轮回执与产物路径。对不出结论先只读探查，不猜。
2. **三级判定 + 文档映射**：
   - **accepted**：PROGRESS 有记录、验收证据齐全 → **跳过不重做**；
   - **produced 未验证**：design / 条目已写但缺证据或用户验收 → **补验证补证据，不重做产物**；
   - **未开始**：index.json 为「未开发」且无产物 → 正常做；
   - **判不清** → 按"未完成"处理，先探查。
3. **只推进最小下一步**：选出下一个未完成的独立交付物，只做它；完成后照常走阶段 4 强制同步，再判下一步，不重跑整条主线。
4. **恢复后先重判级并加载技能**：用 `myworkflow-task-router` 重新判定工作级别（L1/L2/L3），再加载对应技能；hook 每轮纪律照常生效。
5. **交接**：接手或交出时都要四样：已做 / 未做 / 证据（runId 或产物路径）/ 下一步 + 未解决项；不复核不动手。

与既有条款的关系：阶段 0–1 的「进入时读文档」是每次开工的常规读取；本节是**中断 / 接手专用的对账**，不重复执行；「收尾强制同步」照旧——每完成一个最小下一步就同步一次。
