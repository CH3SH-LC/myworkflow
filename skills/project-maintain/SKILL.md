## 核心流程：进入读文档 → 收尾同步 → 四类校验

**何时加载**：用户说"更新进度/同步文档/记录工作/更新 design/更新状态"，或本轮有文件变更且项目有 CLAUDE.md 与 docs/。**不加载**：无 CLAUDE.md（先走 project-init）、纯问答、纯阅读、无改动。

**硬步骤**
1. **识别体系**：新/旧/半迁移/常规/无体系；旧体系先给三选一或读到"永久不改"标记再动。
2. **进入读文档**：必读 CLAUDE.md、docs/STATE.md、docs/PROGRESS.md；按需读 GOAL、两份 index.json、STRUCTURE.md；大文件 grep 定位。
3. **开工自检**：回答"本次改动对应 index.json 哪个点号"；新增功能/行为变更/新模块先补 design（四节齐全、禁写代码方案）；bug/重构/配置/文档可豁免，但 PROGRESS 标「本次无 design（小场景豁免）」。
4. **收尾强制同步**（验证通过后按序做）：PROGRESS 插一行 `- [标签][vX.Y.Z] 一句话` → 语义递增 a.b.c（a 仅用户批准，b 新功能，c 修复）→ 版本记录追加 问题→根因→修改→验证 → design 置「待验收」（仅用户确认可「完成」）→ 刷新 STATE.md → 校验 index.json。
5. **四类校验缺一不可**：悬空（index 的 file 都能 glob 到）/ 孤儿（design 目录集合 == index）/ 状态抽查 ≥3 个 design 文件 / git 变更覆盖（每文件都有记录）；最后输出摘要。

**沉淀（强制）**：收尾必须含**知识条目与脚本库增删改**——新经验用 `node scripts/kb.mjs new ...` 落 docs/knowledge/ 并登记 index.md，再补结论/依据/适用边界/下次怎么做四段；可复用命令落 `scripts/<kebab>.mjs`（Node ESM、`--help`、exit 0/1/2）并在条目里引用；无变化也写「知识/脚本：无变化」。

**完成判据**：条目与版本记录已写、版本号与状态流转合规、四类校验全过、摘要已输出；证据=文档 diff/回读 + 校验输出。只说不写、只写条目不写版本记录不算完成。

# 项目工作维护

## 触发（按需加载，不靠强制钩子）

- **应当加载**：用户说"更新进度 / 同步文档 / 记录工作 / 维护文档 / 更新 design / 更新状态"；本轮产生了代码或文件变更且项目有 CLAUDE.md 与 `docs/`；某次改动需要补 design；在旧四文件体系项目里开始工作。
- **不加载**：目标文件夹没有 CLAUDE.md（先走 skill(name="myworkflow-project-init")）、纯问答、纯阅读、本轮无任何文件改动。
- **加载方式**：由当前任务按需调用 skill(name="myworkflow-project-maintain")。**不存在"每次会话必须先调用本技能"的钩子式约束**——不需要它的时候不要加载，也不要为了"流程完整"空跑一遍。

## 目标

让文档成为工作的副产品而不是额外负担。**两个更新时机分工不同**：进入时（动手前）读文档知上下文；完成时（验证通过后）同步文档并校验无遗漏。两个时机之间是连续的开发工作，**不设逐阶段的用户批准关卡**——用户已授权任务范围内的可逆开发，直接做完再一起汇报。

**"这条内容该写哪"是查表动作，不是判断题**：CLAUDE.md 怎么工作 ／ STRUCTURE.md 东西在哪 ／ `docs/GOAL.md` 为什么做（仅用户批准可改）／ `docs/design/` 做什么 ／ `docs/PROGRESS.md` 做了什么 ／ `docs/STATE.md` 现在在哪 ／ `docs/information/` 学到了什么 ／ `docs/research/` 外部世界怎么说。

**易混场景的落位判据**（照查，别自己发明）：

| 手上这条内容 | 写哪 | 为什么 |
|------|------|--------|
| "这个点还没做完 / 正在做" | `docs/STATE.md` | index 只有四态，**"开发中"不是状态** |
| "为什么当初要这么设计" | 对应 design 的「背景」节 | 设计动机属于需求侧，不属于进度 |
| "上次踩过的坑 / 用户明说过不要 XX" | `docs/information/` | 跨会话的经验资产 |
| "我调研了三个方案，选了这个" | `docs/research/` | 外部世界的论据 |
| "今天改了哪几个文件" | `docs/PROGRESS.md` | 发生过的事实，追加式 |
| "这个项目不接受任何联网依赖" | `CLAUDE.md` 工作规则 | 长期规则，不是一次性经验 |

## 两个更新时机

| 时机 | 做什么 |
|------|--------|
| **进入时**（动手前） | 体系识别 → 读文档 → 开工自检（本次改动指向哪个点号） |
| **完成时**（验证通过后） | 补 design（如需要）→ 统一同步 → 四类校验 → 摘要 |

进入时不做自检就动手 = 项目漂变的起点；完成时不同步 = 下一次会话从零开始猜。

## 单写入入口 + 横向交付合约

**并行开发时最容易坏掉的是共享索引。**因此定两条硬规则：

**① 状态与索引只有一个写入入口。**`docs/STATE.md`、`docs/design/index.json`、`docs/information/index.json`、`STRUCTURE.md`、`docs/PROGRESS.md` 属于**共享只读投影**：只有本技能（单一写入入口 / 一个 owner）在收尾时投影更新。

- 其它成员（并行 teammate、成员的执行者、其它技能）**一律不直接编辑这些文件**，改为**提交变更请求**：`{ 交付物 id, design 点号, 期望状态变更, evidence 引用, 一句话说明 }`。
- 本技能汇总所有变更请求后**一次性写入**，写前检查格式与四态枚举，写后回读校验。
- **禁止十个成员并发覆写同一文件**：并行工作的写范围必须互不重叠；同一文件的并发写只会得到冲突与格式漂移。发现写范围重叠 → 先合并 owner 或把共享部分收归单一入口，再开工。

**② 横向交付合约：按可独立交付的产物切分，一个 owner 端到端负责一份交付物。**

- 切分单位是**交付物**：module 模块 / object 对象 / evidence-package 证据包。每份交付物由**一个 owner 端到端负责**：调查 → 实现 → 自检 → 修复 → 验收。
- **拒绝同一交付物的阶段接力**："背景调查 → 设计 → 检查"、"计划 → 编码 → 审查"这类把一个人的活拆给三个角色的排法，会让每段都缺上下文。
- **横向重排建议**：把相邻阶段的职责并进同一个 owner（谁调查谁设计、谁实现谁自检）；必须并行时**按交付物切分而不是按阶段切分**，并按下面的依赖规则把交付物之间的接口显式化。
- **依赖只允许存在于不同交付物之间**，且必须成对声明 **version + requires**：requires 只接受两种形态——**published-interface**（对方已发布的接口）或 **verified-result**（对方已验证产出的结果）。依赖未就绪就不派发，也不要"先启动再等"。

## 事件驱动滚动补位

- **任一项结算就立即补位**下一个 ready 项，不等同批其它任务；**无全批屏障、无整层等待**，慢任务不阻塞其它 ready 项。
- **未 ready 不派发**：依赖未满足、接口未发布、前置结果未验证，都算未 ready。
- **满额时拒绝并保持 ready（CAPACITY_FULL）**：不排队空等，也不用一次性旁路绕过上限——被拒的项留在 ready 队列里，等有额度再补位。

## 超时、失败与收尾

- **超时先判断进展与可恢复性**：有可见进展或可恢复（换策略、缩小范围、补适配器）就继续；**"状态未知 / 暂停"与"真正失败"严格分开，超时不等于失败**，也不得凭超时把交付物判死。
- **同一 owner 收尾修复**：谁做的谁补完，保留上下文；**不撤走前面的人换一个无上下文的审查员**去接管后半程。
- **全局集成由 leader 与相关 owner 共同负责**：集成问题回到相关交付物的 owner，而不是另起一个"集成角色"重做。

## 阻塞处理顺序

遇到阻塞按顺序走，不要跳步，也不要死磕：

1. **记录**：确切失败信息 / 已尝试的动作 / 影响范围 / 此刻仍能做的其它事。
2. **查现成**：已装服务、源码、现成工具、当前权限——能直接用就不自己造。
3. **能补就补**：写适配器、接口、本地桥接把缺口补齐。
4. **局部阻塞先绕**：先做其它 ready 项，并把 blocker 精确挂到受影响的那份交付物上（不扩散成全局停工）。
5. **确实兜不住才上报**：需要外部账号、人工决策或无法获得的资源时，标记 `needs_user`，同时给出**已尝试路径**与**最小下一步**。

**不得固定"试三次就结束"，也不得无预算地无限重试同一个失败**；权限拒绝不可绕过，只能改路径或上报。

## 用户入口与提问纪律

- **任务内的可逆开发不重复询问**；审批与扩权只有用户入口，模型没有等价工具，不要试图模拟批准。
- **只在真正改变决策、且项目里查不到时**才用 ask_user_question 提问；能从代码、文档、Git 历史查到的，先查。
- **GOAL 冲突必须由用户裁决**：输出「GOAL 回望：本 design 与 GOAL 的「<命题>」一致 ／ 冲突点为 <X>」后，发现冲突就用 ask_user_question 让用户在「修改 GOAL」与「修改 design」之间二选一，禁止自行选择、禁止标注"暂不处理"。

## 证据与结果分层

- **证据诚实**：严格区分「已核实 / 有来源」与「推测 / 未核实」；不夸大，不无证据声称"验证通过"。
- **结果分层**：parent 只收简短结论 + 可核查的 evidence / artifact refs；原始材料留在文件或子会话里。摘要必须含**来源、版本、遗漏、不确定性、未完成项**。

## 体系识别与旧体系迁移

进入一个文件夹时，先用 glob / read 判定它属于哪一类：

| 现象 | 判定 | 处理 |
|------|------|------|
| CLAUDE.md + `docs/{GOAL,STATE,PROGRESS}.md` + `docs/design/index.json` | **新体系** | 直接进"读文档" |
| 根目录 CLAUDE.md + PROGRESS.md + PROGRESS-LITE.md + STRUCTURE.md（无 GOAL/STATE） | **旧体系** | 走下方迁移三选一 |
| 旧四文件与部分 `docs/` 文件并存 | **半迁移** | 走迁移三选一，缺什么补什么 |
| 有 CLAUDE.md、无 `docs/`，且是常规文件夹 | **常规文件夹** | 只读 CLAUDE.md 的工作约定与变更记录；**绝不创建 `docs/`** |
| 没有 CLAUDE.md | **无体系** | 提示用户先走 skill(name="myworkflow-project-init")，不要在这里擅自建体系 |

检测到**旧体系 / 半迁移**时，用 ask_user_question 给三选一：

- **现在迁移**：按下表做迁移计划，逐项列给用户确认后执行。
- **暂不迁移**：本次按旧体系记录（写 PROGRESS.md / PROGRESS-LITE.md）；**每次会话只提示一次，不反复骚扰**。
- **永久不改**：在 CLAUDE.md 末尾追加一行标记 `> 本项目不迁移文档体系（用户决定 YYYY-MM-DD）`，此后识别到该标记直接跳过提示。

迁移计划表（**只做"复制 + 归档"，不移动、不删除**；根目录旧文件默认原样保留）：

| 旧文件 | 去向 | 处理 |
|------|------|------|
| `PROGRESS-LITE.md` | `docs/PROGRESS.md` 条目区 | 复制条目并补 `vX.Y.Z`；无法判断版本的填 `v0.0.0` 并在 `note` 标注 |
| `PROGRESS.md` | `docs/PROGRESS.md` 版本记录区 | 复制为历史段落，原文保留 |
| `STRUCTURE.md` | **原地保留** | 新体系仍在项目根目录，不移动 |
| `CLAUDE.md` | 原地改写"每次启动会话的强制步骤"一节 | 先 read 并展示 diff 摘要，其余内容不动 |
| 旧 `docs/` 里的资料文档 | **原地不动** | 禁止为了"整齐"搬进 `docs/` |

> **禁止为填满 `index.json` 而给历史文档凭空补状态。** 拿不准的一律填「未开发」，`note` 写"历史文档补登记"。历史文档不是本次开发的产物，它的状态无从考证——编一个状态比留空有害得多。

**写入白名单**：只允许写 `<root>/CLAUDE.md`、`<root>/STRUCTURE.md`、`<root>/docs/**`。`docs/` 只收**本次开发产生**的文档（判据：「这份文档是这次开发中写出来的吗？不是 → 原地不动」）。覆盖既有内容前先展示 diff 摘要；若属于用户已授权任务范围内的可逆改动，直接改并在摘要里列出被覆盖的范围，不重复询问。

## 进入时：读文档知上下文

- **必须读**：CLAUDE.md（规则）；`docs/STATE.md`（现在在哪）；`docs/PROGRESS.md` 条目区（最近做了什么）。
- **按需读**：`docs/GOAL.md`（为什么做，判断本次改动是否偏航）；`docs/design/index.json`（要做什么、做到哪）；STRUCTURE.md（找文件时）；`docs/information/index.json`（踩过的坑、用户偏好）。
- **大文件不要整读**：PROGRESS 版本记录区用 grep 定位（如 `pattern: "^## 2026-09-15"`, `path: docs/PROGRESS.md`）。

## 开工自检（动手前回答一句）

> **本次改动对应 `docs/design/index.json` 里的哪个点号？**
> - 能指出点号 → 放行，记下点号，收尾时更新它的状态。
> - **新增功能 / 行为变更 / 新模块 → 必须先补 design**，没有 design 不动手。
> - bug 修复 / 重构 / 配置 / 文档 / 格式化 → **允许豁免**，但必须在 PROGRESS 条目标注「本次无 design（小场景豁免）」。
> - 判断不清 → **默认按"需要 design"处理**。

> `index.json` 的写入**只走单一写入入口**。其它技能与并行成员不得直接改 `index.json`，只能提交变更请求，避免格式漂移与并发覆写。

## 收尾：design 维护（新建 / 补齐）

1. **编号**：现有 `design-NN-<主题>.md` 最大编号 +1，两位数字（`design-01`、`design-02`）。文件名与 `id` 前缀必须一致。
2. **四节齐全**：必须含 **背景 / 需求 / 验收标准 / 点清单**，内容充实（经验量级 ≥20 行；只有标题没有实质内容视为没写）。点号形如 `design-01-P1`，全局唯一。
3. **内容禁令**：只放需求 / 功能 / 设计。**禁止写具体代码方案**——不写函数签名、数据结构、算法步骤、目录布局。design 是"要什么"，不是"怎么实现"。
4. **GOAL 回望**：见上文「用户入口与提问纪律」，冲突交用户裁决。
5. **写 index**：新 design 写入 `designs[]`（含 `goal_check` 那一行原文），点写入 `points[]`，初始状态一律 `未开发`、`evidence` 为空字符串。

## 收尾：强制同步（验证通过后立即执行，不可推迟）

按 1 → 6 顺序执行，全部落地才算完成。

**1. 条目区（`docs/PROGRESS.md`）**：新条目插在条目区最上（日期标题下），**每条严格一行**，不写"为什么"：`- [标签][vX.Y.Z] 一句话做了什么`。标签集合：`[New Feature]` / `[Debug]` / `[Change]` / `[Build]`；同日多条按此顺序排。豁免场景在行尾补「（本次无 design，小场景豁免）」。

```markdown
## 条目

## 2026-09-15
- [New Feature][v0.2.0] 登录支持手机号 + 验证码（design-01-P1）
- [Debug][v0.2.0] 修复会话过期后 401 未跳转登录页（design-01-P3）
- [Change][v0.2.0] 格式化 src/utils 目录（本次无 design，小场景豁免）
```

**约束**：每条严格一行——条目区的价值是让人一次读几百条；只写"做了什么"不写"为什么"，根因留给版本记录区。坏例：`- 修复了一个 bug`（三个月后谁也看不懂）。

**2. 版本号 a.b.c**（写进 `docs/PROGRESS.md` 头部，**单一权威源**；其他文件只能引用它）：

| 位 | 语义 | 递增条件 | 谁批准 |
|----|------|---------|--------|
| a | 大版本 | `0` = 未成熟测试期；正式发布 0→1；此后仅完整项目的大变动 | **用户** |
| b | 小版本 | 新增功能 / 功能增强 / 新增模块 | agent 自动 |
| c | debug | 修 bug、重构、性能微调、文档配置调整 | agent 自动 |

> 一次会话至多递增一次（取本次最高语义）；不产生版本的工作不递增；若存在 `package.json` 等代码清单的 `version`，**以代码清单为准**，与 PROGRESS 头部不一致时必须显式记一行，并在 `docs/STATE.md` 列出差异。

**3. 版本记录区**：追加本版本一段，含 **问题/动机 → 根因（仅 bug 修复需要）→ 修改（文件清单 + 对应 design 点号）→ 验证（真实命令与结果）**。条目区与版本记录区靠版本号 join。

```markdown
### v0.2.0 — 2026-09-15
**问题 / 动机**：会话过期后 API 返回 401，前端未拦截，把 401 当正常数据显示 "undefined"。

**根因**：axios 拦截器只处理 200/201/404/500，401 落到 default 分支；该拦截器上次重构时移入 AuthContext 时遗漏 401 case；测试期 token 有效期 7 天，从未触发过期。
**修改**：`src/api/interceptors.ts` 新增 401 case（清 token 并跳转 /login）；`src/api/interceptors.test.ts` 新增 2 个测试。对应 design-01-P3。
**验证**：pnpm vitest run（48 files, 312 tests）通过；手工清除 cookie 刷新确认跳转登录页。
```

**根因怎么写**：不只说现象（"少一行代码"），要追问"为什么少？什么时候少的？为什么之前没暴露"——指向流程问题、假设错误、测试覆盖不足。这正是未来智能体最需要的上下文。

**4. `docs/design/index.json` 状态流转**（四条约束，逐条执行）：

> 未开发 / 阻塞 / 待验收 / 完成 四态封闭枚举，**"开发中"不写进 index**——它由 `docs/STATE.md` 承载。

> `evidence` 为空的点不得置「待验收」。必须有可指认的证据（验证输出、命令与结果、截图路径），不接受"已测试"这类无证据表述。

> 除非用户在本轮对话中明确说出"确认没问题 / 可以了 / 通过了 / 我验收通过"，否则状态只能停留在「待验收」。禁止以"我已经验证过""测试全绿"为由自行置为「完成」。**用户没说话 = 还没验收。**

> 置「阻塞」必须写具体原因（卡在哪、缺什么、依赖谁）；只写"没做完"不许置阻塞。

流转规则：`未开发 → 待验收`（agent，需真实验证通过且 evidence 非空）；`未开发 → 阻塞`（agent，必须写具体原因）；`待验收 → 完成`（**仅用户**）；`完成 → 待验收`（agent 发现回归）。同步更新 `points[].updated`，并保持 design 文件里的点清单表与 index 一致。

**5. `docs/STATE.md` 刷新**：更新"最后刷新"日期、当前版本、正在做、卡住的、下一步、等用户验收——**只写现在，不写历史**。自检判据：**「文件里是否出现 3 条以上上周的内容？是 → 你把 PROGRESS 的历史抄进来了」**，删掉重写。

**6. `docs/information/` 与静态文件**：本次学到了值得记住的事（试错结论、用户偏好、环境事实、坑）→ 在对应主题文件追加条目（`info-NNN`）并同步 `docs/information/index.json`；无新知识则不写、不凑。STRUCTURE.md 仅在新增/删除/重命名文件或目录时更新（只改内容不更新）；CLAUDE.md 仅在根目录结构、核心规则、子项目变化时更新。

## 校验 — 四类检查，缺一不可

**1. index.json 三处一致校验**

- **悬空检测**：`designs[].file` 与 `points[].file` 的每一项都必须能在 `docs/design/` 下用 glob 定位到；定位不到 = 悬空，修正。
- **孤儿检测**：`docs/design/` 下实际 `.md` 文件集合与 index 的 `file` 集合**必须完全相等**——多一个（孤儿文件未登记）或少一个（悬空条目）都算失败。
- **状态一致性抽查 ≥3 个 design 文件**：逐个文件比对点清单表的点号、状态、证据与 index 是否逐点一致；不一致按 index 修正文件（index 是权威源）。

**2. 变更覆盖检查（git）**

```powershell
# pwsh：覆盖有历史 commit / 仅一个 commit / 无 commit 三种情况
if (git rev-parse --verify HEAD 2>$null) { git diff --name-only HEAD~1 2>$null } else { git status --short }
```

确保每个变更文件都在 PROGRESS 版本记录区有记录。局限：只查最近一次提交——一次会话多次独立提交时用 `git log --oneline` 手动比对；git 不可用则逐项回忆核对。

**3. 日期与版本检查**：PROGRESS 条目区有今天的日期标题？头部版本号已按上文更新？STATE.md 的"最后刷新"是今天？

**4. 输出摘要**（有遗漏已补正时用 `⚠️ 已补正` 标记）：

```
📋 文档同步完成：
✓ PROGRESS.md — 条目区 +1 条（vX.Y.Z），版本记录区 +1 段
✓ design/index.json — design-01-P1 → 待验收（等用户确认）
✓ STATE.md — 已刷新
✓ information/index.json — 无需更新
✓ STRUCTURE.md / CLAUDE.md — 无需更新
```

## 项目规模适配

| 规模 | 文件数 | 处理 |
|------|--------|------|
| 小型 | <20 | 条目一句话；根因一句话；STRUCTURE 只写顶层 + 1 层；design 保持最小四节 |
| 中型 | 20–100 | 标准条目；bug 必写根因；STRUCTURE 顶层 + 2 层 |
| 大型 | 100–500 | 完整条目（全写根因）；STRUCTURE 顶层 + 3 层 + 核心事实；design 按模块分文件 |
| 超大型 | >500 | 根与子项目各自维护一套 `docs/`；本技能在每个子项目根目录下分别执行 |

## 常见问题

- **改一行也要记录？** 独立有意义的变更——记；连续小改动合并成一条。
- **忘了实时记录？** 用 `git log --oneline` 回顾今天的变更补写，变更覆盖检查会发现遗漏。
- **用户没验收就催着走？** 状态停在「待验收」，并在摘要里明确写出"等用户确认"——不要沉默地留在待验收，也不要替用户点完成。
- **PROGRESS 太大？** 先读条目区，需要细节用 grep 定位；条目区触顶后把最老内容移入 `docs/other/progress-archive-YYYY.md`。
- **两个成员想改同一个 `index.json`？** 都改成提交变更请求，由单一写入入口合并写入；这是设计而不是妥协。
